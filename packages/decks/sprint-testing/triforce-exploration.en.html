The Triforce: Testing Features by Layer

UI · API · DB. Whatever you test in a feature or user story, you always think about all three layers: a green screen can hide a broken API and a trigger that fails in silence. Smoke first, then the three layers, with security and integrity probes.

Smoke → UI → API → DBYour lens when testing any feature in the sprint
Playwright · OpenAPI · DBHub · /sprint-testing
Framing: the Triforce is not a technique reserved for exploratory testing. It is the lens you use to test ANY feature or user story. Every time you validate a piece of functionality, you think about its three layers. The three forces: UI (gold), API (magenta), DB (cyan).

the truth that hurts

201 ≠ DB ✓

A 201 Created does not prove the database ended up correct: triggers can fail to run in silence. The layer that responds well is not the layer that persists well. That is why you test all three.

The most important cross-layer rule: a 201 does not prove correct persistence. The green screen, the OK status code and the row in the DB are three different truths. The Triforce exists so you do not confuse them.

Six parts: the axes frame (layers vs levels vs types), the smoke gate, the three layers (UI/API/DB) and the cross-cutting discipline. The core is understanding what each layer proves, and that you ALWAYS go through all the layers, whatever the level or type of test.

the model

Three Layers, Three Truths

UI

What the user sees. Does it render, flow, give feedback? It may show cached or mock data.

API

The contract. Right status, valid schema, auth and RLS? A 2xx does not guarantee the DB.

DB

The persisted truth. Does the row exist, did the trigger run, do the constraints hold?

Feature typeLayer order
UI-focusedUI → API → DB
API-firstAPI → DB → UI
Data-focusedDB → API → UI
Full-stackall three
The feature type decides the layer order. UI-focused starts at UI; data-focused starts at DB. Smoke always goes first, before any layer.

three axes, not one

Layers · Levels · Types

The Triforce is ONE axis: the layers, where you probe (UI · API · DB). It is orthogonal to two other axes the tester decides on every test. They do not compete: they combine.

Layers: where do you probe?

The Triforce. UI · API · DB. Every feature goes through its three layers, always.

Levels: what scope?

component → integration → end-to-end (e2e). How much of the system goes into the test.

Types: with what intent?

functional · regression · smoke · security · performance · usability…

How they cross

The same user story is tested by choosing a level and a type, but ALWAYS going through the three layers. Example: a functional e2e of the checkout and a security test of the API differ in level and type, and are identical in that both think UI/API/DB.

The key mental frame: the Triforce is the LAYERS axis (where), orthogonal to LEVELS (scope: component/integration/e2e) and TYPES (intent: functional/regression/smoke/security/performance/usability). The tester picks level + type per test, but always goes through the three layers. This avoids the misunderstanding that the Triforce is only for exploratory testing.

THE GATE

Smoke First
Validate the Environment, Not the Feature

5-10 minutes of Go/No-Go. Never start deep testing until smoke passes. A broken environment produces false bug reports.

Smoke is mandatory and comes first. It validates that the environment is alive, not that the feature works. They are different questions, and you need both.

in order, ≤10 min

The Smoke Checklist

1

Basic access

The app loads, no 500s, assets render, no red errors in the console (yellow warnings are OK).

2

Authentication

Login works, the session persists on refresh, logout works (skip if the ticket is pre-auth).

3

Happy path

The ticket's primary flow end to end, 3-5 steps, check off each one as it works.

4

Backend integration

Network tab during the happy path: every /api/* call returns 2xx, and the data persists after F5.

ALWAYS check the Network tab, even if the UI looks fine

The UI can render cached or mock data. The network does not lie: if the UI shows something but there was no 2xx call, do not trust the screen.

4 steps in order. Step 4 is the key: the UI can fool you with cache/mock, and the Network tab reveals the truth. Always check the network.

the verdict and its rules

Go / No-Go

✓ PASS → continue

  • Record Smoke: PASSED in memory
  • Go on to UI / API / DB
  • Capture evidence of the home page
vs

✗ FAIL → STOP

  • It is an environment blocker
  • Triage first (NOT auto-Critical)
  • Surface it to the user, do NOT test deeply

The smoke constraints

During smoke: do not run edge cases or negatives · do not open minor bugs (blockers only) · do not go over 10 minutes. Smoke detects blockers, it does not document quality.

PASS→continue, FAIL→STOP (environment blocker, triage without auto-Critical). Constraints: blockers only, no edge cases, ≤10 min. Reporting false bugs from a broken environment is the worst waste.

two different questions

Smoke ≠ Deep Feature Testing

Smoke asks…

"Is the environment alive?" Does it load, authenticate, persist the happy path? If not, everything else is noise.

The Triforce asks…

"Does the feature work well?" Does it meet the ACs, survive edge cases, is it secure and consistent across its three layers?

Order matters

A broken environment produces false bug reports. If smoke fails and you test anyway, you will report "bugs" that are really the environment being down. Smoke validates the environment; the Triforce validates the feature. One first, then the other.

Anti-pattern S7: never skip smoke before the triforce. They are different questions: environment vs feature. The reachability gate (Stage Start) comes even earlier: does the env respond? Three gates, three questions.

LAYER 01 · UI

The UI Layer
What the User Sees

Validate the ACs, discover edge cases, capture evidence, and distrust the screen: it can hide a failure in the layer below.

UI = gold. The loop per AC + edge cases + invalid transitions + DevTools rules.

the loop for every AC

Navigate → Observe → Capture

0

Session + role state

A named session in memory (-s=<KEY>), one per role; the login comes from state-load .auth/<env>-<role>.json, never typed here. When you finish, close and playwright-cli list prove it.

1

Navigate + snapshot

Open the start URL, capture the DOM structure / accessibility tree.

2

Execute + observe

Happy path actions step by step. Expected result? Odd UI state? Red console? 4xx/5xx in the network?

3

Capture + propagate state

Screenshot at the key state ({KEY}-{n}-ac{N}-desc.png) and mark the outline PASSED/FAILED in memory.

DevTools rules

Console: red = log it (yellow is OK). Network: red rows (4xx/5xx) are always noted even if the UI looks fine, because the UI can mask an API failure. >5s of load time = a Performance finding. Disable the cache.

The loop: navigate→snapshot→execute→observe (console+network)→capture→propagate state. The golden DevTools rule: red network rows always count, even when the UI looks green.

If you find a new case while testing…

…that the Planning ATP did not derive (a partition, a boundary, a transition), add it back to the outline set. Coverage is the floor (the ACs) plus this risk layer, not improvised testing in place of planning.

The UI edge case checklist. The special characters (script/DROP TABLE) are basic security probes. What you find feeds back into the plan; it does not replace the plan.

where defects hide

Invalid Transitions: the Blind Spot

For any entity with state (draft→submitted→approved, cart→paid→shipped): fire every valid transition, then fire one the current state should reject.

draft→ submitted→ approved→ closed
the probe: approve(closed) → rejected? a silent 200 with no state change = bug

The happy path almost always works

What breaks is when someone tries to do what the business does not allow: approving something already closed, canceling something already shipped. Invalid transitions are where state machine bugs live.

Ties into the State-Transition technique: 1 TC per invalid transition. The typical bug: a silent 200 OK that changes nothing leaves the user confused.

when to go down a layer

When to Escalate to API / DB

UI renders but the data looks wrong

Go down to §DB to confirm what was really persisted.

A button fires a non-2xx request

Go down to §API to reproduce the call directly.

RLS suspicion: you see rows you should not

Go down to §API and §DB, both.

The UI is the symptom, not the diagnosis

When something looks wrong up top, the cause is almost always below. Escalating a layer is how you get from "this looks odd" to "this is broken here, because of this".

Escalation rules: wrong data→DB; non-2xx→API replay; RLS→both. The UI tells you THAT something fails; the layers below tell you WHY.

LAYER 02 · API

The API Layer
The Contract

Confirm contracts, auth, error handling and RLS. Every status code is more than a number: it is proof that something works (or does not).

API = magenta. The "what it proves" status code matrix + the RLS A/B probe. This layer teaches you to read status codes as evidence.

discover + authenticate

Setting Up API Layer Testing

auth once, reuse
# 1 · SCHEMA (read-only): OpenAPI MCP
list-api-endpoints · get-api-endpoint-schema   # never invoke-api-endpoint

# 2 · TOKEN: credentials ALWAYS from .env, never by hand
bun run api:login staging [--role admin]   # → .auth/tokens.env

# 3 · EXECUTE: curl, in the same call that loads the token
source .auth/tokens.env && curl -H "Authorization: Bearer $API_TOKEN_USER_STAGING" "$API_BASE_URL/<path>"

# record the ticket's endpoints in a table in memory:
# | Method | Endpoint | Purpose | AC |

Token propagation gotcha

Some backends scope the token per workspace/tenant. If a request returns 200 for one user and 403 for another with the same role, propagation is the suspect. Note it as a discovery, not a bug, until you confirm it with the team.

Three tools, one job each (agentic-qa-core/references/api-testing-doctrine.md): the MCP reads the contract, bun run api:login gets the token, curl executes. Token once, reuse. The propagation gotcha: same role, different result = a scoping problem, not necessarily a bug. Confirm before reporting.

every status PROVES something

The Status Code Matrix

ScenarioExpectedWhat it proves
Happy path200 / 201Contract + happy data
Missing required field400Validation is alive
Oversized input400 / 413Size guard
No auth header401Auth required

Another tenant's resource403 / emptyRLS / tenant isolation

The core idea of the API layer: a status code is evidence. 400 proves validation is alive; 403 proves tenant isolation; 409 proves conflict handling. If you do not test the negative, you do not know whether the guard exists.

the security probe almost nobody runs

RLS / Authorization Probe: A/B

Critical for multi-tenant apps. Two users (A, B), the same role. The question: can A touch B's data?

A tries to access B's data
1. A lists resources           → only A's rows
2. A reads resource?user_id=eq.B   → empty array or 403
3. A PATCHes B's row           → 0 rows affected or 403

# result per probe:  VERIFIED  or  VULNERABLE

Any VULNERABLE is Critical bug territory

If A can read or write B's data, it is a cross-tenant leak, the worst kind of defect. It is a blocking finding: it stops the pass immediately.

The A/B probe with two users of the same role: list-only-mine, read-other-tenant, PATCH-other-row. VULNERABLE = Critical = blocking. This is the highest-value security probe of the API layer.

the cross-layer handoff

A 201 Does Not Prove the DB

✓

The API responds 201 Created

The contract says "created". But a successful POST/PATCH only proves the API accepted the request.

?

Did the trigger run? Is the row right?

Triggers can fail to run in silence. The computed total, the relationships, the timestamps: all of that lives in the DB.

→

Go down to §DB to confirm

After every successful POST/PATCH, verify persistence and trigger execution in the database. The response is not the truth.

The golden rule of the Triforce

Each layer proves its truth. The API proves the contract; only the DB proves persistence. Trusting the 201 means trusting the wrong layer.

The cross-layer handoff: 201 ≠ correct DB (silent triggers). Always confirm persistence in the DB after a successful write. This is the lesson that ties the three layers together.

The Layers Above

AYes: 201 + green UI = created correctly
BNo: a 201 does not prove the DB; go down to confirm the row + trigger

Q2User A, with their token, does GET resource?user_id=eq.B and gets B's rows (200). Verdict?

The two key lessons from UI+API: the 201 does not prove the DB, and the RLS A/B probe catches cross-tenant leaks (VULNERABLE = blocking Critical).

LAYER 03 · DB

The DB Layer
The Persisted Truth

Confirm state, constraints, triggers and RLS at the SQL level. Here the question flips: in negative probes, success is the bug.

DB = cyan. State verification + constraint probes (success = bug) + integrity sweeps + RLS in SQL. The layer where the logic inverts: negative probes must fail.

after an API / UI action

State Verification

CheckQuery pattern
The row existsSELECT * FROM {table} WHERE id = '{id}'
The relationshipJOIN child to parent, compare the expected count
The trigger rancompare the stored total vs SUM(items)
Sane timestampsrecent created_at, updated_at >= created_at

This is where the 201 gets checked

"The trigger ran" is exactly the truth the 201 could not give: if the stored total ≠ the sum of the items, the trigger failed in silence even though the API answered 201.

The 4 post-action state checks. "The trigger ran" (stored total vs SUM) is where you catch the silent trigger that the 201 hid.

inverted logic

Constraint Probes: Success Is the Bug

ConstraintProbe (ALL must ERROR)
FKINSERT a child with a nonexistent parent id
CHECKUPDATE to an invalid enum value
UNIQUEINSERT a duplicate of a unique column
NOT NULLINSERT with NULL in a required column

If the probe succeeds, the constraint is missing, and that is the bug

ALL of these probes must fail. An invalid INSERT that goes through means the database is not protecting integrity. Wrap each probe in a transaction and ROLLBACK so you do not pollute staging.

The logic inverts: in negative probes, success = missing constraint = bug. FK/CHECK/UNIQUE/NOT NULL must all error. Always in a transaction + ROLLBACK.

integrity sweeps

Hunting Corrupt Data

SQL · these queries must return 0 rows
-- orphans: children without a parent
SELECT c.* FROM child c LEFT JOIN parent p ON c.fk=p.id WHERE p.id IS NULL;

-- calc mismatch: stored total ≠ real sum
SELECT o.id, o.total, COALESCE(SUM(i.qty*i.unit_price),0) AS calc
FROM orders o LEFT JOIN order_items i ON o.id=i.order_id
GROUP BY o.id, o.total HAVING o.total != calc;

-- impossible domain states
SELECT * FROM orders WHERE status='delivered' AND payment_status!='completed';

Any returned row is an integrity defect

A "delivered" order without a "completed" payment is a state the business should never allow. These sweeps catch the corruption that no UI test would see.

Three sweeps: orphans, calc mismatch, impossible states. Each must return 0 rows. Run them periodically on data-heavy features. They catch what the UI never shows.

real RLS + cascades

RLS at the SQL Level and Cleanup

Real RLS

The qa_team role usually bypasses RLS. To test it for real, impersonate the JWT:

BEGIN;
SET LOCAL request.jwt.claim.sub = '{user-a}';
SELECT * FROM {table}; -- only A's rows
ROLLBACK;

Cleanup cascades

After testing CRUD flows, verify that cleanup cascades:

  • DELETE the parent: do the children go too?
  • Soft-delete: flag set, row still present?
  • Record CLEANUP COMPLETE / INCOMPLETE

If direct SQL bypasses RLS

Fall back to the API §RLS A/B probe, which goes through the application's real enforcement. Two paths to the same security truth.

Real RLS needs JWT impersonation (qa_team bypasses it). Cleanup: DELETE cascades and soft-delete. If SQL bypasses RLS, use the API A/B probe (real enforcement).

THE CRAFT

The Discipline
That Makes the Pass Reliable

When to stop and when to keep going, how to handle time, and why a test passes only if it was observed in its own environment.

The cross-cutting layer: findings triage, TTL, status propagation, evidence. What separates a professional pass from a click-around.

the graduated pause

Blocking vs Non-Blocking

A FAIL during feature testing is not automatically Critical and does not stop the pass by itself. Triage first, then decide.

Blocking → STOP

  • smoke / environment down
  • corruption / loss of integrity
  • exploitable security (RLS VULNERABLE, auth bypass, cross-tenant)
vs

Non-blocking → log + keep going

  • cosmetic, minor validation gap
  • edge case in a non-critical TC
  • security/framework-default finding pending recalibration

Why not stop for everything

Pausing a 17-TC pass for a cosmetic finding wastes the dispatch and loses coverage. A non-blocking finding is logged and the pass continues; all of them are surfaced together at the close of Execution (historically Stage 2). A genuine blocker does stop the pass immediately. With no person present, a worker reports the blocker to its conductor, and a routine cuts the deep exploration short, notes it in Findings, and opens no bug or comment without a brief that covers it.

The graduated pause: blocking (env/corruption/security) stops; non-blocking (cosmetic/minor) is logged and the pass continues. A FAIL is not auto-Critical. The goal is full coverage.

test time without waiting

Time-Dependent Cases (TTL)

Magic links, OTPs, tokens, sessions, caches: "at 14:59 it works, at 15:01 it does not". You do not test them by clicking faster, you need to control time. Pick the highest option the stack allows.

1

Fixture / short TTL

The best one. If the env exposes a configurable TTL, set it to seconds and test the real 14:59/15:01 edge. It exercises the true expiry code.

2

Clock-mock

If the stack lets you inject/freeze time, advance the clock and assert the expiry, as long as the mock drives the real logic and not a test branch.

3

Written manual defer

Last resort. Document the edge you could not exercise, why, and the concrete follow-up (e.g. "add a MAGIC_LINK_TTL override").

Never a bare BLOCKED

Mark BLOCKED — needs time fixture with the chosen option (1/2/3) and a one-line reason. A BLOCKED with no decision path loses coverage in silence.

The 3-option TTL ladder by priority: fixture > clock-mock > written defer. Never a bare BLOCKED: always "BLOCKED — needs time fixture" + option + reason.

closing the pass with rigor

Pass Only if Observed · Evidence That Works

State propagation

A TC is PASSED or FAILED only if it was observed in the environment its precondition names. A unit test, a green CI, reading the code or another environment leave it at NOT RUN, never FAILED. A NOT RUN climbs the ladder: recreate it in the test environment, QA defers with their authority and leaves a follow-up task, then developers, and the owner only if there is doubt.

Evidence discipline

  • Name: {KEY}-{n}-ac{N}-desc.png
  • Capture at the failure state, not while navigating to it
  • evidence/ is gitignored, never committed

The log is the handoff to Reporting

The Execution block of test-session-memory.md (smoke + UI/API/DB tables + Findings) is what Reporting consumes: the Findings feed the bugs, the pass/fail results feed the ATR.

Pass only if observed: PASSED or FAILED require observing the case in the environment of its precondition; everything else is NOT RUN with its reason (BLOCKED while the ladder is still open, DEFERRED (execution) when QA deferred it with a task). That reason is not the ROI's Deferred verdict. Evidence at the failure state, named and gitignored. The Execution memory is the input to Reporting (Findings→bugs, pass/fail→ATR).

quiz · discipline

The Craft of the Pass

Q1On TC #4 of 17 you find misaligned text (cosmetic). Do you stop the pass?
AYes: every FAIL stops the pass and is reported right away
BNo: it is non-blocking, I log it and keep going; I surface everything together at the close
CYes: I open a Critical bug so I do not forget it
No, keep going. A cosmetic issue is non-blocking: it is logged in Findings, the TC stays FAILED and the pass continues so you do not lose the other 13 TCs. Only blockers (env/corruption/security) stop it. A FAIL is not auto-Critical.
Q2A TC validates that a magic link expires after 15 min, but there is no way to move the environment's clock forward. How do you close it?
ALeave it at NOT RUN with no reason
BA bare BLOCKED: it could not be run
CNOT RUN with the reason BLOCKED — needs time fixture + the chosen option, and climb the ladder
NOT RUN with its reason. It was not observed, so it cannot be PASSED or FAILED. Never a bare NOT RUN or BLOCKED: document the edge, why it could not be run, and the path forward. all together

The Complete Feature Testing Pass

Smoke ✓ → UI → API → DB → Findings
  • Smoke first: environment Go/No-Go, ≤10 min, always check the network.
  • Layers by feature type: what changed decides the order; each layer proves its truth.
  • Triage every finding: blocking stops, non-blocking logs and keeps going.
  • Close with rigor: pass only what was observed, every NOT RUN with its reason, evidence at the failure state, Findings into the Reporting handoff.
The recap of the full flow: smoke → UI/API/DB (order by feature) → triage → status → findings to Reporting. The three forces in one pass.

the tester's checklist

How to Do It Well

  • Smoke before everything: a broken environment gives false bugs.
  • Distrust the UI: check the network even if it looks green.
  • Read status codes as evidence: each one proves something.
  • Run the RLS A/B probe: always, on multi-tenant apps.
  • Confirm in the DB after every write: the 201 is not enough.
  • Negative probes: success = bug: in a transaction + ROLLBACK.
  • Test the invalid transitions: that is where defects live.
  • Pass only what was observed: PASSED or FAILED in the precondition's environment; everything else, NOT RUN with its reason.

The goal

That no defect crosses the three layers unseen: not the one the UI hides, not the one the API dresses up, not the one the DB corrupts in silence.

The operational checklist for doing it well. Each point is a lever against a layer's blind spot.

to take away

Three Ideas That Stay

1

Each layer, its truth

The UI shows, the API contracts, the DB persists. A 201 does not prove the database; a green screen does not prove the API.

2

The negative is gold

Error statuses, invalid transitions, constraint probes (success=bug) and RLS A/B catch what the happy path never touches.

3

Discipline over impulse

Smoke first, graduated triage, pass only what was observed. Full coverage is worth more than stopping at the first finding.

The three core ideas: each layer its truth, the value of the negative/security probes, and the discipline of the pass.

Three Layers. One Truth. No Blind Spots.

Smoke validates the environment → the Triforce validates the feature: UI (what you see), API (the contract), DB (what persists). Test the negative, confirm one layer down, and call something passed only if you observed it.
