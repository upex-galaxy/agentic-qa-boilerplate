PART 01

The Three Incidents
Bug · Defect · Improvement

The term does not tell them apart: lexically, a bug IS a defect. What tells them apart is when they are born and what they tell the team about the state of the product.

Stress this: the difference is not semantic, it is strategic. It is an incident management decision, not a dictionary one.

the core idea

Same Term, Different Management

"Bug" and "defect" are synonyms in everyday language. The difference lives in the life stage of the feature: is it already live above Staging, or is it still pre-release?

The axis that decides everything

One question: is the affected feature already live above Staging? If NO (it is still pre-release, whether the current sprint is building it or not) → Defect. If YES (the end user can run into it) → Bug. The Improvement is the third path: it breaks no criterion, it proposes an improvement.

No matter when or where you found it. You can reproduce the failure on localhost or on qa and it is still a Defect; you can see it for the first time on Staging and it is a Bug, if the feature is already in production.

The doctrine is literal: «Classification follows the lifecycle stage of the FEATURE, not the environment where you happened to find the problem» (defect-management-doctrine.md). The case people get wrong most: while testing Story A you stumble on a failure in Story B. Look at the stage of B, not at where you were standing. If B is already in production → Bug, even if you saw it on Staging.

incident #1

Defect: the failure we catch in the sprint

What it indicates

That a User Story under sprint is coming out defective and has to be fixed before it moves up to higher environments.

When it is born

When the feature has not yet crossed Staging toward higher environments, no matter when the failure is discovered. This is normal and desirable: the sprint exists to uncover defects and close them. They are contained, not escaped.

  • It is born from a User Story. It links to the US being built (edge causation: the US causes the Defect).
  • It is containment, not escape. Finding it here is a QA success: the defect never reached the user.
  • If the sprint does its job, the US enters the release free of defects.
Stress this: uncovering defects in the sprint is the goal. A sprint with many defects detected and closed is a healthy sprint, not a sick one.

incident #2

Bug: the regression that escaped

What it indicates

That a feature already released and deployed is failing. Something that was supposed to work stopped working.

When it is born

When the affected feature is already live in production, even if the failure is discovered inside the sprint while testing another Story. Every feature is presumed approved by the quality gate before release: a failure in something already released escaped that gate.

  • The Bug is the incident type for regressions: every time something that should work, fails.
  • It is an escape. It crossed the sprint's safety net and reached production, which is exactly what the metrics must watch.
  • Same symptom as a Defect, different moment, so a different management reading.
The bug is not "worse" than a defect by nature, it is worse by location: it is already in the user's hands. The Defect/Bug distinction is precisely what makes the "escape" measurable.

the same failure, two lives

Case: the Shopping Cart

1

Sprint: new cart US

A user story about the cart is added. QA detects that the total calculation fails. DEFECT  It is in development, it links to the US, and it gets fixed inside the sprint.

2

Release: the US ships clean

The defect was repaired. The cart functionality enters the release free of defects. The user receives it working.

3

Months later: an edge case

An edge case shows up around the same cart (coupon + foreign currency + stock 0). It fails in production. BUG  It is a regression discovered post-sprint.

This is the canonical example from the user. The same component (the cart) first produces a Defect (in sprint) and then a Bug (post-release). The taxonomy captures the difference in timing, and the escape metrics come from there.

incident #3

Improvement: not a failure, an enhancement

A work type for enhancements. Sometimes trivial; sometimes the destination of a Bug or Defect that, after root cause analysis, turns out not to be a failure but a requirements matter.

Direct origin

A small improvement spotted while using the product: copy, UX, a shortcut. It breaks nothing, it raises quality.

Origin by reclassification

A Bug/Defect goes through RCA and it turns out the "error" was actually the specified behavior. It is transformed: into an Improvement, or into a new User Story.

In the workflow this is literal

The is not a Bug transition takes a Bug/Defect from Open to the terminal state Enhancement. The reclassification is wired into the standard's flow, it is not informal.

Connect with part 2: the terminal state "Enhancement" and the "is not a Bug" transition are exactly this path. RCA can turn an error report into a requirement.

The Quality Standard
One Workflow, the Same Fields

The three incidents share exactly the same workflow scheme and the same fields. Reporting with discipline now is what makes measuring possible tomorrow.

Make clear that this is a reusable management standard: a recommendation, not a universal law. But it is a proven, consistent standard that any team can adopt in Jira.

the happy path

The Life Cycle of an Incident

Open→ In Progress→ In Review→ Ready For QA→ Closed ✓

start fixing

Open → In Progress. The dev picks up the incident.

Pull Request / Fixed & Deployed

In Progress → In Review → Ready For QA. The fix reaches QA for retest.

ReTest Passed

Ready For QA → Closed. QA verifies the fix (success terminal).

Wired-in shortcuts and returns

Hard pushed skips the review (In Progress → Ready For QA). back reopens a Closed to Ready For QA when a regression slips in after sign-off.

Standard workflow; the real catalog is .agents/jira-workflows.json. This is the main path. The colors: gray=new, amber=indeterminate (work in progress), green=done. The state category matters for the metrics (part 3).

the most important decision

Triage from Open: the paths of the standard

Open is the triage hub. Not every report gets fixed: half of the management value is in correctly classifying what is not a fix.

is duplicated → Duplicated
Repeated. Another ticket already exists. Terminal.
is WAD → REJECTED
Working As Designed. Not a failure. Terminal.
is CNR → Cannot Reproduce

what gets filled in when reporting

Always (high signal)

Golden rule

Every field you leave empty is a question the dashboard will not be able to answer. Discipline when reporting IS the raw material of the metric.

classifying the impact

Severity → Priority

SeverityCriterionPriorityExample
CriticalCore blocked, no workaround, data lossHighestLogin down, checkout fails

ModerateIssue with an easy workaroundMediumSorting broken but the filter works
MinorLow impact, low priorityLowMissing edge case validation

Severity ≠ Priority

Severity is technical impact (set by QA); Priority is business urgency (set by the team). A typo in the logo (Trivial) can be High priority before a demo. Always keep them apart.

The Severity→Priority mapping is the default; the business can override Priority. Keeping both fields gives two distinct measurement axes.

two taxonomies that feed metrics

Error Type (what) vs Root Cause (why)

Error Type: the symptom

Inferred when reporting, from the observed behavior.

functionalvisualexample · options in .agents/jira-fields.json (error_type); the ShopFlow dashboard data below uses those options

Root Cause: the cause

Set after the fix, in the post-mortem.

code_errorrequirement_errorexample · options in .agents/jira-fields.json (root_cause)

Why both matter

Error Type answers "what kind of failures dominate?" (are we weak on security? on performance?). Root Cause answers "where do they come from?" (code? requirements? integrations?). Two questions, two fields, two charts.

Error Type faces the user (symptom); Root Cause faces the process (cause, post-RCA). Together they allow process improvement questions, not just counting.

the underrated field

Components: Group to Measure

A native Jira field, configurable so it appears on every incident. Its superpower: grouping Bugs, Defects and Improvements by the part of the product they affect.

Real functional modules, not epics

Each component = a real functional module of the app (the route /checkout/cart → component Cart). They are derived from the source and the backlog scope (a module not yet built is declared in advance), and reconciled via jira-administration mode components with a plan a human approves. The "epic" axis is already covered by parent/link, so do not duplicate it here.

What it is really for

"Which part of the app fails the most?" becomes a single query. It enables ownership (which team owns which component) and automatic routing of incidents.

The three axes, kept apart: the parent is always the QA process epic ("QA Defect Management" for bug / defect / improvement) and never a product or development epic. The issue-link carries the origin Story. The components carry the affected module.

And ShopFlow always fills it in

All 40 incidents in ShopFlow mark their Component, so the ownership dashboard exists and says which module concentrates the defects. The rule in one line: what you do not fill in, you cannot measure. That is why it is hygiene recommendation #1, and ShopFlow leaves none empty. We look at it in part 3.

Emphasis: Components maps real functional modules of the app (derived from the code and the backlog scope, reconciled with jira-administration mode components under human approval). They are NOT derived from epics: that axis is already carried by parent and issue-link. ShopFlow fills it in on all 40 incidents, which is why its ownership dashboard can be drawn in full. It is the field most teams forget and the one that enables the most questions.

PART 03

Measuring Quality
From Fields to Answered Questions

A dashboard is not a list of data, it is a set of answers. The goal: for product to see, with their own eyes, how the app is doing. We illustrate it with the ShopFlow example project.

The most important part. The guiding principle: nobody wants to see metrics, they want to resolve doubts. The metrics are the means. The ShopFlow numbers are illustrative, not from a real project.

the guiding principle

Data Only Matters if It Answers Questions

❌ Dashboard as a dumping ground

  • A list of 200 ungrouped tickets
  • Counts with no context ("there are 40 incidents")
  • Metrics nobody knows how to read
  • The product team understands nothing
→

✓ Dashboard as an answer

  • "Are we stopping defects before they escape?"
  • "Which component fails the most?"
  • "Is fix quality getting better or worse?"
  • Product opens Jira and understands the health
First the quality question, then the metric, then the field, then the query. Never the other way around. This order is the heart of the lesson.

from question to query

JQL: the Language of Dashboards

JQL · SHOP project (example)
# All critical defects still open
project = SHOP AND issuetype in (Bug, Defect) AND "Severity[Select List]" = Critical AND statusCategory != Done

# Escape: post-release bugs vs in-sprint defects
project = SHOP AND issuetype = Bug      → 10 (escaped)
project = SHOP AND issuetype = Defect   → 26 (contained)

# Group by component (Components filled in on all 40)
project = SHOP AND issuetype in (Bug, Defect) ORDER BY component

# Report noise: discarded
project = SHOP AND status in (Duplicated, REJECTED, "Cannot Reproduce")  → 3
JQL is the engine behind every dashboard gadget. A well-posed quality question translates almost 1:1 into a JQL clause + a group-by. Show that the fields are literally the filters.

How to Read These Charts

Donut / Pie

Proportion of a total; the parts add up to 100%. "How is the total split?"

Bars

Compare magnitude across categories. "Which one is bigger?"

Stacked bar

The composition of ONE total inside a single bar. "What is this made of?"

Gauge

A single value against its maximum/target (a %). "How close to the ceiling?"

hygiene checklist

Defect Management Discipline

  • Use the right work type: Defect if the feature has not crossed Staging, Bug if it is already live above. It is what makes the escape measurable.
  • Always fill in Components: without it, there is no ownership dashboard.
  • Severity ≠ Priority: two axes, two fields, two questions.
  • Always add evidence: embedded screenshot, trace or log.
  • Set Root Cause after the RCA: it feeds process improvement.
  • Triage honestly: Duplicated/WAD/CNR keep the signal clean.
  • Link US ↔ incident: causes / is blocked by for traceability.
  • Question first, then metric: never a dashboard for its own sake.
The operational checklist. Each point is a direct lever on the quality of the metrics that come later. Discipline when reporting NOW is the reliable metric of TOMORROW.

Three Ideas That Stay

1

The feature stage defines the type

Bug = defect = identical symptom. What changes is whether the feature is already live above Staging, not where or when you found it. Defect contains; Bug leaks; Improvement improves.

2

One workflow, the same fields

The quality standard: the three incidents share a schema. Discipline when filling in, above all Components, is the raw material of every metric.

3

Measure questions, not data

A dashboard is a set of answers. Question first, metric second, field last. Escape Rate is the star of shift-left.

The close of the three concepts. If the audience remembers only three things, let it be these.

Report with Discipline. Measure with Questions.

Distinguish (Bug/Defect/Improvement) → Manage (one workflow, the same fields) → Measure (from filled-in fields to dashboards the product team understands at a glance).
