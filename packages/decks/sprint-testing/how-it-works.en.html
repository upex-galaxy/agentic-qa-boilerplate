The 4 phases of the main path are dispatched as sequential subagents: each report feeds the next briefing, and every stage closes with the lightweight verifier. This map is the index: every node has its own slide.

The mental index of the deck. Main path: Preflight → Phase 0 → Session Start → Planning → Execution → Reporting → Archive. Adjacent pieces: the two modes (single-issue for one Story or one Bug, sprint-wide for the whole sprint), which are asked and never guessed, the handoff from shift-left, the bug veto that collapses to Code-Review-only, the STOP/pause points of Execution, and the handoffs to Documentation / Automation / Regression. Further down, in production, Observation: declared, with no skill of its own. Sprint-wide mode loops the same path per issue, in this session or spread across a fleet.

Two modes, asked; the same pipeline

The mode question, always

Session Start asks: the whole QA backlog of the sprint (sprint-wide) or one issue (single-issue)? A sprint number is a hint, not an answer. It is skipped only when the first token of the arguments names the mode: /sprint-testing sprint-wide 12 · /sprint-testing single-issue UPEX-123. In sprint-wide a second question follows: one executor or a fleet?

Scope by JQL, same cadence

The sprint comes from a JQL with the coverable work types the project declares, intersected with what the instance actually has (a missing type is skipped with a note, it never blocks). Every issue pays the same 4 dispatches: Session Start → Planning → Execution → Reporting.

The mode is not inferred from how the invocation is written: "QA sprint 12" can mean either one. Only sprint-wide creates the sprint session pair and the STP; single-issue creates neither. We say "issue" and not "story" because bugs, defects, tech debt and improvements are coverable too, and there is no "inline" path for a single issue: both modes run the same sequence of 4 subagents. A worker does not ask: its brief fixes the mode. A routine without a brief stops and reports.

Readiness Preflight: probe, don't assume

"QA UPEX-123 on staging" already answers env and scope. Only the gaps get asked, in a single checklist.

A configured MCP stays RED until it actually responds. Every capability is probed before it is used.

Phase 0 · never start blind

Was there already a session? Resume, restart or abort

  • Computes the <scope>: UPEX-123 or sprint-7/UPEX-123 (sprint-wide).
  • Reads progress.md: last completed stage, pending BUG_FOUND or TOOL FAILURE.
  • Offers resume / restart / abort: on restart, it archives the aborted session first. With nobody at the keyboard, a worker picks up its own scope and never restarts; a routine resumes on its own; restart and abort need the word of the brief.
  • In sprint-wide it runs at two levels: once on sprint-7 on entry ("queue of n, k closed, next is X") and again on sprint-7/UPEX-123 when entering each issue.
.session/sprint-testing/<scope>/ plan.md ← session index progress.md ← checkpoint per stage test-session-memory.md ↑ shared domain payload across the 4 subagents .context/PBI/.../STORY-<KEY>-<slug>/ context.md · evidence/ ← the ticket's local stuff

Two memories, two questions. progress.md decides "which stage is next?" · test-session-memory.md carries the TMS modality + ticket context that every subagent reads. Both are checked on resume. Both live in .session/, never in the PBI folder: a re-sync of the PBI cache would destroy the file.

The resume contract comes from session-management.md §4. Interrupting a session loses nothing: the next run detects the state and picks up exactly where it stopped.

Universal entry · sets the table

Session Start: sync, context, PBI folder

  • Resolves the TMS modality and testing.tc_creation_stage; both stay fixed for the session. ATP = Test Plan, ATR = Test Execution, ATS = Test Set; the Story's custom field is only a fallback.
  • Sprint-wide only: STP find-or-create on the first ticket (STP: Sprint#{N}: {goal}). single-issue creates no STP.
  • Fetches the ticket: bun run jira:sync-issues get <KEY> --include-comments → reads the .md files and the Team Discussion in comments.md. Never acli view for custom fields.
  • Loads context + code: business maps, master test plan, module-context.md (synced from the ## Module Context (QA) section of the Epic), repos, data via DBHub.

⏸ The hand-off gate (S10). Writes the Story Explanation in plain language and STOPS: nothing transitions to In Test without your explicit OK. A new PBI folder per ticket, never reused (S9); the [SYNC] files are never written by hand (S14).

Session Start syncs the ticket, builds the PBI folder (context.md + evidence/), writes the session's plan.md and test-session-memory.md under .session/, explains the Story and waits for human confirmation before continuing. If module-context.md does not exist, the AI drafts the body and publishes it in the ## Module Context (QA) section of the Epic description (reading first, without overwriting the PO's text) and syncs again: the local file is never written by hand.

Planning · the doctrine that governs the plan

Verifying ACs is the floor, not the testing

Floor, not ceiling

Coverage = AC conformance + risk beyond the AC (limits, errors, states, anomalies). Never report "% of ACs verified" as completeness.

1 : N by default

Every non-trivial AC explodes into several cases. Collapsing to one needs a written trivially atomic justification.

Criterion ≠ case

A criterion is a business statement; a case is a concrete exploration of how it holds or breaks.

Trigger in the ACMandatory technique
Any input, alwaysEquivalence Partitioning · one case per valid + invalid class
Range / limit / length / date windowBVA · min−1 · min · min+1 … max−1 · max · max+1 · zero/empty/null
State / lifecycle fieldState-Transition · every valid transition + every invalid one
2+ interacting conditions · 3+ factorsDecision Table · Pairwise (recording the reduction) · Error-Guessing charters
Canon: agentic-qa-core/references/test-design-doctrine.md, mandatory load before deriving coverage. EP without BVA misses the off-by-one; a state field with no invalid transition is an incomplete plan.

Planning · the rule that shapes the skill

When does a TC become a work item?

jira-native modalityjira-xray modality (bun xray)
PlanningOutlines only in the ATP (name + 1 line). No Test issues: a native Test is documentation and waits for the Documentation gate.Creates + executes Test issues for the outlines, at executable detail, grouped in the ATS (per-Story Test Set) and executed through a Test Execution: the Test IS Xray's unit of execution.

DocumentationCreates Tests only for what is regression-worthy, after the ROI.Selects + promotes to the Regression Test Plan (RTP) (the project's long-lived Test Plan, the one /regression-testing writes every RTR against) + Test Set, and enriches them.

Format, once per batch

Manual or Gherkin? It is suggested, you choose, and it applies to the whole batch. In a fleet the brief declares it.

Manual in two steps

Xray Cloud silently drops inline steps: create without steps and add them one by one.

The project knob

testing.tc_creation_stage: auto = this table · sprint-testing = Tests in both · test-documentation = in neither.

Guiding principle: a test is persisted to the REGRESSION repository because it will be re-executed, never to inflate a count. The sprint's execution artifact is not the curated repository: that one is decided by the ROI in Documentation. The testing.tc_creation_stage knob is resolved together with the modality; empty or unknown = auto, announced once. Choosing test-documentation in an Xray project has a cost that the user is told about beforehand: with no Tests there is no Test Execution, the ATR carries no runs and the per-TC evidence lives only in its body.

Planning · the trace, before touching a browser

The ATS carries the coverage; ATP and ATR are administrative

Story ── is tested by ── ATS: UPEX-123: {title} ← coverage (Xray panel) ├─ TC→ATS UPEX-123: TC1: should … └─ TC→ATS UPEX-123: TC2: should … (xray also writes the internal membership, never instead of the link) Story ── ATP: UPEX-123: {title} administrative · zero coverage Story ── ATR: UPEX-123: Story Testing administrative · zero coverage ATP and ATR test lists = DERIVED from the ATS membership (S17)

Three-edge check (Gotcha 9)

Link List on Story + ATP + ATR, or bun xray trace UPEX-123. It verifies Story↔ATS, full membership, Story↔ATP and Story↔ATR, and that the lists match the ATS. A TC linked directly to the Story is a last resort: only if the instance has no Test Set work type.

Canonical Test title

If Planning creates the Test issue, the summary is born canonical: {US_ID}: TC#: should <result> [<connector> <condition>] [given <precondition>]. The # is assigned once and never renumbered; Documentation re-verifies it on promotion.

The one declared exception to the ATP item: qa.methodology.gate_mode: light may collapse it per sprint, written in the STP with its debt item (S2).

TC∈ATS is always a TC→ATS link (slug test), in jira-xray and in jira-native; jira-xray also writes Xray's internal membership. TC∈ATP and TC∈ATR stay internal to Xray. Placement cascade for a TC in the cache: TC→ATS→Story (primary) · TC→ATP→Story (placement only) · TC→Story direct (last resort) · if none, orphan. Assignee = yourself, at creation (S19)

ATP, ATS, ATR and every Test are born with an assignee. Xray refuses to edit the membership of a Test Plan that is not yours: an ATP with no owner fails halfway through the flow. If find-or-create returns someone else's, it asks; it never reassigns silently.

Unmapped slug (S18)

Lists the live transitions, proposes the closest one in one question, fires the live id if you say yes and recommends bun run jira:sync-workflows. If you choose to skip it, it stays as a declared N/A; a silent skip, never.

Every Test goes with the QA Test Repository epic as parent; the ATR is born with its Test Environment.

ATS and ATR stay open on purpose when leaving Planning: the membership is not final and the run has not happened. Reporting closes the ATR and completes the ATP but leaves the ATS at designing on purpose, as the hand-off marker to Stage 4; /test-documentation closes it after the ROI verdict. No environment, no ATR. Canon: agentic-qa-core/references/artifact-lifecycle.md §1 (table), §2 (assignee), §4 (fallback). State and transition names are slugs resolved by .agents/jira-workflows.json; each project maps them to its real names. A bug's Re-Test Execution follows the same rule as the ATR: it is born active and closes when the repro Test's run is recorded. An ATP frozen in planning or a TC in draft after its stage is a reportable harness defect: it tells the team the work never went through.

Planning · Bug branch · triage before plan

The veto always beats the risk score

VerdictTriggers
SKIP: Code Review onlypure text/label, CSS/visual, docs, config/infra, refactor with no behavior change; Execution and Reporting collapse to the comment + transition
REQUIRE: full testmoney/billing, data integrity, auth/authorization, external integrations, state machines, calculations, regardless of score

No veto → risk score

New feature +3 · dynamic data +3 · explicit ACs +2 · user-facing +2 · effort >4h +2 · high priority +1 · multi-component +1 → 0-3 LOW (Code Review) · 4-7 MEDIUM (full ATP) · 8+ HIGH (ATP + extended edges). It is presented to the user; with no person, the brief decides, and with no brief the routine stops before Jira.

Bug run rules

Retest ATP + ATR. jira-xray: 1 repro Test created in-sprint when verifying the fix (1:N if the scope justifies it), executed in the ReTest: Execution. jira-native: no TCs in the sprint, defers to Documentation, as always. It runs: reproduce the original → verify the fix → regression in adjacent areas → DB if it is an integrity bug. Golden rule: if it deserves regression, Documentation ends with a persistent Test: reuse the repro one or create one.

Anti-pattern S5: no failure skips the veto → risk-score → severity + root cause tree. If the retest fails or the bug does not always reproduce, diagnosing-bugs narrows down the condition that triggers it, without fixing or instrumenting product code; a bug with no repro goes back to the reporter. Before closing a LOW, blast-radius measures what else the fix breaks (by hand if it is not installed). A hardcoded typo gets SKIP; anything that touches money, data or auth gets tested even if the diff looks trivial.

Execution · mandatory first action

Smoke test: a Go / No-Go gate of ≤10 min

  • Basic access. The app loads, no 500s, no red errors in the console.
  • Authentication. Login, the session persists on refresh, logout.
  • Happy path. The ticket's primary flow end to end.
  • Backend integration. /api/* calls return 2xx; data persists after F5.

Verdict

PASS → continue to the triforce · FAIL → STOP: an environment-level blocker, reported, and nothing gets explored.

Reachability ≠ smoke (S7)

The preflight asked "is the env up?"; the smoke asks "does the feature work?". Both run: skipping the smoke produces false-positive bugs against a broken environment.

No edge cases, no minor bugs, no more than 10 minutes. The smoke validates the feature's environment; the triforce validates the feature.

Execution · layered exploration

The triforce: UI · API · DB

UI

playwright-cli: happy path + edges: empty, max length, 0/−1/MAX_INT, <script>, refresh mid-flow, back button. Screenshot in the FAILED state, with an explicit destination path into evidence/ (the outputDir is left alone).

API

A 3-tool maneuver: OpenAPI MCP schema only → bun run api:login → authenticated curl. Status matrix: 200 happy · 400 missing field · 401 no auth · 403 other tenant · 409 duplicate.

DB

DBHub MCP: persisted rows, triggers (total == SUM of items), FK/CHECK/UNIQUE constraint probes wrapped in a transaction + ROLLBACK.

Order depends on the feature

UI-centric: UI→API→DB · API-first: API→DB→UI · data-centric: DB→API→UI. A non-2xx in the UI escalates you to the API layer; odd data on screen sends you to the DB.

RLS probe (multi-tenant)

With A and B of the same role: can A list/read/edit B's data? Any VULNERABLE = Critical and BLOCKING: authorization bugs never surface on the happy path.

Never run authenticated requests through the OpenAPI MCP: it is for reading the schema. The token is minted with api:login into .auth/tokens.env and used with curl. ALWAYS explore beyond the planned outlines.

Execution · graduated pause

A FAIL is not an automatic Critical: triage first

ClassExamplesAction
BLOCKINGsmoke/env down · data corruption · exploitable security issue (auth bypass, cross-tenant)⏸ pause NOW: the bug is presented and your decision awaited; the next stage is not dispatched
NON-BLOCKINGcosmetic · minor validation gap · edge in a non-critical TC · framework default that needs recalibratinglogged, TC FAILED, and the remaining TCs get finished: everything is carried to the close of Execution
TOOL FAILUREany tool that breaks mid-passSTOP: partial state reported, you choose retry / skip / abort

Before BLOCKED or DEFERRED

An unblock preflight runs per case: out of scope is dropped; otherwise QA tries to unblock it. Only an external cause, proven, allows DEFERRED (execution) with a follow-up; anything else stays BLOCKED. TTL, OTPs: short TTL → clock-mock → the same preflight. PASSED or FAILED only if observed.

Evidence

Screenshots, traces and logs under the ticket's evidence/ (gitignored). You capture the bug, not the navigation that leads to it.

This rule protects coverage: pausing a 17-TC pass over a cosmetic finding wastes the run; a genuine blocker does stop it instantly.

Execution · browser sessions and evidence

One login per role, every capture with its path

One session per ticket, one state per role

A named session (-s=UPEX-123), in memory. The login comes from the role's state, .auth/<env>-<role>.json via state-load, never typed during exploration. And that state is produced only by the app's real login: no service-role key, no user-admin API, no server-generated magic link, no hand-built JWT (browser-sessions.md §4). Two roles = two sessions. Each session is closed before the report and playwright-cli list proves it.

Agentic Pair Testing

The AI and you in your own Chrome. Governed by testing.browser.pair_mode in .agents/project.yaml: null asks once and saves the answer · true is the default mode · false uses dedicated sessions, and pair only if you ask for it, with one confirmation.

Explicit destination (Gotcha 8)

Nobody repoints the outputDir of .playwright/cli.config.json: it stays in the tool's directory. Each capture carries its path into the ticket's evidence/ (the outputDir does not apply the same way to a .png), and the path is shown in chat as soon as it exists.

Visual or position bug

Overlap, misalignment, a shifted axis: before reporting, load /bug-screenshot-annotation, which marks up the capture (circles, arrows, callouts) locally. The annotated PNG goes first as evidence. A text finding does not need it.

Canon: agentic-qa-core/references/browser-sessions.md (cases, pair_mode, fleets) and agentic-qa-core/references/evidence-conventions.md (buckets, annotated image suffix, verifying on disk). Repointing the shared outputDir is last-writer-wins: with several sessions, one session's captures land in another ticket's folder. The annotation working files (crops, overlay HTML) go to the session scratchpad, never to evidence/.

jira-xray: Test Execution description + each Test Run status. jira-native: acceptance_test_results custom field (or fallback comment) → sync → re-read. No ATR snapshot, no report (S3).

Severity recalibration (§5.0)

The QA comment is a summary; the ATR is the audit record; never duplicate it in a second store (S4). Mixed results use PASSED WITH ISSUES and still hand the passing TCs to Documentation.

Reporting · defect management doctrine

Classify before reporting: Bug ≠ Defect ≠ Improvement

Bug

The feature already lives above Staging (visible to the end user).

Defect

Feature still pre-release: the normal output of sprint testing.

Improvement

Not a broken AC: an improvement or under-specified AC found by testing beyond it.

Three axes, never mixed

parent = the "QA Defect Management" process epic (never a product epic) · issue link = the originating Story · components = the affected product module. qa_assignee = yourself, never overwriting an existing owner.

Severity → priority (lookup)

critica→Highest · mayor→High · moderada→Medium · menor→Low · trivial→Lowest (slugs from .agents/jira-required.yaml; override with justification). Title: <EPIC>: <COMPONENT>: <summary>.

Discipline. A reproducible repro + evidence or no ticket (S12) · one layer per bug, never UI+API+DB mixed (S8) · search for duplicates first · full draft in view and your confirmation before creating anything.

Canon: agentic-qa-core/references/defect-management-doctrine.md, mandatory load before reporting. The classification follows the FEATURE's lifecycle, not where the problem was found.

Every stage · the close nobody skips

Lightweight verifier + session footer

Planning · its own lines ATP in ready · every Test in ready (parent QA Test Repository) ATS stays designing · ATR stays active ATR with Test Environment assignee on everything created three-edge check OK Reporting · its own lines ATR close · ATP completed · ATS left at designing (hand-off to Stage 4) Story in qa_approved or blocked deferrals: owner OK + label + plan rows (no OK: in_test, ATR active) every reported issue: QA Defect Management + components + qa_assignee every unmapped slug: ASKED

The common lines live in artifact-lifecycle.md §5 and are not repeated per skill.

How it is answered

Each line is YES or N/A with its reason; a blank line counts as a failure. A NO leaves the stage in NEEDS REVISION and nothing advances. Lightweight: it answers from what it already did, with at most one extra read.

Session footer, in chat only

Each capture shows its path as soon as it exists; at close, the consolidated list (verified on disk, annotations first). Then the footer: skills, MCPs and CLIs used, testing levels touched with an explicit "none" and Refinements proposed:. Never in a Jira comment or in the ATR.

Canon: agentic-qa-core/references/artifact-lifecycle.md §5 (verifier) and agentic-qa-core/references/session-footer-contract.md (footer). This skill's framing is about execution: "levels touched" are the pyramid levels that were exercised by hand or exploratorily. Each subagent returns the footer fields and the orchestrator assembles it once at close. The session's lessons are proposed in .session/sprint-testing/<scope>/refinements.md and never applied to the live skill.

Sprint-wide mode · processing the whole sprint

The plan is local, the state lives in Jira

  • The scope comes from a JQL with the coverable work types the project declares.
  • Local: the usual session pair in .session/sprint-testing/sprint-<N>/: plan.md (scope, waves, assignment) and progress.md (append-only).
  • Loop with one executor: first PENDING issue of Wave 1 → the same 4 dispatches → summary → your OK for the next one. STOP on TOOL FAILURE · ⏸ on blocking BUG_FOUND.
  • Sprint close: the STR: Sprint#{N}: Regression Testing is created as a recap, the STP is closed and open shift-right plan rows are checked. Each regression run of the sprint leaves its own RTR, from /regression-testing.

The state the team sees = the STP

The description carries the stable plan (one writer, read-first); the comments, the append-only progress per closed issue. If they clash with a Story's ATR, the ATR wins.

Checkpoint per stage (S11)

After each subagent, the orchestrator records the stage in progress.md.

Archive on close

.session/… → .session/.archive/<date>-… + summary to persistent memory. What remains is Jira: STP, ATP, ATR, bugs.

The plan.md + progress.md pair is the same convention the other workflow skills use: local scaffolding, not a deliverable: it never travels to another machine. What the team consults is the STP in Jira. Phase 0 runs at two levels: once on sprint-N on entry (how far the sprint has come) and again per issue on sprint-N/KEY when entering each one, so resuming an interrupted sprint is fine-grained: it picks up the exact issue and the exact stage.

Conductor

Talks to you, builds the rounds, seeds a brief.md per issue, mints tokens and browser states. The only writer of the sprint: plan.md, progress.md, STP and the shift-right plan rows. Relays the deferral OK request to the owner; never answers it.

Worker

single-issue on its KEY. Recognized by the fleet worker token in the prompt and by its brief, not by env vars. No checkpoints, no skipping preflight or MCP probes, until worker_done.

launch.txt, always

In .session/sprint-testing/sprint-<N>/: one self-contained line per issue, regenerated in full each round. With no orchestrator, you open N terminals and paste one line in each.

Rounds ≠ waves. A wave is a Jira state bucket (which issues are eligible); a round is how many run at once, up to orchestration.max_workers, which is a cap and never the switch. If no orchestrator is available, the skill does not name it: not in the plan, not in the preflight, not in the ATR.

Fleet mode turns on only with two conditions: the mode is sprint-wide and the user answered the executors question with N. With N=1 nothing changes, byte for byte. The orchestration gate decides one thing only: who opens the sessions (the orchestrator launches and supervises them, or the human pastes the lines from launch.txt). Human decisions stay with the conductor: it asks the TC format once per batch and writes it into every brief, and each round closes with a summary and your checkpoint. The worker creates no sprint state, mints no tokens and runs no bulk syncs; whatever it would need to ask goes out as an ask to the conductor. Canon: sprint-testing/references/fleet-conductor.md.

The scale, and its ceiling

CSA 0-5: 0 the person does it · 1 approval per action · 2 approval per plan or batch · 3 decides within declared limits and escalates outside them · 4 supervision by monitoring · 5 no intervention. None of these three stages goes above 3 (Regression is the exception: it can reach 4 on a clean GO), and that is an architecture decision, not an accident of how much got built. None of the three carries a separate verifier: the PO/Dev and the human checkpoint itself fill that role.

Source: agentic-qa-core/references/stage-gates.md. The DoD says what has to be true to advance; the contract says who was allowed to do what while the stage ran. Both are gates: advancing a stage whose contract was not honored is skipping a gate, just like ticking a DoD that was never verified.

Three golden rules

1 Order is law: smoke before triforce, comment before transition. 2 Triage everything: the veto wins, a FAIL is not an automatic Critical. 3 Traceable or it did not happen: the TC→ATS→Story cascade (the ATS↔Story link is the coverage; ATP/ATR are administrative).
