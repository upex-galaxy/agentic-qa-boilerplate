Step 1 · is it really orchestration?

Two executors, and the subagent is still the default

The repo doctrine (AGENTS.md §3) doesn't change: the one-shot subagent does almost everything. The supervised worker is the second executor, and only when the work doesn't fit in a turn.

They don't compete. The conductor still uses subagents for its own reads. And the cost lesson from the dogfood points the same way: what got expensive was the conductor's subagent reads, not the workers' parallel work. The numbers, with date and source, are in .context/ADR/ADR-0006-forensic-measurements-ledger.md.

The point of this slide is to cool the enthusiasm: orchestrating isn't better, it's different. A supervised worker earns its place when the unit of work is a whole scope (a story, a module) that writes and integrates on its own.

Architecture · why this skill is short

Three layers, and ours points instead of copying

LAYER 3 · REPO DOCTRINE .agents/skills/orca-orchestration/ (T1, versioned, this skill) when to split the work · topology per activity · provisioning · brief · measured gotchas · phrasebook ^ points to v LAYER 2 · GRAMMAR + MACHINE the guides the binary serves (mailbox, Run, Task, worker cycle) versioned WITH the binary. The user stubs carry the command grammar and load next to this skill: cheap to load. ^ operates on v LAYER 1 · APP the running app · reachable runtime · board · mobile

Composition rule

If the binary's guide already says it, we put a pointer here, not a copy. A copy silently drifts at the next release.

What it means for the gate

It's evaluated on binary + runtime, never on "is the vendor skill installed?". A machine with the binary and no stubs is fully capable.

What it means for cost

The orchestration.orchestrator_skills stubs are small and LOAD next to this skill, in the conductor and in the worker: skipping them is what produces invented flags. The binary is asked only for the deep topic a stub points to. The measurement that settled this is in ADR-0006, not here.

This is why SKILL.md is short: what lives in the repo is what no vendor guide has, namely our provisioning gaps, the topology per activity, the brief, the measured gotchas, the git integration and the owner's phrasebook.

Without a runtime, the orchestrator doesn't exist

The gotcha that breaks the gate

The reachability flag is nested in the binary's JSON output. A gate that looks for a flat field fails closed, silently, on a perfectly capable machine. Verify any edit to the gate by running both branches.

Platform rule (Linux)

Outside a managed terminal, on Linux the CLI registers under a different name because the same-named system binary is the GNOME screen reader. The hook applies exactly that rule: environment signal first, then the alternate name on Linux. Use the same executable for every command in the session.

Hard rule 10: never name the orchestrator to the user from a workflow skill when the gate fails. Not in prerequisites, not in an unavoidable probe, not in the ATR environment block, not in a blocker-token sweep. This skill's single line (states A and B, only if the user asked for orchestration) says: level 1 orchestration is already available in this session with one-shot subagents; the professional kind (persistent sessions you talk to, mailbox, board, mobile) needs Orca installed; without it, launch.txt is still written with one paste-ready line per worker. The test for any future edit: would this line still make sense, unchanged, to a tester who has never heard of Orca? If not, it goes in this skill and not in the workflow skill.

Shared vocabulary · without it the reports can't be read

The rule that keeps reports readable

Rounds are numbered inside a wave: "Wave 1, round 2". "Wave" is never reused for concurrency.

Defaults, not policy

The orchestration block in .agents/project.yaml holds the worker cap, the agent and, per tier, model, effort, permission mode and overrides. An explicit user instruction in the conductor session ALWAYS overrides them for that run. Defaults apply only when the user said nothing.

Never ask the user to confirm a default they never mentioned, and never override an instruction they did give because the yaml says otherwise.

How a worker comes in

WORKER mode turns on when a brief names this skill. Its prompt opens with /<workflow-skill> <label> fleet worker: that token tells the domain skill it's running in a fleet, tells the hook it's a launched session (so it never asks the human anything) and, in Claude Code, hands the identity hook the label it uses to build the <label>--<handle> name.

SKILL.md has no mode-routing section with tokens: the mode comes from the role. CONDUCTOR for whoever talks to the owner, WORKER when a brief names the skill, AUTOMATION for an unattended routine. An automation's dispatcher creates the worker that produces and closes its own session; if it catches itself writing the deliverable, it has left its task.

Steps 3-12 · the cycle, in that order

The playbook steps, and the order is law

  • 1 · Gate. State A or B → one line, then carry on through the fallback.
  • 2 · Load the stubs now, next to this skill. Each orchestration.orchestrator_skills skill is the vendor's command grammar; the binary is asked for a deep topic only when a stub points to it. With no stubs installed, the grammar is requested from the binary directly.
  • 3 · Topology by what the work WRITES, plus the claims-vocabulary collision check during triage.
  • 4 · Scope on disk. .session/orchestration/<slug>/ seeded from the templates: run.md, roster.md, COMMON.md, launch.txt.
  • 5 · The playbook cycle, in that order, never splitting create + launch + brief.
  • 6 · Wait inside the turn, a single waiter, rolling windows of 540 s at most, ack verified in the same command that re-arms.
  • 7 · Close each finished worker in the same turn; orphan audit before deleting any worktree.
  • 8 · Harvest learnings.md and skill-improvements.md by calling the retro skill (without it, harvest inline and say so in the report), write kickoff.md, and report to the owner.

Step 5 caused the most incidents: create + launch + deliver the brief is one indivisible operation. A worker sat idle for hours because the brief never arrived (G32).

At harvest, retro ranks candidates and applies none: it leaves them written down for whoever launched the run to decide. A routine or a long-lived worker also keeps a decision log in the run scope (decisions.tsv, or decisions-<label>.tsv per worker) in the show-me-your-work skill's format: one row per decision, with the evidence as a pointer. Step 2 has a cost reason: the user stub is small and gets loaded; what's big is the deep payload the binary serves, and that stays on demand. They are different artifacts and mixing them up is the trap. The measurement that settled it is in ADR-0006. Step 7 has a stability reason: live worktrees nobody closed took the runtime down (G31 in references/gotchas.md).

Step 7 · the launch, and the distinction that cost a whole run

Native path supervises. Custom argv never does.

Native path · the supervised default

The worker-start verb with task, worktree, agent, model and effort level. The runtime launches the agent, so it recognizes and supervises it.

The task spec already arrives as the first prompt (G58), so it stands on its own. The prompt sent after verifying the screen must start with /<workflow-skill> <label> fleet worker …, so the identity hook can name the session <label>--<handle>; then comes the pointer to the brief and the continuity sentence, and the prompt ends with a last ROUTE-SCOPE: sentence naming the instruction-section ids the work needs (or none).

As soon as the handle is read, the conductor renames the tab to <label>--<handle>, and the readiness check includes reading the tab and session names back off the screen. A title like worker-task_… or a generated one is a failed step, redone before dispatching (G84).

Credentials without argv: every MCP, on any harness, reads the worktree's own .env through the .env loader in the MCP configs. No secret is exported into the worker's shell: Bun scripts read the .env with their own autoload and acli uses its stored login. The conductor verifies the credentials on the worker's screen before dispatching work to it.

Custom argv · always unsupervised

A terminal created with its own command line is never supervised: the runtime only recognizes agents it launched itself, and it refuses to adopt one even if the agent is alive on screen (G44).

It's left with one role, and a legitimate one: the self-contained, byte-identical line in launch.txt that a human pastes into their own terminal. An environment-variable prefix doesn't survive that route either.

That's why "worker mode" detection doesn't live in environment variables but in the prompt (the fleet worker token) plus the brief's fields.

Promising both at once is what cost the most. In the dogfood no custom-argv terminal was adopted, the whole fleet ran unsupervised, and the conductor paid for it in manual nudges, one for each worker stopped at each stage boundary.

Permissions rule: each tier launches in the mode declared by orchestration.permission_modes in .agents/project.yaml (the defaults ADR-0024 settled: conductor auto, worker bypass, subagent inherit), translated per harness in references/orca-machine-setup.md §3.1, and never in an "edits only" mode. Auto mode isn't unattended: Claude Code's classifier pauses and asks after several blocks in a row, which is why ADR-0024 put the worker, the one nobody watches, on bypass. A supervised worker gets no argv: its mode comes from the agent's default arguments in the app, and the conductor verifies it on the worker's screen before dispatching work. An edits-only mode covers file edits but not commands, so every script call waits on a human who isn't watching. One worker left every tracker mutation computed and unexecuted.

Step 7 · the brief

A brief is a file, not a message

What it carries on top of the 7 components

  • The run, task and dispatch ids
  • The sibling roster (who else is alive and on what)
  • The channel, and the ban on the harness's messaging tools, on questions to the user, on the structured-question tool and on the mkd deck
  • The escalation rule: errors, blockers and decisions that aren't theirs go to the conductor, never to the human
  • File ownership: which paths are theirs and nobody else's
  • The claims to declare, already pre-granted
  • The report protocol and the report path
  • Its label ([<KEY>-]<slug>) and its full name <label>--<handle>: the first thing it does is rename its own tab; it never asks to rename its session
  • The reminder about forensic trailers on every commit

Why a file and not a message

Anything longer than a couple of sentences goes in a file with a one-line pointer: it can be reread later, which a message can't, and through terminal send it would arrive truncated. It's cited by absolute path to the primary checkout, and never in a system temp directory: that triggers a permissions prompt nobody is watching.

One sentence, and the most important

"Don't return to the prompt until you've sent worker_done; stage boundaries are not checkpoints."

It goes in the launch prompt, not just in the brief. The sentence works as an instruction and fails as a file pointer: in a real fleet, workers whose brief said "no checkpoints" stopped anyway at a stage boundary with work still pending (G58).

"One message, one task". And text typed into a terminal but not sent isn't an instruction: it's just text.

The worker · three messages and not one more

No heartbeats, and a mandatory ask

MessageWhenRule
worker_doneonce, when its whole scope is finishedCarries the result, the modified files and the report path. After that: stop.
askblocking, when the answer shapes the workCarry on with whatever doesn't depend on the answer. If it expires, resume by id.
escalationa real blockerOver the unsupervised route the runtime rejects it: there the blocker goes as a status message with the subject prefixed BLOCKED:
heartbeatneverIt only says "I'm alive" and wakes the conductor. Explicitly banned in the brief, because it contradicts the preamble the runtime injects.

The ask trigger that saved the dogfood

When your own measurement contradicts a conductor instruction: STOP and ask, with both readings and the evidence. Never comply silently, never deviate silently.

One worker did this on its own judgment, and it's the reason the run report isn't wrong. Now it's doctrine, not luck.

The channel, and what isn't a channel

Everything the worker owes upward (status, ask, worker_done, a blocker) goes through the mailbox, which arrives intact; long content goes in its report file with a pointer. It never reports with terminal send: that truncates and can't verify the destination. The rendered screen is a backup for seeing what a worker is doing, never the channel.

It never asks the human: no question tool, no mkd deck, no sweep. Errors, blockers and the four classes of decision go to the session that launched it, which passes them on to the human. Exception: the human wrote to it in its own terminal, or the brief authorizes it in writing.

The worker DOES load the vendor stubs (orchestration.orchestrator_skills), plus references/worker-contract.md, references/channel-discipline.md and its domain skill (/sprint-testing, /test-automation…). Its injected preamble carries the message grammar. And the reverse holds too: a fragment it receives that starts mid-sentence is a truncation; it doesn't answer it, it asks for the pointer.

Hard rule 4 · the channel is an assignment, not a preference

The message goes to the mailbox. The terminal is for driving.

ChannelWhat it carriesIntegrity
orchestration send (the mailbox)Every message between sessions: status, questions, answers, decisions, escalations.Intact, byte for byte (G66)
a file + a one-line pointerAnything longer than a couple of sentences: briefs, reports, scope agreements, evidence, any table.perfect, and can be reread later
terminal sendDriving a terminal: commands, CLI calls, harness slash commands, keystrokes.Lossy: silently truncates, keeps only the TAIL and still reports success (G60, G64)

The test

If a human is going to READ it, it doesn't go through terminal send. If a shell or a TUI is going to EXECUTE it, that's what the verb is for.

The only exception

A supervised worker's first prompt goes through terminal send, because the native launch has no argv. Short, and pointing to a file. The rule is no conversation over terminal send.

The nudge is not the message

Mail doesn't reach a busy worker between turns and still reports success (G46). That's why the one-line nudge over terminal send exists: "check your mailbox: <subject>". The message stays in the mailbox.

What terminal send is great for: running a command in the worker's shell, driving a slash command the session can't invoke for itself (for example /mcp to revive a dead MCP server), reloading plugins and skills mid-flight, and interrupting a worker and verifying on screen. The two verbs are named in .agents/project.yaml (orchestration.message_verb and orchestration.terminal_verb). Full detail: references/channel-discipline.md.

Step 6 · shared fixtures, data and credentials

The claims protocol: a ledger, not a lock

EntityWhy it collides
usertwo workers logged in with the same account invalidate each other's session
fixtureone mutating the dataset another is asserting on
recordthe classic dirty read between two sessions
credentiala refresh rotates the token the other one is holding
env-resourcea feature flag changed for one alters what the other expects
tracker-artifacttwo writers on one description overwrite each other whole

Three intents

read · write · enumerate. The third is the dogfood lesson: a collection endpoint on a shared account exposes the siblings' entities. That is never an assertion target, and it's claimed as enumerate so the conductor knows.

When to wait and when not to

Claims listed in the brief are pre-declared and pre-granted by the conductor at launch: the worker doesn't wait. Only new claims, discovered along the way, wait for the grant.

Arbitration and ledger

First message wins. The conductor keeps claims.md and settles the rare disputes. Everything is released with worker_done. With no runtime: the same ledger, append-only, with a grep before writing and smaller rounds.

The collision check at triage uses the same vocabulary: it's a planning aid, not a runtime. The runtime is the messages.

Steps 8-9 · waiting without building a monitor

Rolling waits, and stalled is not idle

How to wait

  • Rolling foreground waits, 540 s at most, re-armed with the ack in the same command. The harness sets the cap: it kills a foreground command at 600 s, and a round takes longer than that (G51).
  • A longer wait is only a background job if the harness tracks it.
  • The main wake-up signal is the runtime's mail notice.
  • A single waiter. Never a homemade monitor: it competes with the notice, is late by construction and fires on the echoes of the conductor's own messages.
  • Never accept a batch you didn't process. The ack is verified (the acknowledged id is the requested one, the pending count drops) and never inside a compound command.

How to tell stuck from idle

stalled = no spinner line on screen and no worker_done arrived. That's stuck, not idle, and it needs a nudge.

idle = ready for input after the worker_done. That's finished.

The prompt box is drawn always: seeing it means nothing. The signal is the spinner with its time and token counter above the box.

And if the runtime warns that a prompt got stuck while the worker is mid-turn: it's already queued. Don't resend it.

The liveness sweep uses the runtime's native signals first (worker and terminal state) and only then the rendered screen, for a jammed interactive selector. File blocker tokens are the no-runtime fallback.

The "when a worktree?" rule

A worktree when two workers would write the same code file. Same checkout when they write to different systems (the tracker, different artifacts) and file ownership can be declared.

The gotcha we paid for twice

The base-ref flag resolves local refs. Verify the new worktree's SHA against the remote base, and without a || true hiding the failure.

In a same-checkout fleet Critical Rule #15 counts double: any global git discard is banned, because another session shares the tree.

Step 5 · before launching, not after

A fresh worktree is not a ready clone

What's committed travels on its own (each harness's MCP config, the hook, the T1 skills). What's gitignored doesn't, and every gap disguises itself as another failure. The table is what bun run worktree:provision closes; its --dry-run prints what it would do without touching anything.

GapHow it's closed

One command, and the same list in two places

bun run worktree:provision does every step in the table, refuses to run on the primary checkout and exits non-zero on any hard failure. The committed .worktreeinclude names the same files for the worktrees that Claude Code and the Codex app create, and a test keeps the two lists equal.

Credentials: the file isn't enough

The worktree needs its own .env, which the MCPs read through the loader and the Bun scripts through their own autoload, and the agent session restarts after every change. The conductor confirms it on the worker's screen.

Two physical limits

One dev server and one browser per worktree, and every browser automation session is closed before reporting: orphaned headless browsers have run for hours without the fleet noticing (G37).

The dogfood measured the other side: on a normal machine, free disk and the memory of the agent processes cap the round size before the runtime does. Check free disk before a long round: with a full disk the output write fails, not the command, and the worker goes silent (G39). The worker cap per round is orchestration.max_workers in .agents/project.yaml. Dated figures are in references/gotchas.md and in ADR-0006.

Committed hooks · and what dies with a worktree

The repo provisions and rescues by itself

orca.yaml (repo root, committed) scripts: setup: bun run worktree:provision archive: bun run worktree:audit --rescue

What each machine still decides

The trust prompt the first time each hook runs. The origin policy for repository hooks: if it's local-only, orca.yaml is ignored and the script set in the UI wins. And the CLI skips the archive hook unless you pass --run-hooks. Where hooks don't run, the same two commands are run by hand.

ClassWhat it is, per AUDIT_RULES
STATE.session/, .scratch/, the evidence and [LOCAL] PBI notes, .context/reports/, the updater state. --rescue copies it to the same path in the primary, without overwriting.
CACHEcomes back with the command the rule names.
DISPOSABLEcan be lost; test-run outputs are never rescued, by the owner's decision.

The hook warns inside the worktree itself

Without a .env, the hook injects a CREDENTIALS: line. In a linked worktree without node_modules/ or without .husky/_, a WORKTREE: line: git hooks don't run there and Claude Code may not see the repo's skills. The way out is the same: provision and restart the session.

The full audit before deleting (references/coordinator-playbook.md §6): tree status, unintegrated commits (git cherry), worktree:audit with exit 0 as the gate, and the question of whether anyone will resume that session: deleting the directory also leaves the roster's resume command with nowhere to run. Everything durable is cited by absolute path to the primary checkout; what gets written inside a worktree dies with it.

Who did what · identity and traces

One identity line, two trailers

AGENT IDENTITY: worktree=<name|primary> session=<label> harness=<claude-code|codex|opencode|pi> # session where the human types (independent or conductor) ORCA: available. Multi-session orchestration -> /orca-orchestration. Independent session or conductor: ask the human directly (sweep small items, mkd deck for heavy ones). A session launched by a conductor carries "/<skill> <label> fleet worker" and reports to it instead. # launched session (its prompt carries the fleet worker token) ORCA: available. Launched by a conductor (fleet worker token): report through the orca orchestration mailbox and never ask the human (no question tool, no mkd deck, no sweep) unless the human asked you in this session; your launcher relays.

One emitter, one adapter per harness

The .agents/hooks/personality-reinject.mjs hook computes the identity once per prompt and injects it into the context. The second line shows up only when the binary is present (without it, silence) and its text depends on the session's role. At most one setup notice is added (CREDENTIALS: or WORKTREE:).

The label rule

Name set by the user or by the hook → that name. Derived or automatic name → name (short id). Only an id → the full id. Nothing → unknown.

The forensic trailers

Every commit ends with Worktree: and Session:. They're forensic, not attribution: there is no AI attribution in commits, and no harness-branded trailers. Canon: /git-flow-master.

A worker has a single name, <label>--<handle>: session, tab, roster and Session: trailer. In Claude Code the hook builds it from the prompt token plus ORCA_TERMINAL_HANDLE, and in Pi the adapter does the same; in Codex and an OpenCode whose /rename takes an argument the conductor types it; where /rename takes no argument it lives only in the roster. The worker renames its own tab, never its session.

Example name: TK-123-add-google-auth--term_ followed by the handle's uuid; it's parsed by cutting at the last --term_. The worker renames its tab as its first action because that's a CLI call; its session it doesn't, because /rename is user input. The conductor renames the tab again on every sweep. The agent footer on screen shows the id and session lines, readable from the rendered screen. That's useful for the roster and for recovering a session.

The hard rules · each one was paid for with an incident

The hard rules in SKILL.md, and these are the ones that hurt most

  • A finished worker is closed in the same turn. Live worktrees nobody closed took the runtime down (G31).
  • Provision the worktree BEFORE launching. A provisioning gap disguises itself as another failure.
  • Create + launch + deliver the brief = one indivisible operation. Verify it a few minutes later with a working-tree status.
  • Launch each tier in its orchestration.permission_modes mode, never in edits-only: it covers edits but not commands.
  • Never accept a batch you didn't process. An un-acked batch hides everything behind it, and the runtime won't warn again.
  • The stop verb has worktree radius: count first. To close a terminal, you close that terminal (and its tab).
  • Never name the orchestrator to the user from a workflow skill when the gate fails, and never put it in prerequisites, in an unavoidable probe, in the ATR environment block or in a blocker-token sweep.

And one that isn't the skill's

Worker commits carry zero AI attribution (Critical Rule #3) and the two forensic trailers. In a same-checkout fleet, Critical Rule #15 (no global git discards) counts double.

The one discovered at close

A worker's cost is only visible on its own screen and disappears when the conductor closes the terminal. If you want cost accounting, reading the footer is part of the closing ritual. In the dogfood one worker's numbers were lost by closing it correctly and on time.

ADR-0024 put the worker on bypass because auto pauses and asks, and nobody watches a worker's terminal; and hard rule 24 says a launched session never asks the human: it escalates to whoever launched it, who passes the question on (it's on the worker contract slide). The rest is in SKILL.md. None of them is theoretical: each has a date, a repo and a symptom in references/gotchas.md.

Hard rules 17-19 · how a conductor verifies

A success code describes the call, never the outcome

A green receipt is the most dangerous green, because it suppresses exactly the check that would have caught the failure. Read the screen, the mailbox or the row: at the destination, never at the caller (AGENTS.md, Critical Rule #16).

What reported successWhere it's verified
a launch linethe screen: the command may have died in the shell (G11)
a terminal sendthe screen: only the tail may have arrived (G60, G64)
an orchestration sendthe recipient's reply: the receipt can carry "delivered_at": null (G67)
a dispatch in dispatchedthe terminal: it may have been replaced (G68)
the brief delivereda working-tree status a few minutes later
a worker readyits credentials and its name (tab and session), on its own screen
a worker finishedthe integration: git cherry, the PR, the tracker status, before closing

ok: false = a human is typing

On a terminal send it's the runtime protecting a person's input box. Never retry: the retry mixes your keystrokes with theirs. Wait and read the screen (G65).

Mid-sentence = truncated

What gets lost is the head, so the damage looks like a typo and nobody goes looking for the rest. Ask for the pointer; never answer the fragment or reconstruct what you thought it said (G64).

This skill doesn't own a stage, so it doesn't close with the lightweight stage verifier from artifact-lifecycle.md §5: the workflow skill runs that inside each worker. What falls to the conductor is this verification at the destination, which is what hard rule 17 demands.

Hard rules 20-23 · who speaks, who decides, what gets reported

A name is not an address, and a report is a count

Sign with handle and Run

A brief, a report or a seed names its author by the terminal handle (ORCA_TERMINAL_HANDLE, which is in the environment and isn't a self-report) plus the Run id. A name can resolve to nothing, resolve only to itself, or prefix-match another session in another repository and return success (G69, G70).

The receiver verifies the sender

The channel carries no identity. If the payload doesn't identify the sender, the receiver asks instead of inferring it from context. It hurts most in a reply: answering a presumed author is how one repo's scope agreement ended up in another's session.

The conductor decides scope; the worker, execution

It's blast radius, not hierarchy. Whatever widens the brief (another file owner, another ticket, another branch, a shared fixture) stops and escalates. And the other way around: a brief so narrow the worker has to widen it to finish is a conductor defect.

A report is a COUNT

"Almost done" isn't a status. Every report opens with numbers: how many pass, how many are left, how many are blocked and by whom. The standby report (references/standby-report-contract.md) has six parts: a one-line verdict, a metrics table, detail with a closed-vocabulary blocker and who unblocks it, root cause, options and the explicit negative.

The standby report is emitted only on stopping (standby, human in the loop or final state), never mid-flight: that would be a heartbeat in disguise. It has three wrappers with the same numbers: box drawing for a terminal, bullets with a separator for a tracker comment or a PR, and whatever a chat or a document renders natively. This skill isn't a stage owner: the session footer (skills, MCPs, CLIs, test levels) is printed by the workflow skill running inside each worker. When both apply at once, the standby report goes first, because whoever operates decides first and audits afterwards.

The launch line couldn't stay shared (a supervised worker has no argv), so what's shared is the prompt, and the prompt is what carries the behavior.

This is the slide that makes the skill adoptable: a team without the binary runs the same plan with more manual work, and the workflow skills never mention a tool they don't have.

Dogfood · a real sprint, several workers in parallel

What a fleet pays for is the second pair of eyes

A wrong conductor instruction

A worker refused to follow it because its own measurement said the opposite, and stopped to ask. A sequential session would have had the same confident derivation and no second pair of eyes, and would have sent a wrong blocker against a release. That's where hard rule 16 comes from.

A doctrine claim that was already false

An outdated statement about the project's test users, which would have weakened every ATR in the sprint. A worker found it by measuring, not by reading.

A danger between workers

A shared account's token list is visible to everyone who uses it. The claims vocabulary couldn't express that: the enumerate intent was born from it.

Decorative traceability

At harvest, the conductor saw stories linked to their tests in the direction the TMS doesn't count: the coverage existed in the tracker and was recorded nowhere.

What didn't work

The supervised route didn't work on that machine: everything ran through the documented fallback and the conductor paid for it in manual nudges. That's where native path as the supervised default and custom argv as human pasting come from.

Where the numbers are

The deck teaches the lessons, not the numbers. The run's duration, artifacts, findings and cost are, with date and source, in .context/ADR/ADR-0006-forensic-measurements-ledger.md; the incidents, by G id, in references/gotchas.md.

Honesty is part of the deck: the case for a fleet isn't speed, it's the second pair of eyes. The case against, in that run, was that supervision didn't work and every correction was manual. The conductor's verdict was that it would run the next sprint this way, with one condition: fix the supervised route first, or budget for the conductor acting as a manual scheduler.

When NOT to use this skill · three things that look alike

Supervise, hand off a task or pass the whole session

SituationWhat it really isUse
a read, a verification, a map that fits in this turnmost of the workone-shot subagents (AGENTS.md §3)
give a TASK to another agent and supervise itorchestration: Task, Dispatch, mailbox; the work comes back/orca-orchestration

The deciding question

Do you need to supervise, wait for results, answer questions or coordinate dependencies? Then it's orchestration. Do you want to let go of the work and stop worrying about it? That's a handoff, and it carries no Run.

It's also not for

Manual QA per ticket (/sprint-testing), writing test code (/test-automation), branch, commit, push or PR mechanics, or a git worktree without a fleet (/git-flow-master).

A handoff between conductors is a different case: a Run outlives the session that created it. The outgoing conductor writes kickoff.md (Run id, topology, closed rounds, what's in flight, open claims, the owner's next decision) and the incoming one binds to the Run by its run.md id. The Run is never guessed from a listing: Runs from other repos live side by side on the same machine.

references/html-surfaces.md · one gated line, like the rest

A generated page opens next to its terminals

The coverage map from bun run tests:map, an Allure report, these decks or a decision deck: with the runtime ready they open in a tab bound to the worktree, on the same board card and visible from mobile. Without a runtime they open the normal way and nothing is said: the system browser is the normal result, not a degraded one.

Two routes

A file:// URL is enough for a page the owner only READS. For one the owner ANSWERS, a loopback URL served by the tool that renders it sends the result back to the agent with no copy and paste.

The dead end

Reading the result from the clipboard doesn't work: the embedded page doesn't gain DOM focus, even when you bring the tab to the front (G62). That's why the loopback route is the only one that removes manual pasting.

A single copy

Browser storage is per origin: the same page open in two places saves two sets of answers that never meet. Open one, say which is the live one and close the other. Before moving it, check whether it already has saved answers.

The verb grammar is served by the binary, not by this reference. What it does say: pass the explicit worktree selector so the tab ends up bound and not floating, and then verify the tab reports no load error and the page rendered. An open tab is not a page that worked.

Take-away · how to invoke it and what to read

The skill is the HOW. The WHAT still belongs to each workflow skill.

Phrases that trigger it

"orchestrate this", "launch workers", "one session per story", "parallelize the sprint", "how's the fleet doing", "talk to the worker on BK-123", "resume last night's run", "nightly automation".

Phrases that DON'T

A subagent for a read in this turn (that's AGENTS.md §3 and it stays the default). A pure handoff, with no supervision. Passing the whole session to another (/session-handoff). QA per ticket (/sprint-testing). Test code (/test-automation). Git mechanics (/git-flow-master).

Without the binary

Level 1 orchestration = subagents in this same session. Professional orchestration = the runtime installed. The skill says so once, and only if you asked.

Where the depth is

SKILL.md is short on purpose. The full cycle is in references/coordinator-playbook.md; every topic has its own reference, and the References table in SKILL.md is the list.

Three golden rules

1 The subagent is still the default: orchestrate only what doesn't fit in a turn. 2 Create + launch + brief is indivisible, and the close happens in the same turn. 3 Without a runtime, total silence in the workflow skills: launch.txt is written anyway.
