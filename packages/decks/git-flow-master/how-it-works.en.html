Step 2 · 3 of 19

What it decides for you: the strategy

A single source

The git_strategy: block in .agents/project.yaml. Never a separate file or policy prose in AGENTS.md, which only points to the block.

sdet is opt-in

It is never inferred from the layout: a live test/<module>-suite trunk with PRs targeting it confirms it.

Resolution is sticky: the next invocation re-reads the block instead of asking again, and editing it by hand is valid. Order matters: first the declared block, then the signals from the branch layout, and the question as a last resort. The "inherited" branch exists because the boilerplate ships with the block filled in (solo-main) and a new project receives it as is.

Strategy Setup · 5 of 19

solo-main comes by default: it still has to be chosen

The template trap

The boilerplate ships with the block filled in. A new project inherits it and the updater freezes project.yaml, so a value being present does not prove anyone decided it. meta.strategy_source says so: inherited or chosen.

The offer

With an inherited strategy, the skill offers Strategy Setup once per session and spells out what the default costs (no integration branch, no promotion path, no review gate). A "no" stays on the inherited one. Only Strategy Setup stamps chosen.

The questionnaire (each question, only if it applies)

Q1promotion integration to production: fast-forward only / merge commit / squash
Q2merging the working branch: merge commit (--no-ff) / squash / rebase + merge
Q3hotfix: branch from production, PR to production and back-merge the same day
Q4all strategies: direct_push_to_protected · admin_bypass · require_pr_reviews

Then it materializes: it creates branches only if they are missing and syncs only by a real fast-forward, never --force. The push of that sync to a protected branch always asks.

At the end it offers to carry the policy to the host: first bun run git:policy verify (read only), and if there is drift it shows the dry run of apply and writes only with your yes.

Triggers: "set up our git strategy", "configura el flujo de git" (set up the git flow), "bootstrap branching". Single-branch strategies do not answer Q1 to Q3; Q4 always applies, because a lone main is protected too. A question already answered in decisions.* is not repeated, and branch creation is always proposed first. Full mechanics: references/strategy-setup.md.

Push · 6 of 19

Push to a protected branch: Rule #5 reads a variable

git_strategy.policy.direct_push_to_protected in .agents/project.yaml. AGENTS.md does not fix the answer: the variable is the decision.

forbidden

Rejects the direct push and redirects to the PR flow: it proposes a working branch and gh pr create.

confirm

Asks before every push and waits for an explicit yes. This is also what happens if the block is missing or null.

allowed

Standing authorization: it pushes without asking. Asking anyway would turn allowed into confirm.

Admin bypass

Only with admin_bypass: true can the skill offer to skip the PR in an emergency, and even then it reconfirms that the operator has admin rights and the action itself. With false, never.

Push by upstream state

No upstream: git push -u origin {branch}. Behind: git push. Diverged: stop and move to conflict resolution, never force.

The allowed value is stamped by Strategy Setup together with the user, which is why it counts as authorization. The list of protected branches comes from the strategy (slide 4) joined with git_strategy.protected.

Safeguards · 7 of 19

What no strategy relaxes

Rule #6 · history

  • Never rewrite pushed history (rebase or amend on commits already published).
  • Never force-push to a branch others may share.
  • Never delete remote branches without confirmation.
  • Always move forward: new commits, merges preserved.

--force, --force-with-lease and --no-verify only with explicit authorization and an unshared branch.

Rule #15 · no global discards

Prohibited: git restore ., git checkout -- ., git reset --hard, git stash without a path and git clean -f. Another session may share the tree: only your own paths get discarded.

Explicit staging

Never git add -A or git add .: explicit paths, so a secret or someone else's work does not travel along.

Hook rejected the commit

Fix the cause and make a new commit. --amend would act on the previous commit.

These are invariants, not strategy options: no git_strategy value loosens them. In repos with a PBI cache, the skill also checks that nothing from .context/ outside the COMMIT tier ends up staged.

Group by responsibility

Test code, API schemas, test data, skills / docs, config. A test's data and fixtures travel in the same commit as the test.

No AI attribution

No "Generated with…", no AI Co-Authored-By, no Claude-Session: or any other trailer carrying a harness brand. The commit looks like a person wrote it.

The skill proposes all the commits as one block and waits for OK, changes or rejection before running them one by one. The same goes for branch names and PR bodies.

Commit · 9 of 19

Forensic trailers: Worktree: and Session:

Copied from the context

The label runs up to the literal token harness= (it may contain spaces and parentheses). primary outside a worktree; unknown if it does not resolve. Nothing below. On commit, .husky/commit-msg only warns (does not block) if one is missing or a Claude-Session: shows up.

Provenance

They answer which checkout and which session produced the line, for a bisect or a post-mortem of parallel sessions. They name no tool, vendor or model: that is why they do not count as attribution (Rule #3).

One emitter, one adapter per host

Claude Code and Codex run it as a command hook; OpenCode imports the constant from a plugin; Pi loads it from an extension. Same text, no per-harness copies.

They are mandatory on every commit and in every strategy. A missing trailer is less recoverable than an honest unknown. The hook is the same one that re-injects the personality contract.

Step 1b · 10 of 19

What is declared against what the host enforces

$ bun run git:policy plan # the mapping, no network $ bun run git:policy verify # reads the host · exit 1 on drift $ bun run git:policy verify --stamp # also records meta.policy_* $ bun run git:policy apply # dry run $ bun run git:policy apply --yes # writes the ruleset [--allow-loosening] # only if it loosens a guard

verify: once per session, on the first push, PR or merge intent, and in the pre-push hook and bun run repo:check. Unreachable host = warning and exit 0.

A 404 does not mean "no protection"

With rulesets, branches/{b}/protection answers 404 while rules/branches/{b} requires a PR. The tool queries both.

A push that went through may be a bypass

Changes must be made through a pull request in the output: the rule is still live for everyone else and the push is reported as a bypass.

Code owners without a CODEOWNERS

An impossible requirement: every merge ends in a bypass. verify flags it as drift.

Why a script and not a checklist: the reconciliation existed as prose and did not happen. A script makes all the queries on every run. Strategy to ruleset mapping: references/ruleset-parity.md.

Parity · 11 of 19

Drift has three exits, and one is declared

The yaml was wrong

Fix .agents/project.yaml so it says what the host enforces.

The host was wrong

git:policy apply: read the dry run before --yes.

Both are right

It is recorded in policy.accepted_divergences with its reason.

git_strategy: policy: direct_push_to_protected: allowed accepted_divergences: - field: main.direct_push_to_protected enforced: blocked (pull_request rule) accepted: <YYYY-MM-DD> reason: > Why both sides differ on purpose.

verify lists it under ACCEPTED and exits 0; it warns if the entry no longer matches any drift.

verify --stamp records policy_source: accepted, different from verified (host identical to the yaml).

apply keeps the host side of the accepted field: it does not open main to anyone.

With the divergence declared, the remote's Bypassed rule violations line is expected: it is not treated as an anomaly and no PR is opened to "comply" with the rule.

Typical case: the yaml declares allowed because the push credential is on the bypass list, and the host keeps the PR rule for the rest of the contributors. Acceptance is per field and requires a reason. apply is never run to fix a verify nobody read.

The PR: base by strategy, no merge

$ gh pr create \ --title "{type}({ISSUE-KEY}): {description}" \ --body-file "$(mktemp)" \ --base {base} \ [--reviewer {users}] [--label {labels}] [--draft]
BranchBody template
test/*references/pr-test-automation.md: Summary, Changes, Test Plan, Traceability (issue, ATP, ATR, TCs), evidence, Merge danger, checklist
everything elsereferences/pr-templating.md

Merge danger and evidence

A one-way or two-way door, and the blast radius in a word or two. Evidence goes by weight: screenshots, the test that failed and now passes, and console output last.

Title and placeholders

Under 70 characters. A placeholder the skill could not fill stays visible to the author; no section is silently deleted. Labels: check with gh label list.

Stops at creation

The merge is the user's step. Exception: a supervised worker whose brief names the merge runs the owner's instruction and says so in its report.

Optional adversarial gate

A diff over 400 lines or with shared scaffolding: the skill offers /judgment-day before opening and never invokes it on its own.

The body is written to a tempfile and passed with --body-file to avoid escaping problems. Merge danger is the section that used to be called risk; the template placeholder is still RISK. With nobody at the keyboard, a routine writes the body to a file and reports, unless its brief names opening the PR. Without gh or without auth, the skill reports the blocker; it never implies the PR exists.

Scale · 13 of 19

Over 400 lines: decide before coding

The plan is a contract. If the real diff exceeds the estimate, the decision is run again instead of silently stretching the budget. It is returned with its trace, never as a bare label: Chain strategy:, each question answered with the reason for this change, and Decided by:. A trace that only repeats the conclusion counts as undecided. The threshold comes from the research on code review: above it, defect detection drops.

With sdet active, the integration trunk is already the chained mode of every test suite, and this tree is not walked for test automation. It still applies to non-test changes in the same repo.

A monolithic change that is not mechanical and has no shared scaffolding is a planning smell: go back to the story breakdown. The full tree is in references/branching-strategies.md.

Scale · 14 of 19

sdet: one ephemeral trunk per suite

Per ticket

Branch cut from the trunk, never from the previous ticket. Local gate on local and staging, push, Sanity CI, PR to the trunk, --no-ff merge.

Plus Branches

Adjacent work (docs/* chore/* fix/*) between tickets, with a PR to the trunk like any ticket.

Closing

Sync gate so the final diff shows only the suite, one reviewed PR from the trunk to main, and the trunk is deleted. Only main is protected.

The trunk is a stand-in for main for the suite: "never go back to main" means going back to the trunk until the end. The name comes from the scope: test/<module>-suite or test/<STORY-KEY>-<slug>-suite. Every suite PR is merged with gh pr merge --merge: never squash inside the trunk, and only on the final trunk to main PR if the host allows no other method. Full runbook: references/sdet-integration-trunk.md.

Wherewherever you choose.claude/worktrees/outside the repo, visible to the owner
For whomany agent or personClaude Code onlya fleet the owner wants to see and steer

What does not travel

A new worktree brings only what is tracked. Untracked files are moved by hand; gitignored ones (.env, node_modules/, the skills alias, the PBI cache) are missing, and fail with messages that point elsewhere.

Shared across trees

Objects, refs, config, hooks and the stash list. To hand work between sessions you commit, never stash.

When it is not needed

A linear task on a clean tree, or sessions that only read code and write to the tracker: a branch or the same checkout is enough there.

Git blocks the same branch in two worktrees, and that is what makes them safe for parallel sessions. Full reference with the decision guide: git-flow-master/references/worktrees.md.

Isolation · 16 of 19

From creation to removal without losing state

Three paths to the same provisioning

orca.yaml runs worktree:provision in every Orca worktree. Harness worktrees (Claude Code, the Codex app) copy the .worktreeinclude list, the same one the script copies; the Codex app also runs the script from .codex/environments/environment.toml.

<<PRIMARY_ROOT>>

The primary checkout, the same value from any worktree. .session/**, evidence and reports go there: ignored files written inside a worktree die with it.

The audit classifies

STATE goes to the primary (--rescue copies without overwriting) · CACHE comes back with the command it names · DISPOSABLE is lost without regret · UNKNOWN is decided by hand. Exit 1 while STATE or UNKNOWN remains only in the worktree.

The updater refuses

bun sync keeps backups, markers and prompts inside the checkout: in a worktree it aborts and asks you to run it in the primary.

A worktree removed with git worktree remove deletes ignored files without warning, and the Orca CLI skips archive hooks unless --run-hooks is passed. That is why the audit comes before any removal. Provisioning doctrine: orca-orchestration/references/provisioning.md.

What the skill does not do, and where the rule lives

In SKILL.mdRule
SKILL.md 5Force-push to main or to any shared branch.
SKILL.md 5Amend or rebase of an already pushed commit.
Compact RulesCommitting secrets, credentials, .env contents or tokens: git history is forever.
SKILL.md 3AI attribution in commits or PR bodies (AGENTS.md Rule #3).
SKILL.md 4Pushing to a protected branch while skipping the AGENTS.md Rule #5 policy.
SKILL.md 5--no-verify to "go faster": the hook catches the bug you did not see.
SKILL.md 2Mixing responsibilities in one commit (feat + refactor + lint).
SKILL.md 3.4Stacking PRs without naming the dependency chain in the body.
SKILL.md 12Global discards of the working tree (AGENTS.md Rule #15).
SKILL.md no longer has a separate anti-pattern list: each prohibition lives once in the Compact Rules and in the numbered Critical rules, and the table points to where. Force-push, amend, rebase of pushed work and --no-verify are the same Rule 5; global discards are Rule 12 (AGENTS.md Rule #15). The rules protect different things: some protect other people's work, some the history, some the review. With nobody at the keyboard, the skill does the local, reversible work (reading state, branches, commits) and stops before push, PR, merge, a force flag or a bypass, and reports. An absent person never turns confirm into allowed.

Invocation and handoffs

How it is invoked

Claude Code: /git-flow-master.
OpenCode and Codex: load the git-flow-master skill.
Pi: /skill:git-flow-master

On every host it loads itself on intents like "commit and push", "abrí un PR" (open a PR), "tengo conflictos" (I have conflicts) or "configura el flujo de git" (set up the git flow); the description is in English and is matched by meaning. It has no modes: the operation comes from the request.

Who calls it

/test-automation ends in a clean local review and hands over the delivery.
/framework-development dispatches the verified code.
/orca-orchestration cites it as the canon for the trailers and the flat worktree.
/agentic-qa-onboard uses it for Strategy Setup.

Who it calls

/judgment-day: optional gate before the PR.
/regression-testing: Sanity CI of the sdet trunk.
/acli: Jira operations that a commit or PR triggers.
Ticket testing: goes back to /sprint-testing and friends.
