skills-io · how to read this deck

One story, two repos, one pipeline

Every skill in the ecosystem behaves like a terminal process: it receives stdin (context files, Jira fields), depends on other skills (deps) and emits stdout (artifacts, issues, transitions). This deck documents that inputs/outputs contract, phase by phase.

BEFORE · Project context qa-boilerplate · once, and every time the product changes ├─ project-discovery domain + infra maps · project-config.md ├─ test-framework-adaptation KATA adapted to the product's stack └─ project-context data · API · E2E maps · Master Test Plan └─ context skills bun run context:map <slug> · every phase reads them │ ▼ PHASE 1 · Story dev-boilerplate · product-management │ ▼ PHASE 2 · Refinement ⟲ loop dev (INVEST) ⇄ qa (shift-left-testing) │ ▼ PHASE 3 · Implementation dev-boilerplate · sprint-development │ ▼ PHASE 4 · Testing qa-boilerplate ├─ 4a sprint-testing manual QA per ticket ├─ 4a exploratory-testing Execution without a ticket · feeds 4b ├─ 4b test-documentation TMS + ROI ├─ 4c test-automation KATA · Candidate verdict only └─ 4d regression-testing release gate GO / NO-GO │ ▼ PHASE 5 · Production Observation · L4 └─ agentic routine, no skill SLOs · error budget · feeds the next shift-left CROSS-CUTTING spans every phase · "cross-cutting" tab ├─ review pr-review-lead · judgment-day ├─ fleet and handoff orca-orchestration (optional) · session-handoff └─ git · evidence · sync git-flow-master · bug-screenshot-annotation · [SYNC] full skill list .agents/skills/REGISTRY.md

Observation is declared, not implemented: it has no skill of its own (see .agents/skills/ for the current state). It shows up here so the map does not lie about where the system ends.
