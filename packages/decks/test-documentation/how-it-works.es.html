Un ticket solo no ve la falla que más importa

Un link de coverage invertido es invisible en su Story: el link existe y el panel queda vacío. Por eso, al auditar un ticket, el modo ofrece también el barrido project-wide de dirección mixta (varias keys o una JQL → una sola worklist). Corregir dirección es borrar antes de recrear: Jira deduplica par + tipo, así que agregar el link corregido sin borrar es un no-op silencioso. El plan que aprobás dice qué links se borran, por id, y repara hacia el camino del ATS, nunca con links directos TC→Story en masa.

Mode routing de SKILL.md. repair-traceability recorre la cascade en orden: ① TC en ATS y ATS→Story (llena el panel) ② TC solo vía ATP (ubicado, sin coverage) ③ TC→Story directo (last resort válido) ④ sin camino (huérfano). Canon de dirección, borrar-antes-de-recrear y barrido: agentic-qa-core/references/traceability-linking.md §4 y §10. Credenciales faltantes siguen siendo un STOP duro (Critical Rule #10).

antes de la fase 1: tres candados

Nada se documenta sin pasar los gates

Prerrequisito duro

Solo comportamiento ya validado: Story QA Approved, bug cerrado, o sesión exploratoria terminada. El TMS documenta y protege regression, no es una herramienta de exploración (explorar es de /sprint-testing).

Preflight Gate

REQUIRED: issue-tracker operativo (/acli, valida con bun run jira:check) + modalidad TMS resoluble (jira-xray → /xray-cli + creds XRAY_*). OPTIONAL: repos fuente legibles. No toca entorno vivo → sin probes de DB/API/browser. Gaps → UNA checklist; RED bloqueante → STOP.

Fase -1 · Resume check

Lee .session/test-documentation/<scope>/progress.md. Si existe: muestra scope, modalidad, última fase completada y chunks pendientes → ofrece resume / restart / abort (restart archiva primero).

El caso de resume que más importa

Bulk create de la Fase 3 interrumpido a mitad de lote: progress.md registra cada chunk completado (uno por subagente), así que resume salta los TCs ya creados y despacha solo los chunks faltantes.

Los tres candados corren en orden: prerequisito de comportamiento validado (conceptual), preflight de capacidades (mecánico: acli + TMS), y resume de sesión. El skill no ejecuta contra un sistema vivo; su gate se centra en poder ESCRIBIR en el TMS.

Promover sin Test de sprint → crear

Si el verbo dice promover pero el escenario no tiene Test de sprint (Story testeada antes de fijar el valor, o escenario derivado recién ahora), se crea para ese escenario y se anota en progress.md. Nunca se salta el TC.

Los TCs de sprint son borradores

Se escribieron para correr una vez. Antes de entrar a regression se refinan: título canónico, pasos repetibles, precondiciones construibles desde un entorno frío, variables en lugar de ids, split o merge por identidad. Cada TC refinado lleva una línea Refinement Notes.

Modalidad y {{TC_CREATION_STAGE}} se persisten juntos en plan.md §Inputs y son sticky. La tabla completa del knob vive en sprint-testing/SKILL.md §"Which stage creates the TCs"; test-documentation solo la consume. Cualquiera sea el verbo, la regla del título canónico es la misma (ver la slide de promoción al RTP).

alcance bug-driven: la regla que vale oro

Un bug importante DEBE terminar con un Test

1

¿Es candidato de regression?

Aplica los filtros de la Fase 0 + ROI (el bug previo sesga hacia arriba). NO → trátalo como un test fallido: el fix ya se verificó en sprint-testing → Deferred, sin Test nuevo. SÍ → paso 2.

2

¿Vino de un Test ya ejecutado que falló?

SÍ → REUTILIZA ese Test: enlázalo al bug (tests / is tested by) y promuévelo a regression, nunca dupliques. NO → CREA + diseña el Test (native: issue Test; xray: Xray Test + Test Plan / Test Set).

Anula «el bug es el test case»

Esa frase de /sprint-testing cubre solo el retest inmediato del sprint, NO la regression futura. Esta regla decide si debe existir un Test persistente para que el bug nunca regrese en silencio.

Nunca reabras un bug cerrado (D8)

La historia del bug es inmutable. Crea el TC nuevo y enlázalo vía tests / is tested by, no adjuntes regression reabriendo el issue.

Un bug cerrado es evidencia empírica fuerte de que el área regresa: la mayoría califica y se inclina a Candidate, aunque no todos (un typo puntual en un área estable se difiere). La decisión reuse-or-create evita duplicar Tests que ya existen en el set.

Validación contra código fuente: obligatoria antes de documentar

El ATP se escribió ANTES de que el código existiera. Grep a data-testid=, route handlers, rutas de API y formatos de texto; toda divergencia va a una sección Refinement Notes del TC. Saltarse este paso es la causa nº1 de tests automatizados inválidos después.

Lecturas detalladas SIEMPRE por el script de sync (acli view devuelve null en custom fields). Discrepancias típicas: una API asumida que en realidad es SSR/DB directa; "based on N reviews" vs el real "(N reviews)"; IDs hardcodeados vs patrón de variable.

Candidatos ≠ items del TMS

Derivar amplio es gratis; persistir está gateado por ROI (Fase 2). Colapsar un AC a un solo TC exige justificación escrita «trivially atomic». El mapa AC→TC es el piso, no la cobertura.

Improvement bridge

Un test-beyond-AC expone un gap porque el AC estaba infra-especificado → el artefacto correcto es un issue Improvement (doctrina de defect-management), NO un TC de regression ni ensanchar los ACs de la Story después del hecho.

EP sin BVA pierde el off-by-one. La regla de identidad (pre+acción) solo fusiona DENTRO de una partición, nunca a través de particiones, límites o estados. Canon: agentic-qa-core/references/test-design-doctrine.md.

fase 2: prioritize · el gate que nunca se salta

Tres filtros, luego la fórmula

F1

¿Protege contra regressions futuras?

Typo puntual en un área estable → No → Deferred.

F2

¿Bugs previos en esta área?

Sí → prioriza aun con ROI moderado: «falló una vez, puede fallar de nuevo».

F3

¿Nivel de app o de feature?

XSS / a11y / perf / responsive → suites APP-level → Deferred desde este alcance.

Falla cualquier filtro → Deferred

Los tres filtros matan a la mayoría antes de hacer aritmética.

ROI = (Frequency × Impact × Stability) ───────────────────────────────── / 10 (Effort × Dependencies) / 10 = constante de normalización todo en 3 → 0.3 → Deferred (el default) Component Value = ROI × (1 + 0.2 × N) N = flujos E2E que reutilizan el TC estimado, tope N = 3 (máx. ×1.6)
Factor (1-5)15
Frequencyanualcada PR / commit
Impactcosméticoingresos / core
Stabilitymuy volátilmeses sin cambios
Effort (÷)trivialsemana+

Effort y Dependencies son DIVISORES: un "flujo crítico" caro y acoplado DEBE puntuar bajo, y eso es la fórmula funcionando. El "/ 10" no es un sexto factor: lleva el cociente crudo (0.04 a 125) a la escala de los umbrales (0.004 a 12.5). Component Value rescata átomos reutilizables: authenticateSuccessfully con ROI 2.0 reutilizado en 3 flujos → 2.0 × 1.6 = 3.2 → Candidate. N es una estimación cualitativa (nadie cuenta call-sites), con tope 3; se anota en el comment de ROI. Bandas autoritativas: references/tms-conventions.md §9.

Tres capas, tres conteos: la forma saludable

analizados 80 → documentados 12 → automatizados 8. Un test entra al repositorio porque será re-ejecutado, nunca para alcanzar un conteo. Si >50% termina Candidate/Manual → reaplica los filtros con más rigor: la mayoría debe ser Deferred.

El agente puntúa. La persona firma.

El agente deriva escenarios por técnica, calcula el ROI y propone el veredicto. Cada veredicto lo firma la persona, igual que la épica de regresión y el Test Set. Autonomía CSA 2, verificador separado recomendado: un segundo agente re-lee los veredictos contra el ATR. La alarma del >50% Candidate/Manual se responde, no se ignora.

El veredicto (aritmética) es idéntico en ambas modalidades; lo que cambia es el verbo de la Fase 3: con {{TC_CREATION_STAGE}} = auto, CREAR (native) vs PROMOVER + ENRIQUECER (xray); los otros dos valores fijan el verbo en ambas. Deferred nunca es un borrado. Anti-patrón D4: nunca saltarse el scoring de ROI. Contrato agéntico del stage: agentic-qa-core/references/stage-gates.md.

fase 3: document · preflight de contenedores

Epic · Test Set · Test Plan: tres cosas distintas

Regression Epic

= el epic de proceso «QA Test Repository». Resolver found-or-created por JQL (type = Epic AND summary ~ "QA Test Repository"); si falta, pregunta antes de crear y cachea la key en .agents/project.yaml. Todo TC documentado se parenta aquí, nunca a un epic de producto.

paraguas del repositorio

Test Set, dos altitudes

ATS per-Story (obligatorio): ATS: {US_ID}: {story title}, tercer artefacto de la familia ATP/ATR/ATS, parent «QA Test Artifacts», components heredados de la Story. Su link is tested by a la Story es lo que llena el panel de coverage. TS: feature-level (opcional): TS: {EPIC|module}: Validate {feature}, agrupa smoke/regression, components opcional. Native sin work type Test Set → links directos TC↔Story.

coverage

Test Plan

Alcance de ejecución / regression, el conjunto de Tests que corre para un release o ciclo. El ATP en jira-xray ES un issue Test Plan (parent: epic «QA Master Test Plan»). El RTP (RTP: {PROJECT_KEY|module}: Regression Test Plan) es el Test Plan long-lived de regression bajo ese mismo epic: destino de cada TC promovido con label regression-candidate, y nunca se completa: cada corrida regular de /regression-testing escribe su RTR (Test Execution RTR: {scope-id}: Regression Testing) contra él; el STR queda para el cierre del sprint.

ejecución

Modelo de tres ejes (defect-management-doctrine.md)

Parent = bucket de proceso QA (Test → «QA Test Repository» · ATP → «QA Master Test Plan» · ATR y ATS → «QA Test Artifacts») · issue-link = la Story origen · components = el módulo de producto afectado. Tres ejes separados; el parent nunca lleva la traza de producto.

La gente fusiona estos contenedores rutinariamente. Epic = repositorio completo; ATS = el Set per-Story que da coverage (TS: opcional agrupa por feature); Test Plan = alcance de ejecución. En jira-native con work type Test Set el ATS existe igual (membership = links TC→ATS); sin work type, links directos TC↔Story + Regression Epic + label.

Huérfano = TC sin NINGÚN camino a la Story

Ni ATS, ni ATP, ni link directo → test-documentation modo repair-traceability verifica la cascade TC→ATS→Story → TC→ATP→Story → TC→Story. D7: un ATR nunca se enlaza a dos ATPs (1:1). Rechaza títulos «Login test», «Login - error», «TC1: Test form».

Coverage verificado live: SOLO el link ATS→Story (o los links directos Test↔Story) llenan el panel; los links ATP→Story y ATR→Story son trazabilidad administrativa. Cascade de resolución: TC→ATS→Story (primaria) → TC→ATP→Story (placement, no cubre panel) → TC→Story directo (last resort válido; el defecto es no tener ningún camino). La membership TC en ATS es siempre un link TC→ATS en ambas modalidades; jira-xray además escribe la membership Xray-internal (GraphQL vía /xray-cli), nunca en lugar del link. TC en ATP / ATR sigue siendo Xray-internal. Canon: traceability-linking.md §9.

La regla de las dos llamadas de Xray

Una Create Test (registra en Xray) + una Update Issue (pega la Description). Saltarse la segunda deja un TC sin documentación legible en Jira: el fallo silencioso más común.

Anti-patrones D1 · D6

Nunca escribas ADF JSON a mano: los cuerpos rich-text (ATP, ATR, descripción del Test) se escriben en Markdown, se convierten y validan con el conversor .agents/skills/acli/scripts/md-to-adf.ts, y lo que se publica es el ADF JSON resultante; por la vía CLI, acli nunca convierte Markdown solo. Nunca fabriques customfield_NNNNN: corre bun run jira:sync-fields --force y resuelve por {{jira.<slug>}}.

Description siempre con el template completo: Related Story · Priority · ROI · Prior bugs · Test Design (gherkin/steps) · Variables · Implementation Code · Architecture · Test IDs · Preconditions · Expected Results. Cada TC creado: parent «QA Test Repository», components = módulo de producto afectado, assignee = el usuario de la sesión, puesto al crear.

La dispatch de esta fase es la única paralela: N > 10 TCs → subagentes en chunks de 5-10 (ver slide de orquestación). Cada subagente carga /xray-cli o /acli según modalidad y corre este flujo serial para su chunk.

fase 3: document · el artefacto que viaja a automatización

fase 3: el último paso, a dónde van los Candidates

Promover: título primero, label y membership al final

1

Re-derivar

El título sale de Precondición + Acción + resultado verificable del TC, nunca de la redacción del outline de sprint.

2

Conservar el prefijo

{US_ID}: TC#: no cambia. # es un índice estable dentro de la Story: si un hermano quedó Deferred, el hueco queda.

3

Reescribir

Si el summary vivo difiere, [ISSUE_TRACKER_TOOL] Update Issue: el summary es un campo de Jira, nunca pasa por [TMS_TOOL].

4

Verificar, recién ahí promover

Título válido → label regression-candidate + RTP. El cambio viejo → nuevo queda en progress.md.

El RTP, uno por proyecto

RTP: {PROJECT_KEY|module}: Regression Test Plan, parent «QA Master Test Plan», find-or-create (pregunta antes de crear). Assignee = vos al crear: Xray rechaza ediciones de membership en un Test Plan que no es tuyo; si aparece uno ajeno, pregunta antes de reasignar. Pasa a ready con la primera promoción y ahí se queda, nunca complete. Manual entra al mismo RTP con manual-only; Deferred nunca. /test-automation y /regression-testing leen de ahí: un Candidate fuera del RTP no existe downstream.

Agrupar en flujos e2e

Un grupo = un journey que un spec corre de punta a punta, con nombre de journey («Checkout, compra de invitado», no «Checkout tests»). Un TC que usan 2+ flujos es un componente atómico (un Steps module en KATA): se lista bajo cada flujo y su cuenta es la N del Component value. Se escribe en la descripción del RTP, sección ## Regression flows (la copia durable) y como columna en COVERAGE-MATRIX. Un Candidate sin flujo es una alarma, no una categoría.

Secciones "Title on promotion" y del RTP handoff en SKILL.md. La regla del título vale para todo camino de escritura: jira-xray (un Test de sprint seleccionado al RTP) y jira-native (un Test de Stage 4 creado desde un outline de sprint). En jira-native la promoción también viaja en labels del Test; /regression-testing describe cómo lo lee. Ciclo de vida: RTP nace en planning, designed → ready, nunca complete; feature TS queda en designing hasta que cierra su Epic; Preconditions quedan en active.

quién hace qué: centro de comando + subagentes

El hilo principal decide; los subagentes escriben

Inline (orquestador)

Fases -1, 0, 1 y 2: resume, modalidad, análisis y veredictos viven en el hilo principal; planificar y decidir no se delega.

criterio

Paralelo (Fase 3, N > 10)

Chunks de ~5-10 TCs por subagente, cap = 10 subagentes (Jira/Xray throttlean y devuelven 429; el cap está en SKILL.md §Subagent Dispatch). Cada subagente carga /xray-cli o /acli. N ≤ 10 → inline.

fan-out

Error protocol

Fallo de subagente → STOP, reporta el estado parcial (qué TCs aterrizaron, cuáles no, con keys/errores) y ofrece retry / skip / abort. Sin auto-fix, sin rollback.

cierre: dónde encaja y cómo se invoca

Deriva amplio · documenta lo repetible · automatiza los pocos

Cómo invocarlo

Claude Code: /test-documentation <KEY> o /test-documentation repair-traceability <KEY>. OpenCode y Codex: «cargá la skill test-documentation, modo <modo>». También por frases: «document tests», «ROI analysis», «which tests to automate», «fix-traceability».

Handoffs en el pipeline

Entra desde /sprint-testing (Story QA Approved, bug cerrado). Sale hacia /test-automation, que re-alcanza los Candidates: module → Macro · ticket → Medium · bug → Micro (ad-hoc entra donde encaje). Manual y Deferred son terminales.

Artefactos que deja

Durable, en el TMS: TCs enlazados US↔ATS↔ATP↔ATR↔TC con su comment de ROI · Candidates en el RTP con ## Regression flows · comment Prioritization con los Deferred. Local: los dos reportes [LOCAL] de .context/reports/, el caché [SYNC] de test-cases/ (se lee, no se escribe) y la sesión archivada en .session/.archive/.

Las tres reglas para llevar

1. Por defecto, Deferred: 3 filtros + ROI = (F×I×S)/(E×D)/10. 2. Una (precondición + acción) = un TC; los rasgos transversales viven dentro de los tests. 3. Set-first: ATS → ATP → ATR → TC, y un bug importante siempre termina con un Test.

Cierre: Documentation es el puente entre la QA manual (Planning · Execution · Reporting) y la automatización (Automation). La IA acelera el oficio; el criterio y las confirmaciones siguen siendo del humano.
