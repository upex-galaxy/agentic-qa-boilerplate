Capítulo 01

Qué es CI y por qué un tester lo necesita

Integración Continua: cada cambio dispara una verificación automática en una máquina limpia. Para QA significa que la suite corre sola, siempre igual, y deja evidencia que nadie tiene que pedir.

el dolor y el patrón

Sin CI, la suite corre cuando alguien se acuerda

Sin CI

«Corré la regresión antes del release». Corre en TU laptop, con TU .env, con TU versión de Chromium. El reporte queda en tu disco. Si fallás vos, no hay evidencia. Si la app se rompe a las 3 AM, nadie se entera hasta las 9.

Con CI

Un archivo .yml describe QUÉ correr y CUÁNDO. GitHub levanta una máquina limpia, instala todo, corre la suite, guarda screenshots, traces y el reporte Allure, y escribe el resultado en el TMS. Cada noche. Igual. Sin que nadie toque nada.

la jerarquía en 12 líneasesquema
name: Smoke Tests           # el workflow
on:                         # los triggers
  schedule: [...]
  workflow_dispatch: [...]
jobs:
  SmokeTest:                # job 1
    runs-on: ubuntu-latest  # el runner
    steps:
      - uses: actions/checkout@v4   # step (action)
      - run: bun run test:smoke      # step (comando)
  allure-report:            # job 2
    needs: SmokeTest        # espera al job 1

La imagen mental

Un workflow es una receta. Cada job es un cocinero en su propia cocina vacía (el runner). Los steps son los pasos de la receta. Los artifacts son los platos que dejás en la ventanilla para el siguiente cocinero: si no los pasás, el otro no los ve.

Siete términos. Insistir: cada job = máquina nueva y vacía. Por eso cada job repite checkout + setup, y por eso los artifacts existen.

Haz clic en un bloque del YAML →

name y run-name

name es el título fijo del workflow en la pestaña Actions. run-name es el título de CADA ejecución y acepta expresiones ${{ }}: aquí muestra quién lo disparó (github.actor) y en qué rama (github.ref_name).

Sin run-name, GitHub usa el mensaje del commit. Ponerle nombre convierte la lista de runs en un log legible.

docs: workflow-syntax → run-name

on: el trigger

Este workflow despierta cuando se abre o actualiza un pull request hacia main. Ningún cron, ningún botón: solo PRs. Es el gate de la rama: si el framework no compila, el PR queda rojo.

Fíjate en branches: [main]: un PR hacia otra rama no lo dispara. Filtros de rama y de ruta (paths) se combinan con AND.

docs: events-that-trigger-workflows → pull_request

concurrency con cancelación

Un solo build por rama (group: build-${{ github.ref }}). Si haces push dos veces seguidas, el primer run se cancela: no publica nada, así que cancelarlo es gratis y ahorra minutos.

Compara con las suites: ellas usan cancel-in-progress: false porque publican un reporte. Lo vemos en el Capítulo 4.

docs: control-workflow-concurrency

env: variables para todos los jobs

A nivel de workflow, env define variables de entorno que heredan todos los jobs y steps. CI: true es una convención que muchas herramientas leen (Playwright activa forbidOnly, por ejemplo).

Las credenciales NO están escritas aquí: se leen de ${{ secrets.X }}, que GitHub inyecta enmascaradas. Copiar un valor de tu .env al YAML es la falta más grave del curso.

docs: use-variables · use-secrets

el job TestBuild

La clave TestBuild es el id (lo usa needs); name es lo que ves en la UI. runs-on: ubuntu-latest pide una VM Linux de GitHub, limpia. timeout-minutes: 15 mata el job si se cuelga: sin él, el default es 360 minutos de factura.

docs: workflow-syntax → jobs.<job_id>

steps con uses: (acciones)

actions/checkout@v4 clona el repo en el runner (sin esto, la máquina está vacía). fetch-depth: 1 trae solo el último commit: más rápido. El siguiente step (Setup Bun, omitido aquí) es oven-sh/setup-bun@v2, que instala Bun.

@v4 es una etiqueta de versión mayor. Para máxima seguridad, GitHub recomienda fijar un SHA de commit completo en acciones de terceros: una etiqueta se puede mover, un SHA no.

docs: find-and-customize-actions · security/secure-use

steps con run: (comandos)

Cada run es un comando de shell en el runner. Aquí corren los mismos scripts de package.json que corres en local: lint:check (y types:check, omitido por espacio). playwright test --list compila todos los specs sin ejecutarlos: valida que la suite ES ejecutable.

Regla del repo: el YAML nunca inventa comandos. Llama a los scripts de package.json, así local y CI hacen exactamente lo mismo.

Rule #11 de AGENTS.md: los scripts viven en package.json
Explorador clicable. build.yml es el mejor primer archivo: no corre tests, valida el framework. Recorrer name → on → concurrency → env → job → uses → run.

quiz 01: vocabulario y anatomía

¿Se entendió la jerarquía?

Q1El job E2ETests instala Bun y los browsers aunque IntegrationTests ya lo hizo un minuto antes. ¿Por qué?
APor descuido: se podría borrar y ahorrar tiempo
BCada job corre en un runner nuevo y vacío; nada del job anterior sobrevive
CPorque needs borra el estado del job anterior
Runner nuevo por job. Un job es una VM limpia. Lo único que cruza de un job a otro son los artifacts (y los outputs). Por eso las suites repiten los 5 steps de setup en cada job, y por eso allure-report tiene que descargar los resultados con download-artifact.
Q2Un compañero propone escribir la contraseña de staging directamente en env: del YAML «porque total el repo es privado». ¿Qué le decís?
AVale, si el repo es privado no hay riesgo
BMejor ponerla en un comentario para que quede documentada
CNo: va en GitHub Secrets y se referencia con ${{ secrets.X }}; el YAML queda en el historial de git para siempre
Secrets, siempre. El YAML viaja en cada clone, fork y PR; un secret se inyecta en runtime, se enmascara en los logs y se rota sin tocar el código. Además los secrets no llegan a PRs desde forks, que es exactamente la protección que querés.
Q1: runner limpio por job (justifica artifacts y setup repetido). Q2: secrets nunca en YAML.

Run workflow

Tipos válidos: choice, boolean, string, number, environment. Máximo 25 inputs. Se leen con github.event.inputs.X (todo llega como string) o con inputs.X (conserva los booleanos). Por eso el repo compara generate_allure != 'false' entre comillas (el if del job allure-report en smoke.yml).

El patrón ${{ github.event.inputs.environment || 'staging' }} es el fallback para el cron: un run programado no tiene inputs, la expresión devuelve vacío y el || rescata el default. Sin ese ||, la regresión nocturna correría sin entorno.

Formulario vivo: los inputs generan la UI de GitHub y el comando gh equivalente. Dos gotchas: inputs llegan como string en github.event.inputs; el || 'staging' existe por el cron.

Minuto (0-59)

0 = en punto. El intervalo mínimo que GitHub acepta es 5 minutos. Consejo de la doc: evita el minuto 0, es cuando más carga hay y los runs se retrasan; 17 2 * * * arranca más puntual que 0 2 * * *.

Hora (0-23), siempre UTC

2 = 02:00 UTC. En Buenos Aires son las 23:00 del día anterior; en Madrid las 04:00. Regression va a las 00:00 y smoke a las 02:00: dos horas de margen para que la regresión (hasta 60 min) no se solape con el smoke en gh-pages.

Día del mes (1-31)

* = todos. 1 = solo el primero: así pages-squash.yml corre mensual.

Mes (1-12)

* = todos los meses. Casi nunca se usa otra cosa en testing.

Día de la semana (0-6, domingo = 0)

* = todos. 1-5 correría solo de lunes a viernes: útil si el entorno de staging se apaga los fines de semana y no querés ruido rojo el sábado.

Las cuatro trampas del cron (todas documentadas por GitHub)

  • Solo corre en la rama por defecto. Un cron en tu feature branch no hace nada hasta que se mergea a main.
  • No tiene inputs. Por eso cada valor que depende de un input lleva su || 'default'. Y por eso execution_key cae al secret STP_EXECUTION_KEY en la regresión nocturna.
  • Se retrasa bajo carga. Puede arrancar minutos tarde; en casos extremos, saltarse. No es un reloj suizo: es una cola.
  • Se apaga solo. En repos públicos, tras 60 días sin actividad GitHub desactiva los workflows programados. Un repo dormido deja de vigilar.

Por qué dos crons y no uno

Smoke y regression podrían ser un solo archivo con dos crons. Se separan porque contestan preguntas distintas y tienen SLOs distintos: nunca mezcles sus pass-rates (regla R6 de /regression-testing). Estrategia completa en la Parte II.

Cron: 5 campos clicables. Trampas: default branch only, sin inputs (fallbacks), retrasos, auto-desactivación 60 días. Todo de docs.github.com.

La regla que rompe más workflows

Un if: a nivel de job puede leer github, vars, inputs y needs, pero no env ni secrets. Por eso TMS_PROVIDER es una variable y no un secret, y por eso el if del job XrayImport de regression.yml repite vars.TMS_PROVIDER en vez de leer env.TMS_PROVIDER. El comentario justo encima lo dice textual.

quiz 02: triggers, inputs y contextos

¿Quién despertó al workflow?

Q3Agregás schedule: cron '0 6 * * *' a sanity.yml en tu rama feat/sanity-cron y abrís el PR. Pasan tres días. ¿Cuántas veces corrió el cron?
ATres: una por día a las 06:00

CTres, pero fallaron por falta de inputs
Cero. schedule se evalúa sobre el último commit de la rama por defecto. Tu rama puede tener el cron perfecto y GitHub no lo mira. Después del merge, además, recordá que un cron no trae inputs: cada valor necesita su || 'default'.
Q4Querés que un job entero se salte cuando el proyecto no usa Xray. Escribís if: env.TMS_PROVIDER == 'xray' a nivel de job. ¿Qué pasa?

BNo funciona: el if de job no puede leer env; hay que usar vars.TMS_PROVIDER
CFunciona solo si TMS_PROVIDER es un secret
vars, no env. El contexto env no existe cuando GitHub decide si arranca un job. Por eso el job XrayImport de regression.yml escribe if: always() && (vars.TMS_PROVIDER || 'xray') == 'xray' y guarda el proveedor como variable de repositorio, que sí se puede leer ahí. Un secret tampoco serviría: secrets también está vedado en el if de job.

  • Sin needs, todo corre en paralelo. GitHub lanza cada job en su runner apenas puede. El orden lo das vos con dependencias, no con la posición en el archivo.
  • needs encadena. E2ETests espera a que IntegrationTests termine bien. Si la API está rota, no tiene sentido pagar 60 minutos de navegador: el job queda skipped.
  • Un needs fallido salta la cadena… salvo que el job diga if: always(). Los dos jobs finales lo dicen: el reporte y la importación al TMS deben existir sobre todo cuando algo falló.
  • Lista = espera a todos. needs: [IntegrationTests, E2ETests] arranca cuando ambos terminaron (o se saltaron). needs.X.result te dice cómo: success / failure / cancelled / skipped.

Por qué Integration primero

Los tests de API son más rápidos y más baratos que los de UI, y si el backend está caído la UI va a fallar por la misma causa. Ponerlos primero convierte una caída de backend en 6 minutos rojos en vez de 66. Es un fail fast hecho con una sola línea: needs.

Grafo animado. Dos escenarios: noche normal y API caída. Puntos: paralelo por defecto, needs encadena, always() en los finales, lista de needs, fail fast.

uses: una action

Código empaquetado por otro (owner/repo@version). Recibe parámetros en with:. actions/* son de GitHub; oven-sh/setup-bun es de los autores de Bun. Sin checkout, el runner no tiene ni el package.json.

run: un comando

Shell del runner (bash en Ubuntu). Multilínea con run: |. Regla del repo: llama a los scripts de package.json, nunca reinventa el comando. Así CI y tu terminal ejecutan lo mismo.

  • El orden importa. Los steps de un job corren en secuencia, en la misma máquina. Instalar browsers antes de bun install fallaría: el script pw:install vive en node_modules.
  • test:env:check es el step 4 a propósito. Falla en 2 segundos si falta un secret, antes de gastar 3 minutos instalando Chromium. Fallar temprano y con un mensaje claro es diseño, no suerte.
  • @v4, @v2: versiones mayores. Se actualizan solas dentro del mayor. Para acciones de terceros críticas, la doc de GitHub recomienda fijar el SHA completo del commit (40 caracteres) con un comentario # v4.2.2: una etiqueta se puede mover; un SHA no.
  • name es para humanos. Aparece en el log del run. «Install Playwright Browsers» se lee; «step 5» no.
Los 5 steps de setup. uses vs run. Orden secuencial. env:check temprano = fail fast. SHA pinning como recomendación de docs.

simulador: dos runs del mismo grupo se solapan

concurrency: cancelar o encolar, según qué publica

bloque concurrency: de build.yml vs regression.ymlreal
# build.yml: valida, no publica
concurrency:
  # One build per PR branch: a force-push supersedes the run already in flight.
  # Safe to cancel: this job only validates, it publishes nothing.
  group: build-${{ github.ref }}
  cancel-in-progress: true

# regression.yml: publica Allure a gh-pages
concurrency:
  # Suite runs publish Allure to gh-pages. Two overlapping runs race on that
  # deploy and one silently overwrites the other's report. Queue instead of
  # cancelling: a half-finished suite that still uploaded results would leave
  # a partial report standing as if it were the full one.
  group: regression-${{ github.ref }}
  cancel-in-progress: false
runner
run #1 · in_progress
run #2 · nuevo
  • group define quién compite. Puede usar expresiones (github, inputs, vars). build-${{ github.ref }}: un grupo por rama. Los nombres no distinguen mayúsculas.
  • Por defecto solo hay UN pending. Si llegan #2 y #3 mientras #1 corre, #2 se cancela y queda #3. Con queue: max podés encolar hasta 100, pero no combinado con cancel-in-progress: true.
  • FIFO. Los pending arrancan en el orden en que empezaron a esperar.
  • Nivel workflow o nivel job. Todos los workflows lo declaran a nivel workflow; pages.yml usa un grupo fijo (pages-docs-hub) porque siempre publica al mismo sitio.

La pregunta que decide

«¿Este workflow deja algo publicado o compartido?» Si no (validar, lint, compilar): cancelar, es más barato. Si sí (reporte, deploy, rama gh-pages): encolar, porque cancelar a medias deja un estado que parece completo y no lo es. Todos nuestros workflows publican salvo build.yml, que cancela.

Concurrency: cancel vs queue, con los comentarios reales del repo como justificación. Regla: publica → encola; valida → cancela.

forma recomendada para un workflow nuevoejemplo
permissions: {}            # nada por defecto…
jobs:
  publish:
    permissions:
      contents: write    # …y solo este job puede escribir
  notify:
    permissions:
      statuses: write    # p.ej. devolver un commit status a otro repo
  • GITHUB_TOKEN existe siempre. GitHub lo crea por run, con permisos sobre este repo, y lo destruye al terminar. Se usa como ${{ secrets.GITHUB_TOKEN }} o ${{ github.token }}.
  • permissions lo recorta. Cada scope acepta read, write o none. Regla dura: si nombrás UN scope, todos los demás pasan a none. Así pages.yml, con solo contents: write, no puede tocar issues ni PRs.
  • Mínimo privilegio. Las suites (smoke, sanity, regression) no declaran permissions y heredan el default del repo: no necesitan escribir en GitHub, solo leer el código. Publicar a gh-pages lo hace un script con el mismo token, dentro del job allure-report.
  • No cruza repos. El token no puede disparar un workflow en OTRO repositorio. Para eso hace falta un PAT o una GitHub App: lo vemos en la Parte II (Cap 9).
  • Anti-recursión. Un evento provocado con GITHUB_TOKEN no dispara otros workflows (para que no se llamen en bucle), salvo workflow_dispatch y repository_dispatch.
permissions: pages.yml como único ejemplo real con contents: write. Regla: nombrar uno pone los demás en none. No cruza repos → Parte II.

Haz clic en un bloque →

Cabecera: propósito, name, run-name

El comentario de las primeras líneas dice qué pregunta contesta la suite («Daily health check running only @critical tagged tests»). Es la primera línea que lee quien abre el archivo en seis meses. run-name con actor + entorno hace legible la lista de runs.

Triggers: reloj + botón

El cron da la rutina; el dispatch da el control manual con tres inputs que se repiten en las tres suites: environment, generate_allure, execution_key. Sanity añade test_type, grep, test_file; regression añade video_record (la lista viva es el bloque inputs: de cada workflow).

Concurrencia: encolar

Un grupo por suite y rama. cancel-in-progress: false porque el job final publica a gh-pages y dos publicaciones solapadas se pisan.

Bloque env: identidad del run

Qué entorno, qué credenciales (por prefijo de entorno: STAGING_USER_EMAIL), qué proveedor de TMS y si la sincronización está activa. Todo lo sensible por secrets, lo configurable por vars, lo derivado por expresión.

El job de la suite

runs-on: ubuntu-latest, timeout-minutes acorde al tamaño de la suite, y environment: name: igual al input, para heredar los secrets y reglas de ese environment de GitHub.

Los cinco steps de setup

Siempre los mismos, siempre en este orden: código → runtime → dependencias → validación de variables (falla temprano) → browsers. Copiar y pegar es correcto aquí: un job es una máquina nueva.

La suite y el write-back

Un solo run con el script de package.json. Después, con always(), el paso que escribe en el TMS: lee reports/atc_results.json, que KataReporter escribe al salir Playwright (por eso es un step aparte y no parte del test). Detalle en la Parte II, Cap 8.

Evidencia y limpieza

Tres uploads con always() (resultados) y uno con failure() (evidencia extra). Nombres con el prefijo de la suite. Retención la que fije retention-days. Cleanup al final.

El job de reporte

Otro runner: vuelve a hacer checkout (necesita allurerc.mjs y el devDep allure), baja la rama gh-pages para la historia de tendencias, baja el artifact, comprueba que hay resultados y publica con el mismo script que usás en local. Parte II, Cap 7.
