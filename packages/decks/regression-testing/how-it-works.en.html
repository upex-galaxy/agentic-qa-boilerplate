before anything · preflight gate (mandatory)

Nothing gets triggered until the gate is green

CapabilityLevelWhy it matters here
gh CLI authenticatedREQUIREDThe whole pipeline lives in gh: trigger, watch, download. No auth → STOP, the user runs gh auth login.
Workflow filesREQUIRED.github/workflows/ must hold the YAML for the chosen suite, with its inputs.
GitHub Actions SecretsREQUIREDThe runner uses secrets.<ENV>_USER_EMAIL/_PASSWORD + XRAY_*/ATLASSIAN_*. Check with gh secret list: it is the most common silent gap.
Local AllureREQUIREDbunx allure resolves (devDep, version in package.json, no global install) + allurerc.mjs present for bun allure:agent.
Active env confirmedREQUIREDConfirm the target before a long run (default: staging).
[TMS_TOOL] · [ISSUE_TRACKER_TOOL]OPTIONALTMS only if testing.tms_cli is set in .agents/project.yaml: then Phase 1 creates the RTR before the trigger (/xray-cli on jira-xray). /acli only if the verdict forces opening issues.

Two laws of the gate

args-as-answers: suite, env and grep/test_file already arrive as arguments, so only ask about the gaps. probe, don't assume: every capability is tested with a real command. Gaps and REDs go out in ONE checklist; any blocking RED → STOP.

Test credentials, MCPs and browsers live INSIDE the CI runner, not in the orchestrator, so they sit outside this gate. CI uses GitHub Secrets, never values copied from the local .env.

phase 0 · session resume check (mandatory, inline)

Was there already a session? Resume, don't repeat

The session contract

Scope = <env>-<YYYY-MM-DD> (e.g. staging-2026-07-06). State lives in .session/regression-testing/<scope>/{plan.md, progress.md}. If progress.md doesn't exist → new session. If it does → offer resume / restart / abort (restart archives first).

The star case: re-attaching the RUN_ID

If the Monitor died halfway through the watch but plan.md already captured the RUN_ID, the skill re-attaches to the live run instead of re-triggering CI, which saves the entire run. The RTR_KEY also lives in plan.md, so the resumed session knows which Execution CI imported into.

phase-0 · re-attach
# progress.md says "Phase 1.Trigger completed" but the Monitor never reported:
$ gh run view <RUN_ID> --json status,conclusion
{ "status": "in_progress" }   → re-attach to the watch, do NOT re-trigger
Phase 0 and writing plan.md in Phase 1 are not optional: they are the session-management.md contract. Re-attach is the number one reason the RUN_ID is persisted right after the trigger.

phase 1 · execute: pick the suite

The wrong suite gives the wrong signal

SuiteWorkflowDurationUse when
regressionregression.ymllong (read it from the last gh run view)Pre-release validation, full nightly run. The only suite with an RTR.
smokesmoke.ymlshortPost-deploy health check, @critical tests only
sanitysanity.ymlvariableOne feature / one file / one grep pattern

Default rule

A bare "run regression" → regression on the default env · "smoke" or "critical only" → smoke · a file or a grep → sanity.

Gotcha: grep XOR test_file

In sanity, grep and test_file are mutually exclusive: pass both and the workflow silently ignores one. Pick one.

A green 3-minute smoke is NOT a release gate. Matching the suite to the question the user is asking is the workflow's first act of judgment. When the question comes from a change or a diff, the skill loads blast-radius (if it isn't installed, it does it inline and notes it in plan.md) to see which flows the change reaches and picks the suite from there.

phase 1 · execute: the run's record is born before the run

RTR first, CI after

The RTR (Regression Test Results) is a Test Execution RTR: {scope-id}: Regression Testing, with scope-id <env>-<YYYY-MM-DD> or a release tag. CI imports into its key, never into a shared secret. Only the regression suite has an RTR.

1

Resolve the RTP

Look up the Test Plan RTP: {PROJECT_KEY}: Regression Test Plan. If it's missing, it is not created here (that is the /test-documentation promotion): the RTR is born without a testPlan, the gap is declared as N/A in the verifier and the report, and running the promotion is recommended.

2

Find-or-create the RTR

Parent QA Test Artifacts, Test Environment = the active env, assignee = yourself, testPlan → RTP. An RTR for the same scope that is still active (an ENVIRONMENT re-run, a resumed session) gets reused. If it is already closed with a verdict, the new run gets a new RTR with #2 in the scope-id.

3

Persist and hand to CI

RTR_KEY goes into plan.md §Inputs, on the line where the RUN_ID lands later, and goes out to CI as -f execution_key=$RTR_KEY. That input overrides the STP_EXECUTION_KEY secret, which stays only for scheduled runs without a key.

4

Variants

Sprint close: the target is the STR STR: Sprint#{N}: Regression Testing (testPlan → STP and → RTP), with N given by the user or the STP, never invented. jira-native: no RTR; the trigger goes out without execution_key.

One RTR per verdict, and it never reopens

A closed RTR doesn't go back (the reactive transition is not used). A run after the verdict, for example the re-run of a NO-GO that has since been fixed, opens its own RTR.

Source: SKILL.md Phase 1 §Create the RTR (before the trigger) and §TMS sync. The RTR exists before CI starts so the workflow receives its key and imports there. The RTP is the long-lived plan that feeds /test-documentation; this skill only consumes it as the testPlan target and never writes to it.

phase 1 · execute: plan, RTR, trigger, RUN_ID

Plan first, trigger after, persist the RUN_ID right away

phase-1 · trigger
# 1 · phase preflight (always)
$ gh auth status && gh repo view --json name,owner && gh workflow list
# 2 · write .session/regression-testing/<scope>/plan.md BEFORE the trigger
# 3 · create the RTR (previous slide) → RTR_KEY in plan.md §Inputs
# 4 · trigger the suite with explicit inputs
$ gh workflow run regression.yml -f environment=staging -f execution_key=$RTR_KEY \
    -f video_record=false -f generate_allure=true
# smoke and sanity: no RTR and no execution_key (they never write to a regression Execution)
$ gh workflow run smoke.yml -f environment=staging -f generate_allure=true
$ gh workflow run sanity.yml -f environment=staging -f test_type=e2e -f grep="@auth"   # grep OR test_file, never both
# 5 · capture RUN_ID (wait a few seconds: the run can't be queried instantly)
$ RUN_ID=$(gh run list --workflow=regression.yml --limit=1 --json databaseId -q '.[0].databaseId')

Critical checkpoint

The RUN_ID is added to plan.md §Inputs, next to the RTR_KEY, and progress.md records both. Without a persisted RUN_ID there is no re-attach; without the RTR_KEY a resumed session doesn't know which Execution CI imported into. On jira-native, execution_key is omitted on every suite.

Tested commit and artifacts

Record the tested commit in the report (gh run view <RUN_ID> --json headSha) and compare trends only between runs with a known commit: different commit, different baseline. Also, video_record=true inflates the artifacts a lot: use it only for debugging.

The race condition is real: gh workflow run returns before the run exists in the API, hence the short wait before gh run list. The inputs shown are the ones declared by regression.yml, smoke.yml and sanity.yml in .github/workflows/. Video only when debugging flakiness or capturing evidence for one specific bug.

phase 1 · execute: monitor (background dispatch)

A subagent watches; the main thread prepares the analysis

Monitor subagent
$ gh run watch <RUN_ID> --exit-status
# fallback if watch times out on long suites: poll every 60–90s
$ gh run view <RUN_ID> --json status,conclusion
status:     queued | in_progress | completed
conclusion: success | failure | cancelled | timed_out   (only once completed)
  • Background dispatch. The watch lives in a Monitor subagent; meanwhile the main thread builds the report scaffold and loads the classification rubric.
  • Phase gate. Phase 2 does NOT start until the Monitor returns status: completed: a half-finished run produces garbage verdicts.
  • Phase 1 output. A summary with run ID, env, duration, conclusion per job, the artifact list and the Allure URL: https://{owner}.github.io/{repo}/{env}/{suite}/.
Gotcha: the Allure URL is predictable but only live once the "Build & Deploy Allure Report" job finished green. If it failed, analyze from the downloaded artifacts. Workflow config: references/ci-cd-integration.md.

phase 2 · analyze: collect (parallel dispatch ×3)

Gather the evidence before retention expires

phase-2 · collect
# inline (main thread): context + ONLY failed logs (the full --log dumps every step)
$ gh run view <RUN_ID> --log-failed
$ gh run view <RUN_ID> --json artifacts --jq '.artifacts[].name'
# parallel subagents: one per artifact listed by the previous command
$ gh run download <RUN_ID> -n merged-allure-results-staging -D ./analysis/            # A
$ gh run download <RUN_ID> -n e2e-failure-evidence          -D ./analysis/evidence/   # B
$ gh run download <RUN_ID> -n e2e-playwright-report         -D ./analysis/playwright/ # C
# previous run → trend baseline
$ PREV=$(gh run list --workflow=regression.yml --limit=2 --json databaseId -q '.[1].databaseId')
$ gh run download $PREV -n merged-allure-results-staging -D ./analysis/previous/

Allure download on red builds

Never skip the Allure download on red builds: screenshots, traces and videos disappear once the retention window closes. Evidence first, analysis after.

Metadata reads (gh run view) stay inline because they are short; only the downloads justify a dispatch, one subagent per listed artifact. For earlier local triage: bun allure:agent emits AI-readable markdown without parsing HTML.

phase 2 · analyze: parse + metrics

Counts come from test-outcomes; the pass-rate that gates excludes what is blocked

MetricFormula
Pass RatePassed / Total × 100
Pass Rate (gating)over Total − KNOWN-BLOCKED
Durationmax(stop) − min(start)
Trendcurrent pass rate − previous run

Counts and detail, each from its own source

The counts (total, passed, failed, skipped) come from reports/test-outcomes.json: Allure archives an expected failure as passed and can read green over tests that were never observed to pass. Allure rules for the detail of each failure (statusDetails, labels[]: testId = ATC ID, suite, severity) and for the history that FLAKY requires; only if the file isn't in the downloaded artifacts do the counts come from Allure, and the report says so. Detail: Allure > Playwright report.json > raw logs.

The suite label derives from the tag

@smoke/@regression/@e2e/@integration/@critical is the only taxonomy: the suite you read IS the scope CI ran. Never reconcile against another set of labels.

No retries: flakiness surfaces as a failure

The anti-retry policy is retries: 0 (see playwright.config.ts), the anti-retry doctrine: a retry would only mask the flake. Flakiness shows up as an ordinary intermittent failure and the history rule classifies it (>20% over the last 10 runs), never a pass-on-retry. If a downstream project deliberately enabled retries, the skill's rule applies: expose the retries count in the report, not just the final status.

KNOWN-BLOCKED tests (@blocked:{BUG-KEY} tests deliberately parked behind a bug that is already filed) are not regression failures: they are excluded from the gating pass-rate and reported separately with their BUG-KEY, so the decision can't be gamed in either direction.

phase 2 · analyze: classify every failure (6 ways)

Walk the tree in order: first match wins

decision-tree · references/failure-classification.md
Failed test
  ├─ tag @blocked:{BUG-KEY}?  ─────────────────► KNOWN-BLOCKED  (parked; outside gating)
  ├─ a known ticket already tracks it? ────► KNOWN ISSUE
  ├─ environment error pattern? ───────────► ENVIRONMENT
  │    ECONNREFUSED · ETIMEDOUT · net::ERR_ · Navigation timeout · browserType.launch · 502/503
  ├─ no history (first run)? ──────────────► NEW TEST
  ├─ ≥5 runs and fails >20% (same build)? ─► FLAKY
  ├─ 1-4 runs of history? ─────────────────► REGRESSION (label INSUFFICIENT HISTORY)
  └─ anything else ────────────────────────► REGRESSION   ← blocks the release

The #1 misclassification

NEVER mark REGRESSION without checking history first. And a first failure with no history isn't a regression: it's NEW TEST, verified by hand once before classifying.

Dispatch by volume

>10 failures → chunks of ~10 with one classifier subagent per chunk (cap 10), JSONs merged on the main thread. ≤10 → inline: the overhead isn't worth it.

The gate fails closed

Every class except REGRESSION lets the failure through, and the classifier is the one who picks it. That's why each one holds only with its citation (table on the next slide). No citation, an empty citation, or a ticket this same session created to make the failure "known": it counts as REGRESSION.

When a borderline failure can't be resolved from the log, the skill loads diagnosing-bugs only to diagnose (fixing nothing); if the cause is still unproven, the failure stays as REGRESSION. To call something FLAKY you need at least 5 runs of history: with fewer, it is noted as "INSUFFICIENT HISTORY" and counts as REGRESSION for the gate (fails closed); it is re-evaluated on the next run. Order when several match: KNOWN-BLOCKED > KNOWN ISSUE > ENVIRONMENT > NEW TEST > FLAKY > REGRESSION; FLAKY wins only with its full citation and REGRESSION is whatever is left. The failure percentage is computed over a wider window, the last N = min(10, available) runs: 5 is the floor for having a signal, 10 is the window. Compact rule: never FLAKY without citing at least 5 runs of history.

ENVIRONMENT is not a scapegoat

ECONNREFUSED to your own API usually means the app went down. Many unrelated tests red on the same host → ENVIRONMENT; ONE test failing on an endpoint that others use fine → probably a REGRESSION in disguise.

sdet CI-fallback clause

Only on integration-trunk suites: an ENVIRONMENT-class red in Sanity-CI can authorize a merge into the integration trunk (never the final PR to main) if the change passed locally + on staging and the red exists without the change. REGRESSION never qualifies.

Triage decides WHETHER to file; the defect-management doctrine decides WHAT type and with which fields. They are separate axes. Compact rule: never mark KNOWN without a Jira ticket that backs the suppression.

phase 2 · analyze: severity per failure

Severity is orthogonal to classification

A FLAKY test on checkout is still CRITICAL. Classification answers why it failed; severity answers how much we care.

SeverityCriteria
CRITICALCore user flow (login, checkout, payment), or any test tagged @critical
HIGHMajor feature (search, profile, dashboard)
MEDIUMSecondary feature (filters, preferences)
LOWEdge case or admin-only path

Phase 2 output

An analysis block: metrics table + trend delta, one section per category (Regressions first), detail per failed test (name, ATC ID, suite, error, last-pass, screenshot) and a preliminary verdict.

These two axes cross in Phase 3: a REGRESSION with HIGH/CRITICAL severity is a hard veto by itself, whatever the score.

after phase 2 · fleet seam (optional)

Several failure clusters, one worktree per cluster

Triage is never split across sessions: a single conductor session reads the run, classifies and owns the verdict. The fleet is for what comes next, when classification leaves several independent clusters that need code, and only if the user asks to work them at the same time.

Topology

One cluster = one worker = one worktree = one branch. Never two workers on the same cluster: two sessions in one checkout trample each other's git index even when they touch different files. Each fix is written under /test-automation (Plan → Code → Review) and lands according to git_strategy.

launch.txt, always

The conductor writes .session/regression-testing/<scope>/launch.txt, one self-contained line per cluster, whether or not an orchestrator exists on the machine. Launching and supervising belongs to /agent-orchestration; if nothing can launch them, those lines get pasted by hand into terminals.

The verdict doesn't move

GO / CAUTION / NO-GO, the metrics, the RTR (or the sprint-close STR) and every Jira write stay with the conductor. A worker fixes its cluster and reports: it doesn't re-score the run, file the defect or transition the RTR.

Silence rule

If there is no orchestration transport, the skill doesn't mention it: not in the preflight, not in the environment block, not in the report. launch.txt is the fallback and it is already written.

Source: SKILL.md §Fleet seam (optional). The fleet is an option for parallelizing fixes, not for parallelizing judgment. A regression fix is not exempt from the automation gate: it goes through /test-automation like any other test code.

phase 3 · report & decide: the 10-point score

A score guides; three vetoes rule

Factor+3+10−1−2−3
Pass Rate≥95%90–95%——<90%—
Regressions01–2 Low—1+ Medium—High/Critical
@critical testsAll pass————Any failure
Flaky—≤34–5>5——

GO: score ≥ 7

Release approved; post-deploy smoke scheduled.

CAUTION: 4–6

Manual review; accepted risks documented.

NO-GO: < 4

Release blocked; fix + re-run planned.

Hard vetoes: never auto-GO if...

(1) any @critical test fails · (2) any HIGH/CRITICAL REGRESSION exists · (3) pass rate < 90%. They override any score. The gate is binary: a known REGRESSION > 0 = no GO. And smoke and regression are never mixed into a single pass-rate.

The verdict and issue filing stay inline on the main thread: release decisions are never delegated to a subagent.

phase 3 · report & decide: file defects (NO-GO / CAUTION with regressions)

Quality issues go to Jira, not GitHub

1 · Gate + classification

Only REGRESSION and confirmed NEW TEST reach Jira. Type follows the FEATURE's lifecycle, not where it failed: already live on Staging → Bug · pre-release → Defect · desirable behavior beyond the AC → Improvement.

2 · Mandatory field matrix

severity → auto-derived priority · components = affected module · root_cause + error_type + test_environment · qa_assignee = yourself (read-before-write) · evidence = Allure link + ./analysis/evidence/.

3 · Three traceability axes

Parent = the QA Defect Management epic (never a product epic) · causal issue-link → the Story that covers the regressed ATC · components = product module.

4 · Write via /acli

Load /acli first (auth + syntax). Create with acli workitem create --from-json; customfields on an existing issue via REST PUT /rest/api/3/issue/{KEY}. Run the doctrine's filing gate before sending; keep the key for the report.

Canon

agentic-qa-core/references/defect-management-doctrine.md: the same authority /sprint-testing uses. FLAKY, ENVIRONMENT and KNOWN ISSUE never generate a new bug.

Triage (Phase 2) decides whether to file; the doctrine decides type and fields. The skill does NOT open GitHub issues for product failures.

The durable record

It is the RTR in the TMS (the STR only on the sprint-close run) plus the GO / CAUTION / NO-GO comment posted on it. The RTR is closed via complete after the comment, never before and never left open. On jira-native there is no RTR: results are status writes per Test, the verdict goes to the local report and to a comment on the Release issue if one exists, with the skip declared.

The report lives on a single machine

.context/reports/ is in .gitignore: it is generated [LOCAL] output and only exists where the suite ran. Nothing downstream may depend on that file; it is for reading the run cold, not a deliverable.

Post-decision

GO → approved candidate + post-deploy smoke · CAUTION → review with the lead, risks in writing · NO-GO → block, assign issues, plan the re-run (with a new RTR).

Session archive

After the verdict: .session/regression-testing/<scope>/ → .session/.archive/ + a summary into memory. On NO-GO, the archive waits until issue creation finishes.

Source: SKILL.md §TMS sync, §Post-decision actions and §Per-phase progress + Archive, plus .context/reports/README.md. The report is generated on every run with the same structure so it can be scanned fast, but the file is [LOCAL]: what the team sees from another machine is the RTR and its verdict comment. STP and STR only come into play in the run that IS the sprint close: /sprint-testing creates the STP and this skill consumes it; the STR is created by whoever reaches the close first and the other completes it.

stage close · light stage verifier + session footer

Before saying "done": one checklist and two blocks in the chat

Light verifier (artifact-lifecycle.md §5)

Eight common lines: artifacts by KEY, links, statuses, assignee, parent + components, fields and comments written, checkpoint in progress.md, footer printed. Each one is YES or a declared N/A with its reason; a blank line is a failed verifier and any NO leaves the stage in NEEDS REVISION. "Light" means it is answered from what the stage already did, plus at most ONE extra read.

Regression-specific lines
[ ] RTR by KEY, created BEFORE the trigger (went out as execution_key)
[ ] RTR with Test Environment, assignee self, parent QA Test Artifacts
[ ] RTR → RTP via testPlan (missing RTP = declared N/A)
[ ] Verdict comment ON the RTR (not the local file)
[ ] RTR in close via complete, AFTER the verdict; never reactive
[ ] Sprint close: STR → STP and → RTP, closed after the verdict
[ ] RTP intact in ready
[ ] jira-native: declared skip + status per Test + [LOCAL] report
[ ] Unmapped slug → §4 fallback (asked), never a silent skip

Block 1 · Screenshots (relative paths)

Each capture is named in the chat on the turn it appears, and at close the full list goes out: paths relative to the repo, verified with ls, bug annotations first. Here they are usually the evidence attached to the defect, taken from ./analysis/evidence/.

Block 2 · Session Footer, Execution framing

Skills loaded, MCPs called and CLIs actually invoked (gh, bunx allure, acli...), plus the pyramid levels the CI suite exercised, with an explicit "none" on the ones it didn't touch, and the Refinements proposed: line with whatever was proposed in refinements.md.

Chat only

Neither block goes into a Jira comment or the RTR body. With subagents, each stage report carries the five footer fields and the conductor compiles it ONCE at close.

Sources: agentic-qa-core/references/artifact-lifecycle.md §5, agentic-qa-core/references/session-footer-contract.md and SKILL.md §Post-decision actions and §Gotchas. The verifier exists to catch what was silently skipped, for example an RTR left active or a verdict that only exists in the local file. Session learnings are proposed in .session/regression-testing/<scope>/refinements.md and never applied to the live skill.

who decides what, and what happens after GO

The agent executes. The evidence proves. The person decides.

The Regression contract

The agent runs the suite, classifies every failure, computes pass-rate and trend, issues GO / CAUTION / NO-GO and writes the RTR (the STR only on the sprint-close run). The person signs off the CAUTION verdict, and never lets the agent invent the sprint number. The evidence that survives: the Allure report, the RTR linked to its RTP, and the run history that earns the word FLAKY.

CSA autonomy 3, and 4 for a clean GO

It decides within declared limits and escalates outside them; with a failure-free GO, oversight is by monitoring, not by approval. No separate verifier: the only stage that demands one is Automation. Regression is the deliberate exception to the pipeline's ceiling of 3: a run with no failures doesn't need human approval to advance, while every CAUTION or NO-GO is signed by a person.

And after GO comes Observation

The pipeline doesn't end when the suite passes. Observation is the eighth stage: production, capability L4. It has no skill; its working unit is an agentic routine that watches SLOs, error budget, RUM and canary signals, opens backlog items and feeds the next Shift-Left. The person signs off the SLOs, the error-budget policy and the decision to halt releases. It is declared, not implemented: no skill of its own (the state lives in agentic-qa-core/references/stage-gates.md), and saying so is part of the method's honesty.

With nobody at the keyboard: a supervised worker leaves the gates to its conductor; a routine runs the suite, classifies and writes the local report, but without a brief that covers Jira writes it doesn't create the RTR and hands over the verdict as ready to publish.
