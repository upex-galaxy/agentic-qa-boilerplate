AGENTS.md §6.5 · 4 de 19

Antes del binario, la skill

El gate

Antes de cualquier llamada a Bash que nombre uno de estos binarios, la IA verifica que la skill que le corresponde esté cargada. Si no lo está, la carga primero. Sin ella va a ciegas en sintaxis, flags, auth y errores.

El reparto

La skill sabe cuándo y qué; el binario ejecuta el cómo. Por eso una skill de flujo nunca escribe acli … ni bun xray … literal: escribe la etiqueta y carga la skill dueña.

Ejemplos del mapeo

BinarioSkill que se carga antes
acli/acli
jq/acli (su consumidor principal)
bun xray/xray-cli
playwright-cli/playwright-cli + /playwright-best-practices
resend/resend-cli

Mapeo completo, con gh, bunx allure, orca y el resto: AGENTS.md §6.5.

El gate existe porque los errores de estas herramientas son silenciosos: un subcomando inexistente de acli sale con código 0, una lista de Xray se trunca sin avisar. La skill es la que conoce esas trampas.

Utilidad · 5 de 19

/acli: el CLI oficial de Atlassian

Qué resuelve

[ISSUE_TRACKER_TOOL] siempre, y [TMS_TOOL] solo en modalidad jira-native. Cubre Jira Cloud, Confluence y admin de la organización.

El patrón selector

Los comandos que mutan aceptan --key, --jql, --filter o --from-file. En un batch, --yes evita que se cuelgue esperando stdin.

Texto enriquecido

Markdown → ADF con acli/scripts/md-to-adf.ts, que valida antes de publicar; después se relee el campo.

Trampas que la skill conoce

Paginación opt-in. Sin --paginate o --limit, una búsqueda trae la primera página y no avisa.
Exit 0 no prueba nada. Un subcomando inexistente cae en la ayuda del padre con código 0.
workitem edit rechaza campos custom y no tiene flag de components: se setean al crear o por REST PUT.
--out / --in invertidos respecto de Jira: después de cada link se lista y se verifica la dirección.
Auth por producto. jira, confluence y admin son sesiones separadas: verificar antes de un batch.
acli nunca convierte Markdown: pasarle Markdown guarda los caracteres literales. Lo QA-específico (slugs, modalidad, anti-patrones del repo) no está en acli/SKILL.md sino en agentic-qa-core/references/acli-integration.md: la skill de la herramienta queda agnóstica y se comparte entre boilerplates. En un batch, --ignore-errors evita abortar todo por un ítem. Ante un error de backend, el trace id es la única pista y se captura siempre. Los ids de campos custom nunca se escriben literales: se resuelven por slug desde .agents/jira-fields.json.

Utilidad · 7 de 19

Credenciales en .env, el host en un solo lugar

El host no es una variable de entorno

Vive en .agents/project.yaml → issue_tracker.atlassian_url y en ningún otro lado local. Desde el shell se lee con el accesor:

bun run --silent jira:url
bun run --silent jira:url --slug

--slug da el host pelado que pide acli --site.

HerramientaCredencialesLogin
acliATLASSIAN_EMAIL
ATLASSIAN_API_TOKEN		token por stdin a acli jira auth login --site … con el --slug; el CLI guarda la sesión
bun xrayXRAY_CLIENT_ID
XRAY_CLIENT_SECRET
+ el par ATLASSIAN_*		bun xray auth login sin argumentos lee todo de .env

Regla #10

Credencial faltante o rota: parar. Nombrar la variable, apuntar a .env / .env.example y reiniciar la sesión.

En bun xray auth login, los flags solo sirven para pisar un valor del entorno (por ejemplo, otro sitio en una migración). Una copia vieja del host heredada del shell ya apuntó los scripts de sync a un sitio muerto: por eso no hay segunda copia. bun run jira:check valida el setup de Jira. El token de Xray dura 24 horas y se cachea en ~/.xray-cli/: pasado ese tiempo hay que reautenticar, porque un token vencido produce 401 silenciosos que parecen fallas de red. Ninguna credencial se espeja nunca en el yaml versionado; el host sí, porque es un hostname público.

Utilidad · 8 de 19

/xray-cli: dos capas que no se confunden

Chequeo de modalidad

Solo en jira-xray (Jira Cloud con el plugin de Xray). En jira-native esta skill no se usa: los artefactos de test van por /acli.

La membresía del ATS lleva las dos

set add-tests en Xray y un link create <TC> <ATS> --type test por cada miembro. Solo la de Xray es invisible para IQL y para el sync.

Capturar la key

Cada create termina con una línea pelada KEY <PROJ-123> y acepta --json. Nunca se raspa la línea decorada de éxito.

Xray no tiene mutación de cobertura: la cobertura de requisitos es solo un issue link de tipo test entre el artefacto y la Story, y link create es el único comando del CLI que la escribe. El tipo de link se pasa como slug resuelto desde .agents/jira-required.yaml (link_types), nunca como nombre literal.

El orden canónico: primero el Test Set

→

→

→

3 · ATP

Plan derivado

plan add-set PLAN --set ATS

→

4 · ATR

Execution derivada

→

5 · Resultados

Sobre la Execution

import junit --execution
run status

Una lista, no tres

El ATS es la única fuente de qué tests cubren la Story. Plan y Execution derivan su lista con plan add-set y exec add-set; listar ids a mano es justo la deriva que la doctrina prohíbe.

Pasos manuales

Xray Cloud descarta en silencio los pasos pasados al crear un test. Se crea primero, se suma un paso por llamada y se verifica con test get.

Entorno obligatorio

Cada ATR va fijada a un Test Environment, con el valor de active_env, para que los resultados se puedan comparar. Si se escapó una sin entorno: exec set-environment.

Nombres: ATS: {US_ID}: {título} para el Set por Story; los Sets de feature llevan TS:. Opcional: plan add-executions asocia la Execution al Plan.

Este es el flujo que la skill llama "Canonical End-to-End Flow". Los pasos 1 y 2 escriben links de la capa Jira; los pasos de membresía (set add-tests, plan add-set, exec add-set) son de la capa Xray. Si solo quedó cableada la capa Jira, los runs vuelven vacíos y se repara con sync (slide 12).

Utilidad · 10 de 19

La dirección del link se dice con el campo crudo

La única frase medida

En una Story, el borde que cuenta para la cobertura es la entrada de issuelinks que lleva el artefacto bajo inwardIssue. bun xray link create <ARTEFACTO> <STORY> produce exactamente esa forma. La forma opuesta existe, se ve como un link y cubre cero.

Reparar un link invertido

Jira deduplica por par y tipo sin mirar la dirección: crear el correcto encima es un no-op silencioso. Se lee el id del link con trace --json, se mira con link delete --id … --dry-run, se borra con --yes y se recrea.

bun xray trace: el chequeo de tres bordes

BordeQué tiene que cumplirse
Story↔ATSlink test con el Set bajo inwardIssue; el único que cuenta el panel
ATP↔Storymisma forma, desde el Plan; administrativo
ATR↔Storymisma forma, desde la Execution; administrativo
paridadmembresía del ATS = lista del ATP = lista del ATR

Un borde que falla imprime el comando que lo repara. Con varias keys o --jql barre el proyecto y devuelve una lista de trabajo: un link invertido es invisible en una Story y solo se ve en el agregado.

Se verifica contra la cobertura de Xray (trace o el panel), nunca contra la semántica de links de Jira: una lista de links se ve correcta en las dos direcciones. Las descripciones "tests" / "is tested by" se leyeron en direcciones opuestas en la práctica; un nombre de campo no se puede leer de dos maneras. La medición está en ADR-0006. trace no compara los links TC→ATS contra la membresía: esa lectura sigue siendo manual.

Utilidad · 11 de 19

Resultados sobre una Execution que ya existe

Import

JUnit, Cucumber o Xray JSON se importan con --execution <KEY>. Con --project, la API de import no puede setear un padre y acuña una Execution nueva sin padre en cada corrida, fuera de la épica de artefactos QA.

--plan sin --execution

También crea una Execution nueva y la asocia al plan. Es el camino de respaldo de la RTR; /regression-testing crea la RTR primero y pasa su key.

Estados de run

TODO, EXECUTING, PASSED y FAILED son el piso seguro. ABORTED y BLOCKED son defaults de Xray que un proyecto puede no tener: la mutación se rechaza. Un caso bloqueado va a un estado que exista, con la explicación en el comentario; nunca queda en TODO.

Evidencia y defectos

run evidence adjunta archivos o una carpeta, run step-evidence va a un paso, run defect linkea bugs.

ROI manda

Nunca resultados para TCs que el ROI marcó como Manual terminal.

Empujar resultados para un Manual terminal ensucia el reporte Candidate / Manual / Deferred. Con --dir, el CLI parte la carpeta en lotes bajo el límite de tamaño de Xray. Dry-run primero: import y restore de backup escriben de forma irreversible sobre cientos de tests y runs. Antes de importar en lote se verifica que la Execution o el Plan existan (exec get / plan get): un resultado huérfano aborta el import entero. Nunca se arman payloads JSON de Xray a mano fuera del CLI.

Utilidad · 12 de 19

Cuando las capas se desalinean

Sync & repair

Si un camino de respaldo creó el contenedor sin Xray autenticado, la capa Jira lo acepta pero Xray nunca registra los tests: los runs vuelven vacíos.

exec sync · plan sync · set sync
repair --project

Dry-run por defecto, --apply para reenganchar.

Sin MCP de respaldo

El MCP de Atlassian es opt-in y no expone entidades de Xray. Sin credenciales Xray: Regla #10, parar. Las operaciones solo de capa Jira (links, transiciones, comentarios) pueden ir por /acli o Jira REST, y después, con Xray de vuelta, se corre el sync.

test enrich

El sync del PBI va por REST y no ve lo que es interno de Xray. bun xray test enrich lo trae por GraphQL y escribe solo archivos locales: preconditions inline en cada TEST-*.md y un índice por Set en .context/PBI/test-sets/. Se corre después de cada sync que toque tests.

Backup, restore y migración de sitio

Entre sitios se restaura con --sync, porque Xray reasigna los ids numéricos y las keys se conservan, y se cierra con /jira-administration modo instance-migration. Runbook: xray-cli/references/migration-runbook.md.

Lo que falta en la capa Jira solo se reporta: sync nunca borra. backup export captura tests, preconditions, plans, sets y carpetas (runs con --include-runs). Entre export y restore hay que reautenticar, porque la config guarda un sitio a la vez; instance-migration hace falta porque los ids de campos de Jira también cambian. Requisito del sync: credenciales de Xray Y de Jira, porque la vista de la capa Jira sale de Jira REST. test enrich es aditivo y seguro para un pipeline: credenciales faltantes o un test que Xray no conoce se reportan y se saltean, nunca rompen la cadena.

Skills de terceros, instaladas por cli/install.ts

Nivel proyecto, sin commit

Son skills de tier T3: el instalador las agrega a .agents/skills/ junto a las del repo, pero no se commitean. La lista vive en PROJECT_LEVEL_SKILLS de cli/install.ts; bun run setup vuelve a correr la instalación.

Por qué a nivel proyecto

Un flujo depende de ellas y no puede quedar atado a la lista global de plugins de cada persona. Una instalación a nivel usuario también las satisface.

Antes del primer open: ¿con qué login?

CasoCuándoNavegadorCómo termina
(a) anónimopágina pública, localhost, la página de anotación de bugsChromium en memoriaclose
(b) usuario de testla app bajo prueba, logueada con un rol (credenciales en .env)Chromium en memoria + state-load del rolclose
(c) perfil del dueñouna cuenta que un script no puede loguear (SSO, MFA, Google)Chrome real con --profile absoluto, fuera del repoclose (guarda las cookies)
(d) Agentic Pair Testingla persona y la IA prueban juntas en el Chrome de la personael Chrome humano, con attachdetach, nunca close

Reglas para todos los casos

Siempre una sesión con nombre (-s=<KEY>), nunca --persistent. Una cuenta, un navegador vivo. close siempre, y la prueba es playwright-cli list vacío.

testing.browser.pair_mode

En null, la primera sesión agéntica pregunta una vez (dedicada o pair) y guarda true / false. Lo desatendido nunca entra al caso (d).

close es obligatorio aun después de un error; el recibo del close no prueba nada, la lista vacía sí. Nunca pkill ni kill-all mientras otras sesiones trabajan: kill-all mata todos los daemons de la máquina. pair_mode se guarda en .agents/project.yaml editando esa sola línea; el trabajo desatendido (CI, rutinas, un worker sin persona delante) usa siempre los casos a, b o c. El canon es agentic-qa-core/references/browser-sessions.md, de lectura obligatoria antes del primer open. /playwright-cli es la skill del proveedor y sabe el CÓMO de cada verbo; el repo pone QUÉ sesión, QUÉ identidad y QUÉ navegador. El .playwright/cli.config.json que se distribuye lanza todo en memoria y headless: persistir y mostrar la ventana son siempre decisiones explícitas (--profile, --headed).

Comunidad · 15 de 19

Una identidad por rol, un espacio por worktree

Estado por rol

Cada rol de la app tiene un archivo de estado por entorno: .auth/<env>-<rol>.json, con sus credenciales en <ENV>_<ROL>_EMAIL / _PASSWORD. Lo produce el setup de la suite cuando existe; si no, un login agéntico por rol y entorno.

Si falta una mitad del par: parar y nombrar las dos variables. Nunca el usuario de otro rol: sería un PASS falso.

La sesión es un secreto

Un archivo de estado, un perfil o una cookie son credenciales con otra forma. Nunca se imprimen. Una contraseña se tipea con --raw fill <ref> "$VAR": el comando lleva solo el nombre de la variable y --raw suprime el eco. Los archivos van a .auth/ con chmod 600.

Flotas y worktrees

El espacio de nombres de sesiones es el .playwright/ más cercano: cada worktree es el suyo, y el mismo -s en dos worktrees son dos navegadores. En una flota el conductor genera los .auth/ antes de lanzar; un worker solo hace state-load, nunca loguea ni escribe ahí.

Dos roles en un ticket = dos sesiones (-s=<KEY>-admin, -s=<KEY>-member), cada una con su archivo. Login después de goto = estado vencido: se regenera desde su productor.

Nunca se loguea dentro de la sesión de exploración. El perfil del dueño (caso c) vive fuera de todo repo, bajo ~/.agentic-qa/playwright-profiles/, y es de un solo escritor en toda la máquina: antes de abrirlo, playwright-cli list --all. La persona tipea credenciales y 2FA; el agente nunca las escribe ni las guarda. Mediciones detrás de estas reglas: ADR-0008.

MCP · 16 de 19

Se declara la capacidad, se resuelve por sufijo

Prefijo = servidor, sufijo = capacidad

La misma tool llega como mcp__tavily__tavily_search, como mcp__claude_ai_<conector>__tavily_search o con el prefijo de un servidor de usuario. Un worker concluyó una vez "no hay Tavily" por mirar el prefijo. Por eso la IA busca cualquier tool cuyo nombre termine en el sufijo.

Declaración en la skill

En el frontmatter, dentro de metadata.requires_capabilities. Se declara lo que la skill instruye usar, ni más ni menos; bun run skills:check lo verifica.

El vocabulario

CapacidadDónde vive el proveedor

library-docsservidor local comprometido en el repo (resolve-library-id → query-docs)

Dueño del vocabulario y de los sufijos exactos: agentic-qa-core/references/mcp-capabilities.md, espejado en KNOWN_CAPABILITIES de scripts/lint-skills.ts.

Nada alarma al arrancar la sesión cuando un servidor está desactivado (la gente los apaga para ahorrar tokens). La única alarma es el STOP en el punto de uso del slide siguiente. El navegador no es una capacidad: [AUTOMATION_TOOL] es /playwright-cli, un CLI.

MCP · 17 de 19

Sin proveedor: parar, nunca sustituir

Regla #10 · credenciales

Servidor activo pero 401/403 o una falla misteriosa: es el caso de credencial. Con una variable sin setear, Claude Code, OpenCode y DBHub arrancan igual y fallan en silencio en la primera llamada; solo Codex falla fuerte nombrando el servidor. Nombrar la variable, apuntar a .env y pedir reinicio: los valores se leen al arrancar el MCP.

Sin degradar por cuenta propia

WebSearch / WebFetch integrados no son respaldo silencioso de web-search ni de library-docs, y leer archivos de rutas no reemplaza a api-schema.

El procedimiento vive en un solo lugar: agentic-qa-core/references/preflight-gate.md §8. Cada skill que declara una capacidad lo cita con una línea. La tabla de cómo activar cada capacidad por host está en mcp-capabilities.md §5.

MCP · 18 de 19

Locales en el repo, remotos en el harness

Servidores locales: un set, tres formatos

Solo los servidores locales (stdio) se comprometen en el repo. El set canónico es el que declara .mcp.json, y cada uno tiene que existir también en opencode.jsonc y .codex/config.toml con las mismas dependencias de .env. bun run agents:compat:check compara los tres normalizados.

Remotos: a nivel harness

Un servidor remoto cuyo único contenido de proyecto era una API key (búsqueda web, Postman) se conecta una vez por máquina: un conector de claude.ai, un servidor de usuario, la config de usuario de OpenCode o Codex. La lista: cli/lib/harness-level-mcps.ts.

HostActivar o revisar
Claude Code/mcp dentro de la sesión (habilitar, autenticar, reconectar). Lanzar con bun run claude para que .env alimente las ${VAR}. claude mcp list puede marcar como roto un servidor que anda.
OpenCodeenabled: true en opencode.jsonc; los secretos se leen de .auth/opencode/. Reiniciar.
Codex CLI / Desktopcarga la config del proyecto solo en un repo confiable. Reiniciar.

bun run setup:doctor informa qué servidores de nivel harness declaran las configs de usuario de la máquina; un conector en la nube no deja archivo y figura como no detectable, no como faltante.

Búsqueda web: Exa primero, Tavily segundo (cuando no hay Exa o el usuario lo pide). Las referencias a variables mantienen la sintaxis de cada host: ${VAR} en .mcp.json, {file:.auth/opencode/VAR} en opencode.jsonc, env_vars / bearer_token_env_var en .codex/config.toml. Detalle en AGENTS.md §4.5.
