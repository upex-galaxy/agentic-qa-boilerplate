Operators: doing and comparing

  

    
➕ Math
5 + 3      // 8
10 - 4     // 6
"QA" + "!" // "QA!"
With strings, + joins text.

    
⚖️ Comparison
5 === 5    // true
5 !== 3    // true
10 > 7     // true
They always return a boolean.

    
🔗 Logical
a && b  // AND: both
a || b  // OR: either
!a      // NOT: inverts
They combine conditions.

  

  
⚠️
Trap #1: = assigns (stores in the box) · === compares (are they equal?). Mixing them up is the classic beginner bug.

  
Three families, but 80% of the time they will use === to compare. Insist on the = vs === trap: one assigns, the other asks. Mention that == (double) exists, but the professional rule is to ALWAYS use === (triple), which also compares the type. A perfect bridge to the quiz.







  

    
⭐ QUIZ 2 · Operators

    
What does console.log(5 === "5") print?

    

      
      
      
    

    
💡 === compares value and type. 5 is a number, "5" is a string, so the result is false. In testing this matters: an API that returns "404" (text) is not the same as 404 (number).

  

  
This quiz tends to split the room. The explanation connects to APIs: status codes as text vs number is a real bug they will see in integration. If someone brings up ==, celebrate the question and restate: always ===.

Types you will use from day 1

  

    

      
const email: string = "ana@qa.com";
const retries: number = 3;
const passed: boolean = true;

interface User {
  email: string;
  role: "admin" | "viewer";
}

    

    

      
📐 Annotation
: type after the name. Most of the time TypeScript infers it on its own and you do not even write it.

      
📋 interface
The "blueprint" of an object: which fields and of which type. Your test data with a contract.

      
🚧 Union: "admin" | "viewer"
Only these exact values. You write "admni" and get an error instantly. Goodbye silent typos.

    

  

  
Do not memorize syntax, just recognize it when reading. Inference matters for lowering anxiety: when starting out they almost never annotate types by hand. The union type is the most QA-friendly example: a typo in a role or a status is a bug that TypeScript kills for free.







  
async / await: knowing how to wait ⏳

  

    

      
The problem

      
The web is slow: the page loads, the server responds, the animation finishes… Your code runs in milliseconds; the web responds in seconds.

      
// 🤖💥 impatient robot (WITHOUT await):
page.goto("https://app.com/login");
page.click("#login-btn");
// click on a page that HAS NOT LOADED YET ❌

    

    

      
The solution

      
async function runTest() {
  await page.goto("https://app.com/login");
  await page.click("#login-btn");
}

      
await = "wait for this to finish before moving on".
async = "this function contains waits".

      
📜
Golden rule of Playwright: almost every action takes an await. Forgetting it = intermittent (flaky) tests.

    

  

  
Do NOT explain promises or the event loop: an unnecessary black hole in this session. The impatient robot mental model is enough: the machine is faster than the web and has to be slowed down. Mechanical rule: Playwright action → await in front; function with awaits → async in front. 90% of beginner flaky tests = one forgotten await.







  

    
⭐ QUIZ 6 · TypeScript + async

    
Why do we write await page.click("#save-btn")?

    

      
      
      
    

    
💡 Without await, the code keeps running without waiting for the click, so the next step acts on a half-changed page and the test is flaky (sometimes it passes, sometimes not). A forgotten await is the #1 cause of intermittent tests.

  

  
Option A is the dangerous trap: without await it sometimes DOES work (by lucky timing), which is why the bug is treacherous. Introduce the word "flaky" here; they will hear it their whole career. End of Act 3: they now have all the pieces of the language.

Anatomy of a real test: you already know every piece

import { test, expect } from "@playwright/test";

test("successful login", async ({ page }) => {
  await page.goto("https://app.com/login");
  await page.fill("#email", "ana@qa.com");
  await page.fill("#password", "secreto123");
  await page.click("#login-btn");

  await expect(page.locator("#welcome")).toBeVisible();
});

      

    

    

      
📦 import
"Bring me the tools test and expect from the Playwright box."

      
🧪 test("…", async … )
A function that receives the case name… and another function with the steps! Yes: functions travel around as values.

      
🤖 page.fill / page.click
Functions with parameters (Act 2) + the object dot (Act 2) + await (Act 3).

      
✅ expect(...).toBeVisible()
Your expected result turned into code. If it is not met, the test is FAILED.

    

  

  
Peak slide: walk through the code line by line asking "what do you recognize here?": strings, functions, params, the dot, async/await: ALL of it already seen. The only new concept is passing a function as an argument to test(). Do not theorize it, say "we hand the runner the steps so it runs them when its turn comes". The expect is their lifelong expected result.

⭐ QUIZ 7 · Playwright anatomy

    
What does await page.fill("#email", "ana@qa.com") do?

    

      
      
      
    

    
💡 fill = to fill in: the first argument is the selector (where), the second is the text (what). Checking the content would be expect(...).toHaveValue(...). Actions act, expects verify.

  

  
Reinforce the distinction between actions (goto, fill, click: they do things) and assertions (expect: they verify things). A test = actions that bring the app to a state + assertions that check the expected result. That structure is universal in any testing framework.
