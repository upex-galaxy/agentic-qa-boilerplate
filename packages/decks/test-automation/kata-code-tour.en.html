TestContext: the base of everything

tests/components/TestContext.ts
  • TestContext centralizes the Playwright drivers (page, request), the environment config and access to DataFactory.
  • UiBase and ApiBase extend it, so UI and API operations run on the same context.
  • TestContextOptions: page is required for UI tests, request for API tests, and environment defaults to the current one from config.
  • data is both a static property and an instance getter. Any component calls this.data and never imports the factory itself.
tests/components/TestContext.ts
  readonly config = config;

  static readonly data = DataFactory;

  constructor(options: TestContextOptions = {}) {
    this._page = options.page;
    this._request = options.request;
    this.env = options.environment ?? env.current;
  }

  get data(): typeof DataFactory {
    return TestContext.data;
  }

ApiBase: typed HTTP helpers

tests/components/api/ApiBase.ts
  • ApiBase wraps Playwright's APIRequestContext and extends TestContext, so it inherits drivers and config.
  • apiGET and apiDELETE return [APIResponse, TBody]: the ATC gets the raw response (status, headers) and the parsed body in one call.
  • apiPOST, apiPUT and apiPATCH return [APIResponse, TBody, TPayload]. The third element is the payload actually sent, so a spec compares response against request without rebuilding it.
  • Always pass the response model (and the payload model for mutations) as generics so ATCs stay type-safe.
  • The HTTP helpers are protected on purpose: a test cannot skip the component layer with api.apiPOST(...). It goes through an ATC or a layer 3 @step helper.
  • Every helper attaches request and response to the Allure report automatically.

ApiBase: auth, cookies and defensive parsing

tests/components/api/ApiBase.ts
  • setAuthToken stores the token and sends it as Authorization: Bearer on later requests. clearAuthToken removes it.
  • The request accessor prefers page.request when a page exists: it shares cookies and storage with the browser, so under the hybrid { test } fixture API calls carry the cookie. API-only tests fall back to the standalone context, which has no cookie.
  • When there is no request context the accessor throws. A misconfigured fixture fails loudly instead of silently.
  • getResponseJsonObject parses JSON defensively and returns an empty object on failure, so a non-JSON error body does not crash the ATC.
  • requestHeaders.Accept is */* to avoid 406 errors from servers that reject an explicit application/json, even though the body is still JSON.
  • apiEndpoint builds the full URL from config.apiUrl, because Playwright's request context does not use baseURL here.
  • apiPOSTForm sends x-www-form-urlencoded forms for OAuth2 and token endpoints, accepts absolute URLs and masks password in the Allure attachment.

UiBase: native Playwright plus network interception

tests/components/ui/UiBase.ts
  • UiBase is the base class for UI components. It extends TestContext and components use Playwright's native API (this.page) directly: Playwright auto-waits before every action, so no wrapper layer is needed.
  • The page accessor throws when no page exists (for example in API-only tests), so a missing driver fails loudly.
  • buildUrl builds the full URL from config.baseUrl for logging or assertions. For page.goto() use a relative path: Playwright's baseURL already resolves it.
  • interceptResponse registers the response wait first, then runs the triggering action, then awaits the response. That avoids the race where the response arrives before the listener exists.
  • waitForApiResponse does the same capture without triggering an action: use it when the request is already in flight.
  • matchesPattern turns glob-like patterns into a regex: ** matches any path and * one segment. The body parsers return null for non-JSON, so interception never breaks a test.

ExamplePage: the UI reference component

tests/components/ui/ExamplePage.ts
  • It is a reference component with a fictional /example page and placeholder selectors. Copy it to tests/components/ui/YourPage.ts, swap URLs and locators, register it in UiFixture.ts and run bun run kata:manifest.

AuthApi: authentication ATCs

tests/components/api/AuthApi.ts
  • AuthApi is the API component for authentication (POST /api/auth/login, GET /api/auth/me). Endpoints come from config.auth.
  • An ATC is an ACTION plus a VERIFICATION, never a bare GET. A read-only operation is a helper with no @atc.
  • getCurrentUser is that helper: a read-only GET used as a verification step inside ATCs or for test-level assertions. It is decorated @step, not @atc, because it retrieves data and is not a complete action flow.
  • authenticateSuccessfully posts the credentials, asserts the fixed token response (200, access_token, Bearer, expires_in), stores the token with setAuthToken and verifies the session through GET /auth/me.
  • loginWithInvalidCredentials posts bad credentials, asserts the 401 and proves no session was created by calling /auth/me without a token. It saves the current token, clears it for that check and restores it afterwards, so a failed login does not log out the surrounding test.
  • Request and response types are re-exported from AuthApi, so consumers do not import the schema file.
  • The PROJ prefix in @atc('PROJ-101') is a placeholder: use the real project key.

ExampleSteps: precondition chains

tests/components/steps/ExampleSteps.ts
  • A layer 3.5 reference for reusable precondition chains that prepare test state before the real test runs. Copy it to tests/components/steps/YourSteps.ts and replace the fictional endpoints and auth logic.
  • A step has no fixed assertions and no @atc. It combines actions or ATCs to reach a state: authentication, data setup, navigating to a page with data.
  • authenticateUser is a SETUP step: it only fetches the token and does not verify that auth worked. That verification belongs to an ATC.
  • navigateAsAuthenticatedUser chains login, token into browser storage and navigation into one precondition. It takes an object because with three or more parameters bare strings read identically at the call site and swapping two is a silent bug (typescript-patterns.md, section 1).
  • Each step throws a clear error when the driver it needs (request, page) was not passed to the constructor.
  • createTestResource creates data through the API so UI tests start from a known state.

ApiFixture and UiFixture: injection containers

tests/components/ApiFixture.ts · tests/components/UiFixture.ts
  • ApiFixture is a dependency-injection container for all API components. Each gets the same options, so they share one request context and consistent auth.
  • To add an API component: create it in tests/components/api/YourApi.ts, import it in the fixture, add a readonly property and initialize it in the constructor with the shared options.

Integration specs: no browser

tests/integration/module-example/example.test.ts · tests/integration/auth/user-session.test.ts
  • An API spec needs no browser: it uses the { api } fixture directly and ATCs return the tuple [response, body, sentPayload].
  • sentPayload (third element) lets the spec compare the response against exactly what the ATC sent, for example body.user.email against sentPayload.email.
  • Error ATCs (createResourceWithInvalidData) validate the error response themselves, so the spec only builds the invalid payload.
  • ApiFixture loads the token from api-state.json automatically, so specs make authenticated calls without logging in.
  • api.clearAuthToken() removes the token to prove unauthenticated calls return 401. After that, api.auth.authenticateSuccessfully(credentials) obtains and sets a new token at runtime (refresh).

Decorators: @atc

tests/utils/decorators.ts
  • @atc(testId, options) connects a method to a Jira or Xray test case and tracks its execution for reporting and TMS synchronization. It uses the TC39 Stage 3 decorator format.
  • All ATC logging happens only inside the decorator: base components never log.
  • An ATC is a complete mini-flow named {verb}{Resource}{Scenario}, never a single interaction such as fillEmailSuccessfully.
  • Options: softFail continues the test when the ATC fails, severity sets the Allure severity (blocker to trivial) and description adds Allure text.
  • The ATC body runs inside test.step, so it shows up in KataReporter and in the allure-playwright tree on its own. In the terminal it prints one line per ATC (pass, fail, soft fail) with duration and error message.
  • The decorator sets Allure metadata and a link to the Jira test case when config.tms.jira.url is set. Allure may be unavailable (setup projects), so those calls are guarded.
  • It pushes an atc annotation on the running test, which KataReporter reads into reports/test-outcomes.json. A test.skip() inside an ATC throws to stop the test and the decorator lets it propagate: it is NOT RUN, never a failure.

Shared Allure helpers

tests/utils/allure.ts
  • The Allure helpers centralize attachments in one place (DRY). ApiBase uses them for request and response, as do the interception utilities and any component that attaches data.
  • generateAllureFilename strips the protocol and query string, keeps the last two path segments, replaces non-alphanumerics and limits length. It gives names like auth_login_POST_response.
  • attachJsonToAllure fails silently when Allure is unavailable (for example in setup projects) and skips empty data.
  • attachRequestResponseToAllure attaches request and response bodies only when they contain data, with generated filenames.
tests/utils/allure.ts
export function generateAllureFilename(args: AllureFilenameArgs): string {
  const { url, suffix } = args;

  const cleanUrl = url.split('?')[0].replace(/^https?:\/\/[^/]+/, '');

  const segments = cleanUrl.split('/').filter(Boolean).slice(-2);
  const pathPart = segments.length > 0 ? segments.join('_') : 'root';

  const cleanPath = pathPart.replace(/[^a-z0-9]/gi, '_').slice(0, 50);

KataReporter: the custom reporter

tests/KataReporter.ts
  • A custom Playwright reporter with colored terminal output, step-by-step logging, error snippets and a summary. It is registered in playwright.config.ts next to the other reporters.
  • printsToStdio() returns true to tell Playwright this reporter owns stdout, so Playwright adds no supplementary output. Test console.log and stderr output is always shown.
  • In onEnd it builds one outcome record per test the run knew about, from the whole suite (a test whose dependency project failed has no result at all). It writes them to reports/test-outcomes.json and, in GitHub Actions, to the step summary. It never changes the exit code: Playwright still owns it.
  • The headline comes from those records, not from Playwright's ok(), because a setup cascade is ok() there and a known defect is not a pass.
  • Order: outcomes are built first because they decide listOnly, which the ATC report reads. The run id is written to both reports/atc_results.json and reports/test-outcomes.json so a reader can tell a stale pair.
  • playwright test --list reaches onEnd with no attempts: nothing ran, so no outcomes are recorded and the last real run's ATC report is left alone. When no ATC ran, an old report is removed so a later write-back does not import it.
  • Workers write partial ATC results as NDJSON and the coordinator process merges them, so the file is complete by the time onEnd() fires. The final status per ATC is conservative: any failed execution is FAIL, all passed is PASS. The step summary is a convenience, the records file is the contract.

knownDefect and testOutcomes

tests/utils/knownDefect.ts · tests/utils/testOutcomes.ts
  • knownDefect(key) marks the running test as blocked by a known product defect in one call, so the expected-failure flag and the defect key never drift apart. Put the key in the title too (@blocked:BK-999) and call it first in the test body.
  • KataReporter classifies it as known-defect while it fails and as unexpected-pass (an action item) once it passes (ADR-0020). A bare test.fail() still counts as known-defect, but also raises the action item known-defect-without-key. That is why the helper takes the key.
  • testOutcomes.ts gives every test a run knows about exactly one outcome class and computes the headline from those classes, not from Playwright's ok() or Allure's status.
  • It exists because a test skipped by a failed beforeAll is ok() in Playwright, a failed setup project leaves its dependents with no result, and Allure files an expected failure (test.fail) as passed. A headline can say everything passed while known defects and setup failures hide in it.
  • Setup cascade signature: status: 'skipped', expectedStatus: 'passed' and no skip or fixme annotation. A conditional test.skip() does carry the annotation, so it stays skipped.
  • Records are built from suite.allTests(), never from the onTestEnd calls received, because a failed dependency project or --max-failures leaves tests with no results.
  • knownDefectKey takes the key from a known-defect annotation whose whole value is a key, from the @blocked:{BUG-KEY} tag or from a test.fail description starting with Blocked by {BUG-KEY}. Free text never mints a key: fragments such as UTF-8 or SHA-256 are not keys.
  • TEST_STATUS_OF_CLASS maps classes to TMS statuses. Failures that were not observed (the body never ran) become BLOCKED in testStatusOf, because PASSED and FAILED need an observation.
  • outcomeHeadline is green only when nothing failed, nothing passed unexpectedly, no action item is open and every test was reached. Playwright's run status still counts: a worker crash or a global setup error fails the run while every record reads clean.
  • The module is pure: no Playwright runtime import, no file system and no tracker call. Its unit tests (testOutcomes.test.ts, xrayResults.test.ts) run with bun test tests/utils, and Playwright never collects them because every project has its own testMatch.

xrayResults: the Xray import body

tests/utils/xrayResults.ts
  • It builds the Xray JSON body for POST /api/v2/import/execution from one or more reports/atc_results.json. The local write-back (jiraSync.ts) and the CI XrayImport job in .github/workflows/regression.yml share it, so both follow one rule.
  • Why Xray JSON and not JUnit: Xray creates a new Generic Test for every JUnit testcase without a test_key property, and a Playwright testcase calls zero, one or several ATCs. Xray JSON creates a Test only when an entry carries testInfo, which this module never writes. So an import can only write runs onto existing Tests.
  • The ATC id is the Test key: one ATC is one TMS ticket, and every entry is testKey: <atc id>.
  • buildXrayTests marks FAILED when any execution failed and PASSED otherwise. When every execution was a runtime skip, the ATC is left out (NOT RUN, ADR-0020).
  • addUnfinishedAtcs: the atc annotation is pushed when an ATC starts and the record only when it ends. A test that timed out inside an ATC (for example a non-Playwright await that never reaches the decorator's catch) has the first without the second. Those ATCs are sent as FAILED using test-outcomes.json.
  • Both report files carry the run id KataReporter stamped: a report from another run is refused as stale.
  • AtcRun declares playwrightTestId here because bun sync delivers this file while decorators.ts stays the project's own copy, which may predate it. That keeps this file compiling against either copy.
  • CLI (bun run xray:payload): --execution <KEY> --out <file> <report...>. It exits 1 with one line naming every unreadable or stale report or non-Test-key id, and writes nothing when no ATC result is left. Whether the key exists is Xray's call.
  • The import body always targets an existing Test Execution (testExecutionKey), never info.

jiraSync: the write-back to Jira and Xray

tests/utils/jiraSync.ts
  • jiraSync.ts runs after the Playwright process exits (bun run test, then bun run test:sync, gated on AUTO_SYNC=true). It is deliberately not called from global.teardown.ts: KataReporter.onEnd() writes reports/atc_results.json after the teardown project, so an in-process call would read a stale file or none.
  • Targets: Xray Cloud (import of an Xray JSON body) and Jira Direct (a custom field per test).
  • Import modes (XrayImportPayload): testExecutionKey writes runs onto an existing Test Execution, and info lets Xray create a new one. The info schema is closed and has no parent field, so an Execution created that way cannot be attached to the QA Test Artifacts epic by this call.
  • Preferred path: write onto an Execution that already exists (the RTR created by /regression-testing, or the sprint-close STR). It already carries its parent epic, Test Environment, testPlan link and ratified title, so nothing is invented.
  • Fallback path (no STP_EXECUTION_KEY): Xray creates the Execution from info and it lands unparented. No later call can adopt it, because reparenting is a Jira REST PUT /issue/{key} that needs Atlassian credentials the Xray provider lacks. The code does what the API allows: ratified RTR title, Test Environment from the active env and the testPlanKey link when RTP_KEY is set, added only when non-empty because Xray rejects an empty string.
  • STP_EXECUTION_KEY guard: it invites handing it a Test Plan key. Xray writes runs into Test Executions only and a Plan derives its status from them, so an import aimed at one lands nowhere useful. readIssueType is diagnostic only: missing credentials, unreachable Jira or an unexpected payload return null, because a diagnostic must never become a new blocker.
  • Each ATC is one tests entry with testKey only and no testInfo, so Xray cannot create a Test from the import. An id that is not a Test key stops the write-back before any network call, and when every ATC was skipped at runtime there is nothing to send, because Xray's schema needs at least one entry.
  • In CI a missing report means the pipeline is wired wrong (the command runs after Playwright), so it fails loudly (issue 27: the old silent return hid the broken write-back for months). Locally it is ordinary and stays a warning. When every ATC hung, test-outcomes.json alone is enough, because it is then the only record that they ran.
  • resolveTestStatusField: Jira custom-field ids are per instance and a site migration reassigns them, so .agents/jira-fields.json is the single source of truth and JIRA_TEST_STATUS_FIELD is only an explicit override. With neither, the caller aborts instead of PUTting an empty field key, which Jira answers with an opaque 400. The title grammar is {ACRONYM}: {scope-id}: {descriptor}, defined in .agents/skills/agentic-qa-core/references/planning-ladder.md.

Setup: global and authentication

tests/setup/global.setup.ts · ui-auth.setup.ts · api-auth.setup.ts
  • global.setup.ts is the root project and runs first: it creates required directories and validates config. ui-setup and api-setup depend on it.
