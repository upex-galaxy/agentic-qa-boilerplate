MISSION D1

Navigate like a pro

🎯 From a NEW terminal, create your practice folder, get to it using only commands and open it in VS Code.

1. Open a new terminal (not the VS Code one, that one cheats)
2. pwd to find your place, ls to look around
3. Create your practice folder (TypeScript, everything else default):

$npm init playwright@latest mi-dev-craft📋

4. Enter with cd + Tab until mi-dev-craft
5. Finish with:

Hint: "npm: command not found"

Node.js is missing, the kit that closes Coding Base: install the LTS version from nodejs.org and reopen the terminal (the old one does not know about new programs).

Hint: "code: command not found" (Mac)

Open VS Code → Cmd+Shift+P → type "shell command" → "Install 'code' command in PATH". Reopen the terminal.

Hint: I got lost in the folders

cd ~ teleports you to your user folder (home). From there, ls and navigate again. You can't stay lost forever.

✅ Success criterion: VS Code open in mi-dev-craft, launched 100% from the terminal, without touching Finder/Explorer.

Short mission (10-15 min: the Playwright installer downloads the browsers) but diagnostic: whoever does not flow here will suffer with git. "New terminal, not the VS Code one" forces real navigation. cd ~ as a panic button removes the fear of getting lost.

package.json: the project's ID card 📋

package.json
{
  "name": "mi-dev-craft",
  "scripts": {
    "test": "playwright test",
    "test:ui": "playwright test --ui"
  },
  "devDependencies": {
    "@playwright/test": "^1.x"
  }
}

📛 name

The project's identity.

📜 scripts

The team's command cookbook: short aliases for long commands. Run them with npm run <name>.

📦 devDependencies

The shopping list: which tools the project needs and in which version. npm install brings them all.

🚫 node_modules does NOT travel

It weighs hundreds of MB and gets rebuilt from the list with npm install. That is why it NEVER goes into Git (we will ignore it in Act 3).

The double metaphor: scripts = cookbook, dependencies = shopping list, node_modules = the full pantry (rebuildable, not shared). This logic explains the universal ritual "clone → npm install" and sets up the .gitignore of act 3. dependencies vs devDependencies: for a test project everything is dev, so don't go deeper.

MISSION D2

Build your script cookbook

🎯 Define the 4 standard scripts of your suite and use them with npm run.

1. In your package.json, inside "scripts":

"test": "playwright test",
"test:ui": "playwright test --ui",
"test:headed": "playwright test --headed",
"report": "playwright show-report"

2. Try them:

$npm run test📋
Hint: "Unexpected token" when running npm

JSON is strict: double quotes ALWAYS, a comma between entries, no comma after the last one. VS Code underlines the exact error.

🤝

The real value: a team contract. Anyone (or a CI pipeline) runs your suite with npm run test without knowing what is behind it. A universal standard of the ecosystem.

✅ Success criterion: npm run test and npm run test:ui work in your project.

First hand edit of a JSON. The syntax error in the hint will happen to someone, guaranteed, and it is a good lesson (strict JSON vs loose JS). The "team contract" concept connects with future CI/CD: pipelines run npm run test, not raw commands.

⭐ QUIZ 1 · The clone ritual

You clone a teammate's project, run npm run test and it blows up: "Cannot find module '@playwright/test'". First command?

💡 node_modules does not travel with the repo (it is ignored), so the clone arrives "without a pantry". npm install reads the dependencies in package.json and rebuilds it exactly. The universal ritual: clone → npm install → get to work. Option C works... the way taping a torn banknote works: don't do it.

They WILL run into this error the first time they clone something, and the quiz turns it into an "I already knew that" moment. The full ritual clone → npm install → npx playwright install (browsers) they will see in the boss mission when they clone their own repo, if there is time.

Like a video game

Commit = save game. Broke everything? Go back to the last checkpoint. Nothing is really lost after a commit.

📦

Why staging?

You choose WHAT goes in each photo. You changed 5 files but 2 belong to another task → separate photos, clean history.

🔍

git status = your compass

It tells you what is modified, what is in staging and what is missing. When in doubt: git status. Always.

The 3-zone model IS git, and every command makes sense from here. Insist on "git status as a compass": the habit that saves every beginner (it doesn't punish, it only informs). The video game checkpoint metaphor lowers the fear: with frequent commits, nothing gets lost.

The sacred cycle + worthy messages

The cycle (you will do it 1000 times)

$git status📋
$git add .📋
$git commit -m "clear message"📋

git add . = everything modified goes to staging · -m = inline message.

🙈

Before the first commit: create .gitignore with node_modules/, test-results/ and playwright-report/. The pantry and the reports do NOT go into the history.

The message is for a human of the future

❌ Unworthy✅ Worthy
"changes""add login page object with semantic locators"
"fix""fix flaky register test with unique email"
"asdfgh""add API tests for auth endpoints"

Formula: verb + what + (why, if it isn't obvious). The future human reading your history... is almost always you.

The .gitignore BEFORE the first commit is critical: committing node_modules is the #1 beginner mistake (a 500MB repo). Messages: the proof is in git log, and a history of "changes, fix, more changes" is useless to everyone. Convention of the professional repo they are heading to: semantic prefixes (feat:, fix:, test:). Mention it as a preview.

MISSION D3

Real Git in your project

🎯 Put your practice project under version control: init, .gitignore and a first commit with a worthy message.
$git init📋

Create .gitignore (project root) with:

node_modules/
test-results/
playwright-report/
$git add .📋
$git commit -m "add playwright starter suite"📋
$git log --oneline📋
Hint: git asks for your identity

First time with git on this machine:

git config --global user.name "Your Name"
git config --global user.email "you@email.com"

Only once, it stays configured forever.

Hint: did the .gitignore work?

git status BEFORE the add: if node_modules shows up in the list, the .gitignore has a typo or is in the wrong folder.

✅ Success criterion: git log --oneline shows your initial commit, and git status does NOT list node_modules.

From sandbox to reality. The identity config will stop most of them (first time with git), and the hint solves it. Checking the gitignore via git status: a habit of verifying, not assuming. If someone already committed node_modules: delete the whole .git folder and restart the mission, which is simpler than teaching how to undo in this session.

⭐ QUIZ 2 · The 3 zones

You modified 5 files, but 2 belong to another task. How do you get a clean commit with only the 3 relevant ones?

💡 git add accepts specific files, and that is the reason staging exists: to compose EACH photo deliberately. git add . is the shortcut for "everything", not the only way. Clean history = one commit per intent = happy future you.

Validates the 3-zone model with the use case that justifies staging. Option C (delete and recreate) sounds absurd but it is what people do when they don't understand staging, so name it with humor. Commits per intent set the ground for focused PRs.

GitHub: your history, in the cloud ☁️

💻 Your local repothe history on your machine
↑ git push (upload)  ·  ↓ git pull (download)
☁️ GitHub (remote)the team's shared copy

Remote = the shared "official" repo. push uploads your commits; pull downloads other people's. Laptop dies → the history lives.

Connect your project (once)

With the GitHub CLI (recommended: it creates the repo AND connects it):

$gh auth login📋
$gh repo create mi-dev-craft --private --source=. --push📋
Alternative without gh (web)

github.com → New repository → copy the commands GitHub shows under "push an existing repository": git remote add origin … + git push -u origin main.

Simple model: local = your copy, remote = the official shared one. The gh CLI does in 1 command what the web does in 5 steps, but it requires gh installed (brew install gh / winget install GitHub.cli); the web alternative always works. gh auth login is interactive: guide it live.

main is sacred

Nobody pushes straight to main: it is the stable version. Your branch = a safe draft where nothing breaks.

💬

The PR is a conversation

A description of what and why, code you can comment line by line, approval before the merge. The real review happens there.

🧪

In QA

Your suites enter the team repo through a PR, and the CI pipelines run the tests IN the PR before approving. Your work becomes a quality gate.

The branch→PR→review→merge flow is THE industry flow (GitHub Flow). For QA it matters twice: (1) they deliver suites through PRs, (2) their tests RUN on other people's PRs as a gate, so their work decides whether the devs' code gets in. Branch naming convention: test/*, feat/*, fix/*, which the professional repo uses.

MISSION D4 · BOSS 🏆

Your suite, published with a PR

🎯 Your practice project on GitHub, with an improvement entering through a Pull Request: the full professional flow, for real.

1. Repo on GitHub connected (slide "GitHub: your history, in the cloud")
2. Create a branch for a small improvement (a new test, a script, the POM of another page):

$git checkout -b test/mi-mejora📋

3. Make the change → add → commit → push:

$git push -u origin test/mi-mejora📋
$gh pr create --fill📋
Hint: without the gh CLI

After the push, GitHub prints a "Create a pull request" URL in the terminal itself, so open it. Or on the repo's web page: the "Compare & pull request" button.

Hint: who approves it for me?

In this exercise: review it yourself (look at the diff with a reviewer's eyes: would you understand this change with no context?) and merge it. On a real team, a colleague approves. If you are in pairs: review each other! That is real code review.

✅ Success criterion: the URL of a PR of yours, merged, in your GitHub repo. Save it, it is your first delivery with a professional flow.

The boss produces a REAL artifact with a URL: their first PR. If there are pairs, cross them for mutual review, since a colleague's feedback on a diff is the full professional experience. The PR diff on GitHub also shows them visually what changed: the usefulness of git becomes tangible.

⭐ QUIZ 3 · The reason for the ritual

You work ALONE on your suite. Does it make sense to keep using branches and PRs?

💡 Three reasons even when alone: (1) each PR documents a change with intent, a navigable history; (2) CI pipelines run the tests IN the PR: your automatic safety net; (3) the habit, because whoever works with branches alone doesn't improvise when joining a team. The flow IS the training.

Closes the motivation arc: the flow is not bureaucracy for big teams, it is professional discipline with immediate benefits (CI on PRs comes in regression-testing of the professional repo). "The flow IS the training" is the closing line of the act.
