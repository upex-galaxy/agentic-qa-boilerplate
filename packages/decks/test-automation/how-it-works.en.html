plan craft · test-design doctrine: binding

Covering the ACs is the floor, not the goal

1 : N by default

One AC → several ATCs. EP-merge collapses ONLY within a partition (same behavior → one parameterized ATC), never across partitions, boundaries or states.

EP doesn't replace BVA

Wherever there is a range / limit / length / date window: explicit edge cases (min−1 · min · min+1 …). Merging hides the off-by-one.

Risk lives outside the AC

Invalid inputs, auth/error paths, state transitions and anomalies the AC stays silent about also belong in the ATC set.

Trigger in the ACRequired techniqueProduces
Any input (always)Equivalence PartitioningOne parameterized ATC per partition; distinct partitions → separate ATCs
Range / limit / lengthBVAEdges + zero / empty / null
State fieldState-TransitionEvery valid transition + every invalid one
2+ interacting conditionsDecision TableOne ATC per surviving rule
3+ combinable factorsPairwiseAll-pairs set (record the reduction)

Canon: agentic-qa-core/references/test-design-doctrine.md, loaded MANDATORY before deriving ATCs from ACs. Never report "% of ACs verified" as completeness.

An AC is the business statement; an ATC is its concrete exploration (precondition + action + assertions). Collapsing to 1:1 requires a written "trivially atomic" justification.

plan craft · data strategy: classified when you PLAN

Discover → Modify → Generate (strict priority)

1

Discover

Find data already in the required state. Zero DB impact. Preferred.

2

Modify

Take existing data and mutate it through the API into the required state. One mutation.

3

Generate

Create from scratch: faker + POST. Last resort, since it pollutes the environment.

4

Blocker

No viable pattern → NOT automatable; document the gap and escalate.

Override

Use Generate even if the data could be discovered IF the test mutates state, which avoids order dependencies. Every test generates its OWN data (DataFactory / faker): no shared state between tests.

The beforeAll trap

Never expect() inside beforeAll: a failed assertion kills the WHOLE describe and hides the cause. beforeAll only discovers; each test guards its own precondition: test.skip(!order, 'No order available'). That way the report tells "skipped: data missing" apart from "failed: real bug".

This classification happens in the plan, never deferred to the code. Cleanup: Discover needs none; Modify restores in afterAll; Generate deletes in afterEach.

code craft · the architecture: never collapse layers (gotcha 19)

The KATA layers, bottom to top

L1

TestContext

Playwright drivers (page, request), config, environment and DataFactory. No HTTP or UI helpers.

L2

ApiBase / UiBase

HTTP helpers (typed tuple returns) and Playwright helpers. Everything generic lives here, once.

L3

Domain components: UsersApi, LoginPage

@atc lives here. One component per file: {Resource}Api.ts / {Page}Page.ts.

L3.5

Steps: AuthSteps, CheckoutSteps

Reusable ATC chains for preconditions. NOT decorated with @atc.

L4

Fixtures: TestFixture, ApiFixture, UiFixture

Dependency injection. Tests ask for the fixture and receive the components. Steps have no fixture: they are imported and instantiated directly.

Consumers are not a layer

tests/e2e/** and tests/integration/** orchestrate ATCs into scenarios and validate FLOWS: they consume the Fixtures (L4), they are not a fifth layer. That makes four named layers, plus optional Steps.

Two hard rules

A higher layer uses a lower one, never the other way around. Imports ALWAYS through aliases (the ones in tsconfig.base.json, e.g. @api/ @ui/); lint rejects relative ones (../../../).

Flattening layers is an automatic rejection in Review (gotcha 19 in SKILL.md). The separation gives HTTP helpers, UI helpers and agnostic utilities one home each.

Golden rule

Never ask for { ui } in a test that never touches the UI: it opens a browser for nothing. E2E uses { ui } if it needs no API setup; if it does, { test }.

Playwright lazily instantiates only what the test asks for. The wrong fixture means a needlessly slow browser or a missing context.

code craft · the rules that decide the review

ATC rules: the most common rejections

ATC = a complete test case

clickLoginButton() is NOT an ATC; loginWithValidCredentials(data) IS. If it wraps a single page.click() in one line, delete it.

Identity: precondition + action = 1 TC

All the expected results of the same precondition + action are assertions of the SAME TC. Don't split it by panels or endpoints.

Same output → one parameterized ATC

Three ATCs that return 401 are wrong: use a single parameterized loginWithInvalidCredentials(payload).

An ATC never calls another ATC

Reusable chains → Steps module (tests/components/steps/), with no @atc.

Inline locators · helpers vs ATCs

No locators/*.ts: the selector lives in the ATC; 2+ uses → a private readonly arrow. An action that mutates state = ATC; a GET whose response IS the result under test (data, 401, 403, 404) is also an ATC; a GET that only prepares data = helper (@step optional).

Anti-flake discipline

Max 2 positional params (3+ → an object). No waitForTimeout: wait on conditions. retries: 0: a pass on retry is a bug. Ticket ID in every test().

Fixed assertions (status, fields, redirect) go INSIDE the ATC; flow assertions go in the test file. Once these six cards are internalized, most code passes review on the first try.

phase 2 · code: the shape of an API component (L3)

A helper with no decorator, an ATC with @atc

tests/components/api/OrdersApi.ts
export class OrdersApi extends ApiBase {
  private readonly baseEndpoint = '/api/v1/orders';

  @step                                  // helper: read-only, no @atc
  async getOrderById(id: string): Promise<[APIResponse, Order]> {
    return this.apiGET<Order>(`${this.baseEndpoint}/${id}`);
  }

  @atc('UPEX-411')                        // ATC: mutates state, traced to the TMS
  async createOrderSuccessfully(payload: CreateOrderRequest) {
    const [response, body, sent] = await this.apiPOST(this.baseEndpoint, payload);
    expect(response.status()).toBe(201);   // FIXED assertion: lives in the ATC
    expect(body.id).toBeDefined();
    return [response, body, sent];        // 3-tuple: allows chaining
  }
}

GET / DELETE return 2-tuples; POST / PUT / PATCH return 3-tuples (compare what was sent vs what was received). Test files: {verb}{Feature}.test.ts, importing from @TestFixture, never from @playwright/test.

Internal order of the file: types, baseEndpoint, constructor, helpers, ATCs. In UI the pattern is the same: inline locators with getByTestId as the first rung, fixed assertions inside the ATC, void return.

Separate verifier: required before merge

The Automation contract demands a separate verifier in a clean context, for any change and not only high-risk ones: /pr-review-lead (a QA lead review anchored in KATA doctrine) or /judgment-day (two blind judges in parallel, approving only if both agree). You choose the one that fits the change; skipping it is a DoD failure. It is the only stage with this obligation, in exchange for more autonomy at the entry (from 2 to 3 within the approved plan).

The two reviewers run in a clean context and each reads only its own material: the Spec reviewer doesn't see the standards, the Standards reviewer doesn't see the spec, so neither covers for the other. Aggregation is inline: the orchestrator reads the 5 reports without merging or reordering them, and decides. With nobody present, the rejection goes to the conductor or the report, and the change stays unmerged. If a test fails on a REAL product bug: look for an existing bug, annotate test.fail('Blocked by {BUG-KEY}') or create the bug with your confirmation. A red test with no bug key is never an acceptable override.

after accept: who does the git, and against which base

The skill stops at a clean local review

The rule

In the Automation stage, /test-automation ends at a green local review (tests, types, lint) and leaves an explicit handoff; the PR is opened by /git-flow-master, never by /test-automation on its own, against the base declared in the git_strategy: block of .agents/project.yaml.

Default: whatever git_strategy: says

The repo ships solo-main as an inherited default; each project declares its own. /git-flow-master reads it, cuts the test/* branch, pushes and opens the PR against that base. Then git_strategy.policy.merge_mode decides the merge: under auto and human-approves it enables auto-merge and watches the PR until it merges, with a person's approval first under human-approves; under manual it stops at the PR and a person merges.

sdet variant (chained suites)

Each ticket cuts test/{KEY}-{slug} from the integration trunk, passes Sanity CI and opens its PR into the trunk; the trunk reaches main in a single final PR. The local gate passes on local AND staging before the push, and the Git Ledger is appended to progress.md after every branch action.

at scale · batch fleet, an optional second executor

A batch runs in series; in parallel only if the modules don't touch

By default a batch runs in this session, one Work Package at a time, Plan → Code → Review each. The fleet is offered only if you ask for it or the batch has 3+ Work Packages over disjoint modules; it is never entered silently.

Work Package = one test-specs/<ID>/

Its spec.md + automation-plan.md + atc/*.md. A batch is a list of WPs, never of files or TCs. Without a spec.md, the WP is not dispatched.

Partition by module, not by ticket

A worker owns a module's components; WPs from the same module run in series inside it. Never two workers in one module: they share Pages, Apis and fixtures.

One worktree per worker

This skill writes code, and two sessions in one checkout fight over the git index. The conductor creates the worktree and provisions it (bun run worktree:provision) before launching the worker.

What stays with the conductor

api:login, api:sync, the Jira/TMS writes (transitions, labels, links) and bun run kata:manifest at each integration: the manifest is regenerated, never merged by hand. It integrates one branch at a time and re-runs the suite on the merged state.

With or without an orchestrator, the same payload

The conductor always writes launch.txt: one self-contained line per worker. With an orchestrator those lines launch themselves; without one, the person pastes them into terminals. The absence of the orchestrator is not reported anywhere. With no live conductor, the batch runs here, WP by WP, in the order the partition would give.

Full protocol (partition algorithm, collision table, per-worker brief, integration order, git rules per strategy): .agents/skills/test-automation/references/batch-fleet.md. The transport (launching, supervising, closing workers) lives in agent-orchestration, never in this skill. Conflicts in ApiFixture.ts / UiFixture.ts are resolved additively: both registrations are kept.

who decides what: the Automation contract

The agent executes. The evidence proves. The person decides.

  • The agent does: writes spec.md + automation-plan.md, then the KATA code with @atc, runs the three verifiers and leaves the handoff to /git-flow-master, which opens the PR against the git_strategy: base. /test-automation never runs git on its own.
  • The person signs: the plan before a line of code, the merge only where git_strategy.policy.merge_mode gives it to a person (human-approves, manual), and the call on the third review loop.
  • The evidence that survives: green tests, clean types, clean lint, @atc ids that resolve to real tickets, a fresh manifest.
  • CSA autonomy 2 → 3, and only inside the approved plan. Only Regression can reach 4, on a clean GO.
  • Separate verifier: REQUIRED. /pr-review-lead or /judgment-day, in a clean context. Automation is the only stage with this obligation, in exchange for more autonomy at the entry.

Why right here

Feedforward and feedback balance each other: more slack at the entry is paid for with a harder check at the exit. The plan approved before the code is the feedforward; the separate verifier before the merge is the feedback.

Source: agentic-qa-core/references/stage-gates.md, the agentic contract per stage, CSA scale 0-5. The DoD says what has to be true on the way out; the contract says who was allowed to do it while the stage ran. Both are gates.

The three rules to take with you

1 · One ATC = one atomic test case, traced with @atc('TICKET-ID'). 2 · Plan → Code → Review, always in order and with your approval in the middle. 3 · Stability is discipline: retries: 0, no fixed waits, each test with its own data.
