The magic moment of the lab: they watch their click turn into code instantly. Let them record freely for 3-4 minutes. Codegen also SUGGESTS good locators (getByLabel, getByRole): notice how it picked them and use that on the next slide. Anticipate the cleanup: nobody ships recorded code as is.

From draft to a test worth keeping

Clean up the recording: and add the expect

❌ What codegen records (draft) 
await page.goto("https://dojo.upexgalaxy.com/");
await page.getByRole("link", { name: "Login" }).click();
await page.getByLabel("Email").click();   ← useless click
await page.getByLabel("Email").fill("testuser@upex.dev");
await page.getByLabel("Password").click(); ← another one
await page.getByLabel("Password").fill("Test123!");
await page.getByRole("button", { name: "Sign in" }).click();
// ...and THAT'S WHERE IT ENDS. Where is the check? 😱
✅ Your clean version (with an assertion) 
test("successful login on the dojo", async ({ page }) => {
  await page.goto("https://dojo.upexgalaxy.com/login");
  await page.getByLabel("Email").fill("testuser@upex.dev");
  await page.getByLabel("Password").fill("Test123!");
  await page.getByRole("button", { name: /sign in/i }).click();

  await expect(page).toHaveURL(/dashboard/);
});

Cleanup: useless clicks out, a direct goto to the login, and the expect that codegen never writes. Without an assertion there is no test, just a stroll.

Professional rule: codegen to discover locators and a skeleton, a human for intent and assertions. Notice the getByLabel/getByRole locators that codegen picked: they are the modern ones (semantic, stable), better than the #ids of the simulator in earlier decks: the app can change ids, but "the button that says Sign in" is stable. Remember the golden rule: if the exact texts of the dojo differ, adjust to whatever codegen recorded. That IS the exercise.

MISSION 5

Break it on purpose and diagnose

🎯 Cause a controlled failure, read the error without panic and use the trace viewer to see the "black box" of the crash.

1. In your login.spec.ts change the password to "incorrect"
2. Run it with the black box turned on:

$npx playwright test login --trace on📋

3. It fails (expected ✓). Open the report and the trace:

$npx playwright show-report📋
  ✗ login.spec.ts:3 › successful login

  Error: expect(page).toHaveURL(/dashboard/)
  Expected pattern: /dashboard/
  Received string:  "…/login"  ← stayed on login
    at login.spec.ts:9:24

In the report, click the red test → Trace: a timeline with screenshots of every step, network, console. The complete black box of the failure.

Hint: read the error like a detective

Three questions, ALWAYS: what did it expect? (Expected) what did it find? (Received) on which line? (at …). A Playwright error is a well-written bug report, and reading them is your craft.

✅ Success criterion: you found in the trace the screenshot of the moment of failure (the page that stayed on login). Restore the good password and get back to green before moving on.

Anti-fear mission: red is information, not failure. The test "failed" because it FOUND something: a login with a bad password does not reach the dashboard, so the test works! An important distinction to plant: this failure is "a correct test detecting the expected behavior of the system". At a real job they will tell a real bug from a badly written test with these same tools. Do not forget to restore the password.

⭐ QUIZ 1 · Reading errors

Your test fails with: TimeoutError: waiting for getByLabel("Email"). What does it mean?

💡 A TimeoutError on a locator almost always means "I looked and it does not exist (with that name, on this page)". First reflex: open UI mode or the trace and LOOK at which page was there and what the element is really called. Raising the timeout (option C) only makes the error take longer to show up. It sweeps the problem under the rug.

Option C is the most common bad practice of juniors: raise the timeout and pray. Kill that instinct NOW: a long timeout does not fix broken locators. The right reflex: trace/UI mode → look at the real page → fix the locator. Option A teaches not to escalate without diagnosing.

The shape of every test worth keeping

AAA pattern: your compass for Mission 6

test("invalid login shows an error", async ({ page }) => {
  // 1. ARRANGE: set up the scenario
  await page.goto("https://dojo.upexgalaxy.com/login");

  // 2. ACT: perform the action under test
  await page.getByLabel("Email").fill("testuser@upex.dev");
  await page.getByLabel("Password").fill("incorrect");
  await page.getByRole("button", { name: /sign in/i }).click();

  // 3. ASSERT: verify the expected result
  await expect(page.getByText(/invalid|incorrect/i)).toBeVisible();
});

🎬 Arrange

The preconditions of your manual test case: "being on the login page…"

⚡ Act

The steps. ONE main action under test per test.

🔍 Assert

The expected result. A test without an expect is not a test, it is a stroll.

AAA = the structure of their manual test case with other names: preconditions / steps / expected result. The comments in the example are didactic: in real code the structure shows by itself with blank lines. The "one main action per test" rule: if the title carries an "and" (tests this AND that), they are two tests.

Distilled wisdom

Survival tips 🧰

⏳

Never use sleep

Playwright waits by itself for elements to appear (auto-wait). waitForTimeout(5000) = a slow AND flaky test. If you think you need it, an intermediate expect is missing.

🎯

getByRole > CSS selectors

getByRole("button", { name: "Sign in" }) survives redesigns; .btn-primary > div:nth-child(2) dies tomorrow. Semantic locators = cheap maintenance.

1️⃣

One test, one goal

The title describes ONE verifiable behavior. If you need an "and" in the title, split it into two tests.

🔁

Run on every change

Write 3 lines → run. Immediate feedback = small, easy errors. Writing 50 lines without running = bug archaeology.

Four habits that separate juniors from professionals from day 1. Anti-sleep is the most important: auto-wait is THE advantage of Playwright over old Selenium; every waitForTimeout is a confession of not understanding what is being waited for. getByRole connects with the codegen cleanup (slide «From draft to a test worth keeping»). Burn these 4 into memory before the free work of M6.

⭐ QUIZ 2 · The integrator

Your suite passed 15/15 on Monday. On Tuesday it runs again WITHOUT code changes… and a test fails. What is the first professional hypothesis?

💡 A test that fails with no code changes is a sign that something DID change elsewhere: an app deploy, consumed test data (did your registration reuse an email?), network timing. The trace tells you which. If it comes and goes with no cause, it is called flaky, and diagnosing them is a star skill of the QA Engineer (covered in depth in Playwright Pro).

The lab's closing mindset: an intermittent red is not ignored or deleted, it is diagnosed with evidence (trace). Option B is the real temptation in teams in a hurry: deleted tests = coverage lost silently. Remember that Playwright Pro tackles flakiness head on with hooks and isolated data.
