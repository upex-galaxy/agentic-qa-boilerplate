The cure: the request fixture, HTTP without a browser 🚀

test("POST /orders", async ({ request }) => {
  //                          ▲
  //         another fixture, like page
  const res = await request.post("/orders", {
    data: { item: "Coffee", qty: 2 },
  });

});

No goto, no clicks, no waiting for render. One direct request, one direct response. Milliseconds, not seconds.

.get() · .post() · .put() · .delete(). The same language as the backend.

The reveal of the act: there is a sibling fixture of page called request. Anatomy: one request, one response 📦

🚩 The 4 verbs you'll always use

// read
await request.get("/orders");
await request.get("/orders/42");

// create (with a JSON body)
await request.post("/orders", { data });

// update / delete
await request.put("/orders/42", { data });
await request.delete("/orders/42");

📥 What each call returns

const res = await request.get("/orders/42");

res.status();    // 200, 404, 500…
res.ok();        // true if 2xx
await res.json();  // the body as a JS object
res.headers();   // the headers
🔑

status() and ok() are synchronous. json() is async: the body arrives as a stream, which is why it takes await.

The minimal, accurate map of Playwright. Left: the 4 verbs. The second argument { data } serializes to JSON automatically and sets the content-type header. Right: the response (APIResponse). A detail that confuses everyone: status() and ok() are synchronous (you have the status as soon as it comes back), but json() is async because the body is read as a stream, hence await res.json(). New pain: "200 OK" doesn't mean "correct" ⚠️

  

    

      
test("fetches the order", async ({ request }) => {
  const res = await request.get("/orders/42");

  await expect(res).toBeOK();   // ✅ 200… and that's it?
});

// The server answered 200, but the body was:
// { "id": 42, "item": null, "qty": -3 }
// ☠️ garbage data, and the test passed happily

      
🕳️
Checking only the status is a sieve: the endpoint can answer 200 with an incomplete body, null fields or wrong types.

    

    

      
🎯 Three layers to verify
1. Status: is it the right code? 2. Body: is it the right data? 3. Contract: is it the right shape?

      
🧩 The symptom
"Green" tests that catch nothing. They pass even when the backend returns garbage, because they only look at the status.

      
💡 The idea
Assert on the content: exact fields, types, and the full shape of the JSON (schema).

    

  

  
The pain of the act: a weak assertion gives false security. 200 OK only says "the server answered", not "it answered correctly". Three levels to cover: status (201 or 422?), body (is item "Coffee" and qty 2?), and contract/schema (does the JSON have every field with the right types?). The example with a null body and a negative qty is the classic: the status passes, the test passes, and the bug reaches production. The cure comes in the next two slides.







  
requestassertionsschema · datakata

  
The cure: assert status, body and headers 🎯

  

    

      
test("GET /orders/42 full check", async ({ request }) => {
  const res = await request.get("/orders/42");

  // 1 · STATUS
  expect(res.status()).toBe(200);

  // 2 · BODY (the content matters)
  const body = await res.json();
  expect(body.id).toBe(42);
  expect(body.item).toBe("Coffee");
  expect(body.qty).toBeGreaterThan(0);

  // 3 · HEADERS
  expect(res.headers()["content-type"])
    .toContain("application/json");
});

    

    

      
🔢 Exact status
toBe(201) for creation, 422 for validation, 404 for not found. The code tells a story.

      
📋 Body, field by field
toBe · toEqual · toBeGreaterThan · toBeDefined. The same assertions you already use.

      
📨 Headers when they matter
content-type, pagination, rate-limit, auth. Not always, but when the contract demands it.

    

  

  
The cure, layer by layer, with matchers they ALREADY know (toBe, toEqual, toBeGreaterThan). There is no new assertion API, it's the same old expect applied to JSON. Message about status: every code tells a story and you must assert the EXACT one, not just "2xx". 201 vs 200 tells "I created it" apart from "it already existed", and 422 vs 400 tells validation apart from a generic error. The body is where real bugs get caught. Headers: only when the contract asks for them. But asserting 8 fields by hand is tedious and brittle, and that opens the next slide: validating the full shape with a schema.

The pro level: validate the full shape with a schema 📐

  

    

      
Instead of asserting 10 fields by hand, you define the expected shape once (with Zod) and validate the whole body in one go. If a field is missing or a type changes, the schema catches it.

      
import { z } from "zod";

const OrderSchema = z.object({
  id:   z.number(),
  item: z.string(),
  qty:  z.number().positive(),
});

const body = await res.json();
OrderSchema.parse(body);  // 💥 throws if the shape doesn't match

      
🔗
In this repo the contract is generated from the OpenAPI: bun run api:sync writes the TypeScript types to api/openapi-types.ts and api/schemas/ exposes them as per-domain facades. They are types (the compiler checks them), not Zod: Zod doesn't ship with the repo and stays an option if you want to validate at runtime.

The leap from "asserting loose fields" to "validating the full contract". Zod defines the shape once and parse() throws if anything doesn't match: a missing field, a changed type, an unexpected null. A true fact about the repo: the types are NOT written by hand, they are generated from the backend's OpenAPI with bun run api:sync (api/openapi-types.ts, with per-domain facades in api/schemas/). It isn't Zod: the repo doesn't ship it, Zod is the generic example of runtime validation. If the backend changes its contract, your types update and the tests that assumed the old one fail at compile time, real traceability between contract and test. Makes the journey of an HTTP request tangible. Step 1: the request is built (POST verb + path + JSON body). Step 2: await sends it over the network and control PAUSES, waiting. Step 3: the server receives it, validates, writes to the DB and prepares the 201 response. Step 4: the response comes back and await resolves with the res object. ⭐ QUIZ 2 · Assertions

    
Your test does expect(res).toBeOK() and passes. But the body came back as { item: null, qty: -3 }. What went wrong in your test?

    

      
      
      
    

    
💡 toBeOK() only looks at the status. A 200 with garbage data passes just the same. A good API assertion covers all three layers: exact status, body (fields + types, ideally with a schema) and headers when the contract asks for them. No tool guesses which body is "correct": you define that.

  

  
It catches the false security of status-only checks. Option A is the central mental error of the act; C is the "let the tool think for me". Answer B reactivates the three layers. If most get it right, they have internalized that testing an API means verifying content, not just connection. Transition: "You know how to send and verify. But every test needs a logged-in user and prior data. Redoing that by hand for ONE endpoint is the next pain: data setup."

New pain: every test rebuilds its world 🔁

  

    

      
test("updates an order", async ({ request }) => {
  // 1 · log in to get a token…
  const auth = await request.post("/login", {data:creds});
  const { token } = await auth.json();

  // 2 · create an order so there's something to edit…
  const made = await request.post("/orders", {
    headers: { Authorization: `Bearer ${token}` },
    data: { item: "Coffee", qty: 1 },
  });

  // 3 · …and only HERE does the real test begin 😩
});

    

    

      
🧩 The symptom
Login + creating preconditions before every test. 15 lines of ritual for 3 lines of real testing.

      
🔑 The scattered token
The Authorization: Bearer header repeated on every call. Copy it wrong once and you get mysterious 401s.

      
💡 The idea
A fixture that logs in once, hands over an already authenticated client and fresh data, and cleans up at the end. What you saw with use(), now for API.

    

  

  
The pain connects straight to the fixtures session: API setup gets repeated too. Two faces: (1) authentication, getting the token and dragging it into every header; (2) preconditions, creating the order you are going to edit or delete. The idea is the same fixture with use() from the previous pattern, now preparing an already authenticated request + data. Stress the risk of the hand-made token: a badly copied Bearer gives 401s that look like backend bugs but are the test's fault. The solution: centralize auth and data in composable fixtures, exactly what KATA does in act 4.







  
requestassertionsschema · datakata

  
The cure: auth once + unique data per test 🔐

  

    

      
🔑 Authenticated client, ready to go

      
export const test = base.extend({
  api: async ({ playwright }, use) => {
    // log in ONCE, reuse the token
    const ctx = await playwright.request.newContext({
      baseURL: BASE,
      extraHTTPHeaders: { Authorization: `Bearer ${TOKEN}` },
    });
    await use(ctx);     // the test receives it already logged in
    await ctx.dispose();
  },
});

      
Every call now goes out with the token. Zero scattered Bearers.

    

    

      
🎲 Fresh data = independent tests

      
import { faker } from "@faker-js/faker";

// each test generates ITS own unique data
const order = {
  item: faker.commerce.productName(),
  qty:  faker.number.int({ min: 1, max: 9 }),
};
await api.post("/orders", { data: order });

      
🧱
Unique data = no test steps on another. It's the requirement for running in parallel without collisions.

    

  

  
The two pieces that tidy up API setup. Left: an api fixture that creates an APIRequestContext with the baseURL and the Authorization header already set (newContext + extraHTTPHeaders), so the token is resolved once and every call goes out authenticated. dispose() cleans up at the end. Right: faker for unique data per test. This is CRITICAL and connects to parallelization: if two tests create "Coffee" with the same fixed id, they collide; with faker each one has its own data and they are truly independent. Independence is the ticket to parallelism, which we measure in the next slide.

⭐ QUIZ 3 · Data and speed

    
Why should every API test generate its data with faker instead of using a fixed id like "order-1"?

    

      
      
      
    

    
💡 Shared fixed data = collisions: two tests create "order-1" and one breaks the other. Unique data per test = total isolation, and isolation is what lets you parallelize without flakiness. API speed only pays off if the tests don't get in each other's way.

  

  
It joins data (faker) with speed (parallelism). The answer requires understanding that independence is the condition for running fast. Option A underestimates it (it's a minor benefit); C invents an obligation. If they saw the speed jump in the simulator, here they understand the requirement that enables it: without independence, parallelizing multiplies flakiness, not speed. Transition to the closing: "request, assertions, data, speed… how does all this get organized at scale in the real repo? KATA, now from the API side."

KATA: everything in this session, organized in layers 🥋

  

    

      
KATA (Komponent Action Test Architecture) doesn't invent anything: it organizes the client, the assertions and the data into four named layers, plus optional Steps (TestContext, Base, domain Components and Fixtures), where each one extends the previous. The API side is identical to the UI side: only the base changes.

      

        
🎁 Client → Components
Your OrdersApi is a domain component. The API ATCs live there.

        
🎯 Assertions → inside the ATC
Fixed status and schema go inside; business ones go in the test.

        
🔧 Auth + data → Fixtures (L4)
{ api } hands over the authenticated client, ready to use.

      

    

    

      
// The REAL inheritance chain of the repo (API)

class TestContext { ... }        // L1 · drivers, config, DataFactory
class ApiBase extends TestContext // L2 · HTTP helpers
class OrdersApi extends ApiBase // L3 ⟵ your client

// and the fixture injects it:
class ApiFixture {
  orders = new OrdersApi(options);
}

      
🧬
Same architecture as the UI side: only ApiBase swaps for UiBase. Learn it once, apply it to both.

    

  

  
Thesis of the act: KATA is the synthesis of request + assertions + data in one structure. Map it explicitly: your OrdersApi client = component (L3), the fixed assertions live inside the ATC, and auth and data are injected by the { api } fixture (L4). The chain TestContext → ApiBase → OrdersApi is real and accurate (kata-architecture.md), and it's a MIRROR of the UI chain (TestContext → UiBase → LoginPage). A message that lowers the fear: the API side and the UI side share L1 (TestContext) and only differ in L2 (ApiBase vs UiBase). If you understood one side, you understand the other.

The new piece: the API ATC 🎯

  

    

      
class OrdersApi extends ApiBase {

  @atc("PROJ-201")
  async createOrder(data) {
    const [res, body] = await this.apiPOST("/orders", data);

    // FIXED assertions inside:
    expect(res.status()).toBe(201);
    expect(body.id).toBeDefined();   // contract: fields and types
    return [res, body];
  }
}

      
🧩
What about a GET? It's an ATC only if its response is the result you are testing (data, 401, 403, 404). If it only prepares data for another step, it's a helper (@step optional).

    

    

      
🎯 ATC = one complete case
Acceptance Test Case: a mini-flow rather than a loose call: request → fixed status → body shape → returns the tuple.

      
@atc("PROJ-201")
The decorator ties the ATC to its Jira ticket 1:1. Traceability and automatic tracing.

      
⚖️ Fixed inside, business outside
Status 201 and contract (always true) go inside. Business assertions go in the test.

    

  

  
The only truly new piece: the API ATC and the @atc decorator. Real code, a mirror of the repo's LoginPage. Define ATC: a complete case (request + fixed assertions + returns the [response, body] tuple so the test can carry on), not an isolated call. The FIXED assertions (expected 201 status, contract shape) live inside because they are part of "the action finished well"; the BUSINESS ones (is the total correct? does it show up in the user's list?) go in the test. It's the same actions-vs-decision rule as on the UI side. Hard rules: an ATC is atomic (it never calls another ATC; chains are Steps), and @atc gives 1:1 traceability with Jira.

⭐ QUIZ 4 · KATA

    
In a createOrder() ATC, which assertion goes inside the ATC and which in the test?

    

      
      
      
    

    
💡 Fixed, unavoidable assertions (a 201 on create, the contract schema) are part of "the action finished well", so they go inside. The business ones, which change per case (the total, the discount, who can see it), go in the test, in plain sight. Same rule as on the UI side: effects inside, verdict outside.
