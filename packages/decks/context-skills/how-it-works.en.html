Agentic QA · Skill category

<aspect>-context

The context skills: skills that change what the agent knows about one aspect of the product or the method, never what it does next. They arrive without anyone asking for them and are read in parts.

Frontmatter: metadata.kind: context Reading: bun run context:map Live list: REGISTRY.md
This deck explains the whole category, not one skill: why they exist, how they are built, how the map they carry is generated and maintained, who delivers them and how a project creates its own. Press → to advance, S for presenter mode, O for overview, F for fullscreen.

The principle · 2 of 17

A script fetches data; an AI synthesizes knowledge

The dividing line

.context/ holds what a script fetches from a source of truth, plus the little this repo owns. What an AI synthesizes lives in a skill.

Why a skill

That knowledge is authored (an AI writes it, but it is still written) and has to arrive without anyone asking. A skill loads itself through its description; a loose file in .context/ waits for someone to open it.

This is the three-question test from skill-scaffold.md §3. The Jira cache (.context/PBI/) is rebuilt with context:hydrate and is not versioned; an ADR belongs to the repo and is versioned. What falls outside both, the synthesis of the system under test and the judgment to read it, is the territory of the context skills.

The principle · 3 of 17

Facts in the map, judgment in the rules

The question

Would two competent sessions write it differently? Yes: it is judgment, and goes as a dated rule in ## Rules or in references/gotchas.md. No: it is a fact, and goes in the map (or the cache), never in SKILL.md.

Example of judgment

"Orders are soft-deleted: a count without deleted_at IS NULL is wrong." The map describes the table; the rule teaches how to read it.

Every rule, measured

date · rule · measured: how. No measurement, no rule: the idea goes to Engram.

Cite, never copy

A context skill that repeats a fact from .context/ is a second source of truth and fails review. It names the path or the command, and the reader goes to look it up.

The map is the only copy

The HTML map duplicates nothing: it is the only copy of that synthesis. The old markdown files are input to the generator.

Lint watches it

STALE-PATH is strict here: every cited .context/ path has to exist. Only .context/PBI/ is exempt.

Lint controls the "cite" half; the "don't copy" half is a review rule. That is why the map is born before the skill that cites it: a context skill built on nothing would become the source by accident.

How a context skill is built

--- name: <aspect>-context description: "Trigger: <aspect>, <domain words>..." license: MIT compatibility: [claude-code, codex, opencode, pi] metadata: kind: context writes: [references/] # only if it carries a map requires_capabilities: [diagrams] --- .agents/skills/<aspect>-context/ SKILL.md references/gotchas.md references/<map>.html # if it carries a map references/refresh.md # if it carries a map

Contract: agentic-qa-core/references/skill-scaffold.md §1, §2 and §4. KIND-SUFFIX requires the -context suffix for the context kind, and the other way around.

Required body sections

What this skill knowsa single aspect
Sources of truthwhat it cites, with its role
Rulesjudgment, every rule dated
Not herewhat belongs elsewhere

Write scope

metadata.writes exists only in a context skill and can only name its own references/. CONTEXT-WRITES controls it, and also requires refresh.md and forbids any Jira write tag.

gotchas.md follows the measured genre: columns # · Gotcha · Symptom · Fix · Measured · Verified against, and a "No longer true" section where rows that stop holding are moved, without deleting them. requires_capabilities declares what the skill needs when used: diagrams to redraw a figure, db or api-schema depending on the aspect.

The category · 5 of 17

Three families, one kind

With a map · delivered by upstream

They arrive as placeholders and each one keeps an HTML map of the system under test. The list is CONTEXT_MAP_SKILLS in cli/lib/context-maps.ts, with the generator for each map.

Any other <aspect>-context (a billing-context, an auth-context) belongs to the project by construction. Upstream never delivers it, never overwrites it, never deletes it.

The map · 7 of 17

An HTML with a contract the reader understands

<!-- generated by project-context mode data; edited in place by business-data-context refresh; do not hand-edit --> ... <section id="order-lifecycle" data-sources="src/orders/, db:orders" data-updated="YYYY-MM-DD"> <h2>Order lifecycle</h2> <p>...</p> <figure data-diagram="state" data-for="order-lifecycle"> <svg>...</svg><figcaption>...</figcaption> </figure> </section> ... <section id="discovery-gaps">...</section>

Before generation, line 1 says <!-- placeholder: ... -->. The reader, the updater and the doctor only look at that line.

Flat sections

One per unit of fact (an entity, a flow, a journey, a term, an NFR), never nested. The id does not change after CREATE. data-sources says where it came from: repo paths, db:, openapi:, route:.

The text rules

No fact lives only inside a diagram. diagram-design draws the figures (capability diagrams); if it is missing, work stops.

Last section

discovery-gaps: "I could not verify X" is worth more than an invented answer.

The head carries only inline styles, no external scripts, so the file opens from file://. A generated map can contain counts (rows per table, endpoints per group): it is a generated artifact, exempt from Rule #17 like every generated file.

Reading · 8 of 17

The AI never opens the HTML: it reads it through context:map

CommandWhat for
bun run context:map <slug>the whole map as text
bun run context:map <slug> --section <id>one section, when the work touches an entity, a journey or a term
bun run context:map <slug> --listthe index: id · date · sources, for a staleness check
## Order lifecycle <!-- id: order-lifecycle · updated: YYYY-MM-DD · sources: src/orders/, db:orders --> An order starts as a draft and ... [figure: state - Order states]

This is how a section prints (illustrative example).

A placeholder is not an "empty system"

It prints a notice with its generator and exits with code 0: treat it as "there is no map".

Why a reader

Inline SVG is almost all the bytes and none of the facts. scripts/context-map.ts strips SVG, styles, scripts and the head, and reduces each figure to one line. The AI pays only for the text.

A fact is cited with its section id and its data-updated date. A section older than the code it describes is a hypothesis to verify (against the DB, against the contract), not an answer.

Maintenance · 9 of 17

Is this section still current? data-sources answers it

Declared signalStale when
src/orders/there are commits on that path since data-updated (git log --since=<date> -- <path>)
openapi:<tag>the contract changed since the date (output of bun run api:sync, or the git log of the spec)
db:<table>a later migration, or the DB shows a column or constraint the section does not describe
route:<path>the route or page file changed
no sourcesreported as unknown, never silently as current

Two paths, never mixed

A section contradicted by something a session saw: the skill proposes the edit. Several stale, or an entity the map does not have: the generator in UPDATE regenerates only those and shows the diff per section.

Signals specific to the aspect

Each skill with a map adds its own in its references/refresh.md, which belongs to the project. For example, the data one adds cron:<job> and webhook:<event>.

The generic list of signals lives in business-context-maps.md §5, which is synced doctrine. refresh.md holds only what is specific to the aspect and belongs to the project.

The message, as references/refresh.md defines it.

Silence is not approval

Only a yes applies the edit. No evidence, no proposal. A single-turn subagent puts it in its report. A supervised worker sends it to the conductor, which holds the gate. A routine with nobody present puts the proposal in its report and applies nothing, unless the brief approves that exact edit.

Where it writes

Only under its own references/. Never Jira, never .context/, never another skill, never product code. And it never runs a stage of the process.

Step 4 in detail: re-read the section because another session may have edited it, edit that single section block, set data-updated to the date of the edit, add any new signal to data-sources and redraw the figure only if its facts changed. A judgment rule (not a fact) follows the same approval path into gotchas.md or Rules.

Loading · 11 of 17

Only the one for the aspect being touched arrives

In the main conversation

It fires on its description, even if nobody says "map": a question about an odd status code brings in the API one.

In a subagent

The Skill Resolver injects only the context skills whose aspect the dispatch touches, never all of them, and for a map it injects the command (context:map <slug> --section <id>), never the HTML path. With no aspect named, none.

Why it works this way

The map inside a delivered skill is the synthesis of that project: overwriting it in a sync would delete work that cost thousands of tokens. The rule lives in isProjectLocalSkillPath (cli/lib/updater-core.ts) and the one-time delivery exception in cli/lib/context-maps.ts.

The SUT context skills (billing-context, auth-context and similar) are never published upstream. Upstream only owns iql-context, the historical slug project-context (which is a workflow, not a context skill) and sync-ai-context, retired and kept so the updater can remove an old copy.

Analysis before writing

Read the whole source, list where a competent session would misread it (soft delete, derived fields, states the API and the UI name differently) and run each candidate through the three questions.

CREATE and UPDATE

If the folder does not exist, it writes it after the analysis. If it exists, it shows the diff and waits. Old rules are not rewritten: new dated ones are added, and a contradicted one moves to "No longer true".

What it does not create

A request for data-context, api-context, glossary-context or infra-context is answered by pointing to the skill that already ships, never with a second skill on the same aspect.

How to invoke

Claude Code: /project-context context-skill <aspect>. OpenCode and Codex: load the project-context skill, mode context-skill, and name the aspect. refresh-all never includes this mode.
Pi: /skill:project-context context-skill <aspect>

skill-creator is the builder of every skill this repo assembles: draft, test prompts in evals/evals.json and a pass over the description. If it is not installed on the machine, the mode builds the skill from the skill-scaffold.md §4 template and says so in the report, never silently. When what the skill cites is regenerated, the mode offers to run its UPDATE: it is the cheap moment to review the judgment. Contract: project-context/references/context-skill.md.

The method index · 14 of 17

iql-context: the method, as knowledge

What it knows

Why the QA process has the shape it has: phases, named stages (never numbered), the artifact ladder (from MTP to ATR), where each invariant applies and the agentic contract.

What it does not do

It never runs a stage (that belongs to the workflow skills) and knows nothing about the product under test.

Web and repo disagree

The skills apply the doctrine in agentic-qa-core/references/. This skill gives both readings and does not "fix" either one.

How a project adapts it (two seams)

SeamWhat goes there
.agents/project.yaml → qa.methodologyvalues: stages it runs, strict or light gates, execution profile
references/project-overrides.mdprose: a stage run differently, a renamed artifact, a collapsed gate, local vocabulary
The body and the other referencesnone: they are synced as is

What project-overrides.md says wins over the index, for that project only.

Of the context skills that come from upstream, iql-context is the only one with no map and no metadata.writes: it edits nothing of its own. It loads on questions like "why do we create one ATS per story?", "what is an altitude?", "what does light mode mean?". For questions about a single aspect of the method it loads only the reference for that aspect.

For people · 15 of 17

The same file, served to a person

No copy in docs/

bun run docs serves each map from its skill folder, under the virtual folder mapas-de-contexto/. The portal and the AI read the same file.

An ungenerated map

Shows up in the portal with the notice "Sin generar todavía: ejecuta" (Not generated yet: run) followed by that skill's generator.

No markdown twin either

There is no markdown version of the map: the twin is always the one that goes stale.

The local server is scripts/docs-serve.ts and it reads the same CONTEXT_MAP_SKILLS list. This published site does not serve the maps: they belong to the project that generated them, and live in its repo.

Safeguards · 16 of 17

What a context skill never does

C1Read the raw HTML map: always through bun run context:map.
C2Answer about a placeholder as if the system were empty.
C3Regenerate a whole map, or rewrite a section nobody contradicted.
C4Change a section id: a renamed entity is a new section plus a line in discovery-gaps.
C5Copy content from the map or from .context/ into its SKILL.md.
C6Write outside its own references/: no Jira, no .context/, no other skill, no product code.
C7Apply an edit without an explicit yes, or propose it without measured evidence.
C8Take a section older than the code as an answer: it is a hypothesis to verify.
C9Publish a context skill of the system under test upstream.
C1, C2 and C8 protect the quality of what the AI answers; C3, C4 and C7 protect the map; C5, C6 and C9 protect the separation between sources. The numbering belongs to the deck, not to the doctrine.

Close · 17 of 17

Where to read more and who feeds whom

How they are used

They are not invoked like a workflow: they load themselves through their description in each host. To ask for one by hand, in Claude Code /<aspect>-context; in OpenCode and Codex, load the <aspect>-context skill; in Pi, /skill:<aspect>-context. They have no modes.

Who writes their maps

/project-discovery: the domain one (Phase 1) and the infrastructure one (Phases 2-3).
/project-context: the data, API and E2E ones (modes data, api, e2e), and the new skills (mode context-skill).

Who reads them

The workflow skills and their subagents, every time they touch the aspect: /shift-left-testing, /sprint-testing, /test-automation, /test-framework-adaptation and the rest, according to the Skill Resolver.

The canon

agentic-qa-core/references/skill-scaffold.md §3 (the principle) · business-context-maps.md (the map) · skill-resolver.md (who loads them) · cli/lib/context-maps.ts (the list) · scripts/context-map.ts (the reader) · .agents/skills/REGISTRY.md (all skills).
