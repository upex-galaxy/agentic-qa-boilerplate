/session-handoff

When the context window fills up, the session is compacted into a file and a new session picks up exactly where it left off. For you, it is as if the window had been stretched instead of reset.

Manual trigger, by design File in <<PRIMARY_ROOT>>/.session/handoffs/ Same worktree, same harness
Deck for the session-handoff skill. The core idea: a handoff is transplanted context, not a summary. The successor is not a reader being told about someone else's work: it is this session, with a fresh window. Press → to advance, S for presenter mode, O for overview, F for fullscreen.

Shrink the window and carry onHarness compaction: lossy, not addressable, not under your controlnothing to do

The difference that matters: compaction keeps what a summarizer judged relevant. The handoff keeps what the next session needs in order to act, and it is written by the only part that knows the difference.

The "What this is not" table from SKILL.md. It is also not used for a one-off subagent dispatch. If you want to keep working yourself while someone else does a part, that is orchestration, not handoff.

The skill is small on purpose: the heavy artifact is the markdown it produces. The file is written in full before the successor is launched; a successor that starts first reads a file that does not exist yet.

Trigger · 4 of 13

Triggered by the human, when needed

Write one when

  • The window passed the owner's threshold: about 500k tokens unless they name another, because beyond that the model degrades and starts making things up.
  • The session is about to end with work in progress.
  • What comes next will eat a large share of the window (a long read, a big harvest) and what is left will not cover the work after that.
  • The owner asks for it.

Manual is the primary trigger

The human sees the window filling, says so, and the skill runs. No polling, no nagging, no tokens spent guessing.

Do not write one

If what remains fits comfortably in the window. Producing a handoff costs a real slice of context, and a successor launched too early pays the startup cost for nothing.

The threshold is yours

It is the owner's judgment about where this model degrades, not project configuration: it lives in the conversation, never in a yaml key.

Phrases that trigger it: "hagamos el handoff" (let's do the handoff), "pasa el contexto a otra sesión" (pass the context to another session), "continúa esto en otra sesión" (continue this in another session), "hand this session over", "write a handoff".

Trigger · 5 of 13

Can it trigger itself? Partly

No harness hands the agent the current context size. Claude Code, OpenCode and Pi expose it outside the model loop: an automatic mode would be new wiring, not a field waiting to be read.

HarnessBest available signalWhat it carries
Claude Codethe JSON the status line receivescontext_window.used_percentage and the window size
OpenCodea plugin subscribed to message.part.updatedtokens.input / tokens.output of each step-finish, summable
Codex CLIonly the PreCompact eventno number; the window is already full
Pian extension, with ctx.getContextUsage()the current context usage, from any event

Compaction is the wrong moment

All of them warn that compaction is imminent, but by then the window is already spent: the handoff would be written by a session about to be truncated, with the degraded judgment the handoff exists to escape.

If it is ever enabled

It asks once, in two lines, and accepts a no without asking again in that session. It never writes a handoff unless asked.

Full verdict, with sources, the verification date and the version of each harness: references/auto-trigger.md. Read it before promising the owner an automatic mode. The owner's position is recorded there: they prefer the manual trigger.

Step 1 · Capture · 6 of 13

The file opens with one task

Every section is mandatory and in this order. An empty section is written as a none line with its reason: omitted and forgotten look the same, and the successor cannot ask which one it was.

§SectionWhat it prevents
0Your first task. Just one, not a menu. Owner's criteria quoted, numbered.a successor that re-decides what was already decided, and chooses differently
1Identity and authority. What the owner delegated and what they kept; harness, worktree, label, push policy with its resolved value.re-asking what was delegated, or assuming an authority it does not have
2What was built. One paragraph per unit, with SHAs, PRs and paths; what is pushed and what is local only.redoing work that was already finished
3Decisions with their why. Discarded alternatives and who decided.reverting a deliberate choice believing it was an oversight
4Gotchas and observations. Each one measured or read, with the version or date it holds for.paying the same cost twice; it is the most valuable section and the one written thinnest
The order is not decorative: the successor reads top to bottom in a hurry, so the file opens with the one thing to do and closes with what is always valid. Full contract: references/capture-contract.md.

Step 1 · Capture · 7 of 13

And it closes with what is always valid

§SectionWhat it prevents
5Skills, tools and MCPs used. Table with the Load next session? column answered per row, with a reason.reloading everything (and burning the new window) or loading nothing (and guessing syntax)
6Files to read, in order. Absolute paths, what each one is for, which sections.turning the reading into a search problem that is already solved
7Live state you inherit. Running workers, mailboxes, PRs in flight, runs. Everything marked PERISHABLE.acting on a world that has already changed: this is where handoffs break
8Pending items in priority order. What the owner already decided, separate from what awaits their decision.starting with what is interesting instead of what is important
9Owner conventions. How to present decisions, language, register, memory; and the threshold for the next handoff.relearning preferences by getting them wrong first

§9 closes the lineage: it tells the successor at what threshold to write its own -handoff-NN+1 and launch its own successor. If it does not perpetuate itself, the lineage ends at the first session that forgets.

§7 has its own rules: each item with the wall-clock time it was measured, marked PERISHABLE, with the exact command that re-verifies it, ids copied verbatim, and unobserved branches labeled predicted. Before writing §7 everything is re-verified: a measurement from an hour ago does not belong in a section whose purpose is to be fresh.

Step 1 · Capture · 8 of 13

Every claim says whether it was measured

measured / read / predicted

Measured: this session ran it and read the output. Read: it came from a document and was believed. A predicted branch counted as fact sends the successor down a path that no longer exists.

PERISHABLE + time

Whatever decays between writing and reading carries the time it was measured. The instruction is to re-verify and then act, never the other way around.

Perishable before priority

If a live item needs attention before the priority list, it says so on the same line. A waiting worker cannot wait for the §8 order.

Copied ids

Run, dispatch, terminal, session, PR, tracker key, SHA: verbatim, in backticks, ready to paste. "The worker from before" is not an id.

Absolute paths

The successor may start in another directory.

What is not done

With its reason. A handoff that reads like a flawless success hid something, and what is hidden is what bites.

Hard rules 1 to 6 of SKILL.md. They all point at the same thing: that the successor can trust the file without having to reconstruct what was certain and what was a guess.

Step 2 · Write · 9 of 13

One file in the primary

Name

<predecessor-session>-handoff-NN.md. The successor's name is that file without the extension: that is the whole rule. The predecessor's name comes from the session= of the AGENT IDENTITY: line the hook injects; if it says unknown, the owner is asked for a name.

NN

Two digits starting at 01. The primary's directory is listed before choosing: it is never assumed, never counted from a worktree's .session/.

Disposable

.session/ is in gitignore: a handoff describes a session, it is not a project record. It is written in English and the previous one is not deleted. One written by mistake inside a worktree is rescued by bun run worktree:audit --rescue before the worktree is deleted.

Both variables are defined in .agents/README.md, section "Checkout roots". A durable fact that outlives the session does not go in the handoff: it goes to Engram, the repo or the tracker, and the handoff cites it. Before deleting a worktree, bun run worktree:audit lists what it still holds, and with --rescue it copies to the primary the handoff that was written inside it.

Step 3 · Launch · 10 of 13

File first, then the successor

With a reachable runtime

Before launching it verifies three things: the binary is present and the runtime responds; the file exists in full at its final path; the target is the same worktree and the same harness.

Then it opens a terminal in that worktree with the launch line of the harness (Claude launches Claude, OpenCode launches OpenCode, Codex launches Codex, Pi launches Pi), with the successor's name and a first prompt.

It announces it before firing it and tells you which terminal carries it: a second session will show up on your board. A supervised worker launches on its own only if its conductor's brief says so; a routine, only if its brief names handoff and launch. Without that it writes the file, prints the line and stops.

Without a runtime

Everything is the same except who opens the terminal: it prints the line, says where the file is, and you paste it. The prompt is byte-for-byte identical: the path nobody exercises is the one that breaks silently.

The first prompt

Read `<absolute path to the handoff>` top to bottom and continue that session exactly where it stopped.

If §0 requires an order, it is repeated in the prompt: a pointer to a file reads as a reference; an instruction in the prompt reads as an instruction.

The command grammar is not copied into the repo: the binary is asked for its own CLI guide when needed, because a copy drifts out of sync with the next version. The "binary present and runtime reachable" gate is the same one /orca-orchestration uses. Full mechanics: references/successor-launch.md.

Limits · 11 of 13

A handoff is not orchestration

Handoff (esta skill)Orchestration (/orca-orchestration)Memory (Engram)
What movesthe whole sessiona scoped taska durable fact
The one that originates itfinisheskeeps working and supervisescarries on as before
Channel afterwardsnone, by designmailbox, questions, answerssearch in later sessions
Runtime objectsone terminalRun, Task, Dispatch, workernone

The typical mistake

Using the orchestration verbs to launch the successor creates a supervised worker that you then have to release and close, for no reason. The right family is terminal and worktree.

And it is not a briefing

A 7-component briefing scopes a task; a handoff transplants a session. What is durable still gets saved to memory at the end, because the handoff is disposable and memory is not.

If you want orchestration in detail, it has its own deck: ../orca-orchestration/how-it-works.en.html. The handoff and orchestration columns come from references/successor-launch.md; the memory one, from the "What this is not" table of SKILL.md.

Safeguards · 12 of 13

What the skill never does

RuleWhy
Launch the successor before writing the fileit would start by reading a file that does not exist
Switch harness between predecessor and successora handoff built for one agent's conventions is a translation problem for another
Delete the previous handoffthe lineage is the audit trail
Close its own terminalending the predecessor is the owner's decision; if it closes itself it cannot report that the handoff failed
Write a handoff unpromptedthe timing is a judgment about the work, and that judgment belongs to the human
Write secrets into the fileit names the variable where a credential lives, never its value; a cookie, a token or the path of a file in .auth/ stay out (Rule #1)

Closing · 13 of 13

Invocation and where to read more

How it is invoked

Claude Code: /session-handoff.
OpenCode and Codex: load the skill session-handoff.
Pi: /skill:session-handoff

On every host it is also triggered by phrases like "hagamos el handoff" (let's do the handoff) or "pasa el contexto a otra sesión" (pass the context to another session). It has no modes.

What it reads

Its capture contract and its template · the primary's .session/handoffs/ directory, to choose NN · .agents/README.md, "Checkout roots".

What it leaves

A <session>-handoff-NN.md in the primary · a successor session in the same worktree and harness · what is durable in memory via mem_session_summary.

Canon

.agents/skills/session-handoff/SKILL.md and its references: capture-contract.md (the sections), successor-launch.md (the launch), auto-trigger.md (what each harness exposes), templates/handoff.md (the skeleton).

Related: /orca-orchestration for delegating a task and supervising it · agentic-qa-core/references/session-footer-contract.md for what a session reports when it closes.

End of the tour. The map on slide 3 sums it up: capture, write and only then launch. If the window still has room for what is left, the best decision is not to write the handoff.
