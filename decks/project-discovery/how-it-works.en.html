Decide · 2 of 15

Is this a project QA does not know yet?

Use it for

  • Starting with a new product: "set up this project", "onboard this repo", "connect to project".
  • Discovering the architecture from the code: "discover architecture".
  • Adopting this boilerplate to test an app.
  • Filling gaps in an already documented project.
  • Refreshing its two maps, section by section.

Not for this: go to

Data map, API map or E2E map, or the Master Test Planproject-context
Adapting KATA to the project's stack/test-framework-adaptation
Writing automated tests/test-automation
Documenting cases in the TMS/test-documentation
Running suites/regression-testing
Exact API types from OpenAPIbun run api:sync

A "future" PRD or SRS is not for this either: that is creating product, and discovery only describes what already exists.

The boundary with project-context is the one people confuse most. project-discovery generates only two maps: the domain map and the infrastructure map. The data, API and E2E maps and the master test plan are project-context modes, and project-context owns its own diff and its own approval.

Before Phase 1 · 4 of 15

First, where the code is and where the session was left

The target repo (never this boilerplate)

LayoutWhat gets declared
MonorepoOne path. Detected by pnpm-workspace.yaml, turbo.json, nx.json, lerna.json or a root package.json with no dependencies of its own.
Sibling reposOne path per repo. Phase 1 runs once per repo and everything merges into one project-config.md, with no interleaving.
RemoteURL and branch, and it asks you to clone it. Nothing can be discovered from a URL: it needs the code on disk.

If the path is ambiguous, Phase 1 stays blocked until it is resolved.

Phase 0 · resume

If .session/project-discovery/progress.md exists, it shows you the scope, the repo, the last closed phase, the next one and the open gaps. You choose resume, restart or abort.

Why it matters

A full onboarding takes hours. Without resuming, the next session redoes Phase 1 and asks you again for paths you already confirmed. restart archives the previous run in .session/.archive/.

The resolved path is recorded in the Repositories section of .context/project-config.md during Phase 1, and every later reference to the target repo points to that path.

discovery-gaps

No sub-step starts until the output of the previous one exists. Steps 3 and 4 write the business-domain-context map.

One question at a time

First the repo, then the stack, then the environments. It detects what it can from package.json, .env.example or the workflows before asking you.

HIGH risks

No tests, or a hardcoded secret: a row in ### Identified Risks, with the path, never the value. They travel to the closing step as the seed of the Master Test Plan.

Gate

bun run context:map business-domain-context --list shows sections and no placeholder warning, project-config.md has ## Tech Stack and ## Environments, and you say "Phase 1 complete, continue".

The assessment uses simple scales: testing maturity from 0 to 4, documentation status and CI/CD maturity. No separate risk file is written. If no tests, hardcoded secrets and no CI show up together, progress stops: the secrets must be dealt with and the assessment redone before Phase 2.

Phase 1 · 7 of 15

The domain map: the vocabulary of all QA

One term-<slug> section per entity (example)

Business name | Code identifier | UI label | Table | Found in Customer | user | Cliente | users | prisma/schema.prisma Purchase | order | Compra | orders | prisma/schema.prisma

That row is the bridge between how the code talks and how the business talks. The labels come from the shipped i18n files, not from the JSX.

Attributes, relationships and states do not go here: the section points to business-data-context or leaves the gap while that map is a placeholder.

business-model

The Business Model Canvas as a Block | Finding | Found in | Confidence table. A block with no evidence says "Unknown" and goes to discovery-gaps. Marketing copy lowers the confidence.

Who uses it

/sprint-testing loads it to plan the ATP and the cases; /test-documentation, to name the TCs. That is why the glossary is never skipped.

Schema before ORM

If there are both migrations and ORM models, the migrations win: the ORM drifts from the live schema.

The table values are illustrative (the skill uses user as Customer and order as Purchase for the example). Every core entity of the schema has its own term- section, and every enum has its table in enumerations, with the constant value from the code and not free text.

Phase 2 · 8 of 15

Architecture: how it is built, read from the code

infra-context sectionWhat it holds
overviewPattern, stack table, deploy shape.
architectureComponents, data flow, login flow, database at the architecture level, security. It usually carries the main figure.
external-servicesThird-party services, their integration point and the name (only the name) of their environment variable.
nfr-<slug>One per category with evidence: nfr-performance, nfr-security, nfr-reliability…

The API is not documented here

It only records where the spec lives in project-config.md. The types belong to bun run api:sync; the business angle, to project-context in api mode.

Numbers with evidence

"P95 < 500ms" with no test behind it is a gap, not a requirement.

ADRs

A decision that passes the three tests (hard to reverse, surprising without context, real trade-off) becomes .context/ADR/ADR-NNNN-<slug>.md, in Proposed. You are the one who accepts it.

Gate: bun run context:map infra-context --list shows architecture and at least one nfr-, the API contract source is in project-config.md, and you say "Phase 2 complete".

Examples of test-architecture decisions that often pass the three tests: runner, isolation, fixtures and data, auth in tests, selector contract, CI sharding. Personas, journeys and functional specs are not part of this phase either: project-context in e2e mode builds them. If there is no OpenAPI spec, it is noted in discovery-gaps and running project-context in api mode is recommended once discovery ends; an API contract is never written by hand.

Phase 3 · 9 of 15

Infrastructure: so the project runs for testing

First, the system's /qa page, if it publishes one

It is read first, before detecting the stack. It is a hint: every fact is checked against the code and configuration the phase reads anyway, and if they disagree the code wins and the disagreement goes to discovery-gaps. No value is copied into a versioned file. If the page does not exist, that is not a discovery gap.

backend

Runtime, scripts, dependencies, environment variables (required, optional, from external services), database and migrations, local install and start recipe, and the real login flow: endpoint, payload, what it returns and where the session lives.

frontend

Build and output mode, public variables (a secret with a public prefix is a security finding), routing, state, auth client and the test ID strategy, with data-testid as the preferred one.

environments

Environment matrix (URL, branch, auto-deploy, approval), variables per environment, where secrets are stored (never their values), monitoring and how rollback is done.

ci-cd

Workflows, triggers, deploy, IaC or "Not present", and the exact commands CI runs: they win over the local scripts, which can drift.

It detects and then confirms: it never asks you "what stack is it?". With docker-compose.yml, the service inventory comes from there before the code.

In a monorepo it runs per package (backend-<pkg>, frontend-<pkg>); environments and ci-cd stay at project level. Gate: the four sections listed and your "Phase 3 complete".

The backend login flow is the most important input for test-framework-adaptation: it gives it a concrete contract for test authentication. If the project has no test framework at all, it is documented as a gap and nothing is installed in the target repo.

Maps · 11 of 15

A map is HTML inside its skill

Where it lives and how it is read

.agents/skills/<slug>/references/<map>.html, with no copy in .context/ and no markdown twin. It is read with bun run context:map <slug> (or --section <id>, --list), never the raw HTML. bun run docs shows it under "Context maps".

Old markdown

The legacy .md files in .context/ are read as input and cited in data-migrated-from. They are never deleted.

Figures

Made with the diagram-design skill (diagrams capability). If it is missing, it stops and tells you how to install it.

Each section of the map is a flat section with a stable id, data-sources and data-updated; the last one is always discovery-gaps. The freshness check looks at whether the data-sources paths had commits since data-updated, and whether the API contract or the schema changed. A section with no sources is reported as unknown, never as fresh.

Safeguards · 12 of 15

What it never does

#Rule
1Invent entities, flows or requirements that are not in the code or the PRD. Anything unverified goes to discovery-gaps.
2Skip Phase 1 on a start from scratch: everything that follows is left without a base.
3Fill in the data, API or E2E maps. It only generates business-domain-context and infra-context.
4Mix with test-framework-adaptation in the same session: their write limits are different.
5Refresh another skill's maps. Only its own, section by section, never whole.
6Skip the glossary: /sprint-testing and /test-documentation load it as a precondition.
7Invent Jira / Xray field IDs or statuses: they are synced with bun run jira:sync-fields --force and cited as {{jira.<slug>}}.

Target repo untouched: it writes and installs nothing there.

No secrets: it names the .env key or the path, never the value.

No auto-chaining: each phase waits for your confirmation.

The compact rules from SKILL.md. With nobody present (a routine), the skill does the reversible work, stops at every phase gate, leaves ADRs in Proposed and never applies an UPDATE diff. Before using a declared capability (db, api-schema, diagrams) it runs the check at the point of use: if no available tool provides it, it stops and names the capability and how to enable it, without silently falling back to another tool.

Inputs and outputs · 13 of 15

Reads a lot, writes in few places

Reads

  • The target repo: code, README.md, PRD if there is one.
  • What has already been discovered: bun run context:map <slug> --list, .context/project-config.md, legacy markdown.
  • .agents/project.yaml and .env.example.
  • kata-manifest.json, to record the gaps consistently.
  • The database (read-only) and the OpenAPI spec, if present.
  • Business docs you hand it (Confluence, Notion, wikis).

Writes only

  • .context/project-config.md
  • The ## Project Assessment (Phase 1) block of .agents/instructions/agent-project.md
  • .context/ADR/, in Proposed
  • The business-domain-context map and the infra-context map

And its own state

.session/project-discovery/plan.md and progress.md, one entry per closed phase. When Phase 4 ends they are archived.

Capabilities declared in the frontmatter: db, api-schema and diagrams, each with its check at the point of use. Database queries are read-only during discovery. If the session is rejected at a gate, it is not archived: it stays ready to resume from that gate.

Handoff · 14 of 15

When it ends: the next step and what it proposes

Next skill, in a clean session

project-context in refresh-all mode: data → e2e → api → test-plan, each with its own approval. The HIGH risks from Phase 1 go as the seed of the Master Test Plan.

Proposes criteria, does not write them

One line for each context skill that has a map: the criterion a session would need (a term the team and the code name differently, a behavior that only happens in one environment). It becomes a dated rule only on an approved map. "No candidate yet" is a valid answer.

Proposes other context skills

Aspects of the project that deserve their own <aspect>-context. project-context in context-skill mode creates them afterwards, with skill-creator.

Closing · 15 of 15

Invocation and handoffs

How to invoke it

Claude Code: /project-discovery.
OpenCode and Codex: load the project-discovery skill.
Pi: /skill:project-discovery

It has no modes: the scope is chosen in the conversation. It also activates with "onboard this repo" or "set up this project".

Before and after

/agentic-qa-onboard sends you here for a new repo.
Afterwards: project-context (refresh-all) and then /test-framework-adaptation.
If you ask why the process has this shape: iql-context.

Who consumes the maps

/sprint-testing: plans with the glossary.
/test-documentation: names the TCs.
/test-framework-adaptation: takes the login flow and the stack.

What the skill leaves behind

.context/project-config.md · the assessment in .agents/instructions/agent-project.md · the domain map and the infrastructure map, readable with bun run context:map · ADRs in Proposed · an honest list of discovery-gaps · the verified backlog.

Canon: .agents/skills/project-discovery/SKILL.md and its references/ (one per phase). Anatomy of the maps: agentic-qa-core/references/business-context-maps.md.

End of the walkthrough. The map on slide 3 sums it all up: resume if there is a session, pin down the repo and the scope, go through the phases with your confirmation and hand the rest to project-context in a new session.
