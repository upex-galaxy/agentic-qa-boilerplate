Capítulo 06

La estrategia: cuatro suites, cuatro preguntas

Un solo workflow que corra «todos los tests» contesta todo tarde y mal. Cada suite existe porque hay una pregunta distinta, con una urgencia distinta y un costo distinto de respuesta.

La regla que nace de la tabla

Smoke habla del build de la app; sanity habla del cambio; regression habla del producto entero. Tres pass-rates distintos con tres SLOs distintos: nunca los sumes en un número (regla R6 de /regression-testing). Y build no habla de la app en absoluto: habla de nosotros.

La secuencia clásica de la industria es smoke → sanity → regression como gates sucesivos: si smoke falla, no gastás la regresión. En este repo los gates son temporales (cron) y manuales; conectarlos al deploy de la app es el Capítulo 9.

Tabla maestra. Pirámide de suites. Regla R6: no mezclar pass-rates. Referencia a la secuencia smoke→sanity→regression de la industria.

  • Contesta «¿este PR rompe el framework?». Un test que no compila no falla: no existe. Por eso playwright test --list es el step clave: compila cada spec sin ejecutarlo y sin credenciales de app.
  • Mismo orden que la Rule #7 del repo: tests (compilación) → types → lint. Lo que corrés en local antes de commitear, corre aquí antes de mergear. Sin sorpresas.
  • El gate de varlock (L40-44) va primero, antes de bun install: valida que el bloque env del job cumpla .env.schema. Un PR de fork no tiene secrets y muere aquí en 5 segundos, con un summary redactado en vez de un stack trace.

  • 15 minutos de timeout, el más corto de los cuatro: si tarda más, algo está mal en la máquina, no en el código.

Lo que NO hace, a propósito

No corre ni un test contra staging. Correr la suite en cada PR costaría minutos y credenciales por cada push (incluidos forks, que no las tienen) y mezclaría dos preguntas: «¿compila?» con «¿la app funciona?». La segunda se contesta con sanity, a demanda.

build.yml: gate de PR del framework. varlock primero, tests→types→lint, playwright --list. No corre tests contra la app, con justificación.

smoke.yml: ¿la app está viva?

smoke.yml L99-100 · playwright.config.ts proyectos smoke-*real

100        run: bun run test:smoke

# package.json

# playwright.config.ts (comentario del bloque smoke, resumido)
# Smoke Tests - @critical tagged tests, ONE PROJECT PER SURFACE
# smoke-ui  == e2e + @critical
# smoke-api == integration + @critical
{ name: 'smoke-ui',  grep: /@critical/, … }
{ name: 'smoke-api', grep: /@critical/, … }

Por qué dos proyectos y no uno

El comentario del config lo cuenta: un solo proyecto smoke que abarcara e2e + integration tenía que elegir UN bloque use, y eligió el de UI, que le pasaba una sesión de navegador (con cookie) a los tests de API. Un test que esperaba 401 sin token recibía 200. Un proyecto no puede cargar el auth de dos superficies. Se partió en dos que reflejan exactamente a sus suites completas más el grep.

  • El tag decide el alcance. Un test entra en smoke por llevar @critical en su título, no por estar en una carpeta. El mismo tag alimenta el label suite de Allure: una sola taxonomía para CI y reporte.
  • Un job de suite, un job de reporte. Sin integración-primero: los críticos de API y UI corren juntos porque el objetivo es velocidad, no diagnóstico.
  • Cron a las 02:00 UTC: después del deploy nocturno. También a mano tras cualquier deploy: «¿seguimos?».
  • Nunca escribe en la ejecución de regresión. El secret STP_EXECUTION_KEY no se lee aquí (L58-64): un smoke que importara al RTR voltearía Test Runs que pertenecen a un veredicto de regresión completo. Solo importa si le pasás una execution_key explícita.
  • Criterio de tamaño (industria): smoke debería ser menos del 5% de la regresión y terminar en minutos. Si tu smoke tarda 20, es una regresión disfrazada.
smoke.yml: @critical, dos proyectos por bug real de auth compartido (comentario del config), cron 02:00, no importa al RTR sin key explícita.

Nota de seguridad (mejora pendiente, no un bug funcional)

Este step interpola inputs directamente dentro de run: y los pasa por eval. La guía de seguridad de GitHub recomienda no hacerlo: un input es texto controlado por quien dispara, y la forma segura es pasarlo primero a una variable de env: y leerla como "$GREP". Aquí el riesgo es bajo (solo quien tiene permiso de dispatch en el repo puede escribirlo), pero al escribir el tuyo, usá el patrón seguro del Cap 10.

sanity.yml: inputs y precedencia; uso canónico; nota honesta de hardening: interpolación de inputs en run + eval, docs recomiendan env intermedio. Etiquetada como mejora pendiente.

build.yml
solo, automático en el PR
No hacés nada: se dispara solo. Si queda rojo, el PR no se mergea.
smoke.yml
@critical · 2-5 min
gh workflow run smoke.yml -f environment=staging. Verde = seguimos. Rojo = avisar antes de que el equipo pierda la tarde.
sanity.yml
un archivo o un grep
-f test_file=… para tu test nuevo; -f grep="@checkout" para el área del fix. Pequeño, dirigido, con reporte propio.
regression.yml
todo · 20-60 min
Antes del release: /regression-testing crea el RTR y dispara con -f execution_key=<RTR>. Un re-run por ENVIRONMENT antes del veredicto reutiliza el MISMO RTR.
Sanity con test_file. Es exactamente su propósito declarado (L4-5: «Useful for validating new tests in CI before merging PRs»). No dispares la regresión para un archivo: 40 minutos para una respuesta que sanity da en 3.
Smoke. La pregunta es «¿está viva?», no «¿está perfecta?». Solo @critical: login, el flujo de negocio principal, la API respondiendo. Si pasa, el equipo sigue; si no, nadie pierde la tarde probando sobre una app caída.
Regression, vía el skill. El veredicto necesita un run record (RTR) creado ANTES del trigger para que CI importe ahí. Lo hace /regression-testing: crea el RTR, dispara con execution_key, persiste el RUN_ID y luego clasifica. Deck how-it-works para el resto.
Sanity con grep. -f test_type=e2e -f grep="@checkout" corre solo los tests etiquetados. Reporte en /staging/sanity/ (o el custom_allure_url que elijas, p.ej. checkout-fix).
Build, sin hacer nada. El PR dispara build.yml solo. Si además querés ver tu Page refactorizada funcionando, sanity con el archivo que la usa. Nunca los dos en el mismo workflow.
Regression sobre el mismo RTR. Un fallo de entorno antes del veredicto no abre un nuevo RTR: se re-dispara con la misma execution_key. Un RTR nuevo (#2) solo después de un veredicto ya escrito.
Decisor de suite: 6 situaciones → 4 suites, con el comando gh. Escenario 6 refuerza la regla de un RTR por veredicto.

quiz 06: estrategia

¿Qué suite y por qué?

Q1El PM pide «un solo número de calidad» sumando los pass-rates de smoke (98%) y regression (91%). ¿Qué respondés?
A94.5%, promedio simple
BSon suites con preguntas y SLOs distintos: se reportan por separado; el veredicto de release sale solo de regression
C98%: smoke es la que importa para el release
Por separado. Smoke mide «¿está viva?» sobre 5% de los tests; regression mide «¿se rompió algo?» sobre todo. Promediar esconde el 91%, que es el que decide (regla R6: never mix smoke + regression into one pass-rate). El deck how-it-works cuenta cómo el 91% se convierte en CAUTION.
Q2¿Por qué build.yml corre playwright test --list en vez de playwright test?
APara ahorrar minutos: es un atajo temporal
BPorque su pregunta es «¿compila la suite?», no «¿funciona la app?»: lista = compila todo sin ejecutar ni necesitar la app
CPorque los PR no tienen browsers instalados
Pregunta distinta. --list carga y compila cada spec: si un import está roto o un tipo no cierra, falla ahí, sin credenciales de app ni browsers. Ejecutar la suite en cada PR mezclaría el estado del framework con el estado de staging, y haría que un PR de fork (sin secrets) fallara por motivos que no son suyos.
Q1: no mezclar pass-rates (R6). Q2: --list = compilar sin ejecutar; separación de preguntas.

Dos que prueban, dos que cuentan

Los dos primeros ejecutan Playwright y suben evidencia. Los dos últimos no prueban nada: consumen los artifacts para producir el reporte (humanos) y la importación (TMS). Por qué un solo reporte

El veredicto es sobre el producto, no sobre un job. Un PM que abre dos reportes tiene que sumar mentalmente; uno solo con la pestaña Graphs (pirámide de testing, severidades, tendencia) contesta solo. Y la historia de tendencias (history.jsonl) se lleva por {env}/{suite}: dos reportes serían dos historias.

Merge: cp -r de dos carpetas de allure-results; continue-on-error en descargas; merged re-subido para el agente; alternativa pattern+merge-multiple.

Fase 3 del skill
  • Por qué antes. El import de Xray solo escribe dentro de una Execution que ya existe. Si le das solo el proyecto, acuña una Execution nueva y sin padre en cada run (comentario L451-453). Crearla antes garantiza padre, plan y dueño.
  • Un RTR por veredicto. Re-run por fallo de entorno antes del veredicto → misma key. Re-run después de un veredicto → RTR nuevo (#2). Nunca se reabre uno cerrado.
  • El secret es el fallback del cron. Un run programado no tiene inputs; STP_EXECUTION_KEY como secret le da destino. El nombre quedó por compatibilidad; la semántica cambió (L66-76).
  • Smoke y sanity no leen el secret (smoke L58-64): importar el subconjunto @critical en el RTR voltearía Test Runs que pertenecen a un veredicto completo. Solo importan con key explícita.
  • Nunca la key del RTP/STP. Un Test Plan deriva su estado de sus Executions; escribir en él es un error de modelo (L72-73).
  • STR solo al cierre de sprint: entonces la key es la del STR, con doble membresía STP + RTP. Un run regular nunca es el STR.
Flujo de 6 pasos del write-back. Reglas: RTR antes, uno por veredicto, secret = fallback cron, smoke/sanity no leen el secret, nunca RTP/STP, STR solo cierre de sprint.

el problema y las tres formas de resolverlo

De «corre a las 00:00» a «corre cuando la app se despliega»

Hoy

La app despliega a staging a las 22:00; nuestra regresión corre a las 00:00. Si el deploy fue a las 00:30, probamos la versión vieja. Y producción no espera a nadie: el deploy a prod es una decisión humana sin gate automatizado de QA.

Objetivo

Deploy a staging → smoke (inmediato) y regression o sanity del área → el resultado vuelve al commit de la app → deploy-production solo arranca si el gate está verde, con un revisor humano vía environment: production.

El obstáculo: dos repos

El GITHUB_TOKEN de un workflow no dispara nada en OTRO repo, y los eventos de la app ocurren en la app. Cruzar la frontera exige uno de los tres mecanismos, y un token con alcance (PAT fine-grained o GitHub App) en los dos primeros.

Lo que cambia en el write-back
Un run disparado por la app no pasa por /regression-testing, así que nadie creó el RTR antes.
