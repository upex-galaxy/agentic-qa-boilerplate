Chapter 06

The strategy: four suites, four questions

A single workflow that runs "all the tests" answers everything late and badly. Each suite exists because there is a different question, with a different urgency and a different cost of answering.

Build ≠ Smoke ≠ Sanity ≠ Regressiontrigger, scope, duration and what it gateswhen to run which
Ch 6. Source of the smoke/sanity/regression doctrine: docs + research (drizz.dev, getautonoma, harness) + the table in /regression-testing §When to run each suite.

one table worth the whole chapter

Each workflow answers one question and gates one decision

The rule that comes out of the table

Smoke speaks about the app build; sanity speaks about the change; regression speaks about the whole product. Three different pass-rates with three different SLOs: never add them into one number (a compact rule of /regression-testing). And build says nothing about the app at all: it speaks about us.

The industry's classic sequence is smoke → sanity → regression as successive gates: if smoke fails, you do not spend the regression. In this repo the gates are time-based (cron) and manual; connecting them to the app's deploy is Chapter 9.

Master table. Suite pyramid. Compact rule: do not mix pass-rates. Reference to the industry's smoke→sanity→regression sequence.

suite 0: it does not test the app, it tests the test repo

build.yml: the Pull Request gate

excerpt from .github/workflows/build.ymlreal
      - name: Validate env schema (varlock)
        uses: dmno-dev/varlock-action@v1.0.5
        with:
          fail-on-error: true
          show-summary: true

        # .env.core.schema against the job's env block above and writes a
        # REDACTED summary to the job page. The only required item is TEST_ENV
        # (it has a default); project credentials are optional typed examples,
        # so a PR from a fork, which has no secrets, passes here and at
        # test:env:check below. …
      # … Setup Bun · Install Dependencies
      - name: Validate Test Environment Variables
        run: bun run test:env:check
      - name: TypeScript Check
        run: bun run types:check
      - name: ESLint Check
        run: bun run lint:check
      - name: Docs Gates
        run: |
          bun run docs:check
          bun run skills:check
      - name: Documentation Contracts
        run: bun scripts/lint-doc-contracts.ts --base "$BASE_SHA" --head "$HEAD_SHA"
      - name: Skill Activation Evals Check
        run: bun run skills:evals
      - name: Playwright Compile Check
        run: bunx --bun playwright test --list
  • It answers "does this PR break the framework?". A test that does not compile does not fail: it does not exist. That is why playwright test --list is the key step: it compiles every spec without running it and without app credentials.
  • Same order as the repo's Rule #7: tests (compilation) → types → lint. What you run locally before committing runs here before merging. No surprises.
  • The Validate env schema (varlock) step goes first, before bun install: it validates that the job's env block meets .env.schema and leaves a redacted summary on the job page. The only required item is TEST_ENV (it has a default); the test-user pair is optional, so a fork PR, which has no secrets, passes here and in test:env:check.
  • The documentation gates also block the PR. Docs Gates runs docs:check and skills:check (dead links and paths, cited scripts that package.json does not declare, Rule #17, the skills router and the instruction layer). Documentation Contracts fails the PR if a region marked with LINT.IfChange changes without the pages its LINT.ThenChange names changing (or without a Docs-Checked: trailer in a commit of the PR). That is why build.yml's checkout brings the full history (fetch-depth: 0).
  • Cancelable (cancel-in-progress: true): a new push invalidates the previous one and nothing was left published.
  • The shortest timeout of the suites (see timeout-minutes in build.yml): if it takes longer, something is wrong with the machine, not with the code.

What it deliberately does NOT do

It does not run a single test against staging. Running the suite on every PR would cost minutes and credentials on every push (forks included, which do not have them) and would mix two questions: "does it compile?" with "does the app work?". The second one is answered by sanity, on demand.

build.yml: the framework's PR gate. varlock first, tests→types→lint, documentation gates, playwright --list. It does not run tests against the app, and the reason is stated.

suite 1: the cheapest question, the most frequent one

smoke.yml: is the app alive?

excerpt from .github/workflows/smoke.yml step Run Smoke Tests (@critical) · playwright.config.ts smoke-* projectsreal
# smoke.yml
      - name: Run Smoke Tests (@critical) on ${{ env.TEST_ENV }}
        run: bun run test:smoke

# package.json
"test:smoke": "… playwright test --project=smoke-ui --project=smoke-api"

# playwright.config.ts (smoke block comment, abridged)
# Smoke Tests - @critical tagged tests, ONE PROJECT PER SURFACE
# smoke-ui  == e2e + @critical
# smoke-api == integration + @critical
{ name: 'smoke-ui',  grep: /@critical/, … }
{ name: 'smoke-api', grep: /@critical/, … }

Why two projects and not one

The config comment explains it: a single smoke project covering e2e + integration had to pick ONE use block, and it picked the UI one, which handed a browser session (with a cookie) to the API tests. A test that expected 401 without a token got 200. One project cannot carry the auth of two surfaces. It was split into two that mirror their full suites exactly, plus the grep.

  • The tag decides the scope. A test is in smoke because it carries @critical in its title, not because it sits in a folder. The same tag feeds Allure's suite label: one taxonomy for CI and reporting.
  • One suite job, one report job. No integration-first ordering: the critical API and UI tests run together because the goal is speed, not diagnosis.
  • Cron at 02:00 UTC: after the nightly deploy. Also by hand after any deploy: "do we carry on?".
  • It never writes to the regression execution. The STP_EXECUTION_KEY secret is not read here (workflow env block): a smoke that imported into the RTR would flip Test Runs that belong to a full regression verdict. It only imports if you pass an explicit execution_key.
  • Size criterion (industry): smoke should be less than 5% of the regression and finish in minutes. If your smoke takes 20, it is a regression in disguise.
smoke.yml: @critical, two projects because of a real shared-auth bug (config comment), cron 02:00, it does not import into the RTR without an explicit key.

suite 2: the only one that always needs you to tell it what

sanity.yml: does THIS change work?

excerpt from .github/workflows/sanity.yml · step Run Sanity Testsreal
      - name: Run Sanity Tests on ${{ env.TEST_ENV }}
        shell: bash
        env:
          GREP_INPUT: ${{ github.event.inputs.grep }}
          TEST_FILE: ${{ github.event.inputs.test_file }}
          TEST_TYPE: ${{ github.event.inputs.test_type }}
        run: |
          grep_args=()
          if [ -n "$GREP_INPUT" ]; then
            grep_args=(--grep "$GREP_INPUT")
          fi
          # Determine which test command to run
          if [ -n "$TEST_FILE" ]; then
            echo "Running specific test file: $TEST_FILE"
            bun run test "$TEST_FILE" "${grep_args[@]}"
          elif [ "$TEST_TYPE" == "e2e" ]; then
            echo "Running E2E tests"
            bun run test:e2e "${grep_args[@]}"
          elif [ "$TEST_TYPE" == "integration" ]; then
            echo "Running Integration tests"
            bun run test:integration "${grep_args[@]}"
          else
            echo "Running all tests"
            bun run test "${grep_args[@]}"
          fi
InputTypeEffect
test_typechoice all / e2e / integrationpicks the package.json script
grepstring--grep "…": by tag or by title text
test_filestringa path: wins over test_type
custom_allure_urlstring, default sanityreport folder: /{env}/{custom}/
  • Precedence: file > type. And the grep is added on top of either. Passing grep and test_file together works, but the skill discourages it: pick one so the report says what you tested.
  • Its canonical use: validate in CI a test you just wrote, before the PR. gh workflow run sanity.yml -f environment=staging -f test_file=tests/e2e/auth/login.test.ts.

Security note (fixed in the workflow)

This step used to interpolate grep and test_file straight into run: and pass them through eval. An input is text controlled by whoever triggers the run, and GitHub's security guidance says to pass it first into an env: variable and read it quoted. That is what you see above: the three inputs come in through env:, are read as "$GREP_INPUT" and "$TEST_FILE", and the eval is gone: the command is built as a bash array. Same four branches, same messages. When you write yours, follow this pattern (Ch 10).

sanity.yml: inputs and precedence; canonical use; hardening note already resolved: the inputs moved to env:, are read quoted and the eval was removed (bash array). Show the listing as the example of the safe pattern.

build.yml
alone, automatic on the PR
You do nothing: it fires by itself. If it goes red, the PR does not merge.
smoke.yml
@critical · 2-5 min
gh workflow run smoke.yml -f environment=staging. Green = we carry on. Red = warn the team before they lose the afternoon.
sanity.yml
one file or one grep
-f test_file=… for your new test; -f grep="@checkout" for the fix's area. Small, targeted, with its own report.
regression.yml
everything · 20-60 min
Before the release: /regression-testing creates the RTR and fires with -f execution_key=<RTR>. A re-run for ENVIRONMENT before the verdict reuses the SAME RTR.
Sanity with test_file. It is exactly its stated purpose (the header comment: "Useful for validating new tests in CI before merging PRs"). Do not fire the regression for one file: tens of minutes for an answer sanity gives in a few.
Smoke. The question is "is it alive?", not "is it perfect?". Only @critical: login, the main business flow, the API responding. If it passes, the team carries on; if not, nobody loses the afternoon testing on a dead app.
Regression, through the skill. The verdict needs a run record (RTR) created BEFORE the trigger so CI imports into it. /regression-testing does that: it creates the RTR, fires with execution_key, persists the RUN_ID and then classifies. The how-it-works deck covers the rest.
Sanity with grep. -f test_type=e2e -f grep="@checkout" runs only the tagged tests. Report at /staging/sanity/ (or the custom_allure_url you choose, e.g. checkout-fix).
Build, without doing anything. The PR fires build.yml on its own. If you also want to see your refactored Page working, run sanity with the file that uses it. Never both in the same workflow.
Regression on the same RTR. An environment failure before the verdict does not open a new RTR: it is re-fired with the same execution_key. A new RTR (#2) only after a verdict has already been written.
Suite decider: 6 situations → 4 suites, with the gh command. Scenario 6 reinforces the one-RTR-per-verdict rule.

quiz 06: strategy

Which suite and why?

Q1The PM asks for "a single quality number" by adding the pass-rates of smoke (98%) and regression (91%). What do you answer?
A94.5%, a simple average
BThey are suites with different questions and SLOs: they are reported separately; the release verdict comes only from regression
C98%: smoke is the one that matters for the release
Separately. Smoke measures "is it alive?" over 5% of the tests; regression measures "did something break?" over everything. Averaging hides the 91%, which is the one that decides (the skill's compact rule: never mix smoke and regression into a single pass-rate). The how-it-works deck tells how the 91% turns into CAUTION.
Q2Why does build.yml run playwright test --list instead of playwright test?
ATo save minutes: it is a temporary shortcut
BBecause its question is "does the suite compile?", not "does the app work?": list = compiles everything without executing or needing the app
CBecause PRs do not have browsers installed
A different question. --list loads and compiles every spec: if an import is broken or a type does not check, it fails there, without app credentials or browsers. Running the suite on every PR would mix the framework's state with staging's state, and would make a fork PR (without secrets) fail for reasons that are not its own.
Q1: do not mix pass-rates. Q2: --list = compile without executing; separation of questions.

Two that test, two that count

The first two run Playwright and upload evidence. The last two test nothing: they consume the artifacts to produce the report (for humans) and the import (for the TMS). Separating them lets them run in parallel, run even if the suite failed, and each be switched off on its own: generate_allure=false turns one off; TMS_PROVIDER=jira turns the other off.

Merge: two artifacts go in, one report comes out

excerpt from .github/workflows/regression.yml · steps Download … Allure Results, Merge Allure Resultsreal
      - name: Download Integration Allure Results
        uses: actions/download-artifact@v8
        with:
          name: integration-allure-results
          path: regression-artifacts/integration-allure-results
        continue-on-error: true
      - name: Download E2E Allure Results
…        (identical, e2e-allure-results)
      - name: Merge Allure Results
        id: merge_results
        run: |
          mkdir -p merged-allure-results
          if [ -d "regression-artifacts/integration-allure-results" ] && [ -n "$(ls -A …)" ]; then
            cp -r regression-artifacts/integration-allure-results/. merged-allure-results/
…          (same for e2e)
      - name: Check Allure Results
        id: check_allure
            echo "has_results=true" >> $GITHUB_OUTPUT
      - name: Upload Merged Allure Results
        if: steps.check_allure.outputs.has_results == 'true'
          name: merged-allure-results-${{ env.TEST_ENV }}
  • Allure results are loose files (one JSON per test, plus attachments). Merging two folders is copying everything into one: cp -r. Allure then generates ONE report with the two suites as distinct suites inside.
  • continue-on-error on every download: if E2E was skipped (because Integration failed), its artifact does not exist and the download would fail. The report must still come out, with whatever there is.
  • The merged folder is uploaded again as its own artifact (step Upload Merged Allure Results). It is the one the agent downloads in /regression-testing Phase 2 to analyze: gh run download <RUN_ID> -n merged-allure-results-staging.
  • A native alternative: download-artifact@v8 with pattern: '*-allure-results' + merge-multiple: true does the merge in one step. The repo does it by hand so it can log what was missing.

Why a single report

The verdict is about the product, not about a job. A PM who opens two reports has to add them up in their head; a single one with the Graphs tab (testing pyramid, severities, trend) answers on its own. And the trend history (history.jsonl) is kept per {env}/{suite}: two reports would be two histories.

Merge: cp -r of two allure-results folders; continue-on-error on downloads; merged re-uploaded for the agent; alternative pattern+merge-multiple.

Order of truth for the analysis

/regression-testing fixes the source of each thing: the counts come from reports/test-outcomes.json (Allure only if the file is missing, and the report says so); the detail of each failure comes from Allure results JSON > Playwright results.json > logs. Logs are the last resort, not the first. And Allure's suite label derives from the Playwright tag that also chose the scope in CI: one taxonomy, zero reconciliation.

Phase 3 of the skill
  • Why before. The Xray import only writes inside an Execution that already exists. If you give it just the project, it mints a new parentless Execution on every run (XrayImport job comment). Creating it first guarantees parent, plan and owner.
  • One RTR per verdict. Re-run for an environment failure before the verdict → same key. Re-run after a verdict → new RTR (#2). A closed one is never reopened.
  • The secret is the cron's fallback. A scheduled run has no inputs; STP_EXECUTION_KEY as a secret gives it a destination. The name stayed for compatibility; the semantics changed.
  • Smoke and sanity do not read the secret (env block of smoke.yml): importing the @critical subset into the RTR would flip Test Runs that belong to a full verdict. They only import with an explicit key.
  • Never the RTP/STP key. A Test Plan derives its status from its Executions; writing into it is a model error.
  • STR only at sprint close: then the key is the STR's, with double membership STP + RTP. A regular run is never the STR.
The write-back's 6-step flow. Rules: RTR first, one per verdict, secret = cron fallback, smoke/sanity do not read the secret, never RTP/STP, STR only at sprint close.

the problem and the three ways to solve it

From "runs at 00:00" to "runs when the app deploys"

Starting point

The app deploys to staging at 22:00 and our regression runs on cron at 00:00 (illustrative hours; the real one is regression.yml's schedule). If the deploy happened at 00:30, we tested the old version. And production waits for no one: the prod deploy is a human decision with no automated QA gate.

Goal

Deploy to staging → smoke (immediate) and regression or sanity for the area → the result flows back to the app's commit → deploy-production only starts if the gate is green, with a human reviewer via environment: production.

The obstacle: two repos

A workflow's GITHUB_TOKEN fires nothing in ANOTHER repo, and the app's events happen in the app. Crossing the boundary takes one of the three mechanisms, and a scoped token (fine-grained PAT or GitHub App) in the first two.

Twelve checks before opening the PR

    
    
      
  • Purpose in the header. A comment that says which question it answers and when it runs. If you cannot write it, you do not know which suite it is.
    • 
      
  • package.json commands, not invented ones. bun run test:smoke, never npx playwright test … written by hand (Rule #11).
    • 
      
  • Every input has a fallback || 'default' where a cron can fire it.
    • 
      
  • No secret in the YAML. Only ${{ secrets.X }}. Names follow the environment prefix: STAGING_USER_EMAIL.
    • 
      
  • No input interpolated inside run:. Pass it through env: and read it as "$VAR" (docs: secure-use).
    • 
      
  • timeout-minutes on every job. Without it, a hang bills up to 6 hours.
    • 
      
  • if: always() on every results upload and failure() on the extra evidence.
    • 
      
  • Artifact names unique per run, with a suite/job prefix. v4 is immutable.
    • 
      
  • concurrency decided: publishes → cancel-in-progress: false; only validates → true.
    • 
      
  • Minimal permissions if the workflow writes to GitHub; nothing declared if it only reads.
    • 
      
  • Actions pinned to a version (@v7) and, for critical third parties, the full SHA with a version comment.
    • 
      
  • Tested with workflow_dispatch before trusting the cron. A new cron does not run until it is on main; the button does (gh workflow run <file> --ref <your-branch> once the file also exists on main).
    •

quiz 10: your own

    
The mini-course's last check

    

      

        
Q9Your new workflow receives a grep input and uses it like this: run: bun run test --grep="${{ github.event.inputs.grep }}". A security teammate flags it. What do you change?

        

          
ANothing: only people with permission can trigger the workflow

          
Benv: GREP: ${{ github.event.inputs.grep }} and in the run --grep="$GREP": the value does not take part in generating the script

          
CMove it into a secret

        

        
An intermediate variable. An expression inside run: is substituted BEFORE bash reads the script: an input with "; rm -rf … becomes code. With env: the value arrives as an environment variable and bash treats it as data. It is the literal recommendation of GitHub's security guide, and the pattern applied by the Run Sanity Tests step of sanity.yml: inputs through env:, read quoted, no eval.

      

      

        
Q10You finished the workflow, merged it and in the morning it did not run. You check: the cron is fine, the file is on main. What do you look at first?

        

          
AWhether the repo has recent activity (crons are disabled after 60 days in public repos) and whether the run got queued because of load

          
BWhether permissions: write-all is missing

          
CBoth things in A, and also the dispatch form: if gh workflow run does not start it either, the problem is the YAML, not the clock

        

        
Separate the clock from the file. First rule out the cron (60-day inactivity, load delay, a badly converted UTC hour). Then fire it by hand: if the dispatch fails, GitHub shows you the syntax error or the broken step; if it works, the problem was the trigger. B is noise: permissions do not stop a workflow from starting.
