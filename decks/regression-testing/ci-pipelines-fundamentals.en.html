Chapter 01

What CI is and why a tester needs it

Continuous Integration: every change triggers an automatic check on a clean machine. For QA it means the suite runs by itself, always the same way, and leaves evidence nobody has to ask for.

By the end you will know what a workflow, a job, a step and a runner areAnd you will read build.yml without fear
Chapter 1: vocabulary and anatomy. We use build.yml because it is the shortest and does not run tests: it only validates the framework.

the pain and the pattern

Without CI, the suite runs when someone remembers

Without CI

"Run the regression before the release." It runs on YOUR laptop, with YOUR .env, with YOUR Chromium version. The report stays on your disk. If you are the one who fails, there is no evidence. If the app breaks at 3 AM, nobody finds out until 9.

With CI

One .yml file describes WHAT to run and WHEN. GitHub spins up a clean machine, installs everything, runs the suite, saves screenshots, traces and the Allure report, and writes the result to the TMS. Every night. The same way. Without anyone touching anything.

six words you will read a thousand times

Workflow → jobs → steps, executed by a runner

TermWhat it isIn this repo
WorkflowA .yml file in .github/workflows/. It defines when it runs and what it does.smoke.yml, regression.yml…
Event / triggerWhat wakes the workflow up: a PR, a cron, a manual click, an external event.on: schedule / workflow_dispatch
JobA set of steps that runs on ONE machine. Jobs run in parallel unless you declare needs.IntegrationTests, E2ETests

the hierarchy in 12 linesoutline
name: Smoke Tests           # the workflow
on:                         # the triggers
  schedule: [...]
  workflow_dispatch: [...]
jobs:
  SmokeTest:                # job 1
    runs-on: ubuntu-latest  # the runner
    steps:
      - uses: actions/checkout@v7   # step (action)
      - run: bun run test:smoke      # step (command)
  allure-report:            # job 2
    needs: SmokeTest        # waits for job 1

The mental picture

A workflow is a recipe. Each job is a cook in their own empty kitchen (the runner). The steps are the steps of the recipe. The artifacts are the dishes you leave at the pass for the next cook: if you do not pass them along, the other one cannot see them.

Seven terms. Stress it: every job = a new, empty machine. That is why each job repeats checkout + setup, and why artifacts exist.

Anatomy of a workflow: build.yml, piece by piece

.github/workflows/build.yml · excerptreal
name: TestBuild Checks
run-name: ${{ github.actor }} triggered TestBuild Checks on ${{ github.ref_name }}
on:
  pull_request:
    branches:
      - main
concurrency:
  group: build-${{ github.ref }}
  cancel-in-progress: true
env:
  CI: true
  TEST_ENV: 'staging'
  # Test-user pair for the selected TEST_ENV. OPTIONAL here: nothing in this
  # job logs in … A fork PR has no secrets and still passes.
  STAGING_USER_EMAIL: ${{ secrets.STAGING_USER_EMAIL }}
  STAGING_USER_PASSWORD: ${{ secrets.STAGING_USER_PASSWORD }}
jobs:
  TestBuild:
    name: Framework Validation
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - name: Checkout Repo
        uses: actions/checkout@v7
        with:
          fetch-depth: 0
          # Full history: the documentation-contract step diffs the PR range.
      - name: Install Dependencies
        run: bun install
      - name: ESLint Check
        run: bun run lint:check
      - name: Docs Gates
        run: bun run docs:check · bun run skills:check
      - name: Playwright Compile Check
        run: bunx --bun playwright test --list
Click a block of the YAML →

name and run-name

name is the fixed title of the workflow in the Actions tab. run-name is the title of EACH run and accepts ${{ }} expressions: here it shows who triggered it (github.actor) and on which branch (github.ref_name).

Without run-name, GitHub uses the commit message. Naming the runs turns the run list into a readable log.

docs: workflow-syntax → run-name

on: the trigger

This workflow wakes up when a pull request to main is opened or updated. No cron, no button: only PRs. It is the branch's gate: if the framework does not compile, the PR stays red.

Note branches: [main]: a PR to another branch does not trigger it. Branch and path (paths) filters combine with AND.

docs: events-that-trigger-workflows → pull_request

concurrency with cancellation

One build per branch (group: build-${{ github.ref }}). If you push twice in a row, the first run is cancelled: it publishes nothing, so cancelling it is free and saves minutes.

Compare with the suites: they use cancel-in-progress: false because they publish a report. We see that in Chapter 4.

docs: control-workflow-concurrency

env: variables for all jobs

At workflow level, env defines environment variables that every job and step inherits. CI: true is a convention many tools read (Playwright turns on forbidOnly, for example).

The credentials are NOT written here: they are read from ${{ secrets.X }}, which GitHub injects masked. Copying a value from your .env into the YAML is the worst mistake in the course.

In build.yml the test-user pair is optional: nothing in this job logs in, so a fork PR, which receives no secrets, passes anyway.

docs: use-variables · use-secrets

the TestBuild job

The TestBuild key is the id (needs uses it); name is what you see in the UI. runs-on: ubuntu-latest asks for a clean GitHub Linux VM. timeout-minutes: 15 kills the job if it hangs: without it, the default is 360 minutes on the bill.

docs: workflow-syntax → jobs.<job_id>

steps with uses: (actions)

actions/checkout@v7 clones the repo onto the runner (without it, the machine is empty). fetch-depth: 1 would bring only the last commit (faster, and what smoke, sanity and regression use). build.yml uses fetch-depth: 0, the full history, because the Documentation Contracts step compares the PR range and reads its commit messages. The next step (Setup Bun, omitted here) is oven-sh/setup-bun@v2, which installs Bun.

@v7 is a major-version tag. For maximum security, GitHub recommends pinning a full commit SHA on third-party actions: a tag can be moved, a SHA cannot.

docs: find-and-customize-actions · security/secure-use

steps with run: (commands)

Each run is a shell command on the runner. Here they run the same package.json scripts you run locally: lint:check and docs:check / skills:check (plus types:check and other steps, left out for space). The last two are the documentation gates: the PR stays red if there are dead links or paths, or if it breaks a documentation contract. playwright test --list compiles every spec without running it: it validates that the suite IS runnable.

Repo rule: the YAML never invents commands. It calls the package.json scripts, so local and CI do exactly the same thing.

Rule #11 of AGENTS.md: scripts live in package.json

quiz 01: vocabulary and anatomy

Did the hierarchy land?

Q1The E2ETests job installs Bun and the browsers even though IntegrationTests did it a minute earlier. Why?
AAn oversight: it could be deleted to save time
BEach job runs on a new, empty runner; nothing from the previous job survives
CBecause needs wipes the state of the previous job
A new runner per job. A job is a clean VM. The only things that cross from one job to another are artifacts (and outputs). That is why the suites repeat the 5 setup steps in every job, and why allure-report has to download the results with download-artifact.
Q2A teammate proposes writing the staging password straight into the YAML env: "because the repo is private anyway". What do you tell them?
AFine, if the repo is private there is no risk
BBetter to put it in a comment so it stays documented
CNo: it goes in GitHub Secrets and is referenced with ${{ secrets.X }}; the YAML stays in git history forever
Secrets, always. The YAML travels in every clone, fork and PR; a secret is injected at runtime, masked in the logs and rotated without touching the code. Also, secrets do not reach PRs from forks, which is exactly the protection you want.

pages.yml publishes the home page (packages/pages-home), /kata/, /decks/ and the static docs/ site at /docs/, only if the push touched their sources; bun run docs still serves docs/ locally. pages-squash.yml flattens gh-pages on the 1st of every month.
build.yml, and unit-tests.yml only if the PR comes from a fork: a PR from the same repo already had its push run on the same commit, and GitHub shows it on the PR. No suite runs on a PR: the framework is validated, the tests are not executed against staging on every push (it would cost minutes and credentials for every PR, including fork PRs, which have no secrets). Running a suite on a PR is a Part II decision.
unit-tests.yml always, on any branch: it runs the repo's own tests and publishes nothing. pages.yml only if the push touched a path in the workflow's own paths: list (kata-academy, pages-home, decks, docs and the workflow itself; that block is the source). A push that changes a test publishes nothing.
Only regression.yml. No inputs (a cron has no form): TEST_ENV falls back to 'staging' through the || 'staging' in the env block, and STP_EXECUTION_KEY falls back to the secret. Two hours before smoke so they do not step on each other.
Only smoke.yml. It runs at 02:00 UTC: by then the app's nightly deploy should already be up. GitHub warns that crons get delayed on the hour under load; that is why it pays to spread them out.
Any of the five that declares workflow_dispatch, one at a time: you pick which in the UI (or with gh workflow run <file>). The form is generated from the inputs. build.yml has NO button: PR only.
Only pages-squash.yml (cron '0 4 1 * *'): it rewrites gh-pages into a single commit so the generated branch does not grow without limit. A maintenance cron, not a testing one.

workflow_dispatch: the button with parameters

.github/workflows/smoke.yml · excerpt: workflow_dispatch inputsreal
  workflow_dispatch:
    inputs:
      environment:
        description: Select the Test Environment
        required: true
        default: 'staging'
        type: choice

          - local
          - staging
      generate_allure:
        description: Generate Allure Report

        description: 'Key of the Test Execution this run imports into (…)'
        required: false
        default: ''

Valid types: choice, boolean, string, number, environment. Maximum 25 inputs. They are read with github.event.inputs.X (everything arrives as a string) or with inputs.X (which keeps booleans). That is why the repo compares generate_allure != 'false' in quotes (the if of the allure-report job in smoke.yml).

The ${{ github.event.inputs.environment || 'staging' }} pattern is the fallback for the cron: a scheduled run has no inputs, the expression returns empty and the || rescues the default. Without that ||, the nightly regression would run with no environment.

Minute (0-59)

0 = on the hour. The minimum interval GitHub accepts is 5 minutes. Tip from the docs: avoid minute 0, it is when load is highest and runs get delayed; 17 2 * * * starts more punctually than 0 2 * * *.

Hour (0-23), always UTC

2 = 02:00 UTC. In Buenos Aires that is 23:00 the previous day; in Madrid, 04:00. Regression goes at 00:00 and smoke at 02:00: a two-hour margin so the regression (up to 60 min) does not overlap with smoke on gh-pages.

Day of month (1-31)

* = every day. 1 = only the first: that is how pages-squash.yml runs monthly.

Month (1-12)

* = every month. Almost nothing else is ever used in testing.

Day of week (0-6, Sunday = 0)

* = every day. 1-5 would run only Monday to Friday: useful if the staging environment shuts down on weekends and you do not want red noise on Saturday.

The four cron traps (all documented by GitHub)

  • It only runs on the default branch. A cron on your feature branch does nothing until it is merged to main.
  • It has no inputs. That is why every value that depends on an input carries its || 'default'. And why execution_key falls back to the STP_EXECUTION_KEY secret in the nightly regression.
  • It gets delayed under load. It can start minutes late; in extreme cases, be skipped. It is not a Swiss watch: it is a queue.
  • It switches itself off. In public repos, after 60 days without activity GitHub disables scheduled workflows. A sleeping repo stops watching.

Why two crons and not one

Smoke and regression could be a single file with two crons. They are split because they answer different questions and have different SLOs: never mix their pass-rates (rule R6 of /regression-testing). Full strategy in Part II.

Cron: 5 clickable fields. Traps: default branch only, no inputs (fallbacks), delays, auto-disable after 60 days. All from docs.github.com.

The rule that breaks the most workflows

An if: at job level can read github, vars, inputs and needs, but not env or secrets. That is why TMS_PROVIDER is a variable and not a secret, and why the if of the XrayImport job in regression.yml repeats vars.TMS_PROVIDER instead of reading env.TMS_PROVIDER. The comment right above it says so verbatim.

quiz 02: triggers, inputs and contexts

Who woke the workflow up?

Q3You add schedule: cron '0 6 * * *' to sanity.yml on your feat/sanity-cron branch and open the PR. Three days go by. How many times did the cron run?
AThree: once a day at 06:00
BZero: crons only run on the default branch; until the merge to main it does not exist
CThree, but they failed for lack of inputs
Zero. schedule is evaluated on the latest commit of the default branch. Your branch may have the perfect cron and GitHub does not look at it. After the merge, remember too that a cron brings no inputs: every value needs its || 'default'.
Q4You want a whole job to be skipped when the project does not use Xray. You write if: env.TMS_PROVIDER == 'xray' at job level. What happens?

BIt does not work: the job if cannot read env; you have to use vars.TMS_PROVIDER

vars, not env. The env context does not exist when GitHub decides whether to start a job. That is why the XrayImport job in regression.yml writes if: always() && (vars.TMS_PROVIDER || 'xray') == 'xray' and keeps the provider as a repository variable, which can be read there.   • Without needs, everything runs in parallel. GitHub launches each job on its runner as soon as it can. You set the order with dependencies, not with position in the file.
  • needs chains. E2ETests waits for IntegrationTests to finish successfully. If the API is broken, there is no point paying for 60 minutes of browser: the job is skipped.
  • A failed needs skips the chain… unless the job says if: always(). The two final jobs say it: the report and the TMS import must exist above all when something failed.
  • A list = wait for all. needs: [IntegrationTests, E2ETests] starts when both have finished (or been skipped). needs.X.result tells you how: success / failure / cancelled / skipped.

Why Integration first

API tests are faster and cheaper than UI tests, and if the backend is down the UI will fail for the same cause. Putting them first turns a backend outage into 6 red minutes instead of 66. It is a fail fast done with a single line: needs.

the five steps every suite repeats

Steps: uses plugs in an action, run executes a command

.github/workflows/smoke.yml · excerpt: setup steps (identical in sanity and regression)real
    steps:
      - name: Checkout Repo
        uses: actions/checkout@v7        # 1 · fetches the code
        with:
          fetch-depth: 1
      - name: Setup Bun
        uses: oven-sh/setup-bun@v2        # 2 · the runtime
        with:
          bun-version: latest
      - name: Install Dependencies
        run: bun install                  # 3 · node_modules
      - name: Validate Test Environment Variables
        run: bun run test:env:check       # 4 · missing secrets?
      - name: Install Playwright Browsers
        run: bun run pw:install           # 5 · chromium + deps
      - name: Run Smoke Tests (@critical) on ${{ env.TEST_ENV }}
        run: bun run test:smoke           # the suite

uses: an action

Code packaged by someone else (owner/repo@version). It takes parameters in with:. actions/* belong to GitHub; oven-sh/setup-bun belongs to the Bun authors. Without checkout, the runner does not even have the package.json.

run: a command

The runner's shell (bash on Ubuntu). Multiline with run: |. Repo rule: it calls the package.json scripts and never reinvents the command. That way CI and your terminal run the same thing.

  • Order matters. The steps of a job run in sequence, on the same machine. Installing browsers before bun install would fail: the pw:install script lives in node_modules.
  • test:env:check is step 4 on purpose. It fails in 2 seconds if a secret is missing, before spending 3 minutes installing Chromium. Failing early with a clear message is design, not luck.
  • @v7, @v2: major versions. They update themselves within the major. For critical third-party actions, the GitHub docs recommend pinning the full SHA of the commit (40 characters) with a # v4.2.2 comment: a tag can be moved; a SHA cannot.
  • name is for humans. It appears in the run log. "Install Playwright Browsers" reads well; "step 5" does not.
The 5 setup steps. uses vs run. Sequential order. Early env:check = fail fast. SHA pinning as a docs recommendation.

$GITHUB_OUTPUT

A file. You write key=value and GitHub exposes it as steps.<id>.outputs.key to the following steps. To pass it to ANOTHER job, you map it in jobs.X.outputs and read it with needs.X.outputs.key.

$GITHUB_STEP_SUMMARY

Markdown that shows up on the run page, above the logs. The link to the Allure report is written here: the PM does not open logs, they open the summary. regression.yml also writes how many JUnit files it imported into Xray.

::notice / ::warning

Annotations visible in the UI without failing the step. The gate step of the XrayImport job in regression.yml reports "Xray import skipped" with ::notice and with ::warning when the execution_key is missing. The step exits with 0: informing is not failing.

The "detect → decide → skip" pattern

A cheap step checks whether there are results and publishes an output. The following steps carry if: steps.check_allure.outputs.has_results == 'true'. If the suite left nothing (a run cancelled after 10 seconds), the job installs no Bun and generates no empty report. Defensive design with a text boolean.

$GITHUB_ENV is the cousin: echo "VAR=value" >> $GITHUB_ENV creates an environment variable for the following steps of the same job.

Three communication channels: outputs (step→step, job→job), summary (→human), annotations (→UI without failing). Real check_allure pattern.

quiz 03: execution

Does it run or get skipped?

Q5You delete the if: always() from the "Upload Allure Results" step to "simplify". The suite fails that night. What do you find in the morning?
AThe Allure report with the red tests, as always
BNo artifact and no report: when a step fails, the following ones are skipped by default
COnly the failure-evidence artifact
Nothing. The implicit default of every step is success(): if something failed earlier, it does not run. You lose the results precisely on the night you needed them. always() on the uploads is not decoration: it is the difference between "something failed" and "this failed, here is the trace".
Q6The allure-report job wants to know whether the SmokeTest job left results. How can it find out?
ABy reading allure-results/ from disk: jobs share the filesystem
BWith steps.check_allure: step outputs are global
CBy downloading the artifact with download-artifact, or reading needs.SmokeTest.outputs.* if the job declared them
Artifacts or job outputs. Different runners = different disks, so A is impossible. steps.* only exists inside the same job, so B is out too. smoke.yml takes the artifact route (Download Smoke Test Artifacts step) and then checks locally whether anything arrived (Check Allure Results step).
Q5: without always() you lose evidence. Q6: communication between jobs = artifacts or outputs, never a shared disk or steps.*.

simulator: two runs of the same group overlap

concurrency: cancel or queue, depending on what it publishes

excerpt of the concurrency block: from .github/workflows/build.yml vs .github/workflows/regression.ymlreal
# build.yml: validates, does not publish
concurrency:
  # One build per PR branch: a force-push supersedes the run already in flight.
  # Safe to cancel: this job only validates, it publishes nothing.
  group: build-${{ github.ref }}
  cancel-in-progress: true

# regression.yml: publishes Allure to gh-pages
concurrency:
  # Suite runs publish Allure to gh-pages. Two overlapping runs race on that
  # deploy and one silently overwrites the other's report. Queue instead of
  # cancelling: a half-finished suite that still uploaded results would leave
  # a partial report standing as if it were the full one.
  group: regression-${{ github.ref }}
  cancel-in-progress: false
runner
run #1 · in_progress
run #2 · new
  • group defines who competes. It can use expressions (github, inputs, vars). build-${{ github.ref }}: one group per branch. Names are case-insensitive.
  • By default there is only ONE pending. If #2 and #3 arrive while #1 runs, #2 is cancelled and #3 stays. With queue: max you can queue up to 100, but not combined with cancel-in-progress: true.
  • FIFO. Pending runs start in the order they began waiting.
  • Workflow level or job level. All the workflows declare it at workflow level; pages.yml uses a fixed group (pages-docs-hub) because it always publishes to the same site.

The question that decides

"Does this workflow leave something published or shared?" If not (validate, lint, compile): cancel, it is cheaper. If so (report, deploy, gh-pages branch): queue, because cancelling halfway leaves a state that looks complete and is not. All our workflows publish except build.yml and unit-tests.yml, which cancel (unit-tests.yml never on main: there every push is work that has already landed and deserves its own run, so each main commit gets its own group; cancel-in-progress: false is not enough, because the group keeps only one pending run and cancels it when another arrives).

Concurrency: cancel vs queue, with the repo's real comments as justification. Rule: it publishes → queue; it validates → cancel.

the token GitHub lends to every job

permissions: what GITHUB_TOKEN can do

.github/workflows/pages.yml · excerptreal
permissions:
  contents: write        # can push (to gh-pages)
…
# The deploy does not use a third-party action: the workflow builds _site, clones
# gh-pages, syncs only the hub surfaces (rsync --delete) and
# does a git push with the same GITHUB_TOKEN.
recommended shape for a new workflowexample
permissions: {}            # nothing by default…
jobs:
  publish:
    permissions:
      contents: write    # …and only this job can write
  notify:
    permissions:
      statuses: write    # e.g. send a commit status back to another repo
  • GITHUB_TOKEN always exists. GitHub creates it per run, with permissions over this repo, and destroys it when the run ends. You use it as ${{ secrets.GITHUB_TOKEN }} or ${{ github.token }}.
  • permissions trims it. Each scope accepts read, write or none. Hard rule: if you name ONE scope, all the others become none. That is why pages.yml, with only contents: write, cannot touch issues or PRs.
  • Least privilege. The suites (smoke, sanity, regression) declare no permissions and inherit the repo default: they do not need to write to GitHub, only to read the code. Publishing to gh-pages is done by a script with the same token, inside the allure-report job.
  • It does not cross repos. The token cannot trigger a workflow in ANOTHER repository. For that you need a PAT or a GitHub App: we see it in Part II (Ch 9).
  • Anti-recursion. An event caused with GITHUB_TOKEN does not trigger other workflows (so they do not call each other in a loop), except workflow_dispatch and repository_dispatch.
permissions: pages.yml as the only real example with contents: write. Rule: naming one puts the rest at none. It does not cross repos → Part II.

Q7You trigger the regression by hand at 23:58. At 00:00 the cron starts. What happens to the second run, according to regression.yml?

  • Unique names per run. In v4 artifacts are immutable: two uploads with the same name in the same run fail. That is why the smoke-, sanity-, integration-, e2e- prefixes exist.
  • retention-days: 10. After that, they are deleted. The default maximum is 90 (adjustable in Settings). Rule R4 of /regression-testing: download the evidence of a red build before it expires.
  • continue-on-error: true on the download. If the suite never got to upload anything, the report job must not die because of it: it carries on, and the "Check Allure Results" step decides.
  • The Cleanup Workspace step deletes node_modules and results. On a GitHub runner it is redundant (the VM dies anyway); on a self-hosted runner it keeps the disk from filling up.

Header: purpose, name, run-name

The comment in the first lines says which question the suite answers ("Daily health check running only @critical tagged tests"). It is the first line read by whoever opens the file in six months. run-name with actor + environment makes the run list readable.

Triggers: clock + button

The cron gives the routine; the dispatch gives manual control with three inputs that repeat across the three suites: environment, generate_allure, execution_key. Sanity adds test_type, grep, test_file; regression adds video_record (the live list is the inputs: block of each workflow).

Concurrency: queue

One group per suite and branch. cancel-in-progress: false because the final job publishes to gh-pages and two overlapping publishes step on each other.

The env block: identity of the run

Which environment, which credentials (by environment prefix: STAGING_USER_EMAIL), which TMS provider and whether sync is on. Everything sensitive through secrets, everything configurable through vars, everything derived through an expression.

The suite job

runs-on: ubuntu-latest, a timeout-minutes that fits the size of the suite, and environment: name: equal to the input, to inherit the secrets and rules of that GitHub environment.

The five setup steps

Always the same, always in this order: code → runtime → dependencies → variable validation (fails early) → browsers. Copy and paste is right here: a job is a new machine.

The suite and the write-back

A single run with the package.json script. Then, with always(), the step that writes to the TMS: it reads reports/atc_results.json, which KataReporter writes when Playwright exits (that is why it is a separate step and not part of the test). Details in Part II, Ch 8.

Evidence and cleanup

Three uploads with always() (results) and one with failure() (extra evidence). Names carry the suite prefix. Retention is whatever retention-days sets. Cleanup at the end.

The report job

Another runner: it does checkout again (it needs allurerc.mjs and the allure devDep), pulls the gh-pages branch for the trend history, downloads the artifact, checks that there are results and publishes with the same script you use locally. Part II, Ch 7.

Last check of Part I

Q9You copy the E2ETests job to create a "VisualTests" job in regression.yml and leave the upload with name: e2e-allure-results. What happens on the first run?
ABoth jobs write to the same artifact and get merged
BThe second upload fails: in v4 artifacts are immutable and the name must be unique per run
CThe second silently overwrites the first
It fails. Since upload-artifact v4 a name can only be uploaded once per run (except overwrite: true, which overwrites the previous one). The fix is a per-job prefix (visual-allure-results) and, if you want to merge them, download with pattern: '*-allure-results' + merge-multiple: true, which is exactly what the "Merge Allure Results" step of .github/workflows/regression.yml does by hand.
Q10Friday's regression failed. It is Monday (3 days later) and you want the trace. Where is it?
AOn the runner: runners are kept for a week
BIn the run's e2e-failure-evidence artifact, available until day 10: gh run download <RUN_ID> -n e2e-failure-evidence
CIt no longer exists: artifacts last 24 hours
In the artifact, 10 days. The runner died when the job ended; the only thing left is what was uploaded with upload-artifact. retention-days: 10 gives you until day 10. After that, nothing. That is why the skill downloads the evidence of every red build before analyzing it, and why the published Allure report (which lives in gh-pages, not in artifacts) keeps the last 10 runs per suite.
