A single ticket can't see the failure that matters most

An inverted coverage link is invisible on its Story: the link exists and the panel stays empty. That's why, when auditing a ticket, the mode also offers the project-wide sweep for mixed direction (several keys or a JQL → a single worklist). Fixing direction means delete before recreate: Jira deduplicates pair + type, so adding the corrected link without deleting is a silent no-op. before phase 1: three locks

Nothing gets documented without passing the gates

Hard prerequisite

Only behavior that is already validated: Story QA Approved, closed bug, or finished exploratory session. The TMS documents and protects regression, it is not an exploration tool (exploring belongs to /sprint-testing).

Preflight Gate

REQUIRED: working issue tracker (/acli, validate with bun run jira:check) + a resolvable TMS modality (jira-xray → /xray-cli + XRAY_* creds). OPTIONAL: readable source repos. It never touches a live environment → no DB/API/browser probes. Gaps → ONE checklist; blocking RED → STOP.

Phase -1 · Resume check

Reads .session/test-documentation/<scope>/progress.md. If it exists: shows scope, modality, last completed phase and pending chunks → offers resume / restart / abort (restart archives first). With nobody at the keyboard, it resumes by default; restart or abort need the word from the brief.

The resume case that matters most

A Phase 3 bulk create interrupted mid-batch: progress.md records every completed chunk (one per subagent), so resume skips the TCs already created and dispatches only the missing chunks. With nobody at the keyboard, reversible work runs and every TMS write waits for a brief that covers it; an ambiguous mode or a repair-traceability without a ticket stops and reports.

The three locks run in order: the validated-behavior prerequisite (conceptual), the capability preflight (mechanical: acli + TMS), and session resume. The skill does not run against a live system; its gate focuses on being able to WRITE to the TMS.

bug-driven scope: the rule worth its weight in gold

An important bug MUST end with a Test

1

Is it a regression candidate?

Apply the Phase 0 filters + ROI (the prior bug biases it upward). NO → treat it as a failed test: the fix was already verified in sprint-testing → Deferred, no new Test. YES → step 2.

2

Did it come from an already executed Test that failed?

YES → REUSE that Test: link it to the bug (tests / is tested by) and promote it to regression, never duplicate. NO → CREATE + design the Test (native: Test issue; xray: Xray Test + Test Plan / Test Set).

Overrides "the bug is the test case"

That phrase from /sprint-testing covers only the immediate retest in the sprint, NOT future regression. This rule decides whether a persistent Test must exist so the bug never silently comes back.

Never reopen a closed bug (D8)

The bug's history is immutable. Create the new TC and link it via tests / is tested by; don't attach regression by reopening the issue.

A closed bug is strong empirical evidence that the area comes back: most qualify and lean toward Candidate, though not all (a one-off typo in a stable area is deferred). The reuse-or-create decision avoids duplicating Tests that already exist in the set.

Validation against source code: mandatory before documenting

The ATP was written BEFORE the code existed. Grep for data-testid=, route handlers, API routes and text formats; every divergence goes into a Refinement Notes section of the TC. Skipping this step is the #1 cause of invalid automated tests later.

Detailed reads ALWAYS go through the sync script (acli view returns null on custom fields). Typical discrepancies: an assumed API that is really SSR/direct DB; "based on N reviews" vs the real "(N reviews)"; hardcoded IDs vs a variable pattern.

Candidates ≠ TMS items

Deriving broadly is free; persisting is gated by ROI (Phase 2). Collapsing an AC into a single TC requires a written "trivially atomic" justification. The AC→TC map is the floor, not the coverage.

Improvement bridge

A test-beyond-AC exposes a gap because the AC was under-specified → the right artifact is an Improvement issue (defect-management doctrine), NOT a regression TC and NOT widening the Story's ACs after the fact.

phase 2: prioritize · the gate that is never skipped

Three filters, then the formula

F1

Does it protect against future regressions?

One-off typo in a stable area → No → Deferred.

F2

Prior bugs in this area?

Yes → prioritize even with moderate ROI: "it failed once, it can fail again".

F3

App level or feature level?

XSS / a11y / perf / responsive → APP-level suites → Deferred from this scope.

Fail any filter → Deferred

The three filters kill most scenarios before any arithmetic.

ROI = (Frequency × Impact × Stability) ───────────────────────────────── / 10 (Effort × Dependencies) / 10 = normalization constant everything at 3 → 0.3 → Deferred (the default) Component Value = ROI × (1 + 0.2 × N) N = E2E flows that reuse the TC estimated, capped at N = 3 (max ×1.6)
Factor (1-5)15
Frequencyyearlyevery PR / commit
Impactcosmeticrevenue / core
Stabilityvery volatilemonths without changes
Effort (÷)triviala week+
Dependencies (÷)nonecomplex external ones
Effort and Dependencies are DIVISORS: an expensive, coupled "critical flow" MUST score low, and that is the formula working. The "/ 10" is not a sixth factor: it brings the raw quotient (0.04 to 125) down to the scale of the thresholds (0.004 to 12.5). Component Value rescues reusable atoms: authenticateSuccessfully with ROI 2.0 reused in 3 flows → 2.0 × 1.6 = 3.2 → Candidate. N is a qualitative estimate (nobody counts call-sites), capped at 3; it is noted in the ROI comment. Authoritative bands: references/tms-conventions.md §9.

Three layers, three counts: the healthy shape

analyzed 80 → documented 12 → automated 8. A test enters the repository because it will be re-run, never to reach a count. If >50% end up Candidate/Manual → reapply the filters more strictly: most should be Deferred.

The agent scores. The person signs.

The agent derives scenarios by technique, computes the ROI and proposes the verdict. Every verdict is signed by the person, same as the regression epic and the Test Set. CSA autonomy 2, separate verifier recommended: a second agent re-reads the verdicts against the ATR. The >50% Candidate/Manual alarm gets answered, not ignored.

The verdict (arithmetic) is identical in both modalities; what changes is the Phase 3 verb: with {{TC_CREATION_STAGE}} = auto, CREATE (native) vs PROMOTE + ENRICH (xray); the other two values fix the verb in both. Deferred is never a deletion. Anti-pattern D4: never skip ROI scoring. Agentic contract of the stage: agentic-qa-core/references/stage-gates.md.

phase 3: document · container preflight

Epic · Test Set · Test Plan: three different things

Regression Epic

= the "QA Test Repository" process epic. Resolved found-or-created by JQL (type = Epic AND summary ~ "QA Test Repository"); if missing, ask before creating and cache the key in .agents/project.yaml. Every documented TC is parented here, never to a product epic.

repository umbrella

Test Set, two altitudes

Per-Story ATS (mandatory): ATS: {US_ID}: {story title}, third artifact of the ATP/ATR/ATS family, parent "QA Test Artifacts", components inherited from the Story. Its is tested by link to the Story is what fills the coverage panel. Feature-level TS: (optional): TS: {EPIC|module}: Validate {feature}, groups smoke/regression, components optional. Native without a Test Set work type → direct TC↔Story links.

coverage

Test Plan

Execution / regression scope, the set of Tests that runs for a release or cycle. In jira-xray the ATP IS a Test Plan issue (parent: "QA Master Test Plan" epic). The RTP (RTP: {PROJECT_KEY|module}: Regression Test Plan) is the long-lived regression Test Plan under that same epic: destination of every TC promoted with the regression-candidate label, and it is never completed: each regular /regression-testing run writes its RTR (Test Execution RTR: {scope-id}: Regression Testing) against it; the STR is left for sprint close.

execution

Three-axis model (defect-management-doctrine.md)

Parent = QA process bucket (Test → "QA Test Repository" · ATP → "QA Master Test Plan" · ATR and ATS → "QA Test Artifacts") · issue-link = the originating Story · components = the affected product module. Three separate axes; the parent never carries the product trace.

People routinely merge these containers. Epic = the whole repository; ATS = the per-Story Set that gives coverage (optional TS: groups by feature); Test Plan = execution scope. In jira-native with the Test Set work type the ATS exists anyway (membership = TC→ATS links); without the work type, direct TC↔Story links + Regression Epic + label.

Orphan = a TC with NO path to the Story

No ATS, no ATP, no direct link → test-documentation in repair-traceability mode verifies the cascade TC→ATS→Story → TC→ATP→Story → TC→Story. D7: an ATR is never linked to two ATPs (1:1). It rejects titles like "Login test", "Login - error", "TC1: Test form".

The Xray two-call rule

One Create Test (registers in Xray) + one Update Issue (pastes the Description). Skipping the second leaves a TC with no readable documentation in Jira: the most common silent failure.

Anti-patterns D1 · D6

Never hand-write ADF JSON: rich-text bodies (ATP, ATR, Test description) are written in Markdown, converted and validated with the .agents/skills/acli/scripts/md-to-adf.ts converter, and what gets published is the resulting ADF JSON; through the CLI, acli never converts Markdown on its own. Never invent a customfield_NNNNN: run bun run jira:sync-fields --force and resolve by {{jira.<slug>}}.

Description always with the full template: Related Story · Priority · ROI · Prior bugs · Test Design (gherkin/steps) · Variables · Implementation Code · Architecture · Test IDs · Preconditions · Expected Results. Every TC created: parent "QA Test Repository", components = the affected product module, assignee = the session user, set at creation.

This phase's dispatch is the only parallel one: N > 10 TCs → subagents in chunks of 5-10 (see the orchestration slide). Each subagent loads /xray-cli or /acli depending on modality and runs this serial flow for its chunk.

phase 3: document · the artifact that travels to automation

High-quality Gherkin: variables, never hard data

TC · UPEX-101.feature
@critical @regression @automation-candidate @UPEX-101
Scenario Outline: should show auth error when password is incorrect
  """  Bugs covered: UPEX-202 · Related Story: UPEX-101 · ROI: 4.0  """
  # === PRECONDITIONS ===
  Given a verified user exists with {email}
  # === ACTION ===
  When the user submits login with {email} and {wrong_password}
  # === VALIDATIONS ===
  Then a 401 error is returned with "<message>"
  # === EQUIVALENT PARTITIONS ===
  Examples: Wrong password | Empty password | Unknown email
  • Variables, never hardcode. {mentor_id}, not 550e8400-…. A Variables table with how to obtain each value at runtime.
  • Tags always: priority (@critical…@low) + suite (@regression, @smoke if critical path) + @automation-candidate + @{US_ID}.
  • Structured comments: PRECONDITIONS / ACTION / VALIDATIONS / EQUIVALENT PARTITIONS.
  • Docstring with metadata: story, bugs covered, ROI.
  • Parameterize per partition: variants of the same behavior → ONE Test with Examples, not N Tests.
Staging data changes over the years: a literal UUID or email rots the test. Each variable carries its retrieval query ({email} → SELECT email FROM users WHERE active=true LIMIT 1). This Gherkin is exactly what /test-automation will consume.

phase 3: the last step, where Candidates go

Promote: title first, label and membership last

1

Re-derive

The title comes from the TC's Precondition + Action + verifiable result, never from the wording of the sprint outline.

2

Keep the prefix

{US_ID}: TC#: does not change. # is a stable index within the Story: if a sibling ended up Deferred, the gap stays.

3

Rewrite

If the live summary differs, [ISSUE_TRACKER_TOOL] Update Issue: the summary is a Jira field, it never goes through [TMS_TOOL].

4

Verify, only then promote

Valid title → regression-candidate label + RTP. The old → new change is recorded in progress.md.

The RTP, one per project

RTP: {PROJECT_KEY|module}: Regression Test Plan, parent "QA Master Test Plan", find-or-create (ask before creating). Assignee = you at creation: Xray rejects membership edits on a Test Plan that isn't yours; if you find someone else's, ask before reassigning. It moves to ready with the first promotion and stays there, never complete. Manual enters the same RTP with manual-only; Deferred never does. /test-automation and /regression-testing read from there: a Candidate outside the RTP does not exist downstream.

Group into e2e flows

A group = one journey that a spec runs end to end, named as a journey ("Checkout, guest purchase", not "Checkout tests"). A TC used by 2+ flows is an atomic component (a Steps module in KATA): it is listed under each flow and its count is the N of the Component value. It is written in the RTP description, ## Regression flows section (the durable copy) and as a column in COVERAGE-MATRIX. A Candidate with no flow is an alarm, not a category.

"Title on promotion" and RTP handoff sections in SKILL.md. The title rule holds for every write path: jira-xray (a sprint Test selected into the RTP) and jira-native (a Stage 4 Test created from a sprint outline). In jira-native the promotion also travels in the Test's labels; /regression-testing describes how it reads that. Lifecycle: the RTP is born in planning, designed → ready, never complete; a feature TS stays in designing until its Epic closes; Preconditions stay in active.

Inline (orchestrator)

judgment

Parallel (Phase 3, N > 10)

Chunks of ~5-10 TCs per subagent, cap = 10 subagents (Jira/Xray throttle and return 429; the cap is in SKILL.md §Subagent Dispatch). Each subagent loads /xray-cli or /acli. N ≤ 10 → inline.

Error protocol

close: where it fits and how it is invoked

Derive broadly · document what repeats · automate the few

How to invoke it

Claude Code: /test-documentation <KEY>, /test-documentation repair-traceability <KEY> or /test-documentation post-promotion. OpenCode and Codex: "load the test-documentation skill, <mode> mode". Pi: /skill:test-documentation <mode>. Also by phrases: "document tests", "ROI analysis", "which tests to automate", "fix-traceability".

Handoffs in the pipeline

Comes in from /sprint-testing (Story QA Approved, closed bug). Goes out to /test-automation, which re-scopes the Candidates: module → Macro · ticket → Medium · bug → Micro (ad-hoc enters wherever it fits). Manual and Deferred are terminal.

Artifacts it leaves

Durable, in the TMS: TCs linked US↔ATS↔ATP↔ATR↔TC with their ROI comment · Candidates in the RTP with ## Regression flows · Prioritization comment with the Deferred ones. Local: the two [LOCAL] reports in .context/reports/, the [SYNC] cache in test-cases/ (read, not written) and the archived session in .session/.archive/.

The three rules to take away

1. Deferred by default: 3 filters + ROI = (F×I×S)/(E×D)/10. 2. One (precondition + action) = one TC; cross-cutting traits live inside the tests. 3. Set-first: ATS → ATP → ATR → TC, and an important bug always ends with a Test.

Close: Documentation is the bridge between manual QA (Planning · Execution · Reporting) and automation (Automation). The AI speeds up the craft; judgment and confirmations remain the human's.
