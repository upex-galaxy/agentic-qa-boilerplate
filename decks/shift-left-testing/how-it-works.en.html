AGENTIC QA · WORKFLOW SKILL · SHIFT-LEFT

/shift-left-testing

Pre-sprint QA on a batch of backlog Stories: it refines the Acceptance Criteria, surfaces gaps and ambiguities, and leaves the real ATP of each Story drafted at outline maturity. Defects are prevented in the requirements, before anyone writes a line of the feature.

Shift-Left (historically Stage 0) · Pre-sprint Batch of 1-12 Stories No execution: the feature doesn't exist yet Jira is canonical
Welcome. This deck walks through the real workflow of the /shift-left-testing skill step by step: what goes in, what the AI does, which gates wait for your approval and which artifacts come out. Rule of thumb: fixing a defect in the requirements costs 1; in development, 10; in production, 100.

The agentic contract of Shift-Left

The agent rewrites the ACs as Given/When/Then with concrete data, surfaces gaps and ambiguities, drafts the pre-sprint ATP in the Story's field, assigns the AI Effort (Low, Medium or High) and applies the Test-Design Checklist. The person signs off on the batch of candidate Stories and on the per-Story summary, and never lets a Story move to Ready For Dev without that. Evidence that survives: the rewritten ACs, the gaps as open questions to PO/Dev, the dated label and the review subtask. CSA autonomy 2 and no separate verifier: the PO or dev refining the Story is the natural reviewer.

Memorize this column: Preflight → Init → Selection → Refinement → Handoff → Batch report. Each row is a section of the deck; the stage verifier, the session footer and the optional fleet come at the end. The adjacent paths live on the right: approval gates, fallbacks and handoffs to other skills.

before Phase 0: readiness gate

Preflight: probe, don't assume

Law 1 · Args-as-answers

What the user already said (the Story IDs, the modality, "groom the backlog") counts as an answer already given. Only the real gaps get asked, all together, in ONE checklist.

Law 2 · Probe, don't assume

Every capability is checked with a real probe. A blocking RED stops the session: the skill names the exact env var, points to .env and asks you to restart the agent session.

CapabilityNeedProbe / why
/acli (issue tracker)REQUIREDbun run jira:check: all the refinement output lands in Jira
Resolved TMS modalityREQUIREDA: Xray · B: Jira-native. It is persisted for /sprint-testing; the pre-sprint ATP lives in the field in BOTH
/xray-cli + XRAY_* credsN/ANot used pre-sprint: the ATP is field-first and the Test Plan item is created by /sprint-testing Planning from the field
Business maps + MTPREQUIREDbusiness-data-context, business-api-context and business-e2e-context exist AND are generated: bun run context:map <slug> --list lists sections, with no placeholder warning. Plus master-test-plan.md. Skill missing → bun sync · placeholder → the project-context mode · MTP missing → bun run context:hydrate (and if the Epic has no plan, test-plan mode)
Candidate listREQUIREDExplicit IDs or a backlog JQL, size confirmed with the user

A light gate by design

Shift-left never runs against a live system: the app env, test-user credentials, DBHub, OpenAPI, Playwright and resend are all N/A here. Feasibility is established by READING code, APIs and schema, never by running the app.

Preflight runs before everything, even before the resume check. Its two laws prevent the two classic failures: quizzing the user about things they already said, and assuming a CLI is authenticated without testing it. And a placeholder map passes an "is the file there" check while carrying nothing, which is why the probe is --list.

phase 1: selection · the triage funnel

Selection: read carefully, filter out loud

detail read: the reads-vs-writes rule
$ bun run jira:sync-issues get UPEX-100 --include-comments   # 1 Story: ACs + custom fields + comments
$ bun run jira:sync-issues jql "project = UPEX AND issueType = Story AND status in (Backlog, ...)"
# NEVER `acli view` for custom fields: it returns null. `acli search` only for the trivial list.
1

Type filter

Stories only. Bug / Spike / Sub-task / Tech-debt → rejected WITH a one-line reason, never silently.

2

Label freshness

Already shift-left-reviewed with a dated label under 30 days old? It is shown separately: the user decides skip or refresh.

3

Veto table

Money / auth / data-integrity / integration / state machine → FORCE FULL. Pure CSS / copy / docs → SKIP.

4

Risk score

Only without a veto. New feature +3 · dynamic data +3 · AC-light +2 · effort +2 · >5 comments +1…

5 · Data feasibility scan (HIGH only)

Reads the data and API maps (bun run context:map) and the master-test-plan, with no queries or API calls. If the data model doesn't support the ACs → DATA-FEASIBILITY-RISK flag (soft: it doesn't block, it becomes a critical question for the PO).

The funnel runs in strict order: type before label, label before veto, veto before score. Loud rejection IS value: it often reveals that the board is mislabeled. Freshness comes from the dated label, never from the issue's updated timestamp (any comment resets it).

phase 1: veto beats score · candidate gate

Judgment overrides arithmetic, and you approve the set

ScoreLevelRefinement depth
0-3LOWSKIP: PO/Dev write the ACs without QA
4-7MEDIUMStandard refinement (Phases 1-3 + outlines)
8+HIGHExtended: more ambiguity and edge-case hunting; expanded question set

The score is a guide

The user can rescue a LOW if they smell hidden complexity. And the VETO short-circuits: a refunds Story is mandatory refinement even if it scores 2; a CSS tweak is a skip even if it touches five files.

GATE: it presents the table and WAITS for the OK

Phase 1 ends with a ranked table: Accepted (risk · score · veto override · data-feasibility), Rejected (non-Story, with reason), Skipped (LOW), Already Reviewed (skip/refresh?), recommended order and open questions.

Nothing gets refined until the human confirms the set. They can veto Stories, rescue LOWs or change the order. The final accepted list is persisted in progress.md, inside the Phase 1 entry.

After the OK, for each accepted Story: find-or-create the [QA] Shift-Left Review subtask with assignee = self from the create. It is born in {{jira.status.subtask.active}} (status ACTIVE) and stays there until Phase 3; if it already existed closed, it is reopened with reactive. No subtask work type in the catalog → skip with a warning, never blocks.

Optional, with a person at the keyboard: if reading the Stories already shows gaps that don't need code to answer (an AC with no failure path, an undefined term, a number with no unit), they are collected and deduplicated, and the to-questionnaire skill builds one questionnaire for the PO. It is written to .session/shift-left-testing/<batch-id>/, so answers can arrive while the batch is being refined.

Selection is a proposal and the human decides. This gate keeps the human steering the batch, with the same pattern as the Story Explanation gate in sprint-testing. The subtask makes the pre-sprint QA work visible on the board and later receives the long annotations, so the Story stays clean.

phase 2: refinement · one subagent per story, sequential

Refinement: the playbook, at outline scope

Deliberate reuse: most of the logic lives in sprint-testing/references/acceptance-test-planning.md §Phases 1-3; the subagent cites it and applies the shift-left delta. Sequential by design: you present each summary to the user before dispatching the next Story.

It runs (outline scope)

  • Phase 1 · Critical Analysis: business + technical context; LIGHT code reads (is it feasible?), no reproduction
  • Phase 2 · Story Quality Analysis: the heart (next slide)
  • Phase 3 · Refined ACs: Given/When/Then with specific data
  • Phase 4 · outlines: NAMES + coverage count only (feeds the AI Effort and the split decision)
  • Phase 5 · edge cases: names + criticality only
vs

It defers or forbids

  • Parameterization tables, test-data JSON, Faker recipes → in-sprint (/sprint-testing)
  • TC creation → /sprint-testing or Documentation (/test-documentation), depending on the modality
  • Jira mutations → done by Phase 3, never by the subagent
  • Execution: smoke, DB queries, API calls → NOTHING runs
  • Git: no branch or commit, Jira is canonical
  • evidence/ folder: there's nothing to capture
The outline discipline separates shift-left from executable test design: outline titles and coverage count, never the data. The ATP that gets written is already the real one, at outline maturity. Generating Faker recipes now would be wasted work that gets redone in-sprint.

phase 2: story quality analysis + design doctrine

The heart: what the Story leaves unsaid

What you hunt (playbook Phase 2)

  • Ambiguities: location + question for PO/Dev + testing impact + suggested clarification
  • Gaps: missing AC / business rule, why it's critical, risk if omitted
  • Unwritten edge cases: scenario + likely behavior + criticality
  • Contradictions: "the description says X but AC3 says Y", stated explicitly
  • Testability: Yes / Partial / No, listing each vague AC or non-isolable dependency

Toolkit: refinement-questions.md, a catalog by archetype (auth, money, search, state machine, integration, RBAC).

Design doctrine (binding)

  • The ACs are the FLOOR: refinement pushes past the happy path
  • 1:N by default: a non-trivial AC implies several outlines; collapsing to 1 requires a written "trivially atomic" justification
  • Technique by trigger: ranges → BVA · states → State-Transition · interacting conditions → Decision Table · 3+ factors → Pairwise
  • Every inferred scenario carries the NEEDS PO/DEV CONFIRMATION marker, verbatim, all the way to Jira
  • A clean Story is a valid result: zero forced questions; padding and under-derivation are BOTH failures
This is where shift-left creates value: the PO can still act. Every ambiguity caught is a production defect erased before it is born, and every gap is also a missing outline.

phase 2: the staging buffer + per-story gate

shift-left-refinement.md and your OK per Story

shift-left-refinement.md: skeleton + example
├─ Phase 1 · Critical Analysis
├─ Phase 2 · Story Quality Analysis   ← the heart
├─ Phase 3 · Refined ACs
│   Given user with active OTP <5 min
│   When  submits code "000000" (wrong)
│   Then  UI "Invalid code" · API 401 · DB no session
│   NEEDS PO/DEV CONFIRMATION ← if inferred
├─ Phase 4 · Test Outlines (pre-sprint) ← names + coverage
├─ Phase 5 · Edge Cases (pre-sprint)    ← names + criticality
├─ Story Quality Assessment · Critical Questions for PO
├─ Technical Questions for Dev · Suggested Improvements
└─ Data feasibility flags · Recommended testing strategy
  • [LOCAL] buffer, not a deliverable. Written by hand in the Story's PBI folder, under .context/PBI/** (gitignored): it exists only on the machine that ran the batch. Phase 3 publishes its full body into the ATP field, and from then on the canonical copy is the one in Jira.
  • Nothing depends on it being on disk. /sprint-testing short-circuits by reading the SYNCED acceptance-test-plan.md, never this file. The Jira mirrors (story.md, acceptance-criteria.md) are generated only by the sync.
  • Bootstrap: if the PBI folder doesn't exist, the subagent creates it with a minimal context.md. No evidence/.
  • Outline convention: Should <behavior> <condition>, grouped by type with a coverage table (Positive / Negative / Boundary / Integration).
  • Return to the orchestrator: compact JSON with quality, #gaps, #PO/Dev questions, outlines by type, flags.
  • Interview: if the summary carries real doubts and a person is at the keyboard, the orchestrator calls the grilling skill: numbered rounds, each question with a recommended answer, and it doesn't ask what the Story already answers. The NEEDS PO/DEV CONFIRMATION marker only comes off with the answer from whoever owns it (PO or BA for behavior, Dev for feasibility).
  • Glossary: if an answer pins down a term that business-domain-context doesn't have, domain-modeling proposes it as a new section with evidence, and it is applied only if the person says yes. The skill never edits the map on its own.
  • GATE: the orchestrator presents the summary, waits for your OK, records the Phase 2.<n> checkpoint in progress.md and only then dispatches the next Story.
The section order is structural: it becomes the block the PO reads in Jira. The per-Story checkpoint lets you resume a batch halfway without repeating work. If the sprint-testing short-circuit depended on this local file, on any other machine it would silently degrade into a full re-run.

phase 3: handoff · 6 jira mutations per story (via /acli)

Handoff: six mutations, in order

1

ACs → field

Refined ACs go to the acceptance_criteria field. Fallback if it doesn't exist: a "## Acceptance Criteria" comment. Verified with a re-sync.

2

Description

Append "QA Refinements (Shift-Left Analysis)": edge cases + clarified rules + questions. Read first, NEVER overwrite.

3

ATP

Fills the acceptance_test_plan field with the pre-sprint ATP (outline maturity), field-first: the Test Plan item "ATP: {STORY-KEY}: {title}" is NOT created here; /sprint-testing Planning creates it from this SAME field, with no title variant. Fallback if the field doesn't exist: a "## Acceptance Test Plan (ATP)" comment.

4

Comment

ONE handoff comment: a pointer to the field (@PO / @Dev-lead only if they are in project.yaml). Full body inline ONLY if the field doesn't exist.

5

Labels + QA Assignee

shift-left-reviewed + shift-left-{YYYY-MM-DD}. qa_assignee = the record of the QA who followed the story: filled in here, kept for its whole life, and the dev reads it to know who to assign at Ready For QA. Read-before-write, via REST PUT (acli doesn't write customfields).

6

Transition + subtask + trace

analyze → refined and STOP at Ready For Dev, with the AI Effort already assigned. The [QA] Shift-Left Review subtask receives the exhaustive session notes and is closed with complete → Close (the Story stays clean). Re-sync: the ATP landed in the field and the comment is a POINTER; the inline body only applies in fallback mode. test-documentation repair-traceability mode audits it afterwards.

No hand-built ADF and no raw Markdown

Rich-text bodies (ATP, ATR, Test description) are written in Markdown, converted and validated with the .agents/skills/acli/scripts/md-to-adf.ts converter, and what gets published is the resulting ADF JSON; through the CLI, acli never converts Markdown on its own. Raw Markdown shows up in Jira with literal # and **; hand-crafted ADF drifts from the content that repair-traceability audits.

Sequential, one Story at a time, so you check the Jira state before the next mutation. The subagent returns a log per Story: atp_container (field or fallback comment), subtask, labels, transitions, light_verifier and trace_status.

phase 3: transition guardrails + resume

STOP at Ready For Dev, and everything re-runnable

Current statusAction
Backloganalyze → Shift-Left QA, then refined → Ready For Dev
Shift-Left QArefined only
Ready For Devnothing: it's already on target
Beyond (In Progress…)SKIP + warning: the refinement still lands, the workflow isn't touched

Splitting a Story is optional, never a barrier

QA never commits the Story to a sprint. If the AI Effort comes out High, QA leaves a note that it may be too big and need splitting, but the Story still goes to Ready For Dev and the dev works on it. A PO can clone or split it and refine again if they want shorter stories. And it is NEVER transitioned to Ready For Dev without the pre-sprint ATP filled in and the AI Effort assigned: without an ATP there is nothing to judge the verification effort by (anti-pattern L5).

Safe resume: every step is idempotent

  • Section already in the description → skip · ATP field → overwrite OK · comment already exists → skip
  • Labels are set-based · the transition reads the status before applying
  • [QA] Shift-Left Review subtask: looked up by exact title, never duplicated; if it is already in Close it isn't re-transitioned and the notes go in as a new comment (no subtasks in the project → skip with a warning)
  • Subagent error → STOP, partial state reported, options retry / skip / abort. No auto-rollback: the mutations are recorded in the batch report so you can pick up where you left off.
Two non-negotiables: stop at Ready For Dev (splitting a Story is the PO's decision) and always apply both labels; without them the /sprint-testing short-circuit breaks next sprint.

Every closed Story is checked line by line

# + the common template lines:

Each line is YES or a declared N/A with its reason; a blank line counts as a failure. A NO leaves the stage at NEEDS REVISION: fix it or report it, never move on. "Light" means what the agent already did, plus at most ONE read of the Story.

The stage's Definition of Done (stage-gates.md)

The orchestrator checks it against the subagent's report and what is in Jira BEFORE writing the status: completed checkpoint:

  • ACs refined in Given/When/Then with concrete data
  • Gaps, ambiguities and edge cases as questions to PO/Dev
  • Test-Design Checklist applied: every non-trivial AC exploded by technique, or a trivially atomic justification
  • Coverage count with the real 1:N, no minimized count
  • Inferred items marked NEEDS PO/DEV CONFIRMATION
  • No TMS entity created; label + transition applied
  • Statuses per the lifecycle; light verifier run

Unmapped status: you ask, you never skip

If the project renamed the statuses and a slug is missing (for example the subtask's complete), the skill lists the issue's LIVE transitions, asks ONE question with the best candidate, fires the live id with your OK and recommends bun run jira:sync-workflows. .agents/jira-workflows.json is generated: it is never edited by hand.

A stage doesn't end when the subagent returns: it ends when its Definition of Done is met. The light verifier exists to catch what was silently skipped, without re-auditing everything that was just created.

phase 3: session close · batch report + archive

The batch report: the only thing grooming reads

What it aggregates

  • Session metadata: candidates / accepted / rejected / skipped / refined
  • One line per Story: risk · #gaps · #PO questions · #tech Qs · #outlines · final status · trace
  • Deduplicated PO questions, ranked by how many Stories each one blocks
  • Risk distribution + DATA-FEASIBILITY blockers with the pre-work required
  • Recommended sprint planning order (risk + dependencies)

Where it goes, and the close

  • Always: .session/shift-left-testing/<batch-id>/batch-report.md
  • If ALL the Stories share a parent epic → it is published as a comment on that epic; otherwise it is delivered inline to the user
  • Never published on each Story: the per-Story comment already exists (step 4)
  • Final entry in progress.md → Archive: the session folder moves to .session/.archive/
  • Memory close: mem_session_summary with the summary + archive path
"This question blocks three Stories" is exactly how a PO wants to triage. If publishing to the epic fails, it doesn't abort: the local report is authoritative.

If the skill is what failed

A wrong step, a missing verifier or an outdated rule is reported upstream per agentic-qa-core/references/upstream-feedback.md: a draft written locally, published only with your explicit OK and verified with gh issue view.

The footer is the last line of the light verifier: without it, the stage isn't closed. It's where you see which pyramid levels stayed at "none" and whether the session left proposed improvements to review.

optional · big batches · fleet seam

One worker per Story, the same gate

Refinement is sequential by default and stays that way. The fleet (one persistent worker session per Story and a conductor that gathers their reports) only comes in when the user explicitly asks for it on a big batch.

Topology: the same checkout

The skill only writes to Jira: no code, no branch, no contested git index. A worktree per Story would be pure cost.

launch.txt, always

The conductor writes .session/shift-left-testing/<batch-id>/launch.txt, one self-contained line per Story, whether or not the machine has an orchestration transport. Launching, supervising and closing those sessions belongs to agent-orchestration; if nothing can launch them, a person pastes those lines.

The per-Story OK moves to the conductor

The conductor presents each worker's summary as it arrives and waits for the same approve / veto before that Story's Phase 3 handoff. A fleet that skips this is no longer running this skill.

One writer per Story

Two workers never refine the same Story, and every Jira write for a Story belongs to its worker. The batch report and the epic comment stay with the conductor.

With no human at the keyboard, nothing waits

A worker or a routine can't answer: the interview follows the autonomous path of grilling (each doubt with its recommended answer under ## Open Questions, inferred items stay marked and the report says what was assumed), new terms go in as "Proposed glossary terms" and the map isn't edited, and to-questionnaire writes the file and the run moves on. What gets written to Jira (subtask and handoff) only runs if the brief authorizes it; without that authorization the routine leaves the batch ready for handoff.

Silence rule

When the machine has no orchestration transport, the skill doesn't mention it: not in the preflight, not in the batch report, not in the chat. The launch.txt still gets written.

Parallelizing doesn't buy speed at the human's expense: the per-Story gate still exists, only who presents it changes. By default the skill runs sequentially, which is the pace of a team grooming session.
