Template literals: text with blanks

😐 How you did it yesterday

const msg = "Hello, " + name + "! You have " + bugs + " bugs";

It works, but with 3+ variables it turns into a soup of quotes and + signs.

😎 From now on

const msg = `Hello, ${name}! You have ${bugs} bugs`;

Backticks ` (not quotes) + ${...} = a blank where any variable or expression fits.

⌨️

The backtick ` sits next to the 1 on a US keyboard, or is AltGr + } on a Spanish/LatAm keyboard. Required practice: you will use it in every test.

A trivial concept, but used every day: real specs are full of template literals. Retention trick: "string with blanks". It matters to point out where the backtick is on their keyboard, since that is the number one real friction with this syntax. Everything from session 1 with "+" is still valid; this is ergonomics.

Arrow functions: you were already using them 🏹

The same function, in 3 transformation steps:

// 1. The classic from session 1
function double(n) { return n * 2; }

// 2. Same function, with an arrow
const double = (n) => { return n * 2; };

// 3. A single expression → implicit return
const double = (n) => n * 2;

🏹 The arrow =>

Read it as: "receives n and returns n * 2". A compact function, ideal for passing to another function.

👀 Does this look familiar?

test("login", async ({ page }) => {
  ...
});

Your test from session 1 was an arrow function! Now you can finally read every symbol.

The "aha!" moment of the act: the test() they wrote in session 1 already used arrow + async. The 3-step transformation is the mental path, so show it slowly. What the compactness is for: passing functions to map/filter (next act). Do not mention differences in this between function and arrow: unnecessary noise at this level.

Destructuring: unpacking boxes 📤

const user = { name: "Ana", role: "admin" };

// yesterday: one by one
const name = user.name;
const role = user.role;

// today: unpack in one go
const { name, role } = user;

📤 The rule

Braces on the left of the = mean "extract these properties from the object on the right". The names must match.

🎭 Mystery solved

async ({ page }) => { ... }

Playwright hands you an object full of tools. ({ page }) = "from the package you give me, I only unpack page". Mystery from session 1: closed. 🔓

Second "aha!" of the act: ({ page }) finally explained. Playwright passes an object of fixtures (page, request, context, browser...) and the test unpacks what it needs. When they reach KATA they will see ({ api }), ({ ui }), ({ test }), exactly the same pattern. That connection is worth the whole session.

.map(): transform every element 🔄

  

    

      
const users = ["ana", "luis", "mia"];

const emails = users.map(u => `${u}@qa.com`);

// ["ana@qa.com", "luis@qa.com", "mia@qa.com"]

      
Read it as: "for each u in the array, give me back `${u}@qa.com`". A new array, same size, transformed elements.

    

    

      
🆚 Yesterday's loop

        
const emails = [];
for (const u of users) {
  emails.push(`${u}@qa.com`);
}

        
Same result, 4 lines. map says it in 1: arrow functions paying dividends.

      
🧪 In testing
Generate test emails, extract ids from an API response, prepare the data column the test needs.

    

  

  
map/filter/find exist because arrow functions make it cheap to pass "mini-recipes" to other methods. Read the pattern aloud: "for each u, give me back X". Yesterday's loop does not become obsolete: map is the shortcut for the most common case (transforming a whole list).

.filter() and .find(): choosing with criteria 🎯

  

    

      
🚿 filter: everything that matches

      
const users = [
  { name: "Ana",  role: "admin"  },
  { name: "Luis", role: "viewer" },
  { name: "Mia",  role: "admin"  },
];

const admins = users.filter(u => u.role === "admin");
// [Ana, Mia]: an array, it can come back empty []

    

    

      
🔍 find: the first one that matches

      
const luis = users.find(u => u.name === "Luis");
// { name: "Luis", role: "viewer" }
// one object, or undefined if nobody matches

      
🧪
Your test data table, filtered with code: "give me only the admins", "find the inactive user". The condition is the same as yesterday's if/else.

    

  

  
Key distinction: filter returns an array (possibly empty), find returns one element (or undefined, which connects to the undefined they saw in session 1). The condition inside is a boolean expression identical to the ones in an if. The full trio: map transforms, filter selects several, find looks for one.

The problem: data and functions live apart

  

    

      
😵 Everything loose

      
const tester1 = { name: "Ana", bugs: 0 };
const tester2 = { name: "Luis", bugs: 0 };

function findBug(tester) {
  tester.bugs = tester.bugs + 1;
}
// which functions go with which objects?
// who guarantees that tester has .bugs?

    

    

      
🧩 The symptom
Objects on one side, functions on the other. With 5 objects and 15 functions, nobody knows what goes with what.

      
💡 The idea
A class brings together in one place: the data (properties) + the functions that work on it (methods). A mold 🍪 that makes objects already equipped.

    

  

  
Motivation before syntax: the pain is real (a mess of loose functions and objects) and the class is the natural solution. Cookie cutter analogy: the class is the cutter, the objects it makes are the cookies, each independent but with the same shape. That analogy carries the whole section.

Anatomy of a class 🏗️

  

    

      
class Tester {
  constructor(name) {
    this.name = name;
    this.bugs = 0;
  }

  findBug() {
    this.bugs = this.bugs + 1;
    return `${this.name}: ${this.bugs} bugs`;
  }
}

    

    

      
class Tester
"I define the Tester mold." The name always starts with a capital letter, a universal convention.

      
constructor(name)
The function that runs automatically when each object is made. It receives the initial data.

      
this
"This particular object": the cookie being made or used, not the mold.

      
findBug()
A method: a function that lives inside the class and works with the data in this. Without the word function.

    

  

  
Four pieces, one per card. this is the difficulty. Working definition: "the specific object being worked with at that moment". Do not philosophize further: the next slide makes instances and the memory visualizer shows it step by step. Syntax detail: methods without the word function, no commas between them.

new: making cookies 🍪

  

    

      
const ana  = new Tester("Ana");
const luis = new Tester("Luis");

ana.findBug();  // "Ana: 1 bugs"
ana.findBug();  // "Ana: 2 bugs"
luis.findBug(); // "Luis: 1 bugs" ← its own counter!

    

    

      
🏭 new Tester("Ana")
"Make an object with the Tester mold": it runs the constructor with name = "Ana" and hands back the instance.

      
🍪 Each instance, its own memory
ana.bugs and luis.bugs are independent counters. There is one mold; there are many cookies.

      
👀 Spoiler
Playwright's page… is an instance of a class. page.click() = a method. You have spent a whole session using classes.

    

  

  
Instance independence = the concept of quiz 3, stress it: each new creates fresh memory. The page spoiler is another powerful bridge: they are not heading into unknown territory, they are heading toward understanding what they already use. Check question before moving on: "if I do new Tester('Mia') and call findBug once, what is mia.bugs?"

New pain: classes that repeat 😩

  

    

      
class Admin {
  constructor(name) { this.name = name; }
  login() { return `${this.name} logged in`; }
  deleteProject() { return "💥 deleted"; }

class Viewer {
  constructor(name) { this.name = name; }
  login() { return `${this.name} logged in`; }
  watch() { return "👀 watching"; }
}

    

  

  
🚨
constructor and login() are copied and pasted. Look familiar? It is the same pain as the repeated test cases from session 1, and the solution has the same shape: write the common part once.

  
Inheritance is motivated by the same principle that motivated functions in session 1: do not repeat yourself. Admin and Viewer share a constructor and login; each differs by one method of its own. Ask the room: "where have you seen this copy-paste before?" The answer (duplicated test cases) belongs to them and makes the solution theirs.

extends: inheriting the common part 🧬

  

    

      
class User {
  constructor(name) { this.name = name; }
  login() { return `${this.name} logged in`; }
}

class Admin extends User {
  deleteProject() { return "💥 deleted"; }
}

const ana = new Admin("Ana");
ana.login();         // inherited from the parent ✅
ana.deleteProject(); // Admin's own ✅

    

    

      
🧬 extends
"Admin is a User, plus its extras." It inherits the parent's constructor, properties and methods, for free.

      
📞 super(...)
If the child defines its own constructor, the first line must be super(name): "parent, do your part first". If it defines no constructor, it inherits the parent's directly.

      
🥋 Why it matters to you
The KATA framework you are heading to is a chain of extends: your Page inherits dozens of helpers that are already written. Understanding this = reading KATA without fear.

    

  

  
Read extends as: "is a... plus extras". super is needed only when the child defines its own constructor. The example avoids it on purpose to show the simple case first; the next playground does use super. The KATA card is the reason for the whole session: in the professional repo, LoginPage extends UiBase extends TestContext, and they will read that chain naturally.

In class Admin extends User, what does super(name) do?

Page Object: a class that wraps a page 🎁

  

    

      
class LoginPage {
  constructor(page) {
    this.page = page;   // keeps the "remote control"
  }

  async login(email, password) {
    await this.page.fill("#email", email);
    await this.page.fill("#password", password);
    await this.page.click("#login-btn");
  }
}

    

    

      
🎁 The move
Everything you can do on the login page, encapsulated in one class. The selectors live here and only here.

      
📺 constructor(page)
It receives Playwright's page and stores it in this.page: the browser's remote control, now owned by the instance.

      
🧬 Everything from this session, together
class ✓ · constructor ✓ · this ✓ · async method ✓ · await ✓. Zero new concepts, just composition.

    

  

  
Emphasis: there is nothing new on this slide. It is the Tester class with page inside. this.page.fill = "from this instance's remote control, call fill". Official name: Page Object Model (POM), an industry-standard pattern. Drop the term so they recognize it in articles and interviews.







  
The refactor: before / after

  

    

      ❌ Before: 8 lines per test
      
test("successful login", async ({ page }) => {
  await page.fill("#email", "ana@qa.com");
  await page.fill("#password", "secret123");
  await page.click("#login-btn");
  await expect(page.locator("#welcome"))
    .toBeVisible();
});

    

    

      ✅ After: the test tells a story
      
test("successful login", async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.login("ana@qa.com", "secret123");
  await expect(page.locator("#welcome"))
    .toBeVisible();
});

    

  

  
🏆
The test now reads like a manual test case: "create the login page, sign in with these credentials, verify the welcome". And if #login-btn changes, you fix 1 line inside LoginPage, not 50 tests.

  
A double win to highlight: readability (the test reads like their manual test case, closing the circle with the slide "You already know how to code. Just on paper." from Coding Base) and maintenance (the selector changes, so there is 1 single place to fix). The assertion stays in the test on purpose: actions go to the Page Object, and the expects stay where pass/fail is decided. That split reappears in KATA.
