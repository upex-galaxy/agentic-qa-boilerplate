📖 Group by feature

The report reads like an index: Login → its cases. With 100 tests, chapters save lives.

🎯 Run one chapter

npx playwright test -g "Login" runs only that group.

🔧 Focus tools

test.only(...) runs ONLY that test (debugging) · test.skip(...) skips it, on the record. ⚠️ Never commit an .only.

A light concept to warm up. describe takes an arrow function with the tests inside, a syntax they already read fluently. A forgotten .only in a commit is a classic: the suite "passes" in CI because it ran ONE test. Recommended anecdote if you have one of your own.

beforeEach: write the login ONCE 🪝

❌ Before: login copied into every test 
test("view dashboard", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("Email").fill("testuser@upex.dev");
  await page.getByLabel("Password").fill("Test123!");
  await page.getByRole("button", { name: /sign in/i }).click();
  // ...finally the real test
});
// ...and again in the next test 😩
✅ After: the hook does it for everyone 
test.describe("Dashboard", () => {

  test.beforeEach(async ({ page }) => {
    await page.goto("/login");
    // ...login steps, just ONCE
  });

  test("view dashboard", async ({ page }) => {
    // starts ALREADY logged in 🎉
  });

  test("create task", async ({ page }) => {
    // also logged in
  });
});
🪝

beforeEach runs before EACH test in the group, so every test starts with a fresh, logged-in page, independent of the others. There are also afterEach, beforeAll, afterAll (cleanup and heavy setup).

Hooks = the preconditions of their manual test case, in code and shared. A fine point: beforeEach runs for EACH test (isolation: a test does not inherit the previous one's mess); beforeAll runs once per group (faster, less isolated). For this level: beforeEach always, beforeAll when the slowness hurts.

⭐ QUIZ 1 · Hooks

A describe has 3 tests and a beforeEach with login. How many times does the login run when the group runs?

💡 beforeEach = before EACH test. That guarantees isolation: every test starts clean, without inheriting the state (or the mess) of the previous one. Option A describes beforeAll, which is faster but shares state: the classic speed vs isolation trade-off.

The name says it (Each), but the deeper implication is isolation, the property that makes a suite reliable and parallelizable. Plant the word "isolation": it comes back in API testing and in KATA.

The hierarchy: pick locators that survive 🛡️

PriorityLocatorWhy
🥇 1stgetByRole("button", { name: "Sign in" })How a user (and a screen reader) perceives it. Survives redesigns.
🥈 2ndgetByLabel("Email") · getByPlaceholder(...)Anchored to the visible text of the form.
🥉 3rdgetByText("Bienvenida")For non-interactive texts and messages.
4thgetByTestId("submit-btn")An anchor built for testing (data-testid). Ask the dev team for it.
🚨 lastpage.locator(".btn > div:nth-child(2)")Structural CSS: dies with any redesign. Only when there is no alternative.
♿

Hidden bonus: if getByRole cannot find your button, a user with a screen reader has the same problem. Semantic locators = robust tests AND a free accessibility audit.

The table IS the lesson, so let it breathe. Mental rule: "how would you describe the element to a human over the phone?" That is the right locator. The accessibility bonus lifts the conversation: a QA who catches a11y problems in passing adds extra value. data-testid: the convention for asking the dev team for anchors when the DOM is hostile.

Chain and filter: aim precisely 🎯

The problem: there are 10 rows, I want ONE

// "the Delete button in Ana's row"
await page
  .getByRole("row")
  .filter({ hasText: "Ana" })
  .getByRole("button", { name: "Delete" })
  .click();

It reads like the sentence: row → that contains "Ana" → its Delete button. Chaining = narrowing the context step by step.

Web-first assertions (they wait on their own)

await expect(locator).toBeVisible();
await expect(locator).toHaveText("Saved");
await expect(locator).toHaveCount(3);
await expect(locator).toBeEnabled();
await expect(page).toHaveURL(/dashboard/);

They retry automatically until they pass (or time out). That is why you never need sleep: the assertion IS the wait.

filter + chaining solves the most common real case: tables and lists. Web-first assertions close the anti-sleep circle: expect(...).toBeVisible() RETRIES until it shows up, so the smart wait is built into the assertion. Whoever understands this never writes waitForTimeout again.

⭐ QUIZ 2 · Locators

The team redesigns the whole CSS of the app (new classes, new structure, same texts). Which locator still works?

💡 The redesign changed classes and structure (killing A and B) but the button is still a button that says "Sign in". Role and accessible name are the contract with the user, and that contract is the last thing to change. A semantic locator = betting on the contract, not on the implementation.

Key phrase of the explanation: "betting on the contract, not on the implementation". It is a general engineering principle that will come back in API testing (the OpenAPI contract) and in KATA. Plant it well.

Your LoginPage... for real this time 📄

pages/login-page.ts
import { type Page, type Locator } from "@playwright/test";

export class LoginPage {
  readonly emailInput: Locator;
  readonly passwordInput: Locator;
  readonly signInButton: Locator;

  constructor(private page: Page) {
    this.emailInput = page.getByLabel("Email");
    this.passwordInput = page.getByLabel("Password");
    this.signInButton = page.getByRole("button", { name: /sign in/i });
  }

  async goto() {
    await this.page.goto("https://dojo.upexgalaxy.com/login");
  }

  async login(email: string, password: string) {
    await this.emailInput.fill(email);
    await this.passwordInput.fill(password);
    await this.signInButton.click();
  }
}

🆕 vs Coding Classes

The same class you built in the simulator, with 3 production upgrades.

📍 Locators as fields

Declared ONCE in the constructor, typed as Locator, reused in every method.

🏷️ Real TypeScript

type Page imported, readonly (cannot be reassigned), private page = parameter and property in one step.

📤 export

The word that lets other files do import { LoginPage }.

The reunion: the class from the Coding Classes simulator, production version. Three novelties to name without drama: locators-as-fields (the modern POM standard), readonly (const for properties), private page in the constructor (a TS shortcut: parameter + property). export/import: the module mechanism they saw conceptually in Coding Base, which they now use for real.

📜 The sacred split

Actions → live in the Page Object.
Assertions (expect) → live in the test.
The test decides what counts as pass/fail; the page only knows how to be operated.

The actions/assertions split is THE architecture rule of this session (and a quiz question): the Page Object operates the page, the test judges the result. If the POM does expects, it decides pass/fail instead of the test and becomes inflexible. Note the pages/ folder kept separate from tests/, an order that scales.

⭐ QUIZ 3 · POM

According to the sacred split, where does expect(page).toHaveURL(/dashboard/) live?

💡 If login() included the dashboard expect, you could not reuse it for the case "invalid login stays on /login": the method would fail by design. Actions go to the POM because they REPEAT; assertions go to the test because they CHANGE with each case. Reusability vs specificity.

The explanation gives the ARGUMENT, not just the rule: the same login() serves the valid and the invalid case precisely because it assumes no outcome. Whoever answered A and hears this understands WHY, which is worth more than getting it right.

Fixtures: create your own ({ page }) 💉

fixtures.ts
import { test as base } from "@playwright/test";
import { LoginPage } from "./pages/login-page";

export const test = base.extend<{ loginPage: LoginPage }>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await use(loginPage);  // ← the test runs here
  },
});
export { expect } from "@playwright/test";
tests/login.spec.ts, now
import { test, expect } from "../fixtures";

test("valid login", async ({ loginPage, page }) => {
  await loginPage.login("testuser@upex.dev", "Test123!");
  await expect(page).toHaveURL(/dashboard/);
});

🤯 The circle closes

The ({ page }) you have used since Coding Base IS a Playwright fixture. You just learned to build your own: ({ loginPage }) arrives already instantiated and on the login page, with no new, no goto, no beforeEach.

The most abstract concept of the session, so anchor it in what they know: page was always a fixture; extend adds your own to the same mechanism. The fixture pattern: prepare (new + goto) → use(object) = "the test runs here" → (after use: cleanup if needed). Do not go deep on the generic <{...}>: "it tells TypeScript what type the fixture delivers" is enough. The KATA connection goes in the closing.

Not everything deserves a browser: the pyramid 🔺

🖥️ UI / E2E: few, slow, fragile
🔌 API / integration: more, fast, stable
⚙️ Unit: many, instant (dev territory)

Your login test through the UI: ~5 seconds (browser, render, animations). The same login through the API: ~200 ms, and it does not break when someone moves a button.

🖥️ UI when...

You test the user JOURNEY: critical flows, visuals, real interaction.

🔌 API when...

You test business RULES: validations, permissions, data, 4xx errors. Most of your edge cases.

🥋 The dojo is waiting

It has a documented REST API: dojo.upexgalaxy.com/api/docs. Open it NOW and see which endpoints it offers.

The pyramid without dogma: a cost-benefit heuristic, not a religion. Practical message: "are you testing the journey (UI) or the rule (API)?" Validation edge cases through the UI = slowness multiplied; through the API they are milliseconds. Ask them to open /api/docs live, because mission P5 comes from there.

request: Playwright without a browser 🔌

test("API: login returns a session", async ({ request }) => {
  const res = await request.post("https://dojo.upexgalaxy.com/api/auth/login", {
    data: { email: "testuser@upex.dev", password: "Test123!" },
  });

  expect(res.status()).toBe(200);

  const body = await res.json();
  expect(body).toHaveProperty("access_token");
});

test("API: invalid login responds 401", async ({ request }) => {
  const res = await request.post(".../api/auth/login", {
    data: { email: "testuser@upex.dev", password: "mala" },
  });
  expect(res.status()).toBe(401);
});

💉 ({ request })

Another built-in fixture: an HTTP client ready to use, zero browser.

📨 Anatomy

post(url, { data }) sends JSON · res.status() the code · res.json() the body. You already know the statuses (200, 401, 404...) from the job.

🗺️ Shape vs reality

Exact routes and fields: in the dojo's /api/docs. These slides show the SHAPE, the same rule as in P0.

The second test (the sad path through the API) is the strongest argument: validating the 401 through the UI costs seconds and depends on visual messages; through the API it goes straight to the contract. Note that expect here has no await on status (it is not web-first, it is an immediate value). If someone asks, that is the reason; if not, do not complicate it.

⭐ QUIZ 4 · Strategy

You must test 12 combinations of invalid data in the sign-up form. Professional strategy?

💡 The validation RULES live in the backend → API: 12 cases in ~2 seconds, stable. What the UI uniquely contributes is SHOWING the error → 1-2 UI tests cover it. Division of labor: the API tests the rule, the UI tests the experience. Full coverage, fast suite.

The quiz lands the pyramid in a real suite-design decision. The formula "the API tests the rule, the UI tests the experience" is quotable and they will take it to work. Option C exists because real time pressure pushes there. Name it: with API testing, covering everything IS cheap.
