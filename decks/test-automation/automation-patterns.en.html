The pattern: one class = one page 🎁

class LoginPage {
  constructor(page) {
    this.page = page;        // the "remote control"
  }

  // selectors: a single source
  email    = () => this.page.locator("#email");
  password = () => this.page.locator("#password");
  submit   = () => this.page.locator("#login-btn");

  async login(email, password) {
    await this.email().fill(email);
    await this.password().fill(password);
    await this.submit().click();
  }
}

📍 Selectors on top, once

Each selector lives in ONE getter. Did #login-btn change? You edit 1 line, and the 50 tests never notice.

🎬 Actions as methods

login() tells a story: fill, fill, click. The test reads like a manual case.

🧬 Zero new concepts

It is the same old class: constructor · this · async method · await. POM = class + purpose.

We go up from the basic POM: here the selectors are centralized in arrow getters (this.page.locator). Professional rule you will see in KATA: a locator used in 2+ actions is extracted to a getter; used once, it goes inline. Do not philosophize yet: the next slide shows the action-vs-assertion rule, and then they run it live. Drop the official term: Page Object Model, the industry standard pattern.

The golden rule: actions inside, decision outside ⚖️

The Page Object: ACTIONS only

class LoginPage {
  async login(email, pass) {
    await this.email().fill(email);
    await this.password().fill(pass);
    await this.submit().click();
  }                       // does things, doesn't judge
}

The test: the pass/fail DECISION

test("successful login", async ({ page }) => {
  const login = new LoginPage(page);
  await login.login("ana@qa.com", "secreto123");

  await expect(page.locator("#welcome"))
    .toBeVisible();    // the decision is made here
});
🎯

The same login() action serves the happy case and the invalid one. Only the expect the test sets changes. Maximum reuse, with the decision in one visible place. This split shows up again, identical, in KATA.

The distinction that separates the amateur POM from the professional one: actions (effects) live in the Page Object; business assertions (the verdict) live in the test. Honest nuance: FIXED, unavoidable assertions (a mandatory redirect, status 201) can go inside the action as part of "the action finished fine"; BUSINESS assertions go outside. This same rule is KATA Rule 6 (fixed assertions inside, flow assertions outside). Announce it, it is a direct bridge.

🧩 The symptom
Building objects, navigating, authenticating, before every test. Noise that hides what the test actually checks.

      
🧹 And the cleanup?
Who logs out, deletes the created user, resets the state afterwards? Without fixtures: nobody, or it is copied into every test.

      
💡 The idea

📦 What is a fixture?
A ready-to-use resource that the framework builds, injects by name, and cleans up by itself. Dependency Injection (DI) applied to tests.

      
🎁 Playwright built-ins
page · request · context · browser. You ask by name for what you use; the rest is never even created.

      
🛠️ New in this session
Create your own with test.extend: a loginPage fixture, an authedUser… that arrive already prepared in every test.

Mention the technical term (Dependency Injection) once, without getting tangled up, since the intuition is what matters. The ({ page }) destructuring they already master is exactly how fixtures are requested: by name, unpacking only what is needed.

Building a fixture: setup → use → teardown 🔧

  

    

      
import { test as base } from "@playwright/test";

export const test = base.extend({
  // fixture called "loginPage"
  loginPage: async ({ page }, use) => {
    // 1 · SETUP (before the test)
    const login = new LoginPage(page);
    await login.goto();

    // 2 · hand it to the test
    await use(login);

    // 3 · TEARDOWN (after the test)
    await page.close();
  },
});

    

    

      
1 · Before use
Everything you write above use() runs as preparation, once per test that asks for it.

      
2 · await use(value)
The boundary. value is what the test receives in ({ loginPage }). The test runs during this line.

      
3 · After use
Everything below is cleanup: close, delete, reset. It always runs, even if the test fails.

    

  

  
THE technical concept of the act: the async ({ deps }, use) => {} signature and the dividing role of await use(). Key message: use() does NOT mean "run the code", it means "PAUSE here and hand control to the test; when the test finishes, carry on with the cleanup below". It is a sandwich: setup on top, test in the middle (use), teardown at the bottom. The next slide shows it step by step so they see control jumping in and out of the test. The teardown runs even if the test fails, a critical guarantee that gets lost when done by hand.

Two superpowers: lazy and composable ⚡

  

    

      
😴 Lazy: only what you ask for gets created

      
// asks only for "api" → NO browser opens
test("GET /orders", async ({ api }) => {
  await api.orders.getOrders({ limit: 10 });
});

// asks for "ui" → the browser DOES open
test("sees the list", async ({ ui }) => {
  await ui.orders.navigateTo();
});

      
Playwright instantiates only the fixtures the test names. Pure API tests do not pay the cost of a browser.

    

    

      
🧩 Composable: fixtures on top of fixtures

      
base.extend({
  // authedUser DEPENDS on api
  authedUser: async ({ api }, use) => {
    const user = await api.users.create();
    await api.auth.login(user);
    await use(user);
    await api.users.remove(user.id); // cleans up
  },
});

      
A fixture asks for others in its ({ ... }). Playwright resolves the chain and the cleanup order for you.

    

  

  
🥋
These two powers are the engine of KATA: { api } without a browser, { ui } with a browser, { test } combining both: fixtures that depend on fixtures.

  
Two properties that justify the whole investment in fixtures: (1) Lazy: asking only for { api } literally does not open a browser, which is a huge time saver in API suites. True fact from the repo: TestFixture exposes api/ui/test and Playwright instantiates them lazily. (2) Composition: a fixture lists others in its destructuring and Playwright orders setup and teardown in a cascade. The callout connects directly to KATA, which we will see in act 4: { api }, { ui }, { test } are exactly these combined fixtures.

New pain: 300 tests, one after another, 40 minutes ⏳

  

    

      
// Sequential: the sum of EVERYTHING

test 1  ████████        8s
test 2          ██████  6s
test 3                ████████ …
                          ⌛ total = 8+6+...+N
                          = the whole suite, added up

      
🐌
In CI, a sequential suite of 300 tests blocks every PR for half an hour. Slow feedback kills shift-left.

    

    

      
🧩 The symptom
Your machine has 8 cores and you use 1. The other 7 watch a single test run at a time.

      
💡 The idea
Split the tests among several workers (processes) that run at the same time. Wall-clock time drops to that of the busiest worker, not the sum.

      
⚠️ The requirement
To run in parallel, tests must be independent: no shared state, no dependence on order.

    

  

  
The pain of parallelization is the wall clock, and you feel it in CI. Frame it as a wasted resource: 8 cores, 1 in use. The idea (parallel workers) and the non-negotiable requirement (test independence) go together: parallelism is free ONLY if the tests share no state. That connects to the KATA independence rule (each test generates its own data with faker). The simulator on the next slide makes the savings visible and touchable.







  
page objectfixturesparallelizationkata

  
The pattern: workers = isolated processes 👷

  

    

      
👷 One worker = one process
Playwright launches several Node processes. Each one takes tests from the batch and runs them. By default it spreads tests over ~½ of your cores.

      
🧱 Total isolation
Each worker has its own browser and its own fixtures. What happens in one worker never touches another, which is why independence matters.

      
📂 By default: files in parallel
Playwright runs different files in parallel; tests inside a file run in order. fullyParallel: true also parallelizes inside the file.

    

    

      
// playwright.config.ts
export default defineConfig({
  // number of parallel processes
  workers: process.env.CI ? 4 : undefined,

  // parallelizes tests INSIDE each file
  fullyParallel: true,
});

// fine-grained control per block:
test.describe.configure({ mode: "parallel" });
test.describe.configure({ mode: "serial" });

      
🎚️
workers = how many processes. fullyParallel = whether tests in the same file are also split up.

    

  

  
Correct, accurate mental model: worker = Node process with its own browser. By default Playwright uses about half the cores and parallelizes at FILE level (not test level) unless you set fullyParallel: true. mode "serial" forces order inside a describe (use it only when the tests genuinely depend on each other, an antipattern to avoid). The config values are real Playwright. The next slide makes it interactive: have the room pick 1/2/4 workers and watch the clock go down.

Beyond: sharding · and why this repo is careful 🧭

  

    

      
🌐 Sharding: splitting across machines

      
# machine 1 of 3 in CI
npx playwright test --shard=1/3
# machine 2 of 3
npx playwright test --shard=2/3
# machine 3 of 3
npx playwright test --shard=3/3

      
Workers = parallel inside one machine. Shards = parallel across several CI machines, and then the reports are merged.

    

    

      
🐢 This repo's honest stance

      
This repo's config runs serially and without retries, on purpose. The current values of fullyParallel, retries and workers are in playwright.config.ts; the file is the authority.

      
🎯
First determinism, then speed. While the suite is young it runs serially to catch hidden dependencies; parallelism goes up once the tests are solid.

    

  

  
Two closers for the act. Sharding: the next level above workers. It distributes across CI MACHINES with --shard=i/n and merges the reports (blob report + merge-reports). And the repo's honesty: playwright.config.ts documents the stance (serial until the suite is stable), so read it before the session. It is a deliberate decision, not an oversight: first you guarantee the tests are deterministic and independent, and ONLY then do you raise workers. Teach the principle: parallelizing fragile tests multiplies flakiness, not useful speed.

KATA: the three patterns, arranged in layers 🥋

  

    

      
KATA (Komponent Action Test Architecture) invents nothing new: it organizes what you already saw into four named layers, plus optional Steps: TestContext, Base, domain Components and Fixtures, where each layer extends the previous one. Test files consume the Fixtures: they are not a layer.

      

        
🎁 POM → Components layer
Your LoginPage is a domain component. The ATCs live there.

        
🔧 Fixtures → layer 4
{ api }, { ui }, { test } inject the components ready to go.

        
⚙️ Parallelization → config
The same playwright.config.ts: workers, projects, dependencies. It is not a layer: config/ is a DRY zone.

      

    

    

      
// The REAL inheritance chain of the repo

class TestContext { ... }        // L1
class UiBase extends TestContext  // L2
class LoginPage extends UiBase  // L3 ⟵ your POM

// and the fixture ties them together:
class UiFixture {
  login = new LoginPage(options);
}

      
🧬
The extends you mastered is the skeleton. KATA is Page Objects + Fixtures with layers and names.

    

  

  
Thesis of the act: KATA is not a fifth concept, it is the SYNTHESIS of the previous three into one structure. Explicit mapping: POM=components (layer 3), fixtures=layer 4, parallelization=config. The TestContext → UiBase → LoginPage chain is real and accurate for the repo (kata-architecture.md). A message that lowers the fear: if you understood extends, fixtures and POM, you already understand 90% of KATA. Only the vocabulary and the layer order are missing, and that comes now.

The new piece: the ATC 🎯

  

    

      
class LoginPage extends UiBase {

  @atc("PROJ-111")
  async loginSuccessfully(creds) {
    await this.fillAndSubmit(creds);
    await this.page.waitForURL(
      url => !url.pathname.includes("/login"));
    await expect(this.page)
      .not.toHaveURL(/.*\/login.*/);
  }
}

    

    

      
🎯 ATC = a complete test case
Acceptance Test Case: not a loose click, but a whole mini-flow (precondition → action → fixed assertion).

      
@atc("PROJ-111")
The decorator ties the ATC to its Jira ticket 1:1. It gives traceability and automatic tracing. It is a method with a label.

      
🧱 Atomic
An ATC never calls another ATC. Reusable chains? That is a Step (layer 3.5).

    

  

  
The ONLY truly new piece of KATA compared to what they already know: the ATC and the @atc decorator. Code adapted from tests/components/ui/LoginPage.ts (login ATC; ATC ids live in kata-manifest.json). Define ATC: a complete test case (mini-flow), not a single interaction. The @atc('TICKET') decorator ties it to Jira 1:1, giving traceability. Hard rules to mention without overwhelming: atomic ATC (it does not call another ATC), fixed assertions inside / business ones outside (the act 1 rule, now with a KATA name). A decorator is just "a method with a label that adds behavior". Do not get into the mechanics of decorators here.

💡 { api }: since fixtures are lazy, asking only for api does NOT start a browser, and the test runs in milliseconds. Asking for { ui } or { test } "just in case" wastes seconds of browser startup in every test. Ask for the minimum you use.

  

  
Integrates lazy-init (act 2) + fixture selection (act 4). The correct answer requires remembering that { api } does not open a browser. Options B and C are the "ask for too much just in case" antipattern, which in a large suite costs minutes. If most get it right, the session is done: they know how to choose a fixture with a cost criterion.
