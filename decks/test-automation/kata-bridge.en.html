L1 + L2: everything you'll no longer have to write

🎒 L1 · TestContext: the shared backpack

• Per-environment config: URLs and credentials come from .env + config. It kills your hardcoded credentials
• DataFactory (faker inside): fresh data on every run (remember your Date.now() for the unique email? this, industrialized)
• The Playwright drivers (page, request) and the environment, shared by API and UI

🧰 L2 · UiBase / ApiBase: the inheritable helpers

• UiBase: buildUrl, intercepting responses and waiting for network calls, which is what your POMs kept repeating. The form helpers live in each component
• ApiBase: an HTTP client with auth, headers and error handling already solved

// Your LoginPage from Playwright Pro:
export class LoginPage {        // extended... nothing
  // goto, waits, helpers: by hand 😅
}

// In KATA:
export class LoginPage extends UiBase {
  // inherits buildUrl, network waits,
  // config and data: FREE 🎁
  // you only write what's specific to login
}

The extends chain you practiced with User → Admin, paying off its biggest dividend: you only write what's unique to your page.

L1 and L2 together = "what you inherit for free". Direct connections: hardcoded credentials (a pain they have) → TestContext; the Date.now() from the lab → DataFactory; their repeated helpers → UiBase. L3 + the star concept: ATC ⚛️

tests/components/ui/LoginPage.ts (excerpt) · L3 layer
export class LoginPage extends UiBase {

  @step
  async goto() {
    await this.page.goto(this.buildUrl("/login"));
  }

  // login with valid credentials
  @atc('PROJ-111')
  async loginSuccessfully(credentials: LoginCredentials) {
    await this.fillAndSubmitLoginForm(credentials);
    await expect(this.page).not.toHaveURL(/.*\/login.*/);
  }
}

⚛️ ATC

Acceptance Test Case: a method that runs one complete, atomic mini-flow. Your usual login(), with an identity and rules.

🏷️ PROJ-111

Every ATC carries the literal Jira key of the ticket it covers: traceability, from the code to the documented test and back. Never a synthetic id or a template literal.

📦 An object instead of 2 params

Look at the signature: loginSuccessfully(credentials) takes an object { email, password }, and with 3+ values it's the house rule.

ATC = the conceptual heart of KATA. The ATC IS the test case; @atc('PROJ-111') is its representation in code. It's their login() method from the whole series, elevated: identity (Jira key → traceability with the TMS), atomicity (rule on the next slide) and a signature convention. this.buildUrl("/login") shows the chain in action: UiBase builds the URL from config.baseUrl, which comes from TestContext. Zero hardcoded URLs. The term "atomic" is defined formally on the next slide; here "complete and independent" is enough.

The ATC rules: few and sacred 📜

RuleWhat it meansWhy
AtomicAn ATC runs ONE complete mini-flow and NEVER calls another ATCIf A calls B and B changes, A breaks in a chain: the domino that kills frameworks
Chains → StepsNeed login + create project + invite? That's a Steps module that orchestrates ATCsExplicit composition in one place, not hidden coupling
Inline locatorsLocators live INSIDE the ATC; extract them only if 2+ ATCs use themReading an ATC = seeing it whole, without jumping between files
Max 2 loose params3 or more values → an object: loginSuccessfully({ email, password, role })fn(a, b, c, d) = which one was the third? The object documents itself

The 4 rules that differ from what they'd do by instinct. #1 is THE rule: ATCs don't call each other. The dependency domino is the slow death of home-grown frameworks. Steps exists precisely to compose without coupling. Inline locators surprise anyone who learned "extract everything"; KATA prefers local readability, and extraction is EARNED by the second use.

⭐ QUIZ 1 · The sacred rule

Your ATC createProject() needs the user to be logged in. Can it call loginSuccessfully() internally?

💡 The trap in option A: reuse IS good, but hidden coupling isn't. If loginSuccessfully changes and 14 ATCs called it internally, you have 14 invisible breakages. KATA demands that composition be EXPLICIT: a Steps module that orchestrates, or the precondition in the fixture. Same benefit, zero domino.

The most important quiz in the deck: option A is exactly what their instinct (well trained in reuse) tells them. The fine distinction: reusing ≠ hidden coupling. Explicit composition (Steps, fixtures) vs invisible internal calls. Whoever understands this already thinks in architecture.

L4 · TestFixture: your fixtures.ts on steroids 💉

// Your spec in KATA:
import { test, expect } from "@TestFixture";

test("create project", async ({ ui }) => {
  await ui.login.goto();
  await ui.login.loginSuccessfully({ email, password });
  await ui.projects.createProject({ name: "Demo" });
  await expect(ui.page.getByText("Demo")).toBeVisible();
});

ui arrives with ALL the pages instantiated + context + data. Zero new, zero setup, like your loginPage fixture, multiplied.

🎯

Watch the assertions. In POM you learned "actions in the page, assertions in the test". KATA refines it: the fixed assertions (status code, required fields, redirect) live inside the ATC, because they're part of its contract. Only the flow assertions, the ones that depend on the scenario, go in the spec.

🎛️ The selection rule

API-only test({ api }): no browser, it flies
UI-only test({ ui }): pages ready to go
Hybrid (API sets up, UI verifies)({ test }): both worlds

⚡ Why it matters

Asking for { api } in an API test doesn't launch a browser: your suite of 200 API tests runs in seconds. The right fixture = the right speed.

L4 closes the fixtures circle that started in Playwright Pro. The selection rule is daily practice: the common mistake is asking for {test} for everything "just in case", paying for a browser in tests that don't use one. The example spec reads like a story: that's the prize of the whole architecture.

⭐ QUIZ 2 · Fixtures

You write 15 tests that only validate API responses. Which fixture do you ask for?

💡 The "just in case" of option A is expensive: launching a browser for tests that never touch it multiplies the duration of the suite. The rule: ask for the MINIMUM fixture your test needs. The Playwright Pro pyramid, applied at fixture level.

A professional-habit quiz: the minimum fixture needed. It connects with the pyramid (fast API): the architecture rewards whoever chooses well with speed. In the real repo, choosing the wrong fixture is one of the first things flagged in code review.

🔍 Solves Pain 3

"Is there already a login ATC?" The manifest answers in 2 seconds. It's ALWAYS checked before creating a new Component or ATC. Anti-duplication.

🤖 Generated, not edited

bun run kata:manifest regenerates it by reading the code. Never by hand.

🚧 Automatic guardian

Outdated manifest = the commit is blocked (pre-commit hook). The registry never lies because it can't fall behind.

The manifest solves the pain of the 5 QAs: a central registry you can query. Two habits: check it BEFORE creating (anti-duplication) and regenerate it after creating (bun run kata:manifest). The pre-commit hook connects with their git knowledge from Dev Craft: git runs validations before accepting the commit, so the framework protects itself.

House rule: an implementation plan BEFORE writing code. The AI proposes the plan, you approve it, then it gets written. No blind coding.

🧠 So why did I learn all this?

Because your role is NOT typing code, it's having judgment:

✅ Read what the AI proposes and spot what's wrong
✅ Judge: is this ATC atomic? is the fixture the minimum? will the locator survive?
✅ Decide what gets tested, what gets automated and what does NOT

Without the series, the AI dictates to you. With it, you lead.

The slide that recontextualizes the whole series: they learned to code not to type faster than an AI (impossible) but to REVIEW with judgment (irreplaceable). The modern QA Engineer directs agents: approves plans, reviews diffs, enforces the rules. The whole journey was judgment training. This is the most important message of the deck for their careers.

⭐ QUIZ 3 · Agentic judgment

The AI proposes a new ATC: registerUser(name, email, password, role). What do you flag in the review?

💡 "It compiles and passes" is not the standard; it follows the house rules is. The object signature documents itself and doesn't break if a field is added tomorrow. This IS the agentic work: the AI produces, your judgment guarantees. (Option C "fixes" it by breaking functionality, so beware of fixes that amputate.)

A rehearsal of the real role: reviewing AI-generated code. Option A is the complacency trap ("it passes, approved"); the professional standard is rules + judgment, not just green. Point out the pattern in C: fixes that break functionality to satisfy a rule. Judgment also protects against that.

MISSION B2

ATC hunt

🎯 Use the manifest the way you always will: find an existing ATC and read its source code.

1. Open kata-manifest.json
2. Pick a Component that catches your eye
3. Jump to its file (the manifest gives you the path)
4. Read ONE complete ATC, line by line
5. Check the rules: is it atomic? inline locators? object signature if 3+ values?

Hint: there's something I don't recognize

Write down WHAT exactly. If it's advanced TS syntax (generics, decorators), that's normal, you learn it along the way. If it's structure (where does this.config come from?), follow the extends chain upward: the answer lives in UiBase or TestContext. Knowing how to TRACE inheritance is the skill.

📊

Honest goal: you should recognize 80%+ of each ATC (class, this, async/await, locators, params). The remaining 20% is what daily work will give you.

✅ Success criterion: you can explain to a teammate what that ATC does, line by line, and which KATA rule each decision follows.

The mirror mission of the whole series: reading real production code and recognizing 80%. The success criterion (explain it to someone else) is the ultimate comprehension test; in a group, have a few people do it out loud. The hint teaches tracing inheritance: the skill for reading frameworks.

⭐ QUIZ 4 · The final integrator of the series

You're assigned to automate "the user can archive a project". Your FIRST move?

💡 In a team framework, the first move is NEVER to write, it's to check the registry. Maybe ProjectsPage already exists and you only add an ATC; maybe someone already automated archive. Codegen (B) is still useful AFTER, to discover locators. The professional order: manifest → plan → code. Duplicating work is the most expensive bug in teams.

The last quiz of the series, and it sums up the whole mindset shift: from "person who writes code" to "engineer who builds on a shared system". The order manifest → plan → code is literally the /test-automation workflow of the repo. With this they're ready for their first real ticket.
