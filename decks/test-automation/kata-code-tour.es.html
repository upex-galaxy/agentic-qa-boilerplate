Por qué el código no tiene comentarios

Regla crítica 18

El código no lleva comentarios. Un comentario envejece sin que nadie lo note y termina enseñando algo falso. La explicación de la plantilla vive en decks y en la doctrina, que se revisan como documentos.

Pirámide de confianza

Lo que una máquina puede comprobar se comprueba en lint, tipos y tests. Una regla de KATA que se puede chequear con una regla de ESLint no necesita un párrafo que pida cumplirla.

Este deck

Lo que ninguna máquina chequea: el porqué de cada decisión. Cada diapositiva nombra un archivo, muestra un extracto real y explica sus razones.

Los extractos salen del código actual del repo. Si un archivo cambia, el extracto del deck se vuelve a copiar de él.

TestContext: la base de todo

tests/components/TestContext.ts
  • TestContext centraliza los drivers de Playwright (page, request), la configuración del ambiente y el acceso a DataFactory.
  • UiBase y ApiBase extienden de esta clase, así que las operaciones de UI y de API corren sobre el mismo contexto.
  • TestContextOptions: page es obligatorio para tests de UI, request para tests de API, y environment toma por defecto el ambiente actual de la config.
  • data existe como propiedad estática y como getter de instancia. Cualquier componente llama this.data y nunca importa la fábrica por su cuenta.
tests/components/TestContext.ts
  readonly config = config;

  static readonly data = DataFactory;

  constructor(options: TestContextOptions = {}) {
    this._page = options.page;
    this._request = options.request;
    this.env = options.environment ?? env.current;
  }

  get data(): typeof DataFactory {
    return TestContext.data;
  }

ApiBase: helpers HTTP tipados

tests/components/api/ApiBase.ts
  • ApiBase envuelve APIRequestContext de Playwright y extiende TestContext, así hereda drivers y config.
  • apiGET y apiDELETE devuelven [APIResponse, TBody]: el ATC recibe la respuesta cruda (status, headers) y el body ya parseado en una sola llamada.
  • apiPOST, apiPUT y apiPATCH devuelven [APIResponse, TBody, TPayload]. El tercer elemento es el payload realmente enviado, así el spec compara respuesta contra pedido sin reconstruirlo.
  • Pasa siempre el modelo de respuesta (y el de payload en mutaciones) como genéricos para que los ATCs sigan tipados.
  • Los helpers HTTP son protected a propósito: un test no puede saltarse la capa de componentes con api.apiPOST(...). Pasa por un ATC o por un helper @step de la capa 3.
  • Cada helper adjunta pedido y respuesta al reporte de Allure de forma automática.

ApiBase: auth, cookies y respuestas defensivas

tests/components/api/ApiBase.ts
  • setAuthToken guarda el token y lo envía como Authorization: Bearer en los pedidos siguientes. clearAuthToken lo quita.
  • El accessor request prefiere page.request cuando hay página: comparte cookies y storage con el navegador, así que en el fixture híbrido { test } las llamadas API llevan la cookie. En tests solo API usa el contexto independiente, que no tiene cookie.
  • Si no hay contexto de request, el accessor lanza un error. Un fixture mal armado falla fuerte en vez de fallar en silencio.
  • getResponseJsonObject parsea el JSON de forma defensiva y devuelve un objeto vacío si falla, para que un body de error que no es JSON no rompa el ATC.
  • requestHeaders.Accept es */* para evitar errores 406 de servidores que rechazan un application/json explícito, aunque el body siga siendo JSON.
  • apiEndpoint arma la URL completa desde config.apiUrl, porque el contexto de request de Playwright no usa baseURL aquí.
  • apiPOSTForm envía formularios x-www-form-urlencoded para OAuth2 y endpoints de token, acepta URLs absolutas y enmascara password en el adjunto de Allure.

UiBase: Playwright nativo más intercepción de red

tests/components/ui/UiBase.ts
  • UiBase es la base de los componentes de UI. Extiende TestContext y los componentes usan la API nativa de Playwright (this.page) directo: Playwright espera solo antes de cada acción, así que no hace falta una capa de envoltorios.
  • El accessor page lanza un error si no hay página (por ejemplo en tests solo API), para que un driver faltante falle fuerte.
  • buildUrl arma la URL completa desde config.baseUrl para logs o aserciones. Para page.goto() usa una ruta relativa: el baseURL de Playwright ya la resuelve.
  • interceptResponse registra primero la espera de la respuesta, luego ejecuta la acción que la dispara y al final espera la respuesta. Así evita la carrera en la que la respuesta llega antes de que exista el listener.
  • waitForApiResponse hace la misma captura sin disparar una acción: úsalo cuando el pedido ya está en vuelo.
  • matchesPattern convierte patrones tipo glob a regex: ** cubre cualquier ruta y * un segmento. Los parsers de body devuelven null si no es JSON, así la intercepción nunca rompe un test.

ExamplePage: el componente de referencia de UI

tests/components/ui/ExamplePage.ts
  • Es un componente de referencia con una página ficticia /example y selectores de relleno. Cópialo a tests/components/ui/YourPage.ts, cambia URLs y locators, regístralo en UiFixture.ts y corre bun run kata:manifest.
  • Un ATC es un caso de prueba completo, un mini flujo (navegar, actuar, verificar), nunca una sola interacción.
  • Cada ATC tiene un único resultado esperado (partición de equivalencia): con datos válidos termina en una redirección, con email inválido termina en un mensaje de error.
  • Los locators van en línea dentro del ATC. Se extraen a un campo de la clase solo cuando dos o más ATCs los usan (emailInput, passwordInput, submitButton).
  • Estrategia 1, errorMessageTestId: un string data-testid usado con getByTestId, la opción preferida.
  • Estrategia 2, emailInput: una función flecha que devuelve un Locator, para selectores complejos o respaldos encadenados con .or(). Un .or() sobre varios selectores del mismo elemento resuelve a uno solo, por eso no hace falta .first().
  • @atc('PROJ-131') usa una clave de proyecto de relleno: cambia PROJ por la clave real de Jira.

LoginPage: un componente real

tests/components/ui/LoginPage.ts
  • Los locators van en línea con data-testid (login-email-input, login-password-input, login-submit-button, login-error), lo más alto en la prioridad de locators.
  • fillAndSubmitLoginForm es un helper privado que dos ATCs comparten. Por eso no lleva @atc ni aserciones.

AuthApi: ATCs de autenticación

tests/components/api/AuthApi.ts
  • AuthApi es el componente de API de autenticación (POST /api/auth/login, GET /api/auth/me). Los endpoints salen de config.auth.
  • Un ATC es una ACCIÓN más una VERIFICACIÓN, nunca un GET suelto. Una operación de solo lectura es un helper sin @atc.
  • getCurrentUser es ese helper: un GET de lectura que se usa como paso de verificación dentro de ATCs o en aserciones del test. Lleva @step y no @atc porque recupera datos, no es un flujo de acción completo.
  • authenticateSuccessfully envía las credenciales, afirma la respuesta fija (200, access_token, Bearer, expires_in), guarda el token con setAuthToken y verifica la sesión con GET /auth/me.
  • loginWithInvalidCredentials envía credenciales malas, afirma el 401 y comprueba que no se creó sesión llamando a /auth/me sin token. Guarda el token actual, lo limpia para esa comprobación y lo restaura después, para que un login fallido no cierre la sesión del test que lo rodea.
  • Los tipos de pedido y respuesta se reexportan desde AuthApi, así los consumidores no importan el archivo de schemas.
  • El prefijo PROJ de @atc('PROJ-101') es de relleno: usa la clave real del proyecto.

ExampleSteps: cadenas de precondición

tests/components/steps/ExampleSteps.ts
  • Es una referencia (capa 3.5) de cadenas de precondición reutilizables que preparan el estado antes del test real. Cópialo a tests/components/steps/YourSteps.ts y reemplaza los endpoints y la lógica de auth ficticios.
  • Un step no tiene aserciones fijas ni @atc. Combina acciones o ATCs para llegar a un estado: autenticación, datos, navegar a una página con datos.
  • authenticateUser es un step de SETUP: solo obtiene el token y no verifica que la auth funcionó. Esa verificación pertenece a un ATC.
  • navigateAsAuthenticatedUser encadena login, token en el storage del navegador y navegación en una sola precondición. Recibe un objeto porque con tres o más parámetros los strings sueltos se leen igual en la llamada y cambiar dos de lugar es un error silencioso (typescript-patterns.md, sección 1).
  • Cada step lanza un error claro cuando falta el driver que necesita (request, page) en el constructor.
  • createTestResource crea datos por API para que los tests de UI arranquen desde un estado conocido.

ApiFixture y UiFixture: contenedores de inyección

tests/components/ApiFixture.ts · tests/components/UiFixture.ts
  • ApiFixture es un contenedor de inyección de dependencias para todos los componentes de API. Cada uno recibe las mismas opciones, así comparten un contexto de request y una auth consistente.
  • Para sumar un componente de API: créalo en tests/components/api/YourApi.ts, impórtalo en el fixture, agrega una propiedad readonly e inicialízala en el constructor con las opciones compartidas.

tests/components/TestFixture.ts
  • test es el fixture híbrido con UI y API, ui es solo UI y api es solo API. Los tres comparten un TestContext, así que un test híbrido usa los mismos drivers de Playwright.

Specs de integración: sin navegador

tests/integration/module-example/example.test.ts · tests/integration/auth/user-session.test.ts
  • Un spec de API no necesita navegador: usa el fixture { api } directo y los ATCs devuelven la tupla [response, body, sentPayload].
  • sentPayload (tercer elemento) permite comparar la respuesta contra exactamente lo que envió el ATC, por ejemplo body.user.email contra sentPayload.email.
  • Los ATCs de error (createResourceWithInvalidData) validan la respuesta de error por sí mismos, así el spec solo arma el payload inválido.
  • ApiFixture carga el token de api-state.json de forma automática, por eso los specs hacen llamadas autenticadas sin loguearse.
  • api.clearAuthToken() quita el token para probar que una llamada sin autenticar devuelve 401. Después, api.auth.authenticateSuccessfully(credentials) obtiene y fija un token nuevo en runtime (renovación).
  • El proyecto integration depende de api-setup.

DataFactory y tipos de prueba

tests/data/DataFactory.ts · tests/data/types.ts
  • DataFactory es el generador central de datos de prueba. Regla de oro: nunca datos estáticos, siempre dinámicos con Faker, para que los tests no choquen y sigan siendo independientes.
  • Se accede desde un componente como this.data.createUser() (a través de TestContext) o por import directo desde @DataFactory.
  • createUser arma un usuario completo y createCredentials solo email y password. Ambos aceptan overrides para los campos que le importan al test.
  • uniqueId genera un id único para etiquetar datos de prueba, útil para limpieza y trazabilidad. Los generadores de hotel y reserva son una estructura de ejemplo para ampliar.
  • Los tipos de tests/data/types.ts son solo de pruebas (datos generados, estado de fixtures), no tipos del contrato de la API. Los schemas de pedido y respuesta viven en api/schemas/{domain}.types.ts y se importan desde @schemas/{domain}.types.
  • ApiState es el estado de API almacenado (token) que escriben los archivos de setup y lee TestFixture. Así el token llega a los specs.

Decoradores: @atc

tests/utils/decorators.ts
  • @atc(testId, options) conecta un método con un caso de prueba de Jira o Xray y registra su ejecución para el reporte y la sincronización con el TMS. Usa el formato de decoradores TC39 Stage 3.
  • Todo el logging de un ATC ocurre solo dentro del decorador: los componentes base nunca hacen log.
  • Un ATC es un mini flujo completo con nombre {verbo}{Recurso}{Escenario}, nunca una interacción suelta como fillEmailSuccessfully.
  • Opciones: softFail sigue el test aunque el ATC falle, severity fija la severidad de Allure (de blocker a trivial) y description agrega texto a Allure.

KataReporter: el reporter propio

tests/KataReporter.ts
  • Es un reporter de Playwright propio, con salida de terminal en colores, log paso a paso, fragmentos de error y un resumen. Se registra en playwright.config.ts junto a los otros reporters.
  • printsToStdio() devuelve true para avisar a Playwright que este reporter es dueño de stdout, y que no agregue su salida suplementaria. El console.log y stderr de los tests se muestran siempre.
  • En onEnd arma un registro de outcome por cada test que la corrida conocía, desde la suite completa (un test cuyo proyecto de dependencia falló no tiene resultado alguno). Lo escribe en reports/test-outcomes.json y, en GitHub Actions, en el resumen del step. Nunca cambia el exit code: lo sigue manejando Playwright.
  • El titular sale de esos registros y no del ok() de Playwright, porque una cascada de setup es ok() allí y un defecto conocido no es un pase.
  • Orden: los outcomes se arman primero porque deciden listOnly, que lee el reporte de ATCs. El id de corrida se escribe en reports/atc_results.json y en reports/test-outcomes.json, para detectar un par viejo.
  • playwright test --list llega a onEnd sin intentos: no corrió nada, no se registran outcomes y el reporte de ATCs de la última corrida real queda intacto. Si ningún ATC corrió, se borra un reporte viejo para que un write-back posterior no lo importe.
  • Los resultados parciales de ATC los escriben los workers como NDJSON y el proceso coordinador los une, así el archivo está completo cuando dispara onEnd(). El estado final por ATC es conservador: cualquier ejecución fallida es FAIL, todas pasadas es PASS. El resumen del step es una comodidad, el archivo de registros es el contrato.

knownDefect y testOutcomes

tests/utils/knownDefect.ts · tests/utils/testOutcomes.ts
  • knownDefect(key) marca el test en curso como bloqueado por un defecto conocido en una sola llamada, así la marca de fallo esperado y la clave del defecto no se separan. Pon la clave también en el título (@blocked:BK-999) y llámalo primero en el cuerpo del test.
  • KataReporter lo clasifica como known-defect mientras falla y como unexpected-pass (un action item) cuando pasa (ADR-0020). Un test.fail() pelado sigue contando como known-defect, pero además levanta el action item known-defect-without-key. Por eso el helper pide la clave.
  • testOutcomes.ts da a cada test que la corrida conoce exactamente una clase de outcome y calcula el titular desde esas clases, no desde ok() de Playwright ni del estado de Allure.
  • Existe porque un test saltado por un beforeAll fallido es ok() en Playwright, un proyecto de setup caído deja a sus dependientes sin resultado y Allure archiva un fallo esperado (test.fail) como pasado. El titular puede decir que todo pasó mientras los defectos conocidos y los fallos de setup quedan escondidos.
  • Firma de una cascada de setup: status: 'skipped', expectedStatus: 'passed' y ninguna anotación skip o fixme. Un test.skip() condicional sí trae la anotación, así que sigue siendo saltado.
  • Los registros se arman desde suite.allTests(), nunca desde las llamadas a onTestEnd, porque un proyecto de dependencia caído o --max-failures dejan tests sin resultados.
  • knownDefectKey toma la clave de una anotación known-defect cuyo valor completo es una clave, del tag @blocked:{BUG-KEY} o de una descripción de test.fail que empiece con Blocked by {BUG-KEY}. El texto libre nunca crea una clave: fragmentos como UTF-8 o SHA-256 no son claves.
  • TEST_STATUS_OF_CLASS mapea clases a estados del TMS. Los fallos no observados (el cuerpo nunca corrió) pasan a BLOCKED en testStatusOf, porque PASSED y FAILED exigen una observación.
  • outcomeHeadline es verde solo si nada falló, nada pasó de forma inesperada, no hay action items abiertos y se alcanzó cada test. El estado de corrida de Playwright también cuenta: un crash de worker o un error de global setup falla la corrida aunque todos los registros se vean limpios.
  • El módulo es puro: sin import de runtime de Playwright, sin sistema de archivos y sin llamadas al tracker. Sus tests unitarios (testOutcomes.test.ts, xrayResults.test.ts) corren con bun test tests/utils, y Playwright nunca los recoge porque cada proyecto tiene su propio testMatch.

tests/utils/xrayResults.ts
  • Arma el body JSON de Xray para POST /api/v2/import/execution a partir de uno o más reports/atc_results.json. Lo comparten el write-back local (jiraSync.ts) y el job de CI XrayImport de .github/workflows/regression.yml, así ambos siguen una sola regla.
  • Por qué JSON de Xray y no JUnit: Xray crea un Generic Test nuevo por cada testcase de JUnit sin propiedad test_key, y un testcase de Playwright llama a cero, uno o varios ATCs. Xray JSON solo crea un Test cuando una entrada trae testInfo, que este módulo nunca escribe. Así un import solo puede escribir ejecuciones sobre Tests existentes.

  • buildXrayTests marca FAILED si alguna ejecución falló y PASSED en otro caso. Si toda ejecución fue un skip de runtime, el ATC se omite (NOT RUN, ADR-0020).
  • addUnfinishedAtcs: la anotación atc se empuja cuando empieza un ATC y el registro solo cuando termina. Un test que expiró dentro de un ATC (por ejemplo un await ajeno a Playwright que nunca llega al catch del decorador) tiene lo primero sin lo segundo. Esos ATCs se envían como FAILED usando test-outcomes.json.
  • Ambos reportes llevan el id de corrida que estampó KataReporter: un reporte de otra corrida se rechaza por viejo.

jiraSync: el write-back a Jira y Xray

tests/utils/jiraSync.ts
  • jiraSync.ts corre después de que termina el proceso de Playwright (bun run test y luego bun run test:sync, condicionado a AUTO_SYNC=true). No se llama desde global.teardown.ts a propósito: KataReporter.onEnd() escribe reports/atc_results.json después del proyecto de teardown, así que una llamada en proceso leería un archivo viejo o ninguno.
  • Destinos: Xray Cloud (import de un body JSON de Xray) y Jira Direct (un campo personalizado por test).
  • Modos de import (XrayImportPayload): testExecutionKey escribe ejecuciones sobre un Test Execution existente, e info deja que Xray cree uno nuevo. El schema de info es cerrado y no tiene campo padre, así que un Execution creado así no puede colgarse del epic QA Test Artifacts con esta llamada.
  • Camino preferido: escribir sobre un Execution que ya existe (el RTR creado por /regression-testing o el STR del cierre de sprint). Ya trae su epic padre, Test Environment, vínculo testPlan y título ratificado, así que no se inventa nada.
  • Camino de respaldo (sin STP_EXECUTION_KEY): Xray crea el Execution desde info y queda sin padre. Ninguna llamada posterior puede adoptarlo, porque reasignar el padre es un PUT /issue/{key} de Jira REST que necesita credenciales de Atlassian que el proveedor Xray no tiene. El código hace lo que la API permite: título RTR ratificado, Test Environment del ambiente activo y vínculo testPlanKey cuando RTP_KEY está definido, que se agrega solo si no está vacío porque Xray rechaza un string vacío.
  • Guarda de STP_EXECUTION_KEY: invita a pasarle la clave de un Test Plan. Xray escribe ejecuciones solo en Test Executions y un Plan deriva su estado de ellas, así que un import dirigido a uno no llega a ningún lado útil. readIssueType es solo diagnóstico: sin credenciales, con Jira caído o con un payload inesperado devuelve null, porque un diagnóstico nunca debe volverse un bloqueo nuevo.
  • Cada ATC es una entrada de tests con solo testKey y sin testInfo, así Xray no puede crear un Test desde el import. Un id que no es clave de Test frena el write-back antes de cualquier llamada de red, y si todo ATC fue skip de runtime no queda nada que enviar, porque el schema de Xray pide al menos una entrada.
  • Un reporte ausente en CI significa que el pipeline está mal armado (el comando corre después de Playwright), así que falla fuerte (issue 27: el retorno silencioso anterior escondió el write-back roto por meses). En local es normal y queda como advertencia. Si todos los ATCs se colgaron, test-outcomes.json por sí solo alcanza, porque es el único registro de que corrieron.
  • resolveTestStatusField: los ids de campos personalizados de Jira son por instancia y una migración de sitio los reasigna, por eso .agents/jira-fields.json es la única fuente de verdad y JIRA_TEST_STATUS_FIELD es solo un override explícito. Sin ninguno, el llamador aborta en lugar de hacer un PUT con clave de campo vacía, que Jira contesta con un 400 opaco. La gramática del título es {ACRONYM}: {scope-id}: {descriptor}, definida en .agents/skills/agentic-qa-core/references/planning-ladder.md.
