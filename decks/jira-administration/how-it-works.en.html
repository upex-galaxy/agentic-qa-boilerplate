/jira-administration

Two administration tasks that touch the whole project: aligning Jira Components with the real modules of the app, and repointing the repo to a new Atlassian site after a migration. In both, the AI reads first, shows you the plan, and writes nothing until you say yes.

One mode per run Reads before touching Writes only with your OK
Deck for the jira-administration skill. It brings together what used to be two separate commands, jira-components and jira-instance-migration, which survive only as phrases that trigger it. Both tasks are rare and high-impact: a mistake only shows up weeks later, in a filter that no longer discriminates or in a field that received data that was not its own. Decide · 2 of 15

Is something about Jira's structure changing?

Use it for

  • Reconciling the project's Components with the functional modules of the app: create the missing ones and rename the old ones.
  • Repointing the repo to another Atlassian instance after a site migration, and regenerating the catalogs that migration invalidated.

It also activates on "sync Jira components", "the Jira URL changed", "repoint jira" or "migrate the jira instance".

Not for this: goes to

Setting a component on one specific issuethe testing skill that creates the issue, via /acli
Operating tickets: create, transition, comment/acli
Refreshing catalogs without an instance changebun run jira:sync-*, directly
Provisioning Jira for the first timedocs/core/setup/jira-xray.html (docs site)

Each mode has its own "not for this". Components does not touch catalogs or the instance; the migration does not set up a brand-new Jira.

Contract · 4 of 15

Read, show, wait, only then write

No credentials, full stop

If ATLASSIAN_EMAIL or ATLASSIAN_API_TOKEN is missing, it names the variable, points you to .env and .env.example, and asks you to restart the session. No shortcuts, no partial run (Rule #10).

The host lives in one place

.agents/project.yaml → issue_tracker.atlassian_url. A stale ATLASSIAN_URL in .env or in the environment is contamination: it gets deleted, not updated.

Repo without onboarding

If project.project_name is null, the repo is a template: atlassian_url and project_key stay null and the report says so.

Source: Compact Rules in SKILL.md. The single-host rule comes from the instance identity anchor in AGENTS.md: a second copy of the host is exactly the one that goes stale. On a template, the skill does not fabricate a commit to hide the fact that the value is empty.

Components mode · 5 of 15

A component is a module of the app

The convention

A component = a functional module of the running application, derived from its real surface (routes, features). It does not come from the planning taxonomy: an Epic is a unit of work, a component is a unit of the system.

Why it matters

It is mandatory on every bug, defect, improvement and Test, and it is the grouping field of the coverage boards. A filter is only as useful as its power to discriminate.

Why a script and not acli

acli cannot create, rename or delete components. That is why the mode drives scripts/sync-jira-components.ts, which talks to the REST API directly (also bun run jira:components).

Why a plan and not autodetection

Deciding which routes are one module and what to call it is judgment, not mechanics. The AI writes the plan, a person approves it and the script runs only what was approved.

Rename is not create

Deleting and recreating under another name orphans every assigned issue. A rename keeps each assignment, which is how an old component migrates to the convention without bulk-editing issues.

Sources: the header of scripts/sync-jira-components.ts, the "Hard gate" of references/components.md and Part 3 of agentic-qa-core/references/defect-management-doctrine.md. The sprint-testing defect management deck shows the same three-axis model from the reporter's side.

Components mode · 6 of 15

What exists, what is coming and what is already there

Phase 1 · The AI proposes, it does not decide

1a · The codeThe real surface of the app. In Next.js App Router: app/**/page.tsx and app/api/**/route.ts; in other stacks, their router or controllers. It groups using the product's vocabulary: /checkout/cart and /checkout/payment are Checkout.
1b · The backlogEpics and Stories with areas the code does not have yet. A component can be declared before the code: a feature in refinement already has Stories and Tests that need it.
1c · The proposalEach module with what it absorbs (routes or Epic), marked as existing or ahead of the code, so you can correct the grouping.

Using only the code is the easy mistake: it silently erases everything that is planned.

Name clash

If the product has Tests, Runs or Bugs as features, they clash with QA vocabulary. It proposes prefixing with the product name (Bunkai Tests), and the prefix goes into the plan you approve: it is never applied on its own.

Phase 2 · Live components

bun scripts/sync-jira-components.ts \ --list --project {{PROJECT_KEY}}

It lists every component with its issue count, which is what is at stake. Each proposed module ends up as: already exists (skip), exists under another name (rename) or is missing (create).

Source: Phases 1 and 2 of references/components.md. Declaring a component ahead of the code is cheap and safe: create is additive, rename re-labels without touching assignments, and the mode runs again when the map changes. If the module ends up with another name it is a rename; if it never appears, it is an unused row. The backlog is read with bun run jira:sync-issues pull --dry-run or from what is already synced in .context/PBI/epics/.

Components mode · 7 of 15

A JSON plan, a dry run and a yes

Phase 3 · The plan, in .context/reports/jira-components-plan.json

{ "project": "<KEY>", "rename": [{ "from": "Bugs & Defect Heatmap", "to": "Bunkai Bugs" }], "create": [{ "name": "Bunkai Auth", "description": "Login, registration, sessions" }] }

It shows it to you as a table: renames separate from creates, and each rename with its issue count.

Dry run by default

Without --apply the script only shows what it would resolve. A rename whose source is gone, or whose target already exists, becomes a documented skip: re-running a half-applied plan is normal.

Wait for approval

You can change the grouping, the names or the prefix. It regenerates the plan and shows it again until you approve it.

Phase 4 · Apply and verify

bun scripts/sync-jira-components.ts \ .context/reports/jira-components-plan.json --apply bun scripts/sync-jira-components.ts \ --list --project {{PROJECT_KEY}}

The live list has to match the approved plan, with renames showing their issues intact.

Source: Phases 3 and 4 of references/components.md and the usage documented in the script header. The final report carries the resulting components list, what was renamed, what was created, what was skipped and any skip whose reason deserves a look.

Instance-migration mode · 8 of 15

The failure is not a 404: it is a 200 OK

The easy half

Repointing the site URL. It is one line in .agents/project.yaml and an acli login.

The half that prevents corruption

Regenerating the .agents/ catalogs. A site migration reassigns custom field ids instead of keeping them.

First, on the Xray side

A full move between sites follows the /xray-cli runbook and closes with this mode.

Source: "Why this is not a find-and-replace" in references/instance-migration.md. The slug in the diagram is illustrative: any field in the catalog runs the same risk. Closing the Xray move with this mode is covered in xray-cli/SKILL.md and its references/migration-runbook.md.

Instance-migration mode · 9 of 15

From where to where, and what is not touched

Phase 0 · Resolve the two instances

SourceIt detects it instead of asking first: atlassian_url from the yaml, the acli session and bun run --silent jira:url. If they disagree, the repo is already half migrated: it is a repair, and it asks you which one is the real "before".
TargetIt never guesses it. If it did not come with the invocation, it asks: a site the repo has never contacted cannot be detected.
ProbesTwo probes that do not open the .env: test -n "${ATLASSIAN_URL+x}" has to say unset and bunx varlock load --agent --filter ATLASSIAN_URL has to print {}. A hit is contamination to clean up, never evidence.

It confirms <source> → <target> in one line, waits, and tests /rest/api/3/myself on the target: anything other than 200 stops the mode.

Phase 1 · Audit before editing

It sweeps the repo for the source host and classifies each hit as "changes" or "does not change". The table is shown to you before anything is touched.

Does not change

  • An alias domain that redirects to the active site. It cannot be seen from the repo, so confirm it by hand.
  • Historical records: rewriting them falsifies the past.
  • Code whose pattern already generalizes (a regex, not a literal).
  • .context/PBI/: the sync rebuilds it.

On neither list

A CI workflow, a README, .mcp.json: it asks before touching it.

Source: Phases 0 and 1 of references/instance-migration.md. Migrating to an empty or half-provisioned instance regenerates empty catalogs and publishes them, which is worse than doing nothing: that is why the scope check comes before any change. Both hosts are normalized to the bare host, with no scheme and no trailing slash.

Instance-migration mode · 10 of 15

Repoint in order and test it on the target

Phase 2 · Apply

1atlassian_url: https://<target> in .agents/project.yaml, first: everything else reads it. bun run --silent jira:url has to return the target.
2Delete any stale ATLASSIAN_URL the probes found, and whatever exports it into the process.
3Re-login to acli with the site that bun run --silent jira:url --slug gives: if the yaml is wrong, the login fails loudly.

The acli session belongs to the machine

It lives in ~/.config/acli. The re-login repoints every repo on this machine, not just this one. If you still need the old site for another repo, it warns you first.

Phase 3 · Verify, as a table

  • The yaml, bun run --silent jira:url and the acli session all name the target.
  • The probe test -n "${ATLASSIAN_URL+x}" says unset.
  • /rest/api/3/myself on the resolved URL returns 200.

If anything does not match, the migration failed: it says so and stops.

Secrets hygiene

It never opens the .env, not even filtered by key (no cat, grep or source): even an exact grep leaves ATLASSIAN_API_TOKEN in the terminal and in the transcript. It uses the pair by name inside bunx varlock run and checks presence with bunx varlock load --agent (values redacted). It also does not keep a backup of the .env inside the repo, because the .gitignore usually covers the exact name and not the suffixes.

Source: Phases 2 and 3 of references/instance-migration.md. The resolver check is not redundant with the yaml one: it is the only one that proves the tool matches the file, and it warns on stderr if a stale variable contradicts it. To catch an inherited ATLASSIAN_URL: bun run vars:env:check or bun run setup:doctor. In a template repo, atlassian_url stays null.

Instance-migration mode · 11 of 15

The part that gets skipped is the one that corrupts

CatalogRegenerated with
.agents/jira-fields.jsonbun run jira:sync-fields --force
without --force it stops: catalog already populated
.agents/jira-link-types.jsonbun run jira:sync-link-types
has no --force, and swallows it silently
.agents/jira-workflows.jsonbun run jira:sync-workflows
idempotent: --force adds nothing

Before syncing: the manifest

.agents/jira-required.yaml has no ids, but it is the input: jira:sync-workflows catalogs only the work types it declares. If it fell behind, the catalog comes out truncated and with exit 0. It compares it with upstream (bun run jira:baseline warns) and lets you decide per work type.

Prove the ids moved

The .agents/ diff has to show changed ids. And a changed id is not necessarily a correct id: two slugs can swap. It asks the live site what each id is and compares it with the cataloged name.

What slips through most

Select fields with empty options, literal customfield_, status or transition ids outside .agents/, and variables that pin an id above the catalog.

--upex almost never

It downloads the reference catalog from the boilerplate authors, with ids from their site. For your migration, never: it is a scaffold for someone without the Administer permission.

Source: Phase 4 of references/instance-migration.md. If the manifest needs changes, they go first and the syncs after: in the other order the catalogs are regenerated twice. jira:sync-workflows asks for the project key if the yaml has it as null and persists it; in a template that line has to be reverted. The updater never overwrites jira-required.yaml, which is why it falls behind silently.

Instance-migration mode · 12 of 15

Separate commits and what only a person can see

Phase 5 · Commit

chore(jira): sync jira-required.yaml work types with upstream chore(jira): point atlassian_url at the <target> instance chore(jira): refresh field, workflow and link-type catalogs for <target>

The manifest commit goes first and only if something changed. .env is never committed. In a template the yaml commit has no content: it is skipped and says so, with no empty commit.

Push with confirmation

It follows the git strategy via /git-flow-master and does not push without your OK: in a boilerplate, publishing catalogs affects every project that later runs --upex.

The closing report

Verificationhow many ids were checked against the live site and how many do not match
By handdoes the alias domain already resolve to the target?
By handif the manifest was behind, whatever left it behind will do it again

Source: Phase 5 and "Closing report" of references/instance-migration.md. The repo config and the catalog refresh are different responsibilities, which is why they are different commits. If the team consumes the reference catalog with --upex, nobody should run it until upstream publishes its post-migration catalogs.

Safeguards · 13 of 15

What it never does

#Rule
R1Write to Jira, to the repo or to the acli session without your explicit approval, given in the same run. An unattended routine counts the brief as approval only if it names the mode, the project key and, in a migration, both hosts; otherwise it does only the reading and stops before writing.
R2Combine the two modes, or guess one from a bare "fix Jira".
R3Delete and recreate a component that has assigned issues: that is what rename is for.
R4Update an ATLASSIAN_URL in .env or in the environment: it is deleted, because a second copy is the one that goes stale.
R5Guess the target site, or carry on if it does not answer 200.
R6Use --upex to migrate your own instance.
R7Write a host or a project key into a template repo, or fabricate a commit to hide that it is empty.

No shortcuts: missing credentials, full stop.

No false success: an exit 0 does not prove the catalog is complete.

No push on its own: published catalogs travel.

Rules taken from the Compact Rules of SKILL.md and the hard gates of each reference. They rest on Critical Rules #10 (MCP credentials: stop), #5 (push to protected branches according to the project's git policy) and #16 (a success code describes the call, not the outcome: that is why each mode verifies at the destination).

Inputs and outputs · 14 of 15

What it reads, what it leaves

Reads

  • .agents/project.yaml: the host, the project key and whether the repo already has onboarding.
  • ATLASSIAN_EMAIL and ATLASSIAN_API_TOKEN, by name inside bunx varlock run; the .env is never opened.
  • components: the code of the target app and its backlog (.context/PBI/epics/).
  • migration: .agents/jira-required.yaml against the upstream one, and the live site to verify each id.

Leaves

  • components: .context/reports/jira-components-plan.json and, with your OK, the components in Jira.
  • migration: atlassian_url in the yaml and the catalogs jira-fields.json, jira-workflows.json and jira-link-types.json.
  • An acli session repointed on this machine.
  • In the chat: the report, with whatever needs a person marked separately.

Tools: /acli before any Jira operation, scripts/sync-jira-components.ts, the bun run jira:* scripts that package.json declares, and /git-flow-master to commit.

Sources: Compact Rules in SKILL.md, the Prerequisites of references/components.md, Phases 2, 4 and 5 of references/instance-migration.md, and the reports table of .context/reports/README.md, which attributes the components plan to this mode.

Invocation and handoffs

How to invoke it

Claude Code: /jira-administration components or /jira-administration instance-migration. Whatever follows the mode is passed through as is: components BK ../bunkai, instance-migration old.atlassian.net new.atlassian.net.
OpenCode and Codex: load the skill jira-administration, mode components or instance-migration.
Pi: /skill:jira-administration components or /skill:jira-administration instance-migration

Before

When adopting the repo, after bun run jira:sync-fields, jira:sync-workflows and jira:sync-link-types, comes the components mode.
/xray-cli: an Xray site move closes with instance-migration.

After

The testing skills fill in the component of every issue they report: defect management.
/git-flow-master: commits and opens the PR for the migration.

What you take away

Components that reflect the real app without losing a single assignment · a migration that does not silently write into the wrong field · every change seen and approved before it exists.
