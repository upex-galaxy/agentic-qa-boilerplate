Una fuente, tres harnesses

Este repositorio funciona igual en Claude Code, OpenCode y Codex (CLI y Desktop). Existe una sola copia de cada instrucción y de cada skill. Donde los harnesses difieren de verdad, cada uno conserva un adaptador fino y versionado.

La decisión de fondo

Ningún nombre de archivo lo descubren los tres de forma nativa y estable. Claude Code carga CLAUDE.md; OpenCode y Codex cargan AGENTS.md. Mantener dos documentos completos y compararlos en CI no elimina el drift: lo detecta tarde.

Por eso AGENTS.md es el único cuerpo de instrucciones y CLAUDE.md quedó reducido a una línea. Ese @ es la sintaxis de import documentada de Claude Code: trae el archivo al contexto de la sesión sin symlinks, así que funciona igual en un checkout de Windows. 

# CLAUDE.md — el archivo completo
@AGENTS.md

Escribir prosa operativa dentro de CLAUDE.md es drift estructural. La skill sync-ai-context se detiene y lo reporta en vez de propagarlo, y bun run agents:compat:check falla si el archivo deja de ser el shim exacto.

La reparación del alias tiene una salvaguarda: si .claude/skills es un directorio real con contenido propio, se niega a borrarlo y nombra el conflicto. La única excepción es la forma que escribe la CLI de skills (un directorio cuyas entradas son todas punteros hacia .agents/skills): eso se reclama sin pérdida, porque no contiene nada más que enlaces.

Los comandos son transporte, no workflow

Cada comando slash tenía antes el workflow completo escrito adentro. Eso era instrucción duplicada que ningún harness fuera de Claude podía descubrir, y que se desincronizaba de la skill equivalente en cuanto alguien editaba una de las dos.

Hoy los diez sobreviven como alias. El wrapper solo selecciona skill y modo, y reenvía $ARGUMENTS sin tocarlo.

---

argument-hint: [project-path]

La verificación no es cosmética: agents:compat:check rechaza un alias cuya skill destino no exista o cuyo modo no aparezca en su SKILL.md, y compara los veinte wrappers byte a byte contra el manifiesto. Un wrapper al que le crece un cuerpo falla con el mensaje contains workflow prose.

Un emisor de hook, tres adaptadores

El contrato de salida vive una sola vez en .agents/hooks/personality-reinject.mjs, que exporta la constante y la escribe a stdout cuando se ejecuta como script.

  • Claude y Codex lo ejecutan como command hook. En ambos, el texto plano en stdout se agrega como contexto de desarrollador.
  • OpenCode importa la constante desde un plugin fino y la inyecta en el system prompt.

El validador de contrato rechaza rutas absolutas personales en cualquier comando, un emisor compartido que trate CLAUDE.md como canónico, un plugin de OpenCode que reemplace output.system en vez de mutarlo, y la reaparición de los hooks duplicados que se eliminaron.

Paridad de MCPs

Los seis servidores canónicos (context7, tavily, playwright, dbhub, openapi, postman) existen en las tres configuraciones. La comparación no es textual: cada formato nativo (JSON, JSONC, TOML) se normaliza a una forma semántica común (transporte, comando, argumentos, URL, variables de entorno, estado) y recién ahí se compara. Agregar un servidor a un solo harness es un fallo.

Instalación y actualización

bun run setup detecta los tres agentes (binario o configuración de repositorio presente) y deja elegir cuáles configurar. Repara alias y wrappers de forma idempotente. bun run setup:doctor reporta alias, wrappers, adaptadores de hook por harness, paridad de MCPs, configuración de Codex, CLI de Codex y confianza del repositorio.

Si venís de una versión anterior

Un proyecto creado cuando las instrucciones vivían en CLAUDE.md y las skills en .claude/skills/ recibe una migración preflight la primera vez que corre bun run up, antes de que se sincronice un solo componente:

  • La memoria del proyecto pasa de CLAUDE.md a AGENTS.md, y CLAUDE.md queda como shim.
  • Cada skill de .claude/skills/ se mueve a .agents/skills/. Las skills propias del proyecto se preservan igual que las del boilerplate.
  • Si un nombre ya existe en el store canónico, la copia legacy se archiva en .template/pre-agents-migration/ en vez de pisar la canónica.

Nada se borra: todo se mueve o se respalda. La pasada es idempotente y, si algún archivo no se puede resolver sin adivinar, la migración se niega entera antes de tocar nada, en vez de aplicarse a medias.

Codex necesita confianza del repositorio. La configuración de proyecto bajo .codex/ y sus hooks solo cargan en un repositorio marcado como confiable. El doctor reporta ese estado por separado, porque es estado de runtime que no se puede verificar leyendo archivos.

Verificación

bun run agents:compat:check valida el contrato completo: destino del alias, los veinte wrappers contra el manifiesto, los tres adaptadores de hook y la paridad de MCPs. Corre dentro de bun run repo:check, en el hook de pre-push, y condicionalmente en pre-commit cuando los archivos preparados lo afectan.

Para reparar en vez de solo verificar: bun run agents:compat.

Limitaciones conocidas

  • El adaptador de OpenCode usa una transformación de sistema oficial pero marcada como experimental. Claude y Codex están sobre APIs de hook estables. Re-verificar al actualizar OpenCode.
  • El comportamiento de junction en Windows está cubierto por tests unitarios de construcción de ruta y comando. La verificación en una máquina Windows real queda pendiente.
  • Lanzá siempre con bun run claude, bun run opencode o bun run codex: cada uno pasa por dotenv -o, que fuerza que .env gane sobre una variable heredada del proceso padre. Ejecutar el binario pelado se salta eso.
