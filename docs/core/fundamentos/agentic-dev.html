Agentic development: cómo evoluciona un harness

Un repo que trabaja con agentes también tiene que mejorar con el uso. Esta página explica cómo cambia este boilerplate: qué se edita cuando una sesión aprende algo, cómo se comprueba que el cambio no rompió nada y cómo llega ese cambio a los proyectos que lo consumen.

La skill como unidad de cambio

En un proyecto de software normal, lo que cambia es el código. En un harness agéntico cambia también la forma en que el agente trabaja, y esa forma vive en texto: instrucciones, referencias, tablas de gotchas. En este repo ese texto está organizado en skills, una carpeta por flujo de trabajo bajo .agents/skills/. Cada skill tiene un SKILL.md con su frontmatter (nombre, descripción que el harness usa para activarla, metadata.kind) y una carpeta references/ con el detalle que se carga solo cuando hace falta.

Tratar la skill como unidad de cambio tiene una consecuencia práctica. Una lección mal escrita en una skill se carga en todas las sesiones futuras que la activen, se copia a los briefings de cada subagente a través del registry y, si la skill viene de upstream, viaja a cada proyecto consumidor en el próximo update. Un recuerdo equivocado en la memoria de una sesión se olvida. Una regla equivocada en una skill se distribuye. Por eso el repo pone más filtros en el camino hacia una skill que en el camino hacia una nota.

Tampoco todo lo que una sesión aprende merece estar en una skill. El protocolo de refinamiento exige cuatro condiciones a la vez: que la lección siga siendo cierta el próximo sprint, que ningún comando pueda regenerarla desde una fuente de verdad, que cambie lo que el agente hace la próxima vez y que esté pagada con una fecha, una sesión y algo medido. Si falla alguna, va a la memoria de sesión (Engram) o a .context/, donde un comando la vuelve a generar.

El bucle de mejora

El recorrido completo tiene ocho pasos. Empieza con una fricción concreta en una sesión real y termina con esa misma fricción resuelta en un proyecto que nunca la vio. La mitad inferior del dibujo ocurre fuera de este repo, en los proyectos que se crearon a partir de él.

Lo que el dibujo no muestra es dónde se frena cada paso. Una sesión nunca edita una skill en caliente: escribe una propuesta en su propia carpeta de sesión y guarda la misma lección en Engram por si esa carpeta se borra. El dueño del repo lee las propuestas y decide entrada por entrada. Una propuesta sin medición se descarta en esa revisión, aunque suene razonable.

Cómo se mide un cambio

Medir una skill tiene dos preguntas distintas. La primera es si se activa cuando debe y se queda quieta cuando no. La segunda es si, una vez activa, el agente hace lo correcto. Este repo cubre bien la estructura alrededor de ambas y tiene la segunda todavía abierta, y conviene saberlo antes de fiarse de un check verde.

Evals de activación
Las skills con evals/evals.json traen casos positivos y negativos: un prompt, si la skill debería activarse y qué comportamiento se espera. bun run skills:evals los descubre, los cuenta y valida su forma (JSON válido, prompt no vacío, polaridad declarada, ids únicos, la skill esperada existe). No invoca ningún modelo, así que un resultado verde solo dice que los casos están bien escritos. Si la skill se activa de verdad con esos prompts sigue sin medirse, y el propio script lo deja anotado como trabajo pendiente.
Gates estáticos
bun run skills:check ejecuta el lint de skills: frontmatter, vocabulario de metadata.kind, rutas citadas que ya no existen, secciones obligatorias según el tipo de skill. Forma parte de bun run repo:check junto con los tipos, el lint, el contrato de compatibilidad entre harnesses y el manifiesto KATA.
Registry
bun run skills:registry reconstruye .agents/skills/REGISTRY.md, que reúne las compact rules de cada skill. Los subagentes reciben esas reglas en su briefing en lugar de leer el SKILL.md entero. Si alguien edita una regla y olvida regenerar, skills:registry:check lo detecta en el commit.

La guía de Anthropic sobre autoría de skills recomienda escribir las evaluaciones antes que la documentación y medir contra una línea base sin la skill. Este repo tiene la mitad estructural de ese consejo automatizada en CI (skills:evals corre en .github/workflows/build.yml) y la mitad que exige un modelo real queda para cuando haya un grader conectado.

Cómo llega a los proyectos consumidores

Un proyecto creado desde este boilerplate recibe las mejoras con bun run up, que ejecuta cli/update-boilerplate.ts. El updater sincroniza por componentes y nunca pisa los archivos que son identidad del proyecto: AGENTS.md, las configuraciones de MCP de cada harness, los hooks de husky, .agents/project.yaml y cualquier ruta que el proyecto declare en updater.protected_paths.

Cuando upstream y el proyecto no coinciden en un archivo protegido, el updater no decide solo. Cierra con una tabla por superficie y un único prompt de paridad, que guarda en un archivo de un solo uso (parity-plan.md, ignorado por git) dentro del proyecto. Cada fila trae su evidencia (encabezados, claves, servidores MCP) y pide una decisión: conservar la versión del proyecto, tomar la de upstream o fusionar. El agente presenta la tabla, espera la respuesta fila por fila y solo aplica lo elegido. Después vuelve a correr tests, tipos y lint.

El camino de vuelta también está escrito. Si en un proyecto consumidor una skill de upstream falla, la sesión no la edita ahí, porque el siguiente update sobrescribiría el cambio. Redacta un issue con la plantilla skill-feedback, le quita las claves de Jira y los hosts del proyecto, y lo muestra al dueño. Solo con su OK se publica con gh issue create, y después se verifica leyendo el issue de vuelta.

Decisiones que no se re-discuten: ADRs

Algunas decisiones cuestan mucho de revertir: el runner de tests, el modelo de fixtures, cómo se aíslan los datos, cómo se autentican los tests. Si quedan solo en un plan archivado, la próxima sesión las vuelve a discutir o las rompe sin saberlo. Para eso existen los Architecture Decision Records en .context/ADR/, con el formato que popularizó Michael Nygard: contexto, decisión, alternativas descartadas y consecuencias.

La doctrina del repo pide que la decisión pase dos filtros antes de merecer un ADR: que sea arquitectura de tests y que sea difícil de revertir. Un fix de un test flaky o el nombre de un spec no califican. Los ADR son append-only, así que una decisión nueva reemplaza a la vieja con un ADR que la marca como superseded, y nadie borra la anterior.

Errores comunes

Lo que más se repite

Editar una skill de upstream dentro de un proyecto consumidor. Funciona hasta el próximo bun run up, que la sobrescribe y deja una copia en .backups/. Abre un issue skill-feedback, o declara la ruta en updater.protected_paths sabiendo que dejas de recibir los arreglos de ese archivo.

Leer skills:evals en verde como prueba de que las skills se activan bien. Solo valida la forma de los casos.

Guardar en una skill un dato que un comando puede regenerar, como un endpoint o un nombre de estado de Jira. Se queda viejo en silencio. Ese dato va en .context/.

Aceptar "take upstream" en una fila de paridad que menciona claves o servidores que solo tiene el proyecto. Esa opción borra contenido del proyecto; en esos casos la fila sugiere fusionar.

Editar una compact rule y no regenerar el registry. Los subagentes siguen recibiendo la regla anterior hasta que alguien corra bun run skills:registry.

Para profundizar

  • Equipping agents for the real world with Agent Skills (Anthropic Engineering). Por qué las skills son carpetas con instrucciones, scripts y recursos que se cargan por demanda.
