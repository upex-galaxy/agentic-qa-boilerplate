Variables de entorno: quién valida qué

El repo conoce muchas variables y casi ninguna es suya. Esta guía dice a quién pertenece cada una, qué se valida y dónde, qué lee cada harness al arrancar y qué se conecta fuera de .env. La regla corta: nada bloquea la instalación ni el doctor; cada valor lo valida el código que lo lee, con un error que lo nombra.

Fuente canónica

La lista de variables con su alcance vive en cli/lib/variables-manifest.ts; la decisión, en .context/ADR/ADR-0005-validation-scope.md. Esta página es la guía para personas: si alguna vez no coinciden, manda el manifest.

Los tres alcances

Cada variable del manifest lleva un scope. El alcance decide quién tiene derecho a exigirla y, por tanto, cómo se reporta su ausencia.

Alcance Qué es Ejemplos Si falta
Framework (core) Lo que lee el boilerplate. Casi todas están detrás de un interruptor: la sincronía con Xray, el host de Jira, el portal privado de reportes. TEST_ENV (tiene default), AUTO_SYNC, ATLASSIAN_EMAIL y ATLASSIAN_API_TOKEN (cuando el host de Jira está en .agents/project.yaml), XRAY_* (cuando AUTO_SYNC=true) Un aviso del doctor mientras el interruptor esté encendido. El código detrás del interruptor falla nombrándola.
Tooling Herramientas que consiguen su credencial en otro sitio. En .env solo quedan los secretos que usa CI. SLACK_WEBHOOK_URL, PORTAL_* y R2_* (portal privado, solo en GitHub Actions). La búsqueda web, Postman y los logins de acli o resend no son variables de este archivo. Una fila informativa. Nunca un bloqueo.
Proyecto bajo prueba (project) La aplicación que pruebas: su login, su base de datos, su API. El boilerplate las declara como ejemplos tipados para que un .env copiado de la plantilla valide; renómbralas o bórralas al adaptar el framework. LOCAL_USER_EMAIL y STAGING_USER_PASSWORD (nombres de ejemplo), DBHUB_*, API_BASE_URL, OPENAPI_SPEC_PATH Una fila informativa. El consumidor que la lee falla nombrándola: un login vacío lo dice config.testUser en la primera línea de la corrida, no la app.

Los nombres de los interruptores también están en el manifest (featureGate): el host de Atlassian en el yaml, AUTO_SYNC, la pareja AUTO_SYNC más TMS_PROVIDER=xray, y la presencia de PORTAL_URL.

Qué valida varlock y dónde

varlock lee dos archivos versionados que declaran nombres, tipos y sensibilidad, nunca valores. Los valores siguen en .env.

Archivo Quién lo escribe Qué declara
.env.core.schema Generado desde el manifest con bun run vars:schema; lo sincroniza bun run up. No se edita a mano. Las tres secciones, una por alcance. Lo único que varlock se niega a cargar sin valor es TEST_ENV, y tiene default. Todo lo demás es opcional y tipado.
.env.schema Tuyo. Se entrega una vez y el updater no lo vuelve a tocar. Importa el core y añade las variables de tu proyecto. Ahí puedes endurecer un item que el core declara opcional: la declaración del proyecto gana. 
# en .env.schema: exigir la pareja de staging en TU proyecto
# @required=forEnv(staging) @type=email
STAGING_USER_EMAIL=

bunx varlock load --agent      # valida .env con los valores enmascarados
bun run vars:schema:check      # el core generado está al día y el par carga
La excepción es TEST_ENV

@currentEnv resuelve TEST_ENV al inicio y varlock rechaza una segunda declaración del mismo item. Por eso el core conserva su enum y el proyecto no la redeclara; el valor válido lo decide config/variables.ts, que falla nombrando los entornos que sí conoce.

Dónde corre cada validación: bun run vars:schema:check en el pre-commit y en repo:check valida el repo, no tu .env. varlock load en el pre-push solo avisa. La acción de varlock en build.yml valida el esquema contra el job y pasa sin secretos, así que un PR desde un fork también pasa. bun run test:env:check comprueba la forma: que TEST_ENV sea un entorno declarado y que exista la pareja del TMS cuando AUTO_SYNC=true.

Qué lee cada harness

Un harness arranca sus servidores MCP antes de que corra cualquier hook, así que la credencial tiene que estar donde el harness mira al arrancar. Solo se copian las variables que algún MCP del proyecto usa, nunca el .env entero.

Harness Lee Lo escribe Si falta una variable
Claude Code El bloque env de .claude/settings.local.json bun run harness:env, a partir de .env No falla al arrancar: el server muere en su primera llamada autenticada
OpenCode Archivos en .auth/opencode/, referenciados con {file:...} bun run harness:env, a partir de .env Un archivo vacío sustituye una cadena vacía, sin error
Codex El entorno del proceso, por nombre Tú, con bun run codex o direnv Es el único que falla al arrancar nombrando el server

Después de tocar .env: bun run harness:env y reinicia el agente. En Windows los tres wrappers (bun run claude, bun run opencode, bun run codex) cargan .env igual; direnv es opcional en todas las plataformas y en Windows está documentado, no medido.

Validar en el punto de uso

El instalador ofrece credenciales y nunca las exige. El updater marca como requerida solo una variable de framework. El doctor no devuelve error por ninguna credencial. Lo que sí pasa es que el código que necesita un valor falla con un mensaje que nombra la variable, el archivo que la declara y qué hacer si tu app no tiene esa cosa.

El login de la app
config.testUser en config/variables.ts es un getter. Los proyectos ui-setup y api-setup de Playwright lo leen al arrancar, así que una pareja vacía es la primera línea de la corrida. Si tu app no tiene login, quita esos dos proyectos de playwright.config.ts y nadie vuelve a leerlo.
El entorno
Un TEST_ENV que envDataMap no declara falla nombrando los entornos válidos, en lugar de romper más abajo con un undefined.
Jira y Xray
Cada script de sincronía y el CLI de Xray fallan por nombre cuando les falta la credencial. La sincronía de resultados se valida solo cuando AUTO_SYNC=true: en CI corta la corrida, en local avisa.
El portal privado de reportes
scripts/ci/publish-allure-portal.ts exige por nombre las siete variables solo cuando el workflow encuentra PORTAL_URL; sin ella publica en GitHub Pages.

MCPs locales y MCPs a nivel del harness

El principio: un server remoto cuyo único contenido del lado del proyecto era una API key es asunto del harness, no del repo. Solo los servers locales que leen valores del proyecto siguen en .mcp.json, opencode.jsonc y .codex/config.toml, junto a los que no necesitan clave.

Server Dónde vive Por qué
dbhub, openapi En el proyecto, con variables de alcance proyecto (DBHUB_*, API_BASE_URL, OPENAPI_SPEC_PATH) Corren en tu máquina y leen la base de datos y la API de tu app
context7, playwright En el proyecto, sin clave No hay nada que autenticar
Búsqueda web (capacidad web-search), Postman A nivel del harness, una vez por máquina Son remotos y su clave es tuya, no del proyecto. Los skills los resuelven por capacidad: buscan una herramienta cuyo nombre termine en tavily_search, sea cual sea el prefijo del server.

Cómo conectar uno a nivel del harness:

Harness Dónde queda Cómo
Claude Code ~/.claude.json (ámbito de usuario) o un conector de claude.ai claude mcp add --scope user --transport http <nombre> <url>, o conectarlo desde los ajustes de claude.ai; /mcp dentro de la sesión lo lista.
OpenCode ~/.config/opencode/opencode.json, clave mcp Añade el server a la config global; el opencode.jsonc del proyecto no lo redeclara.
Codex ~/.codex/config.toml, tabla [mcp_servers.<nombre>] codex mcp add <nombre> --url <url> --bearer-token-env-var <VAR>
Si tu proyecto venía con esos servers

Un proyecto que adoptó el boilerplate antes de este cambio los conserva: sus archivos MCP están protegidos y bun run up nunca los sobreescribe. La actualización deja una fila de paridad que explica el movimiento, y las dos respuestas son válidas: dejarlos como servers propios del proyecto, o quitarlos y conectarlos a nivel del harness.

Logins de CLI

Los CLIs se autentican solos y guardan su propia sesión. Nada de esto va en .env. 

# Atlassian CLI: sesión persistente en ~/.config/acli/
echo "$ATLASSIAN_API_TOKEN" | acli jira auth login \
  --site "$(bun run --silent jira:url --slug)" --email "$ATLASSIAN_EMAIL" --token

# Resend CLI: guarda la key en el llavero del sistema
resend login

La pareja ATLASSIAN_* sigue en .env porque los scripts de sincronía, el CLI de Xray y el proveedor de TMS la leen por REST; el login de acli no los sustituye. RESEND_API_KEY desapareció de la plantilla porque nada del repo la leía.

Qué te dice el doctor

bun run setup:doctor lista cada variable con su alcance, su interruptor y quién la consume, y añade una sección con los servers a nivel del harness que encuentra en tu configuración de usuario. Un conector de claude.ai no deja archivo, así que ahí dice "no detectable", nunca "falta". El código de salida solo cambia por hallazgos estructurales: no hay .env, las superficies por harness están desincronizadas, el esquema no carga. 

bun run setup:doctor          # tabla por alcance + servers a nivel del harness
bun run setup:doctor --json   # env_var_scopes[] y harness_level_mcps para un agente

Gestores de secretos (próximamente)

El camino recomendado para los valores sensibles es un gestor de secretos (1Password u otro proveedor que varlock resuelva en tiempo de carga) en lugar de un .env con valores en claro. Está planificado como la fase de proveedores del trabajo de secretos y todavía no forma parte del repo: los valores viven en .env. Cuando llegue, los items marcados @sensitive en el esquema serán los que resuelva el proveedor, sin cambiar los alcances de esta página.
