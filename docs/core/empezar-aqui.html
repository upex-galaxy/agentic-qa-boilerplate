La idea en dos minutos

Este repositorio es una máquina de QA que trabaja con un agente de IA. Tú traes el proyecto bajo prueba (el target: un frontend, un backend o ambos) y el boilerplate pone las instrucciones, la capa de conocimiento y las herramientas que el agente usa para planificar pruebas, ejecutarlas, reportar bugs, automatizar y emitir un veredicto de release. Entre cada etapa hay un checkpoint humano: el agente propone y tú apruebas.

Todo lo que puedes invocar pertenece a una de tres categorías:

Tipo Qué es Dónde vive Quién lo invoca
Skill Instrucciones en markdown que guían al agente por tareas largas de varias fases (subagentes, decisiones, referencias). .agents/skills/<nombre>/SKILL.md + references/ El agente la activa cuando tu mensaje coincide con sus triggers. También puedes forzarla con /nombre-del-skill.
Comando Alias generado: elige un skill y un modo, y le pasa tus argumentos. No tiene workflow propio. .agents/compatibility/command-aliases.json, que genera .claude/commands/ y .opencode/commands/ Tú, escribiendo /<nombre>. No se activa solo.
Script CLI en TypeScript que corre en la terminal. scripts/*.ts y cli/*.ts, declarados en package.json Tú, con bun run <script>.

Las tres comparten el mismo combustible: las variables de .agents/project.yaml (nombre del proyecto, URLs por entorno, clave de Jira) y los catálogos de Jira en .agents/. El agente los lee al empezar la sesión y resuelve los placeholders {{VAR}} antes de actuar.

Con quién hablas

El agente tiene una personalidad definida: un QA senior que reporta a un Project Manager, escueto, con respuestas que empiezan por el valor y un menú de temas para profundizar. Si algo de su estilo te sorprende, lee Personalidad.

Instalación

Prerequisitos

El instalador se diagnostica solo y te dice qué falta, pero ahorras una vuelta si instalas antes lo que bloquea.

Herramienta Versión Si falta
Bun >= 1.0.0 Bloquea. El preflight de bun run setup sale con código 1.
Un agente: Claude Code, OpenCode o Codex (CLI o Desktop) última Bloquea. Sin ninguno de los tres, el paso de selección de agentes corta.
git y tar cualquiera Bloquea el scaffolder (git init, extraer el tarball) y los hooks.
node >= 18 Lo exige el doctor del scaffolder.
gentle-ai >= 1.26.5 Aviso. Sin él no se instala Engram (memoria entre sesiones); el resto funciona.
gh, acli, playwright-cli, jq, resend, rg cualquiera Aviso. Cada uno lo necesita un skill concreto; puedes instalarlos cuando ese skill te lo pida.

En Windows funcionan PowerShell y cmd sin WSL. Instala Bun con powershell -c "irm bun.sh/install.ps1 | iex", no con npm i -g bun.

Tres formas de empezar

Recomendado

Scaffolder de npm

bunx create-agentic-qa@latest <nombre-del-repo> descarga el último main sin historial, renombra el proyecto, hace git init, corre bun install y te pasa a bun run setup.

GitHub primero

"Use this template"

Creas el repo desde la web de GitHub, lo clonas y ejecutas bun install y bun run setup. Hereda el historial del boilerplate y el renombrado lo haces a mano.

Solo contribuidores

Clon manual

Para trabajar en el boilerplate mismo (skills, instalador, scripts). Si vas a probar tu propio producto, usa el scaffolder. 

# Camino recomendado
bunx create-agentic-qa@latest mi-proyecto-qa
cd mi-proyecto-qa

# Camino "Use this template" (después de crear el repo en GitHub)
git clone https://github.com/<tu-org>/<tu-repo>.git
cd <tu-repo>
bun install
bun run setup

Si usas la plantilla de GitHub, renombra el proyecto en package.json (name) y en .agents/project.yaml (project.project_name).

Qué hace bun run setup

Es idempotente: cada paso guarda una marca en .template/installer.state.json y una segunda ejecución salta lo que ya terminó.

  1. Detección

    Comprueba Bun y las dependencias, detecta gentle-ai y te deja elegir qué harness configurar: Claude Code, OpenCode o Codex.

  2. Instalación

    bun install, los navegadores de Playwright (bun run pw:install, unos 300 MB de Chromium), Engram con gentle-ai install --preset minimal y los skills de la comunidad con bunx skills add.

  3. Configuración

    Pide las credenciales que usan los MCPs y las guarda en .env. Ofrece direnv allow y, si quieres, crea el repo en GitHub con gh.

  4. Verificación

    Imprime una tabla con los CLIs externos: cuáles están y cómo instalar los que faltan.

  5. Configuración inicial

    Rellena .agents/project.yaml (agents:setup), autentica acli, sincroniza los catálogos de Jira (tu workspace, el estándar de UPEX-Galaxy o saltarlo) y valida con jira:check. Al final genera las credenciales por harness (ver la sección siguiente).

Comprueba el resultado en cualquier momento con bun run setup:doctor (añade --json si lo va a leer un agente). Lista las variables pendientes con la URL donde se genera cada token.

Antes del primer push: la estrategia de git

El scaffold trae solo-main como estrategia por defecto, marcada como heredada. Pídele al agente "set up our git strategy" para que /git-flow-master la defina contigo. Mientras no lo hagas, el hook pre-push falla con un mensaje que te manda aquí. Es la señal de que falta ese paso.

Las conexiones con datos reales (Jira y Xray, la base de datos, la API) tienen su propia guía en Setup.

Credenciales y arranque del agente

Copia .env.example a .env (el instalador lo hace por ti) y rellena los valores. .env está en .gitignore y es la única fuente de verdad de los secretos. Hay dos archivos que se parecen y no hacen lo mismo:

.env .agents/project.yaml
Contiene Secretos y configuración del runtime de tests y de los MCPs. Identidad del proyecto y variables {{VAR}} para el agente.
Ejemplos LOCAL_USER_EMAIL, ATLASSIAN_API_TOKEN, TAVILY_API_KEY, XRAY_CLIENT_SECRET project.project_name, URLs por entorno, issue_tracker.atlassian_url
¿Secretos? Sí No, debe poder commitearse
¿En git? No. Se versiona la plantilla .env.example. Sí

La URL del sitio de Atlassian no va en .env: vive solo en .agents/project.yaml y se lee con bun run --silent jira:url. Una copia vieja en el entorno reconstruía la caché desde un Jira muerto sin avisar, por eso se sacó de ahí.

Cómo llega cada credencial a cada harness

Un harness lee su configuración y arranca los servidores MCP antes de que corra cualquier hook, así que la credencial tiene que estar en un sitio que el harness lea al arrancar. Cada uno lee un sitio distinto:

Harness De dónde lee las credenciales Quién lo escribe
Claude Code El bloque env de .claude/settings.local.json (gitignored). bun run harness:env, a partir de .env.
OpenCode Archivos en .auth/opencode/, referenciados desde opencode.jsonc con {file:...}. bun run harness:env, a partir de .env.
Codex El entorno del proceso. Tú, al lanzarlo con bun run codex, o direnv con el .envrc del repo.

harness:env solo copia las variables que algún MCP usa, nunca el .env entero, y no imprime valores. bun run harness:env:check te dice si .env y esos archivos se desincronizaron.

  1. Rellena .env

    Con los valores que te pidió el instalador o los que faltan según setup:doctor.

  2. Ejecuta bun run harness:env

    Regenera las credenciales de Claude Code y OpenCode.

  3. Reinicia el agente

    Las variables se leen cuando arrancan los servidores MCP. Una sesión abierta no ve los cambios. 

bun run claude     # Claude Code
bun run opencode   # OpenCode
bun run codex      # Codex CLI (Codex Desktop usa la misma config del repo)

Cada wrapper es dotenv -o -e .env -- <binario>. El -o hace que .env gane sobre una variable heredada de la shell; si lanzas el binario a pelo, un valor viejo del entorno puede tapar el del archivo.

Un 401 es la señal

Si falta una variable, Claude Code y OpenCode no fallan al arrancar: el MCP muere en su primera llamada autenticada y parece una herramienta rota. Codex es el único que falla al arrancar nombrando el servidor. Ante un 401/403 o un fallo raro de un MCP: arregla .env, ejecuta bun run harness:env y reinicia la sesión.

El ciclo de vida: cinco fases

Cada fase tiene un disparador, un resultado concreto y una frecuencia. Avanzas cuando existe el resultado de la anterior, y vuelves a Mantenimiento cuando la documentación se aleja de la realidad. 

  una vez por repo           una vez por target              continuo        cuando hay drift
+-----------------+   +---------------+   +-----------+   +-------------+   +---------------+
| 0 Bootstrap     |-->| 1 Discovery   |-->| 2 Adapt   |-->| 3 QA diario |<--| 4 Mantenim.   |
| bun run setup   |   | /project-     |   | /adapt-   |   | 7 stages    |-->| sync + maps   |
|                 |   |  discovery    |   |  framework|   | con skill   |   |               |
+-----------------+   +---------------+   +-----------+   +-------------+   +---------------+
Fase Disparador Produce Cuándo repetir
0 · Bootstrap bun run setup, luego .env y bun run harness:env Dependencias, Engram, skills de la comunidad, MCPs cableados, .agents/project.yaml relleno y los catálogos de Jira (jira-fields.json, jira-workflows.json). Clon nuevo o entorno reseteado.
1 · Discovery /project-discovery con la ruta del repo target o la descripción del stack .context/: PRD, SRS, glosario, mapas de datos, features y API, y el master test plan. Cuatro fases: Constitution, Architecture, Infrastructure, Specification. Target nuevo o cambio grande de arquitectura.
2 · Adapt /adapt-framework, siempre después de Discovery tests/components/, fixtures, config/variables.ts y api/schemas/ adaptados al stack y al modelo de auth del target. Cambio de auth o de stack. Es idempotente: solo retoca lo que sigue genérico.
3 · QA diario El skill dueño del stage en el que estás (tabla siguiente) ATP, ATR, ATS, bugs, test cases en el TMS, tests automatizados, veredictos de regresión. Cada sprint, cada ticket.
4 · Mantenimiento .context/, AGENTS.md o .agents/ ya no reflejan el producto Docs sincronizados (/sync-ai-memory), mapas regenerados (/business-*-map, /master-test-plan), catálogos de Jira al día (jira:sync-*, jira:check, vars:check) y el framework actualizado con bun run up. Cuando aparece el drift. Trátalo como un warning del compilador.

La fase 3 son los stages del IQL

El QA diario sigue los ocho stages del IQL (Integrated Quality Lifecycle). Siete tienen un skill que los ejecuta; Observation está declarado pero todavía no tiene skill. La metodología completa está en IQL y cómo la implementa este repo, en El IQL en este repo.

Stage Momento Skill Resultado
Shift-Left antes del sprint (en lote) /shift-left-testing ACs refinados y ATP previo al sprint en el campo de la historia
Planning en el sprint /sprint-testing ATP (Test Plan), ATS y test cases
Execution en el sprint Exploración UI · API · DB
Reporting en el sprint ATR, comentario de QA y bugs
Documentation después del sprint /test-documentation Test cases en el TMS con veredicto de ROI: Candidate, Manual o Deferred
Automation después del sprint /test-automation Tests KATA con Plan, Code y Review
Regression después del sprint /regression-testing Fallos clasificados y veredicto GO, CAUTION o NO-GO
Observation producción ninguno todavía Declarado, no implementado

Elige tu camino

En la vida de un proyecto pasas por todos, en orden, a medida que una feature madura. En una sesión concreta eliges uno y dejas que el skill conduzca.

Antes del sprint

/shift-left-testing

Historias en Backlog con ACs flojos. Refina en lote, deja preguntas para PO y Dev, escribe el ATP en el campo de la historia y mueve el estado backlog → shift_left_qa → estimation. La feature aún no existe: no hay ejecución.

Manual

/sprint-testing

Ticket en "Ready For QA" o un retest de bug. Planifica, explora UI, API y DB, y reporta ATP, ATR, ATS y bugs en el TMS. Si la historia pasó por Shift-Left hace menos de 30 días, se salta parte de la planificación.

Codificar

/test-documentation, luego /test-automation

El test case pasó el filtro de ROI, el AC es estable y la automatización llega a la superficie. Se documenta en el TMS y se convierte en un test KATA de la suite de regresión.

Release

/regression-testing

Corrida nocturna o previa a un release sobre la suite existente. Clasifica cada fallo (REGRESSION, FLAKY, KNOWN, ENVIRONMENT, NEW TEST) y emite el veredicto.

Evolucionar el framework no es un camino de QA

Cambios en las bases KATA, fixtures, cli/, scripts/ o api/schemas/ van por /framework-development, que tiene su propio Plan, Code, Verify y Archive. Nunca por los cuatro skills de testing.

Tres piezas que se confunden

Tienen nombres parecidos y verbos que se solapan ("adaptar", "sincronizar", "refrescar").

Pieza Cuándo Qué toca
/adapt-framework Una vez por target, después de /project-discovery. El código de tests de este repo (tests/components/, config/, api/schemas/). Nunca el target. Analiza sin escribir, presenta un plan y espera tu aprobación.
sync-ai-context (alias /sync-ai-memory) Cuando los docs para la IA ya no reflejan el repo. AGENTS.md, README.md y el resto de docs críticos, contra los skills, los alias, .context/ y package.json. No toca la memoria de Engram.
project-context (alias /business-*-map, /master-test-plan) Cuando el producto cambia: entidades, features, endpoints, riesgos. Los mapas de .context/business/ y .context/master-test-plan.md. En modo UPDATE muestra el diff y espera aprobación.

agentic-qa-core tiene un papel pasivo: guarda la doctrina compartida (plantilla de briefing, patrones de dispatch, test design, gestión de defectos) que los skills de workflow cargan cuando la necesitan. Nunca lo invocas tú.

Circuito 2: orquestación con subagentes

skill de workflow (/sprint-testing, /regression-testing, ...)
   | escribe un briefing de 7 componentes
   v
subagente (contexto limpio)
   | carga el skill de la herramienta
   v
/acli · /xray-cli · /playwright-cli · MCPs  -->  ejecuta y reporta

La conversación principal coordina y los subagentes hacen la lectura pesada. Cada briefing lleva siete partes: objetivo, docs de contexto, estándares del proyecto, skills a cargar, instrucciones exactas, formato del reporte y reglas. Los estándares salen ya resumidos de .agents/skills/REGISTRY.md (lo genera bun run skills:registry), así el subagente no relee cada SKILL.md. La plantilla está en .agents/skills/agentic-qa-core/references/briefing-template.md.

Antes de trabajar, los skills de testing y /framework-development pasan un chequeo de preparación: herramientas que faltan, MCPs caídos, tokens vencidos o un framework sin adaptar se detectan al principio y no a mitad de la corrida (.agents/skills/agentic-qa-core/references/preflight-gate.md).

Existe un segundo ejecutor opcional, el worker supervisado: una sesión persistente con la que sigues hablando, coordinada por /orca-orchestration. Solo aparece si el binario orca está instalado y su runtime responde.

Circuito 3: auto-carga de skills por CLI

Antes de ejecutar un binario, el agente carga el skill que sabe usarlo (flags, auth, paginación, errores). La fuente es AGENTS.md §6.5.

Los seis MCPs

Los declara .mcp.json y existen igual en opencode.jsonc y .codex/config.toml. La regla general: primero el CLI (gasta menos tokens) y el MCP como respaldo, salvo donde el MCP es la herramienta principal.

MCP Para qué Variables en .env
context7 Documentación oficial y versionada de librerías, frameworks y CLIs. Obligatorio antes que la búsqueda web para dudas de docs. ninguna
tavily Búsqueda web: errores, soluciones de la comunidad, investigación general. TAVILY_API_KEY
playwright Automatización de navegador. Respaldo de /playwright-cli. ninguna
dbhub Consultas SQL para validar datos. Necesita que edites dbhub.toml (guía). DBHUB_TYPE, DBHUB_HOST, DBHUB_PORT, DBHUB_DATABASE, DBHUB_USER, DBHUB_PASSWORD
openapi Solo lectura del contrato de la API: endpoints y schemas. Las requests autenticadas van por curl con el token de bun run api:login (guía). API_BASE_URL, OPENAPI_SPEC_PATH
postman Colecciones de Postman; respaldo para pruebas de API. POSTMAN_API_KEY

El MCP de Atlassian no está entre los seis: es opt-in y se documenta en .agents/skills/agentic-qa-core/references/mcp-atlassian-optin.md. Jira y Xray se manejan con acli y bun xray (guía).

Engram: memoria entre sesiones

Engram es un servidor MCP que guarda memoria estructurada y sobrevive a sesiones y compactaciones. Lo instala bun run setup con gentle-ai install --preset minimal, a nivel de usuario, fuera del repo. Ese preset instala solo Engram: los skills SDD de gentle-ai no vienen, porque los skills de workflow ya cubren Plan, Code y Verify.

Qué hace el agente Cuándo
Guarda (mem_save) Sin que se lo pidas, tras una decisión de diseño, un bug resuelto (con su causa raíz), una convención nueva o una sorpresa del proyecto.
Busca (mem_search) Cuando dices "recuerda", "qué hicimos", "cómo resolvimos", o mencionas trabajo anterior, en cualquier idioma.
Resume (mem_session_summary) Al cerrar la sesión: objetivo, hallazgos, lo hecho, próximos pasos y archivos. Es la semilla de la siguiente sesión.

Si saltas gentle-ai, todo sigue funcionando, pero cada sesión empieza sin memoria.

Catálogo de skills

Workflow: los stages del pipeline

Shift-Left

shift-left-testing

Refinamiento previo al sprint sobre un lote de historias: ACs, huecos, ATP temprano y etiqueta shift-left-reviewed.

Planning · Execution · Reporting

sprint-testing

QA manual por issue o por sprint entero. Produce ATP, ATS, ATR, comentario de QA y bugs.

Documentation

test-documentation

Test cases en el TMS con puntuación de ROI y veredicto Candidate, Manual o Deferred.

Automation

test-automation

Plan, Code y Review sobre KATA, Playwright y TypeScript.

Regression

regression-testing

Regresión, smoke o sanity por CI, clasificación de fallos y veredicto GO, CAUTION o NO-GO.

Framework

framework-development

Evolución del boilerplate: bases KATA, fixtures, cli/, scripts/. No es para tickets.

Setup y contexto del proyecto

Onboarding

agentic-qa-onboard

Tour de orientación y mostrador para quien está perdido: explica en lenguaje llano y ofrece abrir el deck de cada skill.

Generador

project-discovery

Ingeniería inversa del target en cuatro fases. Genera PRD, SRS, glosario y .context/.

Adaptación

adapt-framework

Adapta KATA al stack del target: analiza sin escribir, propone un plan y solo lo aplica con tu aprobación. Idempotente.

Contexto

project-context

Regenera los mapas de datos, features y API y el master test plan, por modo o todos en orden.

Contexto

sync-ai-context

Sincroniza los docs críticos para la IA con las instrucciones, skills, alias y package.json.

Jira

jira-administration

Administración de Jira en dos modos sellados: components y migración de instancia.

Comandos y scripts

Comandos (alias)

Diez alias, definidos en .agents/compatibility/command-aliases.json. Los archivos de .claude/commands/ y .opencode/commands/ los genera bun run agents:compat; no se editan a mano. Codex no tiene comandos: ahí invocas el skill directamente.

Scripts de package.json

Se ejecutan con bun run <nombre>. Agrupados por uso; la lista es la de package.json, sin añadidos.

Instalación, entorno y agentes
setup Preflight y el instalador interactivo. --variables abre el menú de credenciales.
setup:doctor Diagnóstico de solo lectura: variables, dependencias, navegadores, MCPs, confianza de Codex.
harness:env · harness:env:check Genera o verifica las credenciales por harness a partir de .env.
agents:setup Asistente que rellena .agents/project.yaml.
claude · opencode · codex Lanzan el agente con .env cargado.
pw:install Instala Chromium con sus dependencias de sistema.
up Actualiza el proyecto con las novedades del boilerplate.
worktree:provision Prepara un worktree nuevo con lo que git no copia: .env, .auth/, node_modules/ y skills de la comunidad.
Documentación
docs Sirve este portal en local y lo abre en el navegador.
onboarding El mismo servidor, abierto en esta página.
docs:build Regenera el manifiesto del portal.
docs:check Busca links rotos y rutas inexistentes en docs/.
Jira, Xray y caché local
jira:check Verifica el workspace contra .agents/jira-required.yaml.
jira:baseline Avisa si el manifiesto declara menos work types que el de upstream. Nunca bloquea.
jira:sync-fields · jira:sync-workflows · jira:sync-link-types Catalogan custom fields, estados y transiciones, y tipos de link.
jira:components Reconcilia los components del proyecto de Jira con un plan.
jira:sync-issues Trae issues a .context/PBI/: pull, get <KEY>, jql "<query>".
context:hydrate Reconstruye toda la caché de .context/PBI/ con comentarios.
jira:url Imprime la URL de Atlassian del proyecto (--slug para el host).
xray El CLI de Xray (bun xray).
test:sync Después de bun run test, escribe los resultados de los ATCs en Jira o Xray (con AUTO_SYNC=true).
Tests y reportes
test Toda la suite de Playwright.
test:e2e · test:integration Un solo proyecto: E2E o integración.
test:smoke Los proyectos smoke-ui y smoke-api: los tests @critical de E2E e integración.
test:ui · test:headed · test:debug Modo UI, con navegador visible o con el inspector.
test:last-failed · test:retries Repetir lo que falló o correr con dos reintentos.
test:report · test:clean Abrir el reporte de Playwright o borrar resultados y reportes.
test:env:check Valida .env para el TEST_ENV activo.
tests:map Mapa de cobertura Epic, Story y Test en HTML, sin llamar a Jira.
allure:run · allure:agent Corren bun test bajo Allure.
allure:generate · allure:open · allure:watch Generar, abrir o vigilar el reporte de Allure.
API y KATA
api:sync Trae el spec OpenAPI y regenera los tipos de api/schemas/.
api:login · api:login:local · api:login:staging Autentica y deja el token en .auth/tokens.env para usar con curl.
kata:manifest · kata:manifest:check · kata:manifest:watch Regenera, valida o vigila kata-manifest.json, el registro de componentes y ATCs.
Calidad del repo
repo:check · repo:fix Todos los chequeos en cadena, o su versión que corrige lo que puede.
format:check · format:fix Prettier sobre JSON, YAML, CSS y HTML.
lint:check · lint:fix ESLint.
types:check TypeScript sin emitir.
vars:check Placeholders {{VAR}} y {{jira.*}}.
vars:env:check Variables del proceso contra .env.
vars:schema · vars:schema:check Genera o valida el schema tipado de las variables de entorno.
skills:check · skills:registry · skills:registry:check · skills:evals Lint de skills, el registro REGISTRY.md y las evals.
agents:compat · agents:compat:check Genera o valida los archivos por harness (shim, alias, wrappers, hooks, paridad de MCPs).
agents:schema · agents:schema:check El schema de .agents/project.yaml.
git:policy Compara la política de git declarada con la del host.

Además está prepare, que instala los hooks de Husky al hacer bun install. No hay un script env: para cargar .env en tu shell actual usa set -a; source .env; set +a directamente en la terminal.
