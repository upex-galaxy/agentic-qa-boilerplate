# Skills, modes and MCPs

## 5. SKILLS + MODES + MCPs REGISTRY

### Skill tiers (T1-T4)

Skills come in four tiers with different discovery and load rules.

- T1 is project-owned and committed in `.agents/skills/`, listed below under "Skills". It loads silently on trigger.
- T2 is project-vendored: committed in `.agents/skills/` from upstream (for example `judgment-day` from gentle-ai), with license and attribution kept in frontmatter. It loads silently on an explicit trigger.
- T3 is community project-level: installed by `install.ts` into `.agents/skills/` and not committed. It loads silently when its category matches the task domain. It is found by the installed-skill scan (session skill list plus `.agents/skills/` on disk, git-ignored folders included) and never appears in `REGISTRY.md`, which lists committed skills only (`agentic-qa-core/references/skill-composition-strategy.md` §3.1). `skill-creator` is T3 and is always the builder when this repo scaffolds a skill (`/framework-development` for a boilerplate skill, `project-context` mode `context-skill` for a consumer's `<aspect>-context`), so no clone runs without it.
- T4 is community user-level, installed globally. Ask before loading it, unless a committed doctrine (`AGENTS.md`, a T1 `SKILL.md` or a reference it cites) or the operator's standing instructions name it as the instrument for the moment at hand: then load it at that moment without asking, and a missing install follows that doctrine's own gate. Asking is for a skill matched only by task domain; a worker or routine with nobody to ask skips that case and reports it. Loaders: `agentic-qa-onboard` §"Community skills installed at user level" (lint `T4-LOADER`).
- Context skills (`metadata.kind: context`, slug `<aspect>-context`) hold judgment over one aspect, citing `.context/` caches and never restating them (`agentic-qa-core/references/skill-scaffold.md` §3). Upstream ships `iql-context` (the methodology index, adapted per project through `qa.methodology` in `.agents/project.yaml` and the bootstrap-only `references/project-overrides.md`) and the context map skills (`CONTEXT_MAP_SKILLS`, `cli/lib/context-maps.ts`, each naming its generator). The map skills are placeholders: `bun sync` delivers their folder once when absent, each holds its generated HTML map and may write only its own `references/` (`metadata.writes`, lint `CONTEXT-WRITES`). Every other `*-context` is project-local by construction, and `bun sync` never delivers, overwrites or deletes it (`isProjectLocalSkillPath`, `cli/lib/updater-core.ts`). `project-discovery` proposes them at close, `project-context` mode `context-skill` creates them through `skill-creator`, and the skill resolver injects into a briefing only the context skills whose aspect the dispatch touches (`agentic-qa-core/references/skill-resolver.md`).

The orchestration doctrine is the T4 skill `agent-orchestration` (`USER_LEVEL_SKILLS`), loaded by the `orca` row of §6.5 before any orchestration command; this repo's own fleet parts are `agentic-qa-core/references/fleet-launch-seam.md`, `fleet-provisioning.md` and `fleet-project-profile.md`. The orchestration binary ships its own vendor guides and installs them user-level; `agent-orchestration` loads them by name, the `orchestration` guide for a worker and both for a conductor. They gate nothing: availability is decided by the binary plus a reachable runtime. `install.ts` does not install the vendor guides; the binary owns that.

Layout: T1 repo skills live in `.agents/skills/<slug>/` (committed source) and T3 community skills share that project store. Claude Code discovers the same tree through the generated `.claude/skills` alias, while user-level T4 skills stay harness-specific. `install.ts` targets the canonical store for project skills and passes `--agent` only for user-level installs. The full contract is `.agents/skills/agentic-qa-core/references/skill-composition-strategy.md`.

Memory install scope: `cli/install.ts` wires Engram (persistent memory) per agent with the engram binary's own `engram setup <agent>` and never runs `gentle-ai install`, because gentle-ai's orchestrator, agent-routing and hook layer competes with §3. The boilerplate does not use gentle-ai's workflow layer (no SDD, no gentle-ai orchestrator): our workflow skills (`/sprint-testing`, `/test-automation`, `/test-documentation`, `/regression-testing`) cover Plan, Code and Verify natively. Detail: `INSTALLER.md`.

### Skills (lazy-loaded by trigger phrase)

This table is the trigger router, not the inventory: tiers, kinds, flags and full descriptions live in `.agents/skills/REGISTRY.md` (generated by `bun run skills:registry`) and in each `SKILL.md` frontmatter. `bun run skills:check` (`TIER-MISMATCH`) warns when a community skill declared in `cli/install.ts` has no row here, or when a row names a skill `cli/install.ts` does not declare, so the drift shows on every run and is never reconciled by hand. This file is synced, so it routes upstream's skills only. A skill the project authored (an `<aspect>-context` from `project-context` mode `context-skill`, or any other) is routed from the `## Project context skills` table of `agent-project.md`, which `bun sync` never overwrites.

### Skill modes

A multi-mode skill lists its modes in its own `## Mode routing` section, and that section is the only list. Invoke it by name plus mode: `/project-context data` on Claude Code, "load `project-context`, mode `data`" on OpenCode and Codex. The first token of `$ARGUMENTS` that matches a mode is the mode and the rest is forwarded. With no matching token the skill applies its declared default, or asks when a person is present. A former command name (`break-down-tests`, `business-data-map`) survives only as a trigger phrase in its skill's `description`.

### MCPs (decision rules)

Each row is a capability skills declare (`metadata.requires_capabilities`) and resolve by tool-name suffix, so a user-level server or a claude.ai connector exposing the same tools satisfies the row. The committed server that provides it is whatever `.mcp.json` declares (`KNOWN_MCP_IDS` in `cli/lib/agent-compatibility-contracts.ts`); the canon is `agentic-qa-core/references/mcp-capabilities.md`.

| Capability | Use for | Rule |
|---|---|---|
| `api-schema` | API schema, read-only (endpoint discovery, request/response contracts) | `[API_TOOL]` schema-read leg only. Authenticated execution is `curl`, not the MCP: see `agentic-qa-core/references/api-testing-doctrine.md`. |
| `db` | DB queries, data validation | `[DB_TOOL]` primary |
| `library-docs` | Library official docs ("how to use X") | `[DOCS_TOOL]` primary, and required for any library, framework, SDK, API or CLI doc lookup (React, Next, Playwright, Prisma, Tailwind, Express and the like). Prefer it over built-in `WebSearch` / `WebFetch`: a library-docs MCP returns current versioned docs, while built-in web search returns stale blog posts. |
| `web-search` (harness-level: a claude.ai connector or a user-scope server, not `.mcp.json`) | Community solutions ("how to solve X"), troubleshooting, non-doc web research | `[WEB_SEARCH_TOOL]` primary, and required for any general web search: community fixes, error message lookups. Prefer it over built-in `WebSearch` / `WebFetch`, since a search MCP returns ranked, summarized results and the built-in is shallower. No provider available: stop at the point of use (Rule #10). |
