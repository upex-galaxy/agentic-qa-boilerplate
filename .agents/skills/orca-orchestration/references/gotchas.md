> Loaded by: the conductor, when something behaves strangely — and read once in full before the
> first fleet on a new machine.
> Every row was PAID FOR in a real session, in one of four repos, on the date given. None of it
> is in any vendor guide. The `verified against` column is the app version the behaviour was last
> confirmed on; re-confirm with `orca agent-context --json` after an upgrade, and move a row to

## 1 · Runtime and mailbox

| # | Gotcha | Symptom | Fix | Measured | Verified against |
|---|---|---|---|---|---|
| G1 | **An unacknowledged batch replays forever** and hides everything queued behind it. Delivery is FIFO and a bound Run replays the same batch until it is acked | a `check` returns a message you recognize from 20 minutes ago | ack in the SAME command that re-arms the wait: `check --ack <id> --wait --types … --timeout-ms …`. Leave no window in which the ack can be forgotten | 2026-09-04, curacity, Sprint 20: a wave-1 status reappeared at the head of the queue while wave 2 was already launched, and wave 2's first reports were invisible | 1.4.190 |
| G2 | **An unacked batch also kills the notice.** The runtime notifies only on empty → non-empty, so once mail is unread it never notifies again | four messages accumulate for hours and the conductor believes the mailbox is quiet | verify every ack (`acknowledged` equals the id requested, pending count drops) and NEVER put it in a compound command whose exit code gets swallowed | 2026-09-14, upexgalaxy: an ack inside a compound command exited 1, nobody checked | 1.4.190 |
| G3 | **A Run admits exactly ONE actionable waiter**, and an orphaned one blocks the mailbox. A waiter started with a shell `&` holds the slot with nobody listening | `check` returns a failure naming an existing waiter instead of a batch. A quiet mailbox and a blocked one look identical | arm the waiter as a tracked foreground/background TASK, never with `&`. Recover by locating and killing the stale `orchestration check` process, then re-arm | 2026-09-04, curacity | 1.4.190 |
| G4 | **Every scripted call needs `</dev/null`.** The binary reads stdin when stdin is attached, and inside a loop or a background shell that read never returns | the command hangs with no output, indistinguishable from slow work | `</dev/null` on EVERY subcommand, not just the orchestration ones | 2026-09-04, curacity: a loop creating 18 tasks blocked on the FIRST call for 3+ minutes; with `</dev/null` all 18 finished in seconds | 1.4.190 |
| G5 | **`check --wait` writes keepalive JSON to stderr every 15 s** (`_keepalive`), unrelated to heartbeat messages | a merged stream looks like it is receiving messages that are not there | filter with `jq 'select(._keepalive|not)'` when merging streams | 2026-09-17, schema notes | 1.4.190 |
| G6 | **Do not build a monitor.** The runtime injects the notice itself; a homemade poller competes with it and can null it, and it triggers on ECHOES — the conductor's own messages are visible on the worker's screen, so a grep for a completion token reads them back as a report | a "report" that is actually the conductor's own instruction, or a notice that never fires | no monitor. Wait inside the turn with one waiter | 2026-09-13, upexgalaxy | 1.4.190 |
| G7 | **A reply body can arrive empty on the worker side** | the worker receives a bare `Re:` and asks the same question again | duplicate a substantive reply with `terminal send` and say in the body that you did | 2026-09, upexgalaxy | 1.4.190 (not re-measured) |
| G8 | **`task-create --deps <json_array>` has an undocumented element shape** — strings with ids, or objects? No example anywhere, and the schema's notes are empty | a dependency graph that silently does not constrain anything | do not use `--deps` yet. Order rounds by hand in `roster.md` | 2026-09-17, schema read | 1.4.190 |
| G9 | **A task reaches `dispatched` only through a real Dispatch.** A manual status update to `dispatched` is rejected | the ledger says `ready` while the worker is clearly working | create the Dispatch with the launch itself: `worker-start … --agent` (native, supervised) moves the task in the same step, and the plain `dispatch` form gives an addressable id without supervision (G48) | 2026-09, curacity | 1.4.190 |
| G10 | **The permission classifier can block the dispatch call itself**, independently of the terminal running fine | the task stays `ready` instead of `dispatched` | **cosmetic, not functional**: the worker already has its full command. Do not retry around the block; note the gap, continue, and square the ledger with a task status update when the worker finishes | 2026-09-06, curacity | 1.4.190 |
| G46 | **`orchestration send --to <terminal handle>` never reaches a busy agent.** It queues mail nothing tells the worker to read, and **both it and `terminal send` return `ok: true`**, so the useless call is indistinguishable from the useful one | the worker works on, oblivious; the conductor believes it delivered | the only verb that reaches a RUNNING session is `terminal send`. Mailbox addresses (`run:<id>`, `dispatch:<id>`) are for messages a worker will `check`, never for a nudge | 2026-09-17, bunkai dogfood: the preamble pointer was sent the wrong way first and had to be resent | 1.4.190 |
| G47 | **`dispatch-show --preamble` prints NOTHING under `--json`.** The preamble is text-only output; the JSON form returns the dispatch object without it | a playbook scripted with `--json` everywhere silently delivers an empty preamble | drop `--json` for this ONE call, write the text to a file in the conductor's scope, then point the worker at the file | 2026-09-17, bunkai dogfood | 1.4.190 |
| G48 | **`dispatch` WITHOUT `--inject` still creates a dispatch row** (`status: dispatched`, a real addressable id). The vendor grammar documents only the `--inject` case, so a reader cannot tell | a conductor believes it has no dispatch id to address and falls back to screen-scraping | use the plain form on the unsupervised path and keep the id: it is what `dispatch:<id>` and the worker's `worker_done` route on | 2026-09-17, bunkai dogfood (`ctx_0201eebb18f7`) | 1.4.190 |
| G49 | **`task-create --task-title` is accepted and discarded** | every task comes back with `"title": null`, and a task listing is unreadable | put the human-readable label in `--spec` (and in `roster.md`), never only in the title flag | 2026-09-17, bunkai dogfood (3 of 3 tasks) | 1.4.190 |
| G51 | **A realistic wait cannot stay inside the turn.** The harness caps a foreground command at 600 s, while a round runs tens of minutes | a `check --wait --timeout-ms 1800000` is killed mid-wait and the conductor cannot tell a timeout from a dead mailbox | roll the wait: `--timeout-ms 540000`, re-armed with the verified ack in the SAME command, as many times as the round needs. A longer single wait is a background job only when the harness tracks it; the runtime's own mailbox notice stays the primary wake-up | 2026-09-17, bunkai dogfood | 1.4.190 |
| G53 | **`escalation` is rejected on the unsupervised path.** A terminal whose `--from` handle owns no supervised dispatch gets `Rejected escalation:` returned as a `status` message, not as an error the worker can act on | a worker reports a hard blocker and nothing arrives; it reads its own rejection as a reply | on that path the brief tells workers to send blockers as `--type status` with the subject prefixed `BLOCKED:`. `escalation` is for supervised workers | 2026-09-17, bunkai dogfood (2 escalations refused) | 1.4.190 |
| G56 | **`run-current` returns a null Run for a dispatched worker.** Being dispatched does NOT bind your terminal to the dispatching Run | a worker concludes it is unbound and either guesses a Run from a listing or refuses to create its own | correct and useful: a worker that is ALSO a conductor creates its own Run with no collision, and its upstream reporting still routes, because `worker_done` routes by Dispatch and not by the bound Run. This is what makes a nested conductor legal | 2026-09-17, bunkai dogfood (live dispatched worker with `ORCA_TERMINAL_HANDLE` set) | 1.4.190 |
| G57 | **The first `worker_done` revokes the Dispatch, and everything addressed to it afterwards bounces.** `capability_revoked_at` is stamped at that moment | a question the worker raised BEFORE finishing can no longer be answered (`reply` returns `dispatch_inactive`, code and message, not a warning), and a second `worker_done` comes back as `Rejected worker_done: … capability is revoked` even though the worker kept working and produced real output | answer a worker's questions BEFORE it settles, and read a settled worker's later output from its report and its screen, never from the mailbox. A worker that keeps working after `worker_done` is not misbehaving; it has simply lost its channel | 2026-09-18, bunkai-sync2 (a 04:21 question answered at 05:1x: refused; the 04:49 `worker_done` rejected) | 1.4.190 |
| G59 | **`ask` times out returning EXIT 0.** After its timeout it prints `ask timeout after <ms>ms (thread <id>)` on stdout and exits zero | a worker that branches on `$?` concludes it was answered and proceeds as if the conductor had replied; here it decided a scope question alone | never read `ask` success from the exit code: grep stdout for `ask timeout` and treat that as unanswered. Decide the fallback IN THE BRIEF, before dispatch, so an unanswered `ask` resolves to a stated default instead of the worker's judgement | 2026-09-18, bunkai-sync2 (900 s timeout, exit 0, unilateral decision followed) | 1.4.190 |

## 5 · Two laws worth more than any single row

1. **An exclusion declared by SELECTOR only excludes where someone already looked; one declared by
   MECHANISM excludes where nobody has looked yet.** Three separate incidents shared this shape (a
   forbidden trailer matched by exact string instead of by rule, a contrast check that stopped at the
   first background image, a rename sweep that missed prose). Prefer the mechanism.

2. **Beware a tool whose radius exceeds the intention.** The worktree-wide terminal stop, a repo-wide
   git discard, an untargeted stash: each does more than the sentence that called it. Count, scope,
   or pick the narrower verb.
