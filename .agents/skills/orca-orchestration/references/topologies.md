# Topologies — One Shape per Repo Activity

> Loaded by: the conductor, at triage, before anything is created.
> The question is never "how many workers". It is **what does this work write**, because that is
> what decides whether a shared checkout is safe.

---

## 1 · The table

| Activity | Topology | Isolation | Why |
|---|---|---|---|
| `sprint-testing` sprint-wide (N issues) | **fleet in the SAME checkout**, one worker per issue (or per 2-3 tightly coupled issues) | per-worker browser session / profile / output dir, per-issue session sub-scope, writes go to the tracker | it writes no code. The state of record lives in the tracker plus the session scope, so a worktree per issue is pure cost: setup time, disk, provisioning surface, and N times the dependency install |
| `shift-left-testing` batch | same checkout, one worker per story | tracker only | same reasoning, even more so: the output is refined criteria and an early test plan |
| `test-automation` batch | **hybrid by component**: one Orca worktree per worker, one worker per MODULE; stories that share a module run SEQUENTIALLY inside that worker | own checkout, own branch, own PR | it writes code. Two sessions in one checkout collide on the git index even when they never touch the same file. And multiple test cases in one module share pages / APIs / fixtures, so two workers on one module produce merge conflicts in the fixture files by construction |
| `framework-development` waves | same checkout (`solo-main`) with **explicit file ownership per worker** and pathspec-scoped commits; OR a worktree per wave when two workers must touch the same module | the `File ownership` list in each worker brief | measured on 2026-09-15: four workers, 24 commits, one git-index collision that produced the pathspec-commit rule |
| `regression-testing` triage | conductor reads CI; one worker per real failure CLUSTER, each in a worktree | own checkout per cluster | every fix is code. Cluster first: three failures with one root cause is ONE worker, not three |
| `project-discovery` / `project-context` | **not a fleet**: one-shot subagents | — | these are reads. A subagent returns a map inside the turn and costs nothing to clean up |
| unattended routines | scheduled automation over an EXISTING workspace | `references/automations.md` | a fresh workspace per run loses the out-of-git state the routine reads |

**The owner's rule of thumb**: if the task touches files another live session is touching, worktree;
if not, the shared checkout. In manual QA there is almost never a file conflict; in automation there
almost always is.

## 2 · Component ownership, for the automation batch

The partition unit is the **module**, expressed as ownership of `tests/components/<module>/`. The
rule has no exception:

> **Never two workers on the same module.** Not in the same round, not in different worktrees, not
> "just for one file".

Consequences the conductor applies at triage:

1. Group the batch's work packages by module. A group is one worker, and the packages inside it run
   one after another in that worker's session.
2. A package that genuinely spans two modules is assigned to ONE worker, which then owns both, and
   both are removed from every other group.
3. The generated KATA manifest is regenerated by the **conductor**, once per integration, never by a
   worker: it is a whole-repo artifact and N workers regenerating it is N conflicting rewrites of the
   same file.
4. Spec-level plans and progress files are per package, so they never collide.

Detailed batch mechanics live with the skill that owns the WHAT:
`test-automation/references/batch-fleet.md`.

## 3 · When a worktree, precisely

Create an Orca worktree when ANY of these is true:

- the work commits code, or runs a generator that rewrites tracked files;
- the work needs its own branch and its own PR;
- the work runs a build, a dev server or anything that writes into a shared build directory;
- two live sessions would otherwise share one git index.

Stay in the shared checkout when ALL of these are true:

- the work's output is tracker artifacts, evidence files and session notes;
- the files it writes are partitioned by an ownership list nobody else appears in;
- nothing it runs writes to a shared build directory.

And note what a worktree is NOT: the harness's own worktree feature lives inside the repo, is
invisible to the board and the phone, and has no managed terminal. For a fleet, always the Orca
worktree. Mechanics, the untracked-files gotcha, the multi-session safety rules and the cleanup
checklist: `git-flow-master/references/worktrees.md`.

## 4 · Git rules per topology

### Same checkout (fleet)

- Stage explicit paths. `git add -A` / `git add .` in a shared tree stages another worker's
  half-finished edit and a secret that happened to be lying there.
- Commit with a pathspec so the commit cannot pick up anything outside your ownership list:
  `git commit -F <message-file> -- <path> <path>`.
- **Re-read every file immediately before editing it.** Another worker may have changed a shared
  neighbour since your last read; an edit built on a stale read silently reverts their work.
- On `index.lock`: wait ~5 s and retry. Do not delete the lock file.
- No repo-wide discards, ever (Critical Rule #15). Restore only paths YOU modified in THIS session.
- The conductor regenerates whole-repo generated files, after the round.

### Own worktree

- `git fetch origin` then verify the new worktree's SHA against `origin/<base>`. A base-ref flag
  resolves LOCAL refs, so a worktree can be born behind the remote; this was paid for twice, and the
  fix is the verification, not the merge. Never hide it behind `|| true`.
- Bring the base in with an ADDITIVE merge. Never rebase or amend anything already pushed
  (Critical Rule #6).
- Push YOUR branch only; open the PR the project's git strategy asks for. A protected branch is
  resolved by `git_strategy.policy.direct_push_to_protected`, never by assumption.
- The base branch cannot be checked out in a worktree if the primary checkout holds it. A worker
  "on the base branch" is in reality a session in the primary checkout — and there the worktree-wide
  terminal stop has extra radius, so count terminals before closing anything.
- Integrate, verify, THEN release the worker, THEN run the orphan audit, THEN remove the worktree
  (`references/coordinator-playbook.md` §6).

## 5 · Sizing a round

- The worker cap comes from `.agents/project.yaml` → `orchestration.max_workers`, and an explicit
  user instruction overrides it for that run.
- Rounds are numbered inside a wave when the workflow has waves (`sprint-testing` only):
  "Wave 1, round 2". **A round is concurrency; a wave is a tracker-status bucket.** Never reuse one
  word for the other.
- The real ceiling is usually not context but the tracker and TMS rate limits, plus how many reports
  one conductor can actually process in a turn. Four is the shipped default for a reason.
- An ad-hoc single-issue job (a retest, one urgent fix) runs as N=1, outside the rounds, and still
  counts against the cap while it is live.
