# Phase 2 — Architecture Discovery

> Read this when running any Phase 2 sub-step: Architecture, External Services, Non-Functional. Phase 2 writes the first half of the `infra-context` map; Phase 3 (`phase-3-infrastructure.md`) writes the second.

---

## Phase 2 outputs: the infra map

Phase 2 writes into ONE file: `.agents/skills/infra-context/references/infra-map.html`. Its anatomy (line-1 banner, flat `<section id data-sources data-updated>`, figures, `discovery-gaps` last, `data-migrated-from`) is `agentic-qa-core/references/business-context-maps.md` §2; this reference says WHAT goes in each Phase 2 section. The generated banner names both phases as the generator: `<!-- generated by project-discovery Phases 2-3; edited in place by infra-context refresh; do not hand-edit -->`.

| Section id | Content |
|------------|---------|
| `overview` | Architectural pattern, tech stack summary, deployment shape in one paragraph. |
| `architecture` | Component structure, containers and data flow, auth flow, database at architecture level, security architecture, performance hooks, ADR citations. Usually earns the map's main figure. |
| `external-services` | Third-party dependencies and their integration points. |
| `nfr-<slug>` | One section per non-functional category with evidence: `nfr-performance`, `nfr-security`, `nfr-reliability`, `nfr-scalability`, `nfr-observability`, `nfr-compliance`. |
| `discovery-gaps` | Shared with Phase 3; always the last section. |

```
bun run context:map infra-context --list

                            (or scaffolded from the boilerplate); never create it here.
  → placeholder notice:     CREATE: build every Phase 2 section from the sources.
  → a list of sections:     UPDATE: staleness check per section
                            (business-context-maps.md §5), regenerate ONLY the
                            stale ones, show a section-level diff, WAIT for
                            explicit approval. NEVER regenerate the whole map.
```

Within one discovery session, whichever of Phase 2 or Phase 3 runs first CREATEs the map; the other adds its own section ids to it (an addition, not a regeneration) and shows them at its phase gate.

Legacy input: a project's old `.context/SRS/architecture.md` and `.context/SRS/non-functional-specs.md` (the `legacy` list of `infra-context` in `CONTEXT_MAP_SKILLS`, `cli/lib/context-maps.ts`) are read as INPUT when present and cited in `data-migrated-from` on the sections they seed. Never delete or rewrite them.

> **Personas, user journeys and functional specs are not Phase 2 outputs.** `project-context` mode `e2e` builds them as the persona, journey and feature sections of `business-e2e-context`, and reads a legacy `.context/SRS/functional-specs.md` as its own input.

> **API contracts are NOT a Phase 2 output.** The canonical API contract lives in two places, neither of which is owned by `project-discovery`:
> - **Technical surface** — `api/openapi-types.ts` (generated by `bun run api:sync` from the project's OpenAPI spec). This is the authoritative request/response shape for tests and automation.
> - **Business angle** — the map inside `business-api-context` (produced by `project-context` mode `api`). Auth flows, critical endpoints, architecture behind the API.

Every numeric claim cites its evidence in the section or sits in `discovery-gaps`. Never invent numbers.

## 1. Architecture (`overview`, `architecture`)

### Discovery process

1. **Component inventory** — map the folder structure to architectural roles:
   - `ls -la <repo>/src/` then drill into `app/`, `pages/`, `components/`, `services/`, `controllers/`, `repositories/`, `modules/`, `features/`.
   - Identify pattern: MVC, Clean/Hexagonal, Feature-based, Modular monolith.
   - Trace imports with grep to confirm dependency direction.

2. **Database at architecture level**: which stores exist, what owns them, how the app reaches them. Prefer live schema over ORM definitions (ORMs drift):
   - If `[DB_TOOL]` is configured: query `information_schema.tables` for the target schema (usually `public`) to size and group the subsystems.
   - Fallback: read `prisma/schema.prisma`, `src/entities/*.ts` (TypeORM), `src/db/schema.ts` (Drizzle), or raw `schema.sql` / `migrations/`.
   - Record store, provider, access layer and subsystem grouping here. Tables, columns, relationships and state machines belong to `business-data-context` (`project-context` mode `data`): cite its section ids, never restate them.

3. **Data and auth flow**: the request path through the layers, and the login sequence (where credentials go, what comes back, where the session lives).

4. **Security architecture** — auth method (session / JWT / OAuth), password storage (bcrypt/argon2), session lifetime, TLS posture, secret handling, data-at-rest encryption.

### Section content

**`overview`**: pattern, a stack `<table>` (`Layer | Technology | Found in`; `.context/project-config.md` §Tech Stack holds the same facts in short form, so keep the two consistent), deployment shape in one paragraph.

**`architecture`**:
- Component structure: a `<table>` `Directory | Responsibility | Found in`.
- Containers and data flow: the figure (below), with every fact it shows also in the text.
- Auth flow: the login sequence in numbered steps; the concrete request detail lands in Phase 3's `backend` section.
- Database: stores, providers, access layer, subsystem grouping, pointer to `business-data-context`.
- Security architecture: authN / authZ / data protection.
- Performance hooks: caching layers and rate limits discovered.
- ADRs: cite each `.context/ADR/ADR-NNNN-<slug>.md` this phase seeded (see SKILL.md §Phase 2).
- QA relevance: components to test, environment requirements.

### Figures

Before drawing, run the point-of-use check for capability `diagrams` (`agentic-qa-core/references/business-context-maps.md` §7). Draw with diagram-design, never hand-drawn SVG, ASCII or Mermaid.

- The `architecture` section usually earns a container-level figure (apps, APIs, stores, external services and the arrows between them). Without one, record in `discovery-gaps` why not (e.g. a single-process app where a table says it all).
- A sequence figure for the auth flow is optional; the numbered steps are the facts.
- Keep each figure to diagram-design's node budget; split by subsystem when the whole app will not fit.
- Tables beat figures for inventories (components, services, NFR entries).

## 2. API contract source (recorded, not documented)

This skill does not document endpoints. The API contract has two canonical sources, owned by two different tools:

| Angle | Owner | Output | When to use |
|-------|-------|--------|-------------|
| Technical surface (request/response types) | `bun run api:sync` (script: `scripts/sync-openapi.ts`) | `api/openapi-types.ts` + `api/openapi.json` | Every time the spec changes. Consumed by `api/schemas/*.types.ts` facades and by automated tests. |
| Business angle (auth, critical paths, architecture) | `project-context` mode `api` | the map inside `business-api-context` | After discovery, re-run whenever auth or critical flows change. |

During Phase 2, your job is to confirm which of those two sources is available and record the result:

1. **Locate the OpenAPI spec** (authoritative, saves hours):
   - Files: `openapi.yaml`, `openapi.json`, `swagger.yaml`, `swagger.json`, `api-spec.*`.
   - Generator signals in `package.json`: `swagger-jsdoc`, `@nestjs/swagger`, `fastify-swagger`, `zod-to-openapi`, `drf-spectacular` (Python).
   - Runtime endpoint: try `/api/docs`, `/swagger`, `/openapi.json`, `/api-docs/openapi.json` via `[API_TOOL]`.
   - If present, note the URL / file path in `.context/project-config.md` under "API spec source". `bun run api:sync` will consume it.

2. **If no OpenAPI spec exists**: record it in the infra map's `discovery-gaps` and recommend the user run `/project-context api` (after discovery completes) to capture at least the auth flow and critical endpoints. Do **not** hand-write an API contract document.

> **Gotcha**: if a legacy `.context/SRS/api-contracts.md` exists from an old run, flag it to the user as likely drifted from the spec. Do not update it in place.

## 3. External services (`external-services`)

### Discovery process

- `.env.example` keys that are NOT framework-owned (not `NODE_ENV`, `DATABASE_URL`, `NEXTAUTH_SECRET`).
- `grep -r "process\.env\." src/` to see which env vars code actually reads.
- Client instantiations: `grep -r "new .*Client\|createClient\|\.initialize" src/`.

### Section content

A `<table>`: `Service | Purpose | Env key (name only) | Integration point | Found in`. Then one short paragraph per service whose failure a test must account for (webhooks, payment callbacks, email delivery). `data-sources`: the client files and `.env.example`.

## 4. Non-functional (`nfr-<slug>`)

### Discovery process

1. **Performance**:
   - Caching: `grep -r "cache\|redis\|memo" src/`; Next.js `revalidate`, `cache:` options.
   - Timeouts/limits: `grep -r "timeout\|limit\|rateLimit" src/`.
   - DB query shape: `select`, `include`, `take`, `skip` patterns; pagination strategy; N+1 hot spots.
   - Connection pool size: check ORM config (`src/lib/db.ts`, Prisma `DATABASE_URL` pool params, `DATABASE_POOL_SIZE`).

2. **Security**:
   - Auth mechanism: see the `architecture` section.
   - Headers: `next.config.js` `headers()` function, Helmet config, CSP strings.
   - Input sanitization: `sanitize-html`, `xss`, `DOMPurify`, `validator` usage.
   - Secret handling: `.env` pattern, secret managers (Vercel env, AWS Secrets Manager, Doppler).
   - Package signals: grep `package.json` for `helmet`, `xss`, `csrf`, `bcrypt`, `argon2`.

3. **Reliability**:
   - Error boundaries: `error.tsx` (Next.js App Router), `ErrorBoundary` components.
   - Retry logic: `grep -r "retry\|Retry\|attempt" src/`; look for exponential backoff.
   - Health endpoints: `find src -name "*health*" -o -name "*ready*"`.
   - Logging stack: `winston`, `pino`, `bunyan`, console patterns.
   - External-call resilience: circuit breakers, timeouts around fetch/axios.

4. **Scalability**:
   - Stateless design: no in-memory state, sessions in Redis / JWT / DB.
   - Async processing: queues (`bullmq`, `pg-boss`, `celery`, `sidekiq`), workers, cron handlers.
   - DB scaling: connection pooling, read replicas, sharding (rare).
   - Deployment model: serverless (Vercel / Lambda) vs long-running (Node/Docker) affects scaling assumptions.

5. **Observability**:
   - APM: `@sentry/*`, `@datadog/*`, `newrelic`, `@opentelemetry/*`.
   - Metrics: `prom-client`, custom counters/gauges/histograms.
   - Tracing: OpenTelemetry spans, `trace`, `span` usage.
   - Log shipping: `pino-pretty`, log drains in hosting platform config.

6. **Compliance**: GDPR / SOC2 / HIPAA / PCI-DSS signals; mark "Needs Review" when not verifiable.

### Section content

One `nfr-<slug>` section per category with evidence (a category with none becomes a `discovery-gaps` line, "not implemented, recommend adding"). Each section holds a `<table>` of entries:

| ID | Title | Target | Implementation | Evidence |
|----|-------|--------|----------------|----------|
| NFR-<CATEGORY>-NNN | <title> | <measurable or inferred> | <how it is done> | <path> |

Then details as needed, and a closing QA-relevance line (is it testable, which tool: k6, Artillery, OWASP ZAP). Preserve NFR IDs across UPDATEs; downstream plans may cite them.

## Gotchas

- **Missing OpenAPI is common.** Most repos either lack a spec or have a stale one. Never trust OpenAPI without spot-checking 3-5 endpoints against code. If stale, flag it in `discovery-gaps`.
- **Undocumented internal endpoints.** Admin-only routes, cron handlers, webhook receivers, feature-flag toggles often sit outside the public API surface. Search for `/admin/`, `/internal/`, `/webhook/`, `/cron/` path prefixes and name them as components in `architecture`.
- **Auth patterns that resist automation.** OAuth with third-party redirects, CAPTCHA-gated login, device-fingerprint MFA — document these and flag them as "needs manual setup" rather than pretending they can be E2E-tested.
- **Rate limits you cannot verify.** If middleware config references an external service (Upstash, Redis), you may only see "rateLimit = true" without the actual numbers. Record what you can see and list the gap.
- **NFR numbers must be evidenced or flagged.** "P95 < 500ms" with no load test evidence is a discovery gap, not a spec. Prefer "Target: [unknown] — inferred from `timeout: 30000` config" over inventing a number.
- **Security posture is never "complete".** A codebase without Helmet is not a failing grade — it's "Helmet not present, CSP not configured — recommend security review". Avoid pass/fail framing.
- **Do not scrape secrets.** If you stumble onto hard-coded keys in the source, do NOT paste them into the map. Record "hard-coded secret detected at `<path>`" in `nfr-security` and make sure the Phase 1 assessment carries it as a HIGH risk. Also see SKILL.md §Gotchas for the broader credential policy.
- **Large schemas.** For 50+ tables, group subsystems in the `architecture` figure and leave the table-level picture to `business-data-context`.
