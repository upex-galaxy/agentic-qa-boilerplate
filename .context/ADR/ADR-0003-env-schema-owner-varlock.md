# ADR-0003 — varlock owns the env schema; the schema ships in two files

- **Status:** Proposed
- **Date:** 2026-09-23
- **Deciders:** framework owner (boilerplate maintainer); drafted by `/framework-development` from the env-secrets SPIKE (D1-D7 approved 2026-09-23)
- **Tags:** env, secrets, validation, ci, updater
- **Supersedes:** —
- **Superseded by:** —

## Context

Every environment variable this repo knows about is routed by `cli/lib/variables-manifest.ts` (installer, `setup --variables`, doctor, drift checks), documented by `.env.example`, and validated at test time by `config/validateTestEnv.ts`. Three copies of the same knowledge, kept in lockstep by `scripts/check-vars.ts`. None of them is a typed schema: a value's type, its sensitivity and whether it is required in a given environment live in comments and in scattered code. An agent session has no way to see which variables are set without reading a file that holds the secrets, and a missing MCP credential is first noticed when the server dies on its first authenticated call (AGENTS.md Critical Rule #10).

The SPIKE (`.session/spikes/env-secrets/plan.md`) compared varlock (`@env-spec`, `varlock load` / `run`, per-item sensitivity, redacted `--agent` output, provider plugins, a CI action) with Zod-on-`process.env` and found the overlap total on env and varlock strictly richer. The owner approved D1(a): the schema is GENERATED from the manifest, which keeps the routing fields (`destinations`, `valueSource`, `critical`) env-spec has no decorator for.

The P0 probe (`probe.md`) measured two constraints that shape the file layout:

1. varlock parses any file starting with `.env` as `.env[.<env>][.<type>]` with at most two segments after `env`, and refuses to import a file not named `.env.*`. The name the SPIKE proposed for the synced half, `.env.schema.core`, is rejected (`Unsure how to interpret filename`).
2. An IMPORTED file is never treated as environment-specific even when its name carries an env qualifier. This rule is stated in the JSDoc of `isEnvSpecific` in varlock's env-graph source, not in the public docs.

## Decision

We will make varlock the single owner of env schema, validation, typing and redaction, and ship the schema in two committed files that mirror the synced/project-owned split of `config/variables.core.ts` / `config/variables.ts`:

- `.env.core.schema` — GENERATED by `bun run vars:schema` from `VAR_MANIFEST` plus `RUNTIME_KNOBS` (`cli/lib/env-schema.ts`), plainly SYNCED by the updater (component `env-schema`), never hand-edited. `bun run vars:schema:check` fails the pre-commit gate and `repo:check` when it is stale.
- `.env.schema` — PROJECT-OWNED (delivered once, then on the protected watchlist). Holds `@import(./.env.core.schema)`, the root decorators (`@currentEnv=$TEST_ENV`, `@generateTsTypes`) and the project's own variables.

Invariants every later phase must uphold:

- **No file under version control holds a value.** Both schema files declare names, types, sensitivity and requiredness only. Values stay in `.env` / `.env.local` or come from a provider at runtime.
- **The schema's `@required` is the RUNTIME contract**, identical to what `validateTestEnv` enforces today: `TEST_ENV` plus the active environment's test-user credentials. Install-time necessity (the day-0 Atlassian credentials) stays in the manifest's `required` and is expressed in the schema through `VarSchemaHints.required`. CI must validate a build without any Atlassian token.
- **Every key `.env.example` documents is declared**, including the commented optional knobs, because varlock treats an undeclared empty key in `.env` as a validation failure.
- **The core file name is `.env.core.schema`, and it relies on rule (2) above.** `varlock` is pinned EXACTLY in `package.json` (no caret), and `vars:schema:check` loads the committed pair through the pinned varlock in a scratch directory on every run, so a bump that changes the import rule fails the gate instead of silently dropping every core variable from validation. A bump is a deliberate change that re-runs that check.
- **No `bunfig.toml` preload.** Injection, when it comes (P2), goes through explicit `varlock run` wrappers; preload would bind every `bun` / `bunx` invocation in the repo to schema validity.

## Consequences

- **Positive:** one typed, self-documenting schema that humans, CI and agents read the same way; `varlock load --agent` gives an agent a redacted picture of which variables are set and from where, closing the Rule #10 diagnosis gap before an MCP server is touched; the CI job page carries a redacted summary; `.env.example` and `check-vars` keep working unchanged in this phase, so the change is reversible by deleting two files, one devDependency and one script.
- **Negative / trade-offs:** a second generated artifact to keep fresh (mitigated by the gate); a reliance on an undocumented varlock rule (mitigated by the exact pin and the pair-load check); varlock is an early-stage project that moves fast (mitigated by the pin and by the fact that the fallback is a plain `.env.local` any dotenv loader reads).
- **Neutral / follow-ups:** P2 routes the wrappers and test scripts through `varlock run`, retires `dotenv-cli` and `.env.example`, and rewrites the process-env drift rule over `overrideKeys`; P3 declares the secret provider in `.agents/project.yaml` and adds overlays as `@import`s (never `-p` flags: an explicit path replaces the default ladder, `probe.md` P0.1); P4 wraps the MCP servers with the standalone binary; P5 adds Zod in `ApiBase` for response contracts, which does not touch env. `env.d.ts` is generated on every load and gitignored, as the varlock docs recommend; `processEnv=none` until a phase actually reads the typed `ENV`.

## Alternatives considered

- **Zod schema over `process.env`** — rejected: covers types and required only; no sensitivity classification, no redaction, no agent-safe mode, no CI action, JS-only. The SPIKE found varlock strictly richer on env.
- **Hand-written `.env.schema` parsed back into the manifest (D1(b))** — rejected for now: needs an env-spec parser in `cli/` that is not published as a package; revisit only if the manifest becomes a maintenance burden.
- **Directory import (`config/env/.env.schema`)** — the documented alternative to the flat file; rejected by the conductor in favour of the flat file because the updater already ships single root files through a `file-list` component (`.env.example` is the precedent), `.gitignore` needs one negation instead of a directory rule, and a flat file is what a human opens when validation fails. Recorded so nobody re-proposes it without new information: it is the fallback if rule (2) ever changes.
- **`bunfig.toml` preload** — rejected (R2): couples every bun process in the repo to schema validity.
